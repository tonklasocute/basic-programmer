# บทที่ 40: Index, Query Optimization, Joins

## แนวคิดหลัก (Concept)

บทที่แล้วทิ้งคำถามไว้ว่าฐานข้อมูลทำให้ query เร็วขึ้นได้อย่างไรในทางเทคนิค — คำตอบคือ **Index** ซึ่งแท้จริงแล้วก็คือโครงสร้างข้อมูลที่เรียนมาแล้วใน Part 4 (ส่วนใหญ่คือ B-Tree ซึ่งเป็นญาติของ BST จากบทที่ 16) นำมาประยุกต์ใช้กับฐานข้อมูล บทนี้อธิบายว่า Index ทำงานอย่างไร, ฐานข้อมูลตัดสินใจ "แผนการ query" อย่างไร (Query Optimization), และกลไกภายในของการ JOIN ที่กล่าวถึงในบทที่แล้ว

- **Index** — โครงสร้างข้อมูลเสริมที่สร้างขึ้นเพื่อ**ค้นหาแถวได้เร็วขึ้นโดยไม่ต้องสแกนทั้งตาราง** คล้ายดัชนีท้ายเล่มหนังสือที่ช่วยหาหน้าที่ต้องการโดยไม่ต้องพลิกอ่านทุกหน้า — ฐานข้อมูลส่วนใหญ่ใช้โครงสร้าง **B-Tree** (ต้นไม้ที่สมดุลเสมอ คล้าย AVL Tree จากบทที่ 16 แต่แต่ละ node มีลูกได้มากกว่า 2)
- **Query Optimizer** — ส่วนของฐานข้อมูลที่วิเคราะห์คำสั่ง SQL แล้วเลือก **Execution Plan** (แผนการทำงาน) ที่คาดว่าจะเร็วที่สุด เช่น ตัดสินใจว่าจะใช้ Index หรือสแกนทั้งตาราง (Full Table Scan) จะ JOIN ตารางไหนก่อน
- **Join Algorithm** — วิธีการภายในที่ฐานข้อมูลใช้รวมข้อมูลจากสองตารางเข้าด้วยกัน มีหลายแบบ เช่น **Nested Loop Join** (ไล่เทียบทุกคู่ คล้าย Brute Force O(n²)), **Hash Join** (สร้าง Hash Table จากตารางเล็กก่อน คล้ายบทที่ 15), **Merge Join** (ต้องการข้อมูลที่เรียงแล้ว คล้ายหลักการ Merge Sort บทที่ 21)

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Index มีไว้เปลี่ยน O(n) เป็น O(log n) สำหรับการค้นหาในฐานข้อมูล — หลักการเดียวกับ Binary Search (บทที่ 22)**: ถ้าตารางมีข้อมูลนับล้านแถวและไม่มี Index การค้นหาแถวเดียวต้องสแกนทีละแถว (Full Table Scan, O(n)) แต่ถ้ามี Index ที่เป็น B-Tree การค้นหาลดเหลือ O(log n) ซึ่งต่างกันมหาศาลเมื่อข้อมูลมีขนาดใหญ่
- **Query Optimizer มีไว้เพราะ SQL เป็นภาษา "บอกว่าต้องการอะไร" ไม่ใช่ "บอกว่าทำอย่างไร"**: เมื่อเขียน `SELECT ... WHERE ... JOIN ...` เราไม่ได้บอกฐานข้อมูลว่าต้องไล่ตรวจแถวไหนก่อน ใช้ Index ตัวไหน หรือ JOIN แบบไหน — Query Optimizer ต้องคิดคำนวณเองว่าวิธีไหนเร็วที่สุดสำหรับ query นั้นๆ โดยพิจารณาจากสถิติของข้อมูลจริง (ขนาดตาราง, การกระจายของค่า)
- **Join Algorithm ต่างกันมีไว้ให้เหมาะกับสถานการณ์ต่างกัน**: เหมือนที่ Part 5 สอนว่าไม่มีอัลกอริทึม sort ตัวเดียวที่ดีที่สุดในทุกกรณี (Bubble Sort vs Merge Sort บทที่ 21) การ JOIN ก็เช่นกัน — Nested Loop เหมาะกับตารางเล็ก, Hash Join เหมาะกับตารางใหญ่ที่ไม่เรียงลำดับ, Merge Join เร็วมากถ้าข้อมูลเรียงอยู่แล้ว

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Index** เหมือน **ดัชนีท้ายเล่มพจนานุกรมหรือหนังสือเรียน** — แทนที่จะพลิกอ่านทุกหน้าเพื่อหาคำว่า "Algorithm" (Full Table Scan) เปิดดัชนีท้ายเล่มที่เรียงตามตัวอักษรแล้วกระโดดไปหน้าที่ถูกต้องทันที (เหมือนหลักการ Binary Search บทที่ 22 พอดี)
- **Query Optimizer** เหมือน **แอปนำทางที่คำนวณเส้นทางที่เร็วที่สุดให้อัตโนมัติ** — เราแค่บอกจุดหมายปลายทาง (สิ่งที่ต้องการ) แอปคำนวณเองว่าจะไปทางไหนเร็วที่สุดโดยดูสภาพจราจรจริง (สถิติของข้อมูล) ไม่ใช่เราบอกทีละเลี้ยวเอง
- **Nested Loop Join** เหมือน **การจับคู่นักเรียนสองห้องโดยเทียบชื่อทีละคู่จนครบ** — ช้าแต่ตรงไปตรงมา เหมาะกับห้องที่มีนักเรียนน้อย
- **Hash Join** เหมือน **การแบ่งนักเรียนเป็นกลุ่มตามอักษรตัวแรกของชื่อก่อน แล้วค่อยจับคู่เฉพาะกลุ่มเดียวกัน** — เร็วกว่ามากเมื่อมีนักเรียนจำนวนมาก เพราะไม่ต้องเทียบข้ามกลุ่มที่ไม่มีทางตรงกัน

## แผนภาพอธิบาย (Visual explanation)

### Full Table Scan vs Index Search — ต่างกันเหมือน Linear Search vs Binary Search (บทที่ 21-22)

```
ตาราง Users มี 1,000,000 แถว   หา WHERE email = 'alice@mail.com'

ไม่มี Index (Full Table Scan):              มี Index บนคอลัมน์ email (B-Tree):
ไล่ตรวจทีละแถวจนกว่าจะเจอ                      กระโดดไปยัง node ที่ตรงกันทันที
O(n) = อาจต้องตรวจ 1,000,000 แถว              O(log n) = ตรวจแค่ ~20 ครั้ง (log₂ 1,000,000 ≈ 20)

เปรียบเทียบตรงกับ Linear Search vs Binary Search ที่เรียนในบทที่ 21-22 ทุกประการ
```

### B-Tree Index — โครงสร้างคล้าย BST แต่แต่ละ node มีลูกได้หลายตัว

```
                    [50, 100]
                   /    |     \
            [10,30]  [60,80]  [120,150]
            /  |  \   /  |  \   /   |   \
          ...          ...          ...

ต่างจาก BST (บทที่ 16) ที่แต่ละ node มีลูกได้แค่ 2 ตัว
B-Tree แต่ละ node เก็บได้หลายค่าและมีลูกได้หลายตัว -> ต้นไม้เตี้ยกว่ามาก (fewer levels)
เหมาะกับฐานข้อมูลที่อ่านข้อมูลจาก disk เป็นก้อน (block) ทำให้จำนวนครั้งที่ต้องอ่าน disk น้อยลง
```

### Nested Loop Join vs Hash Join

```
Nested Loop Join (เทียบทุกคู่ - O(n×m)):        Hash Join (สร้าง Hash Table ก่อน - O(n+m)):

for row1 in table_A:        (n แถว)             hash_table = {row.key: row for row in table_B}  <- O(m)
    for row2 in table_B:      (m แถว)            for row1 in table_A:                              <- O(n)
        if row1.key == row2.key:                     if row1.key in hash_table:  <- O(1) lookup!
            match!                                       match!

n × m ครั้ง (ช้าเมื่อทั้งสองตารางใหญ่)              n + m ครั้ง (เร็วกว่ามากเมื่อตารางใหญ่)
เหมาะกับตารางเล็ก หรือมี Index ช่วย                 เหมาะกับตารางใหญ่ที่ไม่มี Index ตรงกับ join condition
```

### EXPLAIN — เครื่องมือดู Execution Plan ที่ Query Optimizer เลือก

```sql
EXPLAIN SELECT * FROM Orders WHERE customer_id = 5;

ผลลัพธ์ (ตัวอย่าง):
type: ref            <- ใช้ Index ค้นหา (ไม่ใช่ Full Table Scan)
key: idx_customer_id  <- ชื่อ index ที่เลือกใช้
rows: 3               <- คาดว่าต้องตรวจแค่ 3 แถว (ไม่ใช่ทั้งตาราง)

ถ้าเห็น type: ALL แปลว่าเป็น Full Table Scan -> สัญญาณว่าอาจต้องเพิ่ม Index
```

## ตัวอย่างโค้ด (Code example)

```sql
-- ===== สร้าง Index บนคอลัมน์ที่ query บ่อย =====
CREATE INDEX idx_email ON Customers(email);              -- Index เดี่ยว
CREATE INDEX idx_customer_product ON Orders(customer_id, product);  -- Composite Index (หลายคอลัมน์)

-- ===== เปรียบเทียบ query ก่อน/หลังมี Index ด้วย EXPLAIN =====
EXPLAIN SELECT * FROM Customers WHERE email = 'alice@mail.com';
-- ก่อนมี idx_email: type=ALL (Full Table Scan, ช้าเมื่อตารางใหญ่)
-- หลังมี idx_email: type=ref (ใช้ Index, เร็วมาก)

-- ===== JOIN สามชนิดที่พบบ่อย =====
-- INNER JOIN: เอาเฉพาะแถวที่ตรงกันทั้งสองฝั่ง
SELECT c.name, o.product
FROM Customers c
INNER JOIN Orders o ON c.id = o.customer_id;

-- LEFT JOIN: เอาทุกแถวจากตารางซ้าย แม้ไม่มีคู่ตรงกันในตารางขวา (เติม NULL แทน)
SELECT c.name, o.product
FROM Customers c
LEFT JOIN Orders o ON c.id = o.customer_id;
-- ลูกค้าที่ยังไม่เคยสั่งซื้อเลยก็ยังปรากฏในผลลัพธ์ (product = NULL)

-- ===== Query ที่ optimize แล้ว vs ยังไม่ optimize =====
-- ยังไม่ optimize: ใช้ function ครอบคอลัมน์ที่มี index -> Index ใช้งานไม่ได้! (ต้อง Full Table Scan)
SELECT * FROM Orders WHERE YEAR(order_date) = 2026;

-- optimize แล้ว: เปรียบเทียบตรงๆ โดยไม่ครอบ function -> Index ยังใช้งานได้
SELECT * FROM Orders WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01';
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `CREATE INDEX idx_email ON Customers(email)` — คำสั่งนี้บอกฐานข้อมูลให้สร้าง**โครงสร้าง B-Tree แยกต่างหาก** ที่เก็บค่า `email` เรียงลำดับพร้อมตัวชี้กลับไปยังตำแหน่งแถวจริงในตาราง `Customers` — ทุกครั้งที่มีการ `INSERT`/`UPDATE`/`DELETE` แถวในตาราง ฐานข้อมูลต้อง**อัปเดต Index นี้ด้วย** (นี่คือ trade-off ที่จะอธิบายในหัวข้อ Time/Space Complexity)
2. `CREATE INDEX idx_customer_product ON Orders(customer_id, product)` — เป็น **Composite Index** (Index บนหลายคอลัมน์พร้อมกัน) โดยลำดับคอลัมน์สำคัญมาก: Index นี้ใช้เร่ง query ที่กรองด้วย `customer_id` เพียงอย่างเดียว หรือ `customer_id` และ `product` พร้อมกัน ได้อย่างมีประสิทธิภาพ แต่**ใช้เร่ง query ที่กรองด้วย `product` เพียงอย่างเดียวไม่ได้** (เหมือนการเปิดพจนานุกรมที่เรียงตามตัวอักษรตัวแรกก่อน แล้วค่อยตัวที่สอง — ถ้ารู้แค่ตัวที่สองจะหาไม่ได้เร็วเหมือนกัน)
3. `LEFT JOIN` ต่างจาก `INNER JOIN` ตรงที่**เก็บทุกแถวจากตารางฝั่งซ้าย (Customers) ไว้เสมอ** แม้จะไม่มีแถวใน `Orders` ที่ตรงกันเลยก็ตาม (เติมค่า `NULL` ในคอลัมน์จากตารางขวาแทน) ในขณะที่ `INNER JOIN` จะ**ตัดทิ้งลูกค้าที่ไม่เคยสั่งซื้อเลย**ออกจากผลลัพธ์ทันที — การเลือกชนิด JOIN ที่ถูกต้องขึ้นอยู่กับว่าต้องการเห็นข้อมูลที่ "ไม่มีคู่" หรือไม่
4. `WHERE YEAR(order_date) = 2026` เทียบกับ `WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01'` — แม้ทั้งสองแบบให้ผลลัพธ์เหมือนกันทุกประการ แต่แบบแรก**ครอบคอลัมน์ `order_date` ด้วยฟังก์ชัน `YEAR()` ก่อนเปรียบเทียบ** ทำให้ Query Optimizer **ไม่สามารถใช้ Index บน `order_date` ได้เลย** เพราะ Index เก็บค่า `order_date` ดิบๆ ไม่ใช่ผลลัพธ์ของ `YEAR(order_date)` — ต้องสแกนทุกแถวมาคำนวณ `YEAR()` ใหม่ทุกครั้ง (Full Table Scan) ในขณะที่แบบที่สองเปรียบเทียบ `order_date` ตรงๆ ทำให้ Index ยังคงใช้งานได้เต็มประสิทธิภาพ

## Time Complexity

| Operation | ไม่มี Index | มี Index (B-Tree) |
|---|---|---|
| ค้นหาแถวเดียวด้วยเงื่อนไข equality | O(n) — Full Table Scan | **O(log n)** |
| ค้นหาช่วงข้อมูล (range query) | O(n) | **O(log n + k)** โดย k คือจำนวนแถวที่ตรงเงื่อนไข |
| INSERT/UPDATE/DELETE | O(1) เพิ่มเข้าตารางตรงๆ | **O(log n)** เพิ่มเติม เพราะต้องอัปเดต Index ด้วย |

| Join Algorithm | Time Complexity |
|---|---|
| Nested Loop Join | O(n × m) |
| Hash Join | O(n + m) |
| Merge Join (ข้อมูลเรียงแล้วทั้งคู่) | O(n + m) |

## Space Complexity

- แต่ละ Index ที่สร้างเพิ่มใช้พื้นที่เพิ่มเติม **O(n)** (ประมาณเท่ากับขนาดของคอลัมน์ที่ทำ Index บวก pointer กลับไปยังแถวจริง) — ยิ่งสร้าง Index มากเท่าไหร่ ยิ่งใช้พื้นที่มากขึ้นตามไปด้วย นี่คือเหตุผลที่ไม่ควรสร้าง Index บนทุกคอลัมน์โดยไม่จำเป็น

## แนวทางปฏิบัติที่ดี (Best Practices)

- สร้าง Index บนคอลัมน์ที่ใช้ใน `WHERE`, `JOIN ON`, และ `ORDER BY` **บ่อยๆ** เท่านั้น — ไม่ใช่ทุกคอลัมน์ เพราะแต่ละ Index มีต้นทุนด้านพื้นที่และทำให้ INSERT/UPDATE ช้าลง (ต้องอัปเดต Index ทุกตัวที่เกี่ยวข้อง)
- หลีกเลี่ยงการครอบคอลัมน์ที่มี Index ด้วยฟังก์ชันใน `WHERE` (เช่น `YEAR(date_column)`) เพราะทำให้ Index ใช้งานไม่ได้ ให้ปรับเงื่อนไขให้เปรียบเทียบคอลัมน์ดิบๆ แทนเสมอที่ทำได้
- ใช้ `EXPLAIN` ตรวจสอบ Execution Plan ก่อน deploy query ที่สำคัญเข้า production เสมอ โดยเฉพาะ query ที่ทำงานกับตารางขนาดใหญ่ เพื่อยืนยันว่า Query Optimizer เลือกใช้ Index ตามที่คาดหวังจริง (ไม่ใช่ Full Table Scan โดยไม่ตั้งใจ)

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- สร้าง Index บนทุกคอลัมน์โดยไม่พิจารณาว่าใช้บ่อยแค่ไหน ทำให้ INSERT/UPDATE ช้าลงมากโดยไม่ได้ประโยชน์ที่คุ้มค่า (Over-indexing)
- เขียน query ที่ครอบคอลัมน์ด้วยฟังก์ชันใน `WHERE` โดยไม่รู้ว่าทำให้ Index ใช้งานไม่ได้ (เหมือนตัวอย่าง `YEAR(order_date)`) แล้วสงสัยว่าทำไม query ถึงช้าทั้งที่มี Index อยู่แล้ว
- สร้าง Composite Index โดยเรียงลำดับคอลัมน์ผิด (ไม่ตรงกับรูปแบบ query ที่ใช้จริง) ทำให้ Index ไม่ถูกใช้งานเต็มประสิทธิภาพ
- ใช้ `INNER JOIN` ทั้งที่ควรใช้ `LEFT JOIN` (หรือกลับกัน) ทำให้ผลลัพธ์ขาดข้อมูลที่ควรมี หรือมีข้อมูลที่ไม่ต้องการปนมา

1. อธิบาย Index คืออะไร ทำงานอย่างไรถึงทำให้ query เร็วขึ้น เชื่อมโยงกับโครงสร้างข้อมูลที่เคยเรียนมา
2. ทำไมการครอบคอลัมน์ด้วยฟังก์ชันใน `WHERE` (เช่น `YEAR(date)`) ถึงทำให้ Index ใช้งานไม่ได้

4. Nested Loop Join, Hash Join, Merge Join ต่างกันอย่างไร แต่ละแบบเหมาะกับสถานการณ์ไหน

## ข้อคิดสำคัญ (Key Takeaways)

- Index เป็นโครงสร้างข้อมูล B-Tree ที่เร่งการค้นหาจาก O(n) เป็น O(log n) เหมือนหลักการ Binary Search แต่แลกมาด้วยพื้นที่เพิ่มและ INSERT/UPDATE ที่ช้าลง
- Query Optimizer วิเคราะห์ SQL แล้วเลือก Execution Plan ที่เร็วที่สุดโดยอัตโนมัติ สามารถตรวจสอบด้วย `EXPLAIN` ว่าใช้ Index จริงหรือไม่
- การครอบคอลัมน์ด้วยฟังก์ชันใน `WHERE` ทำให้ Index ใช้งานไม่ได้ เป็นข้อผิดพลาดที่พบบ่อยที่สุดที่ทำให้ query ช้าโดยไม่รู้ตัว
- INNER JOIN เก็บเฉพาะแถวที่ตรงกันทั้งสองฝั่ง ส่วน LEFT JOIN เก็บทุกแถวจากตารางซ้ายแม้ไม่มีคู่ตรงกัน
- Join Algorithm มีหลายแบบ (Nested Loop, Hash, Merge) เหมาะกับสถานการณ์ต่างกัน เชื่อมโยงโดยตรงกับหลักการ Brute Force, Hash Table, และ Merge Sort จาก Part 4-5
- บทถัดไปจะเรียน Transactions, ACID, Isolation Levels, CAP ซึ่งเชื่อมโยงกลับไปที่ปัญหา Concurrency (Part 8) โดยตรง — เมื่อหลาย query แก้ไขข้อมูลพร้อมกันในฐานข้อมูล จะเกิด Race Condition แบบเดียวกับที่เรียนในบทที่ 37 ได้เช่นกัน
