# บทที่ 36: Thread, Mutex, Semaphore, Atomic

## แนวคิดหลัก (Concept)

บทที่ 34 กล่าวถึง Immutability ว่าช่วยแก้ปัญหาที่พบใน "โปรแกรมที่มีหลาย thread ทำงานพร้อมกัน" ไว้ล่วงหน้า บทนี้เปิด **Part 8: Concurrency** โดยอธิบายว่า thread คืออะไรกันแน่ และทำไมการมีหลาย thread เข้าถึงข้อมูลเดียวกันพร้อมกันถึงเป็นปัญหาที่ต้องมีเครื่องมือพิเศษมาจัดการ

- **Process (โพรเซส)** — โปรแกรมที่กำลังทำงานอยู่ มีพื้นที่หน่วยความจำเป็นของตัวเองแยกจาก process อื่นโดยสิ้นเชิง (ทบทวนจากบทที่ 3)
- **Thread (เธรด)** — หน่วยการทำงานที่เล็กกว่า process โดย**หลาย thread ภายใน process เดียวกันแชร์หน่วยความจำเดียวกัน** (heap, global variable) ทำให้สื่อสารกันง่ายกว่าข้าม process แต่ก็เสี่ยงต่อการเข้าถึงข้อมูลพร้อมกันโดยไม่ปลอดภัย
- **Race Condition (ภาวะแข่งขัน)** — สถานการณ์ที่ผลลัพธ์ของโปรแกรมขึ้นอยู่กับ**ลำดับเวลา (timing)** ที่ thread หลายตัวเข้าถึง/แก้ไขข้อมูลร่วมกัน ทำให้ผลลัพธ์ไม่แน่นอนและคาดเดาไม่ได้ (จะเจาะลึกในบทถัดไป)
- **Mutex (Mutual Exclusion)** — กลไก "กุญแจ" ที่รับประกันว่ามีแค่ thread เดียวเท่านั้นที่เข้าถึงส่วนของโค้ด (Critical Section) ในเวลาหนึ่งๆ ได้
- **Semaphore** — กลไกคล้าย Mutex แต่**อนุญาตให้หลาย thread เข้าถึงพร้อมกันได้ตามจำนวนที่กำหนด** (ไม่ใช่แค่ 1 ตัวเหมือน Mutex)
- **Atomic Operation (การกระทำแบบอะตอมมิก)** — การกระทำที่รับประกันว่า**ทำงานเสร็จสมบูรณ์ในครั้งเดียวโดยไม่มี thread อื่นมาแทรกกลางคันได้เลย**

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Thread มีไว้ใช้ประโยชน์จาก CPU หลายคอร์และทำงานหลายอย่างพร้อมกันอย่างมีประสิทธิภาพ**: คอมพิวเตอร์สมัยใหม่มี CPU หลายคอร์ (บทที่ 1) การรันโปรแกรมด้วย thread เดียวใช้ประโยชน์จากคอร์เดียวเท่านั้น การแบ่งงานเป็นหลาย thread ทำให้ใช้พลังประมวลผลได้เต็มที่ (เช่น เว็บเซิร์ฟเวอร์ที่รับหลายคำขอพร้อมกัน)
- **Mutex/Semaphore มีไว้ป้องกันข้อมูลเสียหายจากการเข้าถึงพร้อมกัน**: เมื่อหลาย thread แชร์หน่วยความจำเดียวกัน (ต่างจาก process ที่แยกกัน) การแก้ไขข้อมูลเดียวกันพร้อมกันโดยไม่มีการควบคุมทำให้เกิดผลลัพธ์ที่ผิดพลาดและคาดเดาไม่ได้ — เครื่องมือเหล่านี้บังคับให้การเข้าถึงข้อมูลที่ใช้ร่วมกันเป็นระเบียบ
- **Atomic Operation มีไว้แก้ปัญหาพื้นฐานที่สุด: การเพิ่มค่าตัวแปรเพียงหนึ่งครั้งอาจไม่ใช่การกระทำเดียวจริงๆ ในระดับฮาร์ดแวร์**: คำสั่งที่ดูเหมือนง่ายอย่าง `counter += 1` แท้จริงประกอบด้วย 3 ขั้นตอนแยกกัน (อ่านค่า, บวกเพิ่ม, เขียนค่ากลับ) ถ้า thread อื่นแทรกเข้ามาระหว่างขั้นตอนเหล่านี้ ผลลัพธ์จะผิดพลาดได้ — Atomic Operation รับประกันว่าทั้ง 3 ขั้นตอนนี้เกิดขึ้นเป็นหน่วยเดียวที่แบ่งแยกไม่ได้

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Process vs Thread** เหมือน **บ้านสองหลังแยกกัน (process) เทียบกับห้องหลายห้องในบ้านหลังเดียวกัน (thread)** — คนในบ้านคนละหลังไม่แชร์ห้องครัวกัน (หน่วยความจำแยกกัน) แต่คนในห้องต่างๆ ของบ้านเดียวกันใช้ห้องครัวเดียวกันได้ (แชร์หน่วยความจำ) ซึ่งสะดวกกว่าแต่ก็ต้องผลัดกันใช้อย่างมีระเบียบ
- **Mutex** เหมือน **ห้องน้ำสาธารณะที่มีกุญแจล็อกได้แค่คนเดียว** — คนแรกเข้าไปแล้วล็อก คนอื่นต้องรอข้างนอกจนกว่าคนแรกจะออกมาและปลดล็อก รับประกันว่ามีคนใช้ห้องน้ำแค่ทีละคนเท่านั้น
- **Semaphore** เหมือน **ที่จอดรถที่มีจำนวนช่องจอดจำกัด (เช่น 3 ช่อง)** — รถคันที่ 1, 2, 3 จอดได้พร้อมกัน แต่คันที่ 4 ต้องรอจนกว่าจะมีคันใดคันหนึ่งออกไปก่อน (ต่างจาก Mutex ที่มีแค่ 1 "ช่อง" เท่านั้น)
- **Atomic Operation** เหมือน **การโอนเงินผ่านตู้ ATM ที่ไม่มีทางถูกขัดจังหวะกลางคัน** — ระบบธนาคารรับประกันว่าการหักเงินจากบัญชีหนึ่งและเข้าบัญชีอีกที่หนึ่งจะเกิดขึ้นครบถ้วนเป็นชุดเดียว ไม่มีทางที่จะหักเงินออกไปแล้วแต่ระบบล่มก่อนที่เงินจะเข้าอีกบัญชี (จะเชื่อมโยงกับ Transactions ในบท Databases)

## แผนภาพอธิบาย (Visual explanation)

### Race Condition — ทำไม counter += 1 ถึงผิดพลาดเมื่อมีหลาย thread

```
counter = 0   (เริ่มต้น)

Thread A ต้องการเพิ่ม counter        Thread B ต้องการเพิ่ม counter
(counter += 1 แยกเป็น 3 ขั้นตอนจริงๆ):

1. อ่านค่า counter -> A เห็น 0
                                      1. อ่านค่า counter -> B เห็น 0   (แทรกเข้ามาก่อน A เขียนเสร็จ!)
2. บวกเพิ่ม 0+1 = 1
                                      2. บวกเพิ่ม 0+1 = 1
3. เขียนค่ากลับ -> counter = 1
                                      3. เขียนค่ากลับ -> counter = 1   (เขียนทับค่าของ A!)

ผลลัพธ์สุดท้าย: counter = 1     (ผิด! ควรจะเป็น 2 เพราะทั้งสอง thread เพิ่มคนละครั้ง)

นี่คือ Race Condition: ผลลัพธ์ขึ้นกับจังหวะเวลาที่ thread สลับกันทำงานพอดี
```

### Mutex แก้ปัญหานี้ — บังคับให้เข้าถึงทีละ thread

```
counter = 0
mutex = Lock()

Thread A:                            Thread B:
mutex.acquire()  <- ล็อกสำเร็จ
1. อ่าน counter -> 0
2. บวก -> 1                          mutex.acquire()  <- รอ! เพราะ A ถือกุญแจอยู่
3. เขียน -> counter = 1                   (block จนกว่า A จะปลดล็อก)
mutex.release()  <- ปลดล็อก
                                      mutex.acquire()  <- ได้กุญแจแล้ว! เข้าทำงานได้
                                      1. อ่าน counter -> 1   (ค่าล่าสุดที่ A เขียนไว้)
                                      2. บวก -> 2
                                      3. เขียน -> counter = 2
                                      mutex.release()

ผลลัพธ์สุดท้าย: counter = 2     ✓ ถูกต้อง! เพราะ Critical Section ถูกเข้าถึงทีละ thread เท่านั้น
```

### Semaphore — อนุญาตหลาย thread พร้อมกันตามจำนวนที่กำหนด

```
semaphore = Semaphore(2)     <- อนุญาตสูงสุด 2 thread พร้อมกัน

Thread A: acquire() -> ได้ทันที (นับ: 1/2 ใช้งานอยู่)
Thread B: acquire() -> ได้ทันที (นับ: 2/2 ใช้งานอยู่ - เต็มแล้ว)
Thread C: acquire() -> ต้องรอ! (semaphore เต็มแล้ว)

Thread A: release() -> ปล่อยคืน (นับ: 1/2 ใช้งานอยู่)
Thread C: acquire() -> ได้แล้ว! (นับ: 2/2 ใช้งานอยู่)

เปรียบเทียบ: Mutex คือ Semaphore ที่จำกัดแค่ 1 เท่านั้น (กรณีพิเศษของ Semaphore)
```

## ตัวอย่างโค้ด (Code example)

```python
import threading

# ===== Race Condition โดยไม่มี Mutex — ผลลัพธ์ผิดพลาดและไม่แน่นอน =====
counter = 0

def increment_unsafe():
    global counter
    for _ in range(100000):
        counter += 1                          # ไม่ปลอดภัย! 3 ขั้นตอนแยกกันที่ thread อื่นแทรกได้

threads = [threading.Thread(target=increment_unsafe) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()                                    # รอทุก thread ทำงานเสร็จก่อน

print(f"Expected: 400000, Got: {counter}")     # มักได้ค่าน้อยกว่า 400000 (ไม่แน่นอนทุกครั้งที่รัน!)

# ===== แก้ด้วย Mutex (threading.Lock) — รับประกันผลลัพธ์ถูกต้อง =====
counter_safe = 0
mutex = threading.Lock()

def increment_safe():
    global counter_safe
    for _ in range(100000):
        with mutex:                             # acquire() อัตโนมัติตอนเข้า, release() อัตโนมัติตอนออก
            counter_safe += 1                     # Critical Section: เข้าถึงได้ทีละ thread เท่านั้น

threads = [threading.Thread(target=increment_safe) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(f"Expected: 400000, Got: {counter_safe}")   # ได้ 400000 ทุกครั้งที่รัน ✓

# ===== Semaphore — จำกัดจำนวน thread ที่เข้าถึงทรัพยากรพร้อมกัน =====
semaphore = threading.Semaphore(2)               # อนุญาตแค่ 2 thread พร้อมกัน (เช่น จำกัด connection pool)

def access_limited_resource(thread_id):
    with semaphore:
        print(f"Thread {thread_id} is using the resource")
        import time
        time.sleep(1)                             # จำลองการทำงานที่ใช้เวลา
    print(f"Thread {thread_id} released the resource")

resource_threads = [threading.Thread(target=access_limited_resource, args=(i,)) for i in range(5)]
for t in resource_threads:
    t.start()
for t in resource_threads:
    t.join()
# มีแค่ 2 thread ทำงานพร้อมกันได้เสมอ ตัวที่เหลือต้องรอคิว
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `increment_unsafe()` เรียกโดย 4 threads พร้อมกัน แต่ละ thread รัน loop 100,000 รอบ ในทางทฤษฎีควรได้ `counter = 400000` แต่ผลลัพธ์จริงมักน้อยกว่านั้นและ**ไม่เท่ากันทุกครั้งที่รัน** — เพราะ `counter += 1` ไม่ใช่การกระทำแบบ atomic (ตามที่อธิบายในแผนภาพ Race Condition) เมื่อหลาย thread แทรกจังหวะกันพอดี การเพิ่มค่าบางครั้งจึง "หายไป"
2. `with mutex:` ใน `increment_safe()` — ใช้ `Lock` เป็น context manager (`with`) ซึ่งเรียก `mutex.acquire()` อัตโนมัติตอนเข้า block และ `mutex.release()` อัตโนมัติตอนออกจาก block (แม้เกิด exception ก็ยัง release ให้เสมอ) — ระหว่างที่ thread หนึ่งถือกุญแจอยู่ (`acquire()` สำเร็จ) thread อื่นที่พยายาม `acquire()` เดียวกันจะ**ถูก block (หยุดรอ)** จนกว่า thread แรกจะ `release()` — รับประกันว่ามีแค่ thread เดียวเข้าไปแก้ไข `counter_safe` ได้ในแต่ละครั้ง
3. `threading.Semaphore(2)` — ต่างจาก `Lock` (ที่อนุญาตแค่ 1) ตรงที่กำหนดจำนวนสูงสุดที่เข้าถึงพร้อมกันได้ (2 ในตัวอย่างนี้) เมื่อ thread ที่ 3, 4, 5 พยายาม `acquire()` ในขณะที่มี 2 thread กำลังใช้งานอยู่แล้ว จะต้องรอจนกว่าจะมี thread ใดตัวหนึ่ง `release()` ก่อน — เหมาะกับสถานการณ์ที่ทรัพยากรมีจำกัดแต่ไม่ได้จำกัดแค่ 1 (เช่น connection pool ของฐานข้อมูลที่รองรับ 2 connection พร้อมกัน)
4. `t.join()` — บล็อกให้ main thread รอจนกว่า thread `t` จะทำงานเสร็จสิ้นก่อนไปทำงานบรรทัดถัดไป ถ้าไม่เรียก `join()` โปรแกรมหลักอาจพิมพ์ค่า `counter` ออกมาก่อนที่ทุก thread จะทำงานเสร็จจริง ทำให้เห็นค่าที่ยังไม่สมบูรณ์

## Time Complexity

- การ `acquire()`/`release()` ของ Mutex/Semaphore: **O(1)** เมื่อไม่มีการแข่งขัน (ไม่มี thread อื่นถือกุญแจอยู่) แต่ถ้ามี thread ต้องรอคิว เวลาที่ใช้ขึ้นอยู่กับว่าต้องรอนานแค่ไหน (ไม่ใช่ Time Complexity ในความหมายปกติของ Big O แต่เป็นเวลาจริงที่ขึ้นกับพฤติกรรม runtime)
- โปรแกรมที่ใช้ Mutex ป้องกัน Critical Section ทำให้ส่วนนั้น**ทำงานแบบ sequential (ทีละ thread)** แม้จะรันบนหลาย thread ก็ตาม — นี่คือ trade-off: ปลอดภัยแต่สูญเสียประโยชน์บางส่วนของการทำงานแบบขนาน ถ้า Critical Section มีขนาดใหญ่เกินจำเป็น

## Space Complexity

- Thread แต่ละตัวใช้พื้นที่เพิ่มเติมสำหรับ **Call Stack ของตัวเอง** (เชื่อมโยงบทที่ 3) แม้จะแชร์ heap ร่วมกับ thread อื่นก็ตาม — การสร้าง thread จำนวนมากเกินไปจึงสิ้นเปลืองหน่วยความจำมากกว่าที่คิด
- Mutex/Semaphore ใช้พื้นที่ **O(1)** สำหรับเก็บสถานะ (ล็อกอยู่หรือไม่, จำนวนที่เหลือ) ไม่ขึ้นกับขนาดข้อมูลที่ป้องกัน

## แนวทางปฏิบัติที่ดี (Best Practices)

- ทำ **Critical Section ให้เล็กที่สุดเท่าที่จำเป็น** — ล็อกเฉพาะโค้ดที่แก้ไขข้อมูลที่ใช้ร่วมกันจริงๆ เท่านั้น ไม่ใช่ล็อกทั้งฟังก์ชันโดยไม่จำเป็น เพื่อลดเวลาที่ thread อื่นต้องรอคิว
- ใช้ `with` (context manager) กับ `Lock`/`Semaphore` เสมอแทนการเรียก `acquire()`/`release()` ตรงๆ เพื่อรับประกันว่า `release()` จะถูกเรียกเสมอแม้เกิด exception ระหว่างทาง (ป้องกัน deadlock ที่จะเรียนในบทถัดไป)
- พิจารณาใช้ **Immutability (บทที่ 34)** เพื่อหลีกเลี่ยงปัญหา Race Condition ตั้งแต่ต้น — ถ้าข้อมูลไม่ถูกแก้ไขเลย ก็ไม่มีความจำเป็นต้องใช้ Mutex ป้องกันการแก้ไขพร้อมกัน (เป็นแนวทางที่บางภาษา/framework สมัยใหม่เลือกใช้แทนการล็อก)

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- คิดว่าการกระทำง่ายๆ อย่าง `counter += 1` เป็น atomic โดยธรรมชาติ ทั้งที่จริงๆ ประกอบด้วยหลายขั้นตอนย่อยที่ thread อื่นแทรกได้เสมอ
- ลืม `release()` กุญแจ (โดยเฉพาะเมื่อไม่ใช้ `with` และเกิด exception ก่อนถึงบรรทัด `release()`) ทำให้ thread อื่นที่รออยู่ **ค้างตลอดไป** (จะเชื่อมโยงกับ Deadlock ในบทถัดไป)
- ล็อก Critical Section ที่ใหญ่เกินความจำเป็น (เช่น ล็อกทั้งฟังก์ชันทั้งที่มีแค่บรรทัดเดียวที่แก้ไขข้อมูลร่วมกันจริงๆ) ทำให้เสียประโยชน์ของการทำงานแบบขนานไปมาก
- ใช้ Semaphore ที่มีค่าเริ่มต้นไม่ตรงกับจำนวนทรัพยากรจริงที่มี (เช่น ตั้ง Semaphore(5) ทั้งที่มี connection pool แค่ 3) ทำให้เกิดข้อผิดพลาดจากการใช้ทรัพยากรเกินขีดจำกัดจริง

## คำถามสัมภาษณ์งาน (Interview Questions)

1. อธิบายความแตกต่างระหว่าง Process และ Thread โดยเฉพาะเรื่องการแชร์หน่วยความจำ
2. Race Condition คืออะไร เกิดขึ้นได้อย่างไรแม้แต่กับการกระทำง่ายๆ อย่างการเพิ่มค่าตัวแปร
3. Mutex ต่างจาก Semaphore อย่างไร ยกตัวอย่างสถานการณ์ที่ควรใช้แต่ละแบบ
4. Atomic Operation คืออะไร ทำไม `counter += 1` ถึงไม่ใช่ atomic operation โดยธรรมชาติ
5. ทำไมการล็อก Critical Section ที่ใหญ่เกินไปถึงเป็นปัญหา แม้จะทำให้โค้ดปลอดภัยจาก Race Condition ก็ตาม

3. เขียนโปรแกรมจำลอง "connection pool" ของฐานข้อมูลที่รองรับ 3 connection พร้อมกันด้วย Semaphore แล้วทดสอบด้วย 10 thread ที่พยายามขอ connection พร้อมกัน วัดว่า thread ที่ต้องรอคิวใช้เวลารอนานแค่ไหน

## Mini Project

**"ระบบจำลองธนาคารแบบ Multi-threaded (Concurrent Bank Simulation)"**: เขียนโปรแกรมที่:
1. สร้าง `BankAccount` (ต่อยอดจากบทที่ 30) ที่รองรับการเข้าถึงจากหลาย thread พร้อมกันอย่างปลอดภัย โดยใช้ `Lock` ป้องกัน Critical Section ในทุก method ที่แก้ไข `_balance`
2. จำลองสถานการณ์ที่หลาย thread พยายามถอนเงินจากบัญชีเดียวกันพร้อมกัน (เช่น 10 thread ถอนคนละ 100 บาทจากบัญชีที่มี 500 บาท) แล้วพิสูจน์ว่าไม่มีทางที่ยอดเงินจะติดลบได้ แม้จะมีการแข่งขันสูง
3. เปรียบเทียบเวอร์ชันที่ **ไม่มี** Lock กับเวอร์ชันที่ **มี** Lock โดยรันหลายรอบและบันทึกผลลัพธ์ที่ได้ พิสูจน์ให้เห็นว่าเวอร์ชันไม่มี Lock ให้ผลลัพธ์ที่ผิดพลาดและไม่แน่นอน (เช่น ยอดเงินไม่ตรงกับที่คำนวณด้วยมือ) ในขณะที่เวอร์ชันมี Lock ให้ผลลัพธ์ถูกต้องเสมอ
4. เพิ่มระบบ "โอนเงินระหว่างบัญชี" ที่ต้องล็อกทั้งสองบัญชีพร้อมกัน (ใบ้: ต้องระวังเรื่องลำดับการล็อกเพื่อไม่ให้เกิด Deadlock ซึ่งจะเรียนรายละเอียดในบทถัดไป)

## ข้อคิดสำคัญ (Key Takeaways)

- Thread คือหน่วยการทำงานที่แชร์หน่วยความจำเดียวกันภายใน process เดียวกัน ต่างจาก Process ที่แยกหน่วยความจำกันโดยสิ้นเชิง
- Race Condition เกิดขึ้นเมื่อผลลัพธ์ของโปรแกรมขึ้นอยู่กับจังหวะเวลาที่หลาย thread เข้าถึงข้อมูลร่วมกัน แม้แต่การกระทำง่ายๆ อย่าง `counter += 1` ก็ไม่ปลอดภัยเพราะไม่ใช่ atomic operation
- Mutex บังคับให้เข้าถึง Critical Section ได้ทีละ thread เท่านั้น ส่วน Semaphore อนุญาตให้เข้าถึงพร้อมกันได้ตามจำนวนที่กำหนด (Mutex คือกรณีพิเศษของ Semaphore ที่จำกัดแค่ 1)
- Atomic Operation รับประกันว่าการกระทำหนึ่งเกิดขึ้นครบถ้วนโดยไม่มี thread อื่นแทรกกลางคันได้ เป็นรากฐานที่ Mutex/Semaphore ใช้สร้างการป้องกันขึ้นมา
- ควรทำ Critical Section ให้เล็กที่สุดเท่าที่จำเป็นเสมอ เพื่อรักษาประโยชน์ของการทำงานแบบขนานไว้ให้มากที่สุดในขณะที่ยังปลอดภัยจาก Race Condition
- บทถัดไปจะเจาะลึก Race Conditions และ Deadlock เพิ่มเติม ซึ่งเป็นปัญหาที่ซับซ้อนกว่าที่เกิดขึ้นได้แม้จะใช้ Mutex/Semaphore แล้วก็ตาม ถ้าออกแบบลำดับการล็อกไม่ถูกต้อง
