# บทที่ 39: SQL vs NoSQL, Normalization

## แนวคิดหลัก (Concept)

ตลอด Part 1-8 ข้อมูลของเราอยู่ในหน่วยความจำ (RAM) เสมอ — เมื่อโปรแกรมปิด ข้อมูลก็หายไป บทนี้เปิด **Part 9: Databases** ซึ่งสอนวิธี**เก็บข้อมูลถาวร**ที่ต้องอยู่รอดแม้โปรแกรมปิดไปแล้ว โดยเริ่มจากคำถามพื้นฐานที่สุด: จะเลือกเก็บข้อมูลแบบไหน? บทนี้เปรียบเทียบสองปรัชญาหลักในการออกแบบฐานข้อมูล และเทคนิค **Normalization** ที่ใช้จัดระเบียบข้อมูลเชิงสัมพันธ์ให้ไม่ซ้ำซ้อน

- **SQL Database (Relational Database)** — ฐานข้อมูลที่เก็บข้อมูลเป็น**ตาราง (table)** ที่มีโครงสร้าง (schema) ตายตัวชัดเจน แต่ละแถว (row) คือ record หนึ่งรายการ แต่ละคอลัมน์ (column) คือ attribute หนึ่งอย่าง เชื่อมโยงข้อมูลระหว่างตารางด้วย **Foreign Key**
- **NoSQL Database** — ฐานข้อมูลที่**ไม่บังคับโครงสร้างตายตัว**แบบตาราง มีหลายรูปแบบย่อย: **Document Store** (เก็บเป็น JSON-like document เช่น MongoDB), **Key-Value Store** (เก็บเป็นคู่ key-value เช่น Redis), **Column-Family** (เช่น Cassandra), **Graph Database** (เก็บเป็น vertex/edge ตามบทที่ 19 โดยตรง เช่น Neo4j)
- **Normalization (การทำนอร์มัลไลซ์)** — กระบวนการจัดโครงสร้างตาราง SQL ให้**ลดความซ้ำซ้อนของข้อมูล**และป้องกันความผิดปกติเมื่อแก้ไข/ลบข้อมูล (anomaly) โดยแบ่งเป็นระดับ (Normal Form) ตั้งแต่ 1NF ถึง 3NF (และสูงกว่า)

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **SQL มีไว้รับประกันความถูกต้องและความสัมพันธ์ของข้อมูลที่ซับซ้อน**: เมื่อข้อมูลมีความสัมพันธ์ชัดเจน (ลูกค้าหนึ่งคนมีหลายคำสั่งซื้อ, คำสั่งซื้อหนึ่งรายการมีหลายสินค้า) SQL Database บังคับ schema และความสัมพันธ์ผ่าน Foreign Key ทำให้ข้อมูลที่ไม่สอดคล้องกัน (เช่น คำสั่งซื้อที่อ้างถึงลูกค้าที่ไม่มีอยู่จริง) ถูกป้องกันไว้ตั้งแต่ระดับฐานข้อมูล
- **NoSQL มีไว้แก้ปัญหาที่ SQL ทำได้ไม่ดีนัก: ข้อมูลที่โครงสร้างเปลี่ยนบ่อยหรือต้องการขยายขนาด (scale) ในแนวนอนอย่างมหาศาล**: ถ้าแต่ละ record มีโครงสร้างต่างกันได้ (เช่น สินค้าแต่ละประเภทมี attribute ไม่เหมือนกัน) การบังคับ schema ตายตัวของ SQL กลับเป็นอุปสรรค — NoSQL ยืดหยุ่นกว่าและมักออกแบบมาให้กระจายข้อมูลไปหลายเครื่องได้ง่ายกว่า (จะเจาะลึกใน CAP Theorem บทถัดๆ ไป)
- **Normalization มีไว้ป้องกัน "Update/Insert/Delete Anomaly"**: ถ้าเก็บชื่อลูกค้าซ้ำในทุกแถวคำสั่งซื้อของลูกค้าคนนั้น (ข้อมูลซ้ำซ้อน) เมื่อลูกค้าเปลี่ยนชื่อ ต้องแก้ไขทุกแถวที่ซ้ำกัน — ถ้าแก้ไม่ครบจะเกิดข้อมูลไม่สอดคล้องกัน (บางแถวชื่อเก่า บางแถวชื่อใหม่) Normalization แก้ปัญหานี้ด้วยการแยกข้อมูลที่ควรอยู่คนละที่ออกจากกันตั้งแต่ต้น

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **SQL Database** เหมือน **แบบฟอร์มราชการที่มีช่องกรอกตายตัว** — ทุกใบต้องมีชื่อ, เลขบัตรประชาชน, ที่อยู่ ครบตามช่องที่กำหนดไว้เป๊ะ จะขาดช่องไม่ได้ และการเชื่อมโยงระหว่างแบบฟอร์ม (เช่น อ้างอิงเลขคำร้องก่อนหน้า) ต้องตรงกับที่มีอยู่จริงในระบบเสมอ
- **NoSQL Document Store** เหมือน **แฟ้มสะสมผลงาน (portfolio) ของแต่ละคนที่มีเนื้อหาไม่เหมือนกันเลย** — นักออกแบบกราฟิกใส่รูปภาพ นักเขียนใส่บทความ นักดนตรีใส่ไฟล์เสียง แต่ละแฟ้มมีโครงสร้างต่างกันได้ตามธรรมชาติของเจ้าของ ไม่มีแบบฟอร์มตายตัวบังคับ
- **Normalization** เหมือน **การเก็บที่อยู่ลูกค้าไว้ในสมุดที่อยู่กลางแทนที่จะเขียนซ้ำในทุกใบเสร็จ** — ใบเสร็จแต่ละใบแค่อ้างอิง "รหัสลูกค้า" กลับไปที่สมุดที่อยู่กลาง เมื่อลูกค้าย้ายบ้าน แก้ไขแค่ที่เดียวในสมุดที่อยู่ ใบเสร็จเก่าทุกใบก็อ้างอิงถูกต้องอัตโนมัติ

## แผนภาพอธิบาย (Visual explanation)

### SQL (ตารางมีโครงสร้างตายตัว เชื่อมกันด้วย Foreign Key)

```
ตาราง Customers:                      ตาราง Orders:
+----+---------+-------+              +----+-------------+---------+
| id | name    | email |              | id | customer_id | product |
+----+---------+-------+              +----+-------------+---------+
| 1  | Alice   | a@... |              | 101| 1           | Laptop  |
| 2  | Bob     | b@... |              | 102| 1           | Mouse   |
+----+---------+-------+              | 103| 2           | Monitor |
                                       +----+-------------+---------+
                                              |
                                              └──> Foreign Key ชี้กลับไปที่ Customers.id
                                                   (Orders.customer_id ต้องมีอยู่จริงใน Customers เสมอ)
```

### NoSQL Document Store — แต่ละ document มีโครงสร้างต่างกันได้

```
{
  "_id": "product_001",
  "type": "laptop",
  "name": "Gaming Laptop",
  "specs": { "ram": "16GB", "cpu": "i7", "gpu": "RTX 4060" }     <- laptop มี specs แบบนี้
}

{
  "_id": "product_002",
  "type": "book",
  "name": "Learn Python",
  "author": "John Doe", "pages": 350                              <- book มี attribute ต่างจาก laptop โดยสิ้นเชิง
}

ทั้งสอง document อยู่ใน collection เดียวกันได้ โดยไม่มี schema ตายตัวบังคับให้เหมือนกัน
```

### Normalization — จากข้อมูลซ้ำซ้อน (Unnormalized) สู่ 3NF

```
Unnormalized (ข้อมูลลูกค้าซ้ำในทุกแถว):
+-----+------------+--------------+---------+
| id  | customer   | customer_email| product |
+-----+------------+--------------+---------+
| 101 | Alice      | a@mail.com   | Laptop  |
| 102 | Alice      | a@mail.com   | Mouse   |    <- ชื่อและอีเมล Alice ซ้ำ! ถ้า Alice เปลี่ยนอีเมล ต้องแก้ 2 แถว
+-----+------------+--------------+---------+

หลัง Normalize (แยกเป็น 2 ตาราง เชื่อมด้วย Foreign Key):
Customers:                            Orders:
+----+-------+------------+           +-----+-------------+---------+
| id | name  | email      |           | id  | customer_id | product |
+----+-------+------------+           +-----+-------------+---------+
| 1  | Alice | a@mail.com |           | 101 | 1           | Laptop  |
+----+-------+------------+           | 102 | 1           | Mouse   |   <- แค่อ้างอิง id=1 ไม่ซ้ำข้อมูลเลย
                                       +-----+-------------+---------+

ถ้า Alice เปลี่ยนอีเมล -> แก้แค่ 1 แถวในตาราง Customers เท่านั้น ทุก Order ที่อ้างอิงถูกต้องอัตโนมัติ
```

## ตัวอย่างโค้ด (Code example)

```sql
-- ===== SQL: สร้างตารางพร้อม Foreign Key (หลัง Normalization) =====
CREATE TABLE Customers (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL
);

CREATE TABLE Orders (
    id INT PRIMARY KEY AUTO_INCREMENT,
    customer_id INT NOT NULL,
    product VARCHAR(100) NOT NULL,
    FOREIGN KEY (customer_id) REFERENCES Customers(id)   -- บังคับว่า customer_id ต้องมีอยู่จริง
);

INSERT INTO Customers (name, email) VALUES ('Alice', 'a@mail.com');
INSERT INTO Orders (customer_id, product) VALUES (1, 'Laptop'), (1, 'Mouse');

-- JOIN ดึงข้อมูลจากสองตารางมารวมกันตามความสัมพันธ์
SELECT Customers.name, Orders.product
FROM Orders
JOIN Customers ON Orders.customer_id = Customers.id;
-- ผลลัพธ์: Alice | Laptop
--          Alice | Mouse

-- ทดสอบว่า Foreign Key ป้องกันข้อมูลไม่สอดคล้องกัน:
INSERT INTO Orders (customer_id, product) VALUES (999, 'Keyboard');
-- Error: Foreign key constraint fails (customer_id=999 ไม่มีอยู่จริงใน Customers)
```

```python
# ===== NoSQL (จำลองด้วย Python dict แทน MongoDB จริง): เก็บข้อมูลแบบยืดหยุ่น =====
products_collection = [
    {
        "_id": "product_001",
        "type": "laptop",
        "name": "Gaming Laptop",
        "specs": {"ram": "16GB", "cpu": "i7", "gpu": "RTX 4060"}
    },
    {
        "_id": "product_002",
        "type": "book",
        "name": "Learn Python",
        "author": "John Doe",
        "pages": 350                          # attribute ต่างจาก laptop โดยสิ้นเชิง ไม่มี schema บังคับ
    }
]

def find_by_type(collection, product_type):
    return [doc for doc in collection if doc["type"] == product_type]

print(find_by_type(products_collection, "book"))
# [{'_id': 'product_002', 'type': 'book', 'name': 'Learn Python', 'author': 'John Doe', 'pages': 350}]
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `FOREIGN KEY (customer_id) REFERENCES Customers(id)` — บรรทัดนี้คือหัวใจของ SQL Database: มันบังคับว่าค่าของ `customer_id` ในตาราง `Orders` **ต้องตรงกับค่า `id` ที่มีอยู่จริงในตาราง `Customers` เสมอ** ฐานข้อมูลจะปฏิเสธ (โยน error) ทันทีถ้าพยายาม insert แถวที่ `customer_id` ไม่มีอยู่จริง (เห็นได้จากตัวอย่าง `customer_id=999` ที่ล้มเหลว) — นี่คือกลไก **Referential Integrity** ที่ SQL รับประกันให้อัตโนมัติ
2. `SELECT ... FROM Orders JOIN Customers ON Orders.customer_id = Customers.id` — คำสั่ง `JOIN` รวมข้อมูลจากสองตารางเข้าด้วยกันโดยจับคู่แถวที่ `Orders.customer_id` ตรงกับ `Customers.id` — นี่คือผลตอบแทนของ Normalization: แม้ข้อมูลจะถูกแยกเก็บคนละตาราง (ไม่ซ้ำซ้อน) แต่ยังคง**ดึงกลับมารวมกันได้เมื่อต้องการ** ผ่าน JOIN
3. `find_by_type(collection, product_type)` — เพราะ NoSQL Document Store ไม่มี schema ตายตัว โค้ดที่อ่านข้อมูลต้อง**เตรียมรับมือกับ document ที่มีโครงสร้างต่างกัน**ได้ (ในตัวอย่างนี้แค่กรองด้วย `type` ซึ่งเป็น field ที่ทุก document มีร่วมกัน แต่ field อื่นอย่าง `specs` หรือ `author` มีเฉพาะบาง document เท่านั้น) — นี่คือทั้งข้อดี (ยืดหยุ่น) และข้อควรระวัง (โค้ดฝั่งแอปพลิเคชันต้องรับผิดชอบตรวจสอบโครงสร้างเอง แทนที่ฐานข้อมูลจะบังคับให้)

## Time Complexity

- **SQL**: การ query ด้วย index (จะเรียนละเอียดในบทถัดไป) ทำได้ **O(log n)** เทียบเท่า Binary Search (บทที่ 22) แต่ JOIN ระหว่างตารางขนาดใหญ่โดยไม่มี index ที่เหมาะสมอาจเสีย **O(n × m)** (n, m คือขนาดของแต่ละตาราง)
- **NoSQL**: การอ่าน document ด้วย key/id โดยตรงมักเป็น **O(1)** (คล้าย Hash Table บทที่ 15) แต่การ query ด้วยเงื่อนไขที่ไม่ใช่ key หลักอาจต้องสแกนทั้ง collection **O(n)** ถ้าไม่มี index รองรับ

## Space Complexity

- **หลัง Normalization**: ใช้พื้นที่**น้อยกว่า**เพราะไม่มีข้อมูลซ้ำซ้อน (ชื่อ/อีเมลลูกค้าเก็บแค่ครั้งเดียว) แต่ต้องแลกกับการ JOIN ที่มีต้นทุนด้านเวลาเพิ่มขึ้นตอน query
- **NoSQL (มัก Denormalize โดยเจตนา)**: อาจใช้พื้นที่**มากกว่า**เพราะเก็บข้อมูลซ้ำในหลาย document โดยตั้งใจ (เช่น embed ข้อมูลลูกค้าไว้ในทุกคำสั่งซื้อ) เพื่อแลกกับความเร็วในการอ่านที่ไม่ต้อง JOIN เลย

## แนวทางปฏิบัติที่ดี (Best Practices)

- เลือก SQL เมื่อข้อมูลมีความสัมพันธ์ชัดเจนและต้องการความถูกต้องสูง (เช่น ระบบธนาคาร, ระบบสต็อกสินค้า) เลือก NoSQL เมื่อโครงสร้างข้อมูลเปลี่ยนแปลงบ่อยหรือต้องการขยายขนาดในแนวนอนอย่างมหาศาล (เช่น log ระบบ, ข้อมูล session, ข้อมูล social media feed)
- ทำ Normalization อย่างน้อยถึงระดับ **3NF** เป็นค่าเริ่มต้นเมื่อออกแบบ SQL Database ใหม่ เว้นแต่มีเหตุผลด้านประสิทธิภาพที่ชัดเจนที่ต้องทำ Denormalization (เก็บข้อมูลซ้ำโดยตั้งใจเพื่อความเร็ว) ในบางส่วน
- อย่ามองว่า SQL กับ NoSQL เป็นคู่แข่งที่ต้องเลือกอย่างใดอย่างหนึ่งเสมอ — ระบบจริงจำนวนมากใช้**ทั้งสองแบบร่วมกัน** (Polyglot Persistence) เช่น ใช้ SQL เก็บข้อมูลธุรกรรมหลัก และใช้ NoSQL (เช่น Redis) เก็บ cache หรือ session

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- เลือก NoSQL เพียงเพราะ "เร็วกว่า" หรือ "ทันสมัยกว่า" โดยไม่พิจารณาว่าข้อมูลจริงมีความสัมพันธ์ที่ซับซ้อนซึ่งเหมาะกับ SQL มากกว่า ทำให้ต้องเขียนโค้ดฝั่งแอปพลิเคชันจัดการความสัมพันธ์เองแทนที่จะให้ฐานข้อมูลช่วย
- ไม่ทำ Normalization เลย เก็บข้อมูลซ้ำซ้อนในทุกแถวโดยไม่ตั้งใจ ทำให้เกิด Update Anomaly (แก้ไม่ครบทุกที่ที่ซ้ำ) โดยไม่รู้ตัว
- ทำ Normalization มากเกินไป (Over-normalization) จนต้อง JOIN หลายตารางสำหรับ query ง่ายๆ ทำให้ performance แย่ลงโดยไม่ได้ประโยชน์ที่คุ้มค่า
- ลืมว่า NoSQL ไม่มี Referential Integrity ให้อัตโนมัติเหมือน SQL Foreign Key ทำให้ข้อมูลที่อ้างอิงกันไม่สอดคล้องกันได้ง่ายถ้าไม่ตรวจสอบเองในโค้ดแอปพลิเคชัน

## คำถามสัมภาษณ์งาน (Interview Questions)

1. อธิบายความแตกต่างหลักระหว่าง SQL และ NoSQL Database พร้อมยกตัวอย่างสถานการณ์ที่เหมาะกับแต่ละแบบ
2. Normalization คืออะไร แก้ปัญหาอะไร (Update/Insert/Delete Anomaly คืออะไร)
3. Foreign Key ทำหน้าที่อะไรใน SQL Database ทำไม NoSQL ถึงไม่มีกลไกนี้โดยธรรมชาติ
4. Denormalization คืออะไร ทำไมบางครั้งถึงจงใจทำแม้จะขัดกับหลักการ Normalization
5. NoSQL มีกี่ประเภทหลัก แต่ละประเภทเหมาะกับข้อมูลแบบไหน

## แบบฝึกหัด (Practice Exercises)

## Mini Project

**"ระบบเปรียบเทียบการออกแบบฐานข้อมูล (Database Design Comparison Tool)"**: เขียนโปรแกรมที่:
1. จำลองระบบจัดการร้านค้าออนไลน์ทั้งแบบ SQL (ใช้ SQLite ผ่าน Python `sqlite3`) และ NoSQL (จำลองด้วย dict/JSON ในไฟล์) โดยมีข้อมูลลูกค้า, สินค้า, คำสั่งซื้อ
2. Implement เวอร์ชัน SQL ให้ทำ Normalization ถึง 3NF (แยกตาราง Customers, Products, Orders, OrderItems พร้อม Foreign Key ครบถ้วน)
3. Implement เวอร์ชัน NoSQL ที่จงใจ Denormalize (embed ข้อมูลลูกค้าและสินค้าไว้ในแต่ละคำสั่งซื้อโดยตรง)
4. เขียนฟังก์ชันทดสอบ "ลูกค้าเปลี่ยนที่อยู่" แล้วเปรียบเทียบว่าเวอร์ชัน SQL แก้ไขข้อมูลกี่จุด เทียบกับเวอร์ชัน NoSQL ที่ต้องแก้ไขในทุก document ที่มีข้อมูลซ้ำ พร้อมสรุปผลว่าแนวทางไหนเหมาะกับสถานการณ์นี้มากกว่า

## ข้อคิดสำคัญ (Key Takeaways)

- SQL Database เก็บข้อมูลเป็นตารางที่มี schema ตายตัว เชื่อมโยงกันด้วย Foreign Key ที่รับประกัน Referential Integrity อัตโนมัติ เหมาะกับข้อมูลที่มีความสัมพันธ์ชัดเจน
- NoSQL Database ยืดหยุ่นกว่าในเรื่องโครงสร้างข้อมูล เหมาะกับข้อมูลที่เปลี่ยนแปลงบ่อยหรือต้องขยายขนาดในแนวนอน แต่ต้องจัดการความสอดคล้องของข้อมูลเองในฝั่งแอปพลิเคชัน
- Normalization ลดความซ้ำซ้อนของข้อมูลด้วยการแยกตารางตามความรับผิดชอบ ป้องกัน Update/Insert/Delete Anomaly แต่แลกมาด้วยต้นทุนการ JOIN ที่เพิ่มขึ้น
- Denormalization (การเก็บข้อมูลซ้ำโดยตั้งใจ) เป็นทางเลือกที่ใช้เพื่อความเร็วในการอ่าน มักพบใน NoSQL หรือ SQL ที่ปรับแต่งเพื่อ performance เฉพาะจุด
- ไม่มีคำตอบที่ถูกเสมอไประหว่าง SQL กับ NoSQL — ต้องเลือกตามลักษณะข้อมูลจริงและความต้องการของระบบ และหลายระบบใช้ทั้งสองแบบร่วมกัน
- บทถัดไปจะเจาะลึก Index, Query Optimization, และ Joins ซึ่งขยายความจากการ JOIN และ query ที่เห็นในบทนี้ อธิบายว่าฐานข้อมูลทำให้ query เร็วขึ้นได้อย่างไรในทางเทคนิค
