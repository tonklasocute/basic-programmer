# บทที่ 42: TCP/IP, DNS, HTTP/HTTPS, SSL/TLS

## แนวคิดหลัก (Concept)

Part 9 สอนวิธีจัดเก็บและจัดการข้อมูลภายในฐานข้อมูลเครื่องเดียว แต่ในโลกจริง ข้อมูลต้องเดินทางระหว่างเครื่องคอมพิวเตอร์นับล้านเครื่องทั่วโลก บทนี้เปิด **Part 10: Networking** โดยอธิบายว่าเมื่อพิมพ์ URL ในเบราว์เซอร์แล้วกด Enter เกิดอะไรขึ้นบ้างกว่าจะได้หน้าเว็บกลับมา — เป็นคำถามสัมภาษณ์งานคลาสสิกที่ครอบคลุมเกือบทุกหัวข้อในบทนี้

- **TCP/IP** — ชุดโปรโตคอลพื้นฐานที่สุดของอินเทอร์เน็ต **IP (Internet Protocol)** ทำหน้าที่หาเส้นทางส่งข้อมูล (packet) จากเครื่องหนึ่งไปอีกเครื่องหนึ่งโดยใช้ที่อยู่ (IP Address) ส่วน **TCP (Transmission Control Protocol)** ทำหน้าที่รับประกันว่าข้อมูลถึงปลายทางครบถ้วนและเรียงลำดับถูกต้อง
- **DNS (Domain Name System)** — ระบบที่แปลงชื่อโดเมนที่มนุษย์จำง่าย (เช่น `google.com`) ให้เป็น IP Address ที่คอมพิวเตอร์ใช้สื่อสารกันจริง
- **HTTP/HTTPS** — โปรโตคอลระดับสูงที่กำหนดรูปแบบการขอ-ตอบข้อมูลระหว่างเบราว์เซอร์ (client) กับเซิร์ฟเวอร์ **HTTPS** คือ HTTP ที่เข้ารหัสข้อมูลด้วย SSL/TLS
- **SSL/TLS** — โปรโตคอลเข้ารหัสที่ทำให้ข้อมูลที่ส่งผ่านเครือข่ายอ่านไม่ออกแม้ถูกดักจับระหว่างทาง และยืนยันตัวตนของเซิร์ฟเวอร์ว่าเป็นของจริง

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **TCP/IP มีไว้ให้เครื่องคอมพิวเตอร์ที่ไม่รู้จักกันมาก่อนสื่อสารกันได้อย่างน่าเชื่อถือ**: อินเทอร์เน็ตประกอบด้วยเครือข่ายย่อยนับไม่ถ้วนที่เชื่อมต่อกัน ข้อมูลต้องเดินทางผ่านหลาย router กว่าจะถึงปลายทาง ระหว่างทางอาจมี packet สูญหายหรือมาถึงไม่เรียงลำดับ — TCP รับประกันว่าจะตรวจจับและแก้ไขปัญหาเหล่านี้ให้อัตโนมัติ ทำให้แอปพลิเคชันระดับบนไม่ต้องกังวลเรื่องนี้เอง
- **DNS มีไว้เพราะมนุษย์จำชื่อได้ดีกว่าตัวเลข**: การจำ `142.250.196.14` ยากกว่าการจำ `google.com` มาก แต่คอมพิวเตอร์ต้องการ IP Address ในการส่งข้อมูลจริง — DNS ทำหน้าที่เป็นสมุดโทรศัพท์ขนาดใหญ่ที่แปลระหว่างสองสิ่งนี้ให้อัตโนมัติ
- **HTTP มีไว้เป็นภาษากลางที่ทุกเว็บเซิร์ฟเวอร์และเบราว์เซอร์เข้าใจตรงกัน**: ไม่ว่าจะใช้เบราว์เซอร์ยี่ห้อไหนหรือเซิร์ฟเวอร์เขียนด้วยภาษาอะไร ทุกฝ่ายเข้าใจรูปแบบ HTTP request/response เดียวกัน ทำให้ระบบที่แตกต่างกันโดยสิ้นเชิงคุยกันได้
- **SSL/TLS มีไว้ป้องกันข้อมูลจากผู้ดักฟังระหว่างทาง**: ข้อมูลที่ส่งผ่าน HTTP ธรรมดาเดินทางเป็น**ข้อความธรรมดา (plain text)** ผ่าน router หลายตัวที่เราไม่รู้จัก — ถ้ามีใครดักจับข้อมูลระหว่างทาง (เช่น รหัสผ่าน, เลขบัตรเครดิต) จะอ่านได้ทันที SSL/TLS เข้ารหัสข้อมูลก่อนส่งเพื่อป้องกันปัญหานี้

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **IP Address** เหมือน **ที่อยู่บ้านที่ใช้ระบุตำแหน่งเฉพาะเจาะจง** ส่วน **TCP** เหมือน **บริการไปรษณีย์ลงทะเบียนที่รับประกันว่าพัสดุถึงปลายทางและแจ้งเตือนถ้าพัสดุหาย** (ต่างจากการส่งพัสดุธรรมดาที่ไม่รับประกันอะไรเลย)
- **DNS** เหมือน **สมุดโทรศัพท์ที่แปลงชื่อคนเป็นเบอร์โทรศัพท์** — เราจำชื่อ "ร้านพิซซ่าโปรด" ได้ง่ายกว่าเบอร์โทร 10 หลัก สมุดโทรศัพท์ (DNS) ช่วยแปลให้อัตโนมัติทุกครั้งที่ต้องการโทรจริง
- **HTTP Request/Response** เหมือน **การสั่งอาหารที่ร้านอาหาร** — ลูกค้า (client) บอกเมนูที่ต้องการ (request) พนักงาน (server) นำอาหารมาเสิร์ฟพร้อมใบเสร็จ (response) ทั้งสองฝ่ายเข้าใจรูปแบบการสั่งและการเสิร์ฟแบบเดียวกันไม่ว่าจะเป็นร้านไหน
- **SSL/TLS** เหมือน **จดหมายที่ใส่ในซองล็อกรหัสที่เปิดได้เฉพาะผู้รับที่ถูกต้องเท่านั้น** — แม้จดหมายจะผ่านมือบุรุษไปรษณีย์หลายคนระหว่างทาง (router หลายตัว) ก็ไม่มีใครอ่านเนื้อหาข้างในได้เลยนอกจากผู้รับปลายทางจริง

## แผนภาพอธิบาย (Visual explanation)

### ภาพรวม: เกิดอะไรขึ้นเมื่อพิมพ์ URL แล้วกด Enter

```
1. ผู้ใช้พิมพ์ https://www.example.com ในเบราว์เซอร์

2. DNS Lookup: แปลง "www.example.com" -> IP Address (เช่น 93.184.216.34)
   เบราว์เซอร์ -> DNS Resolver -> Root DNS -> .com DNS -> example.com DNS -> ได้ IP กลับมา

3. TCP Handshake (3-way): เบราว์เซอร์เชื่อมต่อกับเซิร์ฟเวอร์ที่ IP นั้น
   Client -> SYN -> Server
   Client <- SYN-ACK <- Server
   Client -> ACK -> Server
   (การเชื่อมต่อ TCP พร้อมใช้งานแล้ว)

4. TLS Handshake: (เพราะเป็น https) เจรจาการเข้ารหัสก่อนส่งข้อมูลจริง

5. HTTP Request: เบราว์เซอร์ส่งคำขอ GET / ไปยังเซิร์ฟเวอร์ (ผ่านการเชื่อมต่อที่เข้ารหัสแล้ว)

6. HTTP Response: เซิร์ฟเวอร์ส่ง HTML กลับมา -> เบราว์เซอร์แสดงผลหน้าเว็บ
```

### TCP 3-Way Handshake — สร้างการเชื่อมต่อที่เชื่อถือได้ก่อนส่งข้อมูลจริง

```
Client                                    Server

  |------ SYN (ขอเชื่อมต่อ) --------------->|
  |<----- SYN-ACK (ตกลง + ขอกลับ) ----------|
  |------ ACK (ยืนยันรับทราบ) ------------->|

  ทั้งสองฝั่งยืนยันพร้อมสื่อสารกันแล้ว -> เริ่มส่งข้อมูลจริงได้
  (ต่างจาก UDP ที่ส่งข้อมูลทันทีโดยไม่ตรวจสอบว่าอีกฝั่งพร้อมหรือไม่ - เร็วกว่าแต่ไม่รับประกันความถูกต้อง)
```

### HTTP Request/Response — โครงสร้างพื้นฐาน

```
HTTP Request:                              HTTP Response:

GET /products?id=5 HTTP/1.1                HTTP/1.1 200 OK
Host: example.com                          Content-Type: application/json
User-Agent: Mozilla/5.0...                 Content-Length: 128
Accept: application/json
                                            {"id": 5, "name": "Laptop", "price": 25000}
(Body - ว่างเปล่าสำหรับ GET)

Method: GET (ขอข้อมูล), POST (ส่งข้อมูลใหม่), PUT (อัปเดต), DELETE (ลบ)
Status Code: 200 (สำเร็จ), 404 (ไม่พบ), 500 (เซิร์ฟเวอร์ผิดพลาด) ฯลฯ
```

### SSL/TLS Handshake (แบบย่อ) — เจรจาการเข้ารหัสก่อนส่งข้อมูล

```
Client                                    Server

  |--- "สวัสดี, รองรับการเข้ารหัสแบบไหนบ้าง?" ->|
  |<-- ใบรับรอง (Certificate) + Public Key -----|
  |    (ตรวจสอบใบรับรองกับ Certificate Authority ว่าเซิร์ฟเวอร์เป็นของจริง)
  |--- สร้างกุญแจลับร่วมกัน (encrypted) ------->|

  จากนี้ไป: ข้อมูลทั้งหมดถูกเข้ารหัสด้วยกุญแจที่ตกลงกันไว้
  แม้มีคนดักจับข้อมูลระหว่างทาง ก็อ่านไม่ออกเพราะไม่มีกุญแจถอดรหัส
```

## ตัวอย่างโค้ด (Code example)

```python
import socket
import requests                                  # library สำหรับทำ HTTP request ระดับสูง

# ===== DNS Lookup: แปลงชื่อโดเมนเป็น IP Address =====
ip_address = socket.gethostbyname("www.example.com")
print(f"IP Address: {ip_address}")                 # เช่น 93.184.216.34

# ===== TCP Socket พื้นฐาน (ระดับต่ำ) — จำลอง HTTP request ด้วยมือ =====
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)   # SOCK_STREAM = ใช้ TCP
sock.connect(("www.example.com", 80))                          # เชื่อมต่อ (เกิด 3-way handshake ที่นี่)

request = "GET / HTTP/1.1\r\nHost: www.example.com\r\nConnection: close\r\n\r\n"
sock.send(request.encode())                                     # ส่ง HTTP request แบบดิบๆ

response = sock.recv(4096).decode(errors="ignore")
print(response[:200])                                             # ดูส่วนหัวของ response
sock.close()

# ===== HTTP Request ระดับสูงด้วย library (วิธีที่ใช้จริงในงาน) =====
response = requests.get("https://api.github.com/users/octocat")   # https -> ใช้ TLS อัตโนมัติ
print(response.status_code)                                        # 200
print(response.headers["Content-Type"])                             # application/json; charset=utf-8
data = response.json()                                               # แปลง response body เป็น dict
print(data["name"])                                                   # "The Octocat"

# ===== HTTP Methods ต่างๆ =====
requests.get("https://api.example.com/users/5")               # ขอข้อมูล
requests.post("https://api.example.com/users", json={"name": "Alice"})  # สร้างใหม่
requests.put("https://api.example.com/users/5", json={"name": "Bob"})    # อัปเดตทั้งหมด
requests.delete("https://api.example.com/users/5")               # ลบ

# ===== ตรวจสอบใบรับรอง SSL (verify=True เป็นค่าเริ่มต้นเสมอ - อย่าปิดโดยไม่จำเป็น!) =====
try:
    requests.get("https://self-signed.badssl.com", timeout=5)
except requests.exceptions.SSLError as e:
    print("SSL Certificate verification failed:", e)               # ป้องกันการเชื่อมต่อกับเซิร์ฟเวอร์ปลอม
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `socket.gethostbyname("www.example.com")` — ส่งคำขอ **DNS Lookup** ไปยัง DNS Resolver ที่ตั้งค่าไว้ในระบบปฏิบัติการ (มักเป็นของผู้ให้บริการอินเทอร์เน็ตหรือ Google DNS `8.8.8.8`) ซึ่งจะไล่ถามต่อไปยัง Root DNS Server -> TLD DNS Server (`.com`) -> Authoritative DNS Server ของโดเมนนั้น จนได้ IP Address กลับมา — ผลลัพธ์นี้มักถูก**แคชไว้**ชั่วคราว (ทั้งในเบราว์เซอร์และ OS) เพื่อไม่ต้องถามซ้ำทุกครั้ง
2. `sock.connect(("www.example.com", 80))` — บรรทัดนี้เป็นจุดที่เกิด **TCP 3-Way Handshake** จริงๆ ในระดับ operating system (ส่ง SYN, รับ SYN-ACK, ส่ง ACK กลับ) ก่อนที่ `connect()` จะคืนค่าสำเร็จ การเชื่อมต่อ TCP ต้องเสร็จสมบูรณ์ก่อนเสมอก่อนที่จะส่งข้อมูล HTTP ใดๆ ได้
3. `sock.send(request.encode())` — ส่ง**ข้อความ HTTP request แบบดิบ**ที่เขียนเองตามรูปแบบ HTTP Protocol (`GET / HTTP/1.1\r\nHost: ...`) ผ่านการเชื่อมต่อ TCP ที่เพิ่งสร้างไว้ — สังเกตว่านี่คือ HTTP ธรรมดา (port 80, ไม่เข้ารหัส) ข้อมูลที่ส่งเป็น plain text ที่ใครก็ตามที่ดักจับระหว่างทางอ่านได้ทันที ต่างจาก `requests.get("https://...")` ที่ใช้ TLS เข้ารหัสให้อัตโนมัติ
4. `requests.get("https://api.github.com/...")` — library `requests` จัดการทุกขั้นตอน (DNS Lookup, TCP Handshake, TLS Handshake, สร้าง HTTP request, รับ response, ตรวจสอบใบรับรอง SSL) ให้อัตโนมัติทั้งหมดในบรรทัดเดียว — นี่คือ **Abstraction** (ทบทวนจากบทที่ 30) ที่ซ่อนความซับซ้อนของเครือข่ายทั้งหมดไว้เบื้องหลัง interface ที่เรียบง่าย
5. การจับ `requests.exceptions.SSLError` — เมื่อใบรับรอง SSL ของเซิร์ฟเวอร์**ไม่ถูกต้องหรือไม่น่าเชื่อถือ** (เช่น self-signed certificate ที่ไม่ได้ออกโดย Certificate Authority ที่เชื่อถือได้) `requests` จะปฏิเสธการเชื่อมต่อทันทีเป็นค่าเริ่มต้น (`verify=True`) — นี่คือกลไกป้องกัน**การปลอมตัวเป็นเซิร์ฟเวอร์อื่น (Man-in-the-Middle Attack)** ที่ SSL/TLS มอบให้

## Time Complexity

Networking ไม่ได้วัดด้วย Big O เหมือนอัลกอริทึม แต่มี**ต้นทุนด้านเวลาแฝง (latency)** ที่สะสมกันในแต่ละขั้นตอน:
- DNS Lookup: มักมีการแคชไว้ ทำให้ครั้งถัดๆ ไปเกือบจะ **O(1)** (ไม่ต้องถามใหม่)
- TCP 3-Way Handshake: ใช้เวลาอย่างน้อย **1 RTT (Round-Trip Time)** ก่อนส่งข้อมูลได้จริง
- TLS Handshake: ใช้เวลาเพิ่มอีก **1-2 RTT** สำหรับเจรจาการเข้ารหัส (เวอร์ชัน TLS ใหม่กว่าลดจำนวน round-trip ลงได้)
- HTTP Request/Response: ขึ้นกับขนาดข้อมูลและความเร็วเซิร์ฟเวอร์ในการประมวลผล

## Space Complexity

- DNS Cache ใช้พื้นที่ **O(k)** โดย k คือจำนวนโดเมนที่เคยถูกเรียกดูและยังไม่หมดอายุ
- TCP Connection แต่ละตัวใช้หน่วยความจำเล็กน้อยที่ทั้งสองฝั่งเพื่อเก็บสถานะการเชื่อมต่อ (buffer สำหรับข้อมูลที่รอส่ง/รับ)

## แนวทางปฏิบัติที่ดี (Best Practices)

- ใช้ **HTTPS เสมอ** สำหรับทุกเว็บไซต์/API ที่รับส่งข้อมูลจริง โดยเฉพาะข้อมูลที่ละเอียดอ่อน (รหัสผ่าน, ข้อมูลส่วนตัว, ธุรกรรมทางการเงิน) เพราะ HTTP ธรรมดาส่งข้อมูลเป็น plain text ที่ดักจับได้ง่าย
- **ไม่ปิดการตรวจสอบใบรับรอง SSL** (`verify=False`) แม้แต่ในสภาพแวดล้อมทดสอบ เพราะเป็นการเปิดช่องให้เกิด Man-in-the-Middle Attack ได้ ถ้าจำเป็นต้องทดสอบกับ self-signed certificate ให้เพิ่มใบรับรองนั้นเข้า trust store แทน
- ใช้ HTTP Method ให้ตรงกับความหมายจริง (`GET` สำหรับดึงข้อมูลอย่างเดียว, `POST` สำหรับสร้างใหม่, `PUT`/`PATCH` สำหรับอัปเดต, `DELETE` สำหรับลบ) เพื่อให้ระบบและเครื่องมือ (caching, logging) ทำงานได้ถูกต้องตามมาตรฐาน

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ใช้ HTTP ธรรมดา (ไม่เข้ารหัส) ส่งข้อมูลที่ละเอียดอ่อน ทำให้ข้อมูลถูกดักจับอ่านได้ง่ายระหว่างทาง
- ปิดการตรวจสอบใบรับรอง SSL (`verify=False`) เพื่อ "แก้ปัญหาเร็วๆ" โดยไม่เข้าใจความเสี่ยง ทำให้เปิดช่องโหว่ด้านความปลอดภัยที่ร้ายแรง
- คิดว่า DNS Lookup เกิดขึ้นแค่ครั้งเดียวตลอดไป โดยไม่รู้ว่ามีการแคชและหมดอายุ (TTL) ทำให้เข้าใจผิดเมื่อเปลี่ยน DNS record แล้วบางเครื่องยังเห็น IP เก่าอยู่ชั่วขณะ
- สับสนระหว่าง TCP กับ UDP — ใช้ TCP สำหรับงานที่ต้องการความเร็วสูงสุดโดยไม่สนใจว่าข้อมูลจะสูญหายบ้าง (เช่น video streaming, การเล่นเกมออนไลน์) ทั้งที่ UDP เหมาะกว่าในกรณีนี้ เพราะ TCP มีค่าใช้จ่ายจากการรับประกันความถูกต้องที่ไม่จำเป็นเสมอไป

## คำถามสัมภาษณ์งาน (Interview Questions)

1. "เกิดอะไรขึ้นเมื่อพิมพ์ URL ในเบราว์เซอร์แล้วกด Enter" — อธิบายทุกขั้นตอนตั้งแต่ DNS ถึงการแสดงผลหน้าเว็บ
2. TCP ต่างจาก UDP อย่างไร แต่ละแบบเหมาะกับสถานการณ์ไหน
3. อธิบาย TCP 3-Way Handshake ว่าทำงานอย่างไรและทำไมต้องมี 3 ขั้นตอน (ไม่ใช่ 2 หรือ 4)
4. HTTPS ต่างจาก HTTP อย่างไร SSL/TLS เข้ามาเกี่ยวข้องตรงไหน
5. อธิบายว่าทำไมการปิดการตรวจสอบใบรับรอง SSL ถึงเป็นความเสี่ยงด้านความปลอดภัย

## แบบฝึกหัด (Practice Exercises)

1. เขียนโปรแกรมที่ใช้ `socket` เชื่อมต่อไปยังเว็บไซต์หนึ่งด้วย HTTP ธรรมดา (port 80) แล้วพิมพ์ HTTP response ที่ได้กลับมาแบบดิบๆ ออกมาดู สังเกตโครงสร้าง headers และ body
2. เขียนโปรแกรมที่ใช้ `requests` เรียก REST API สาธารณะ (เช่น GitHub API) ด้วยทั้ง `GET` และตรวจสอบ Status Code, Headers, และ Body ของ response
3. ใช้ `socket.gethostbyname()` เปรียบเทียบเวลาที่ใช้ระหว่างการเรียกครั้งแรก (ยังไม่มีแคช) กับครั้งถัดไป (มีแคชแล้ว) ของโดเมนเดียวกัน

## Mini Project

**"เครื่องมือวิเคราะห์การเชื่อมต่อเว็บไซต์ (Website Connection Analyzer)"**: เขียนโปรแกรมที่:
1. รับ URL จากผู้ใช้ แล้วแสดงผลแต่ละขั้นตอน: เวลาที่ใช้ในการทำ DNS Lookup, TCP Handshake, TLS Handshake (ถ้าเป็น HTTPS), และเวลารวมจนได้ response กลับมา
2. ตรวจสอบและแสดงข้อมูลใบรับรอง SSL ของเว็บไซต์ (วันหมดอายุ, ผู้ออกใบรับรอง) ถ้าเป็น HTTPS
3. เปรียบเทียบเวลารวมระหว่างการเรียก URL เดียวกันด้วย HTTP กับ HTTPS (ถ้าเว็บไซต์รองรับทั้งคู่) เพื่อดูว่า TLS Handshake เพิ่มเวลาแฝงเท่าไหร่
4. สร้างรายงานสรุปสถานะสุขภาพของการเชื่อมต่อ (เร็ว/ปกติ/ช้า) พร้อมคำแนะนำถ้าตรวจพบปัญหา (เช่น ใบรับรองใกล้หมดอายุ)

## ข้อคิดสำคัญ (Key Takeaways)

- TCP/IP เป็นรากฐานของอินเทอร์เน็ต โดย IP หาเส้นทางส่งข้อมูล และ TCP รับประกันว่าข้อมูลถึงครบถ้วนและเรียงลำดับถูกต้อง
- DNS แปลงชื่อโดเมนที่มนุษย์จำง่ายให้เป็น IP Address ที่คอมพิวเตอร์ใช้สื่อสารกันจริง พร้อมกลไกแคชเพื่อลดเวลาการค้นหาซ้ำ
- HTTP กำหนดรูปแบบการขอ-ตอบข้อมูลมาตรฐานระหว่าง client และ server ผ่าน Method (GET/POST/PUT/DELETE) และ Status Code
- HTTPS คือ HTTP ที่เข้ารหัสด้วย SSL/TLS ป้องกันข้อมูลจากการถูกดักจับหรือปลอมแปลงระหว่างทาง ควรใช้เสมอสำหรับข้อมูลที่ละเอียดอ่อน
- คำถาม "เกิดอะไรขึ้นเมื่อพิมพ์ URL แล้วกด Enter" ครอบคลุมทุกหัวข้อในบทนี้เรียงต่อกันเป็นลำดับ: DNS -> TCP Handshake -> TLS Handshake -> HTTP Request/Response
- บทถัดไปจะเรียน REST, GraphQL, WebSocket, gRPC ซึ่งเป็นสถาปัตยกรรม/โปรโตคอลระดับสูงที่สร้างบน HTTP (และบางส่วนบน TCP โดยตรง) เพื่อออกแบบ API ให้เหมาะกับสถานการณ์ต่างๆ ปิดท้าย Part 10: Networking
