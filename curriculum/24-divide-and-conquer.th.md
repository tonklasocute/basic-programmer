# บทที่ 24: Divide and Conquer

## แนวคิดหลัก (Concept)

ตลอดหลายบทที่ผ่านมา เราเห็นรูปแบบเดิมซ้ำแล้วซ้ำเล่าโดยไม่ได้ตั้งชื่อมันอย่างเป็นทางการ: Merge Sort (บทที่ 21) แบ่งอาร์เรย์ครึ่งหนึ่งไปเรื่อยๆ, Binary Search (บทที่ 22) ตัดข้อมูลทิ้งครึ่งหนึ่งทุกรอบ — ทั้งสองคือตัวอย่างของเทคนิคเดียวกันที่เรียกว่า **Divide and Conquer** บทนี้จะดึงหลักการร่วมออกมาให้เห็นชัดเจน พร้อมเครื่องมือวิเคราะห์ time complexity ของมันอย่างเป็นระบบ (Master Theorem) และตัวอย่างใหม่ๆ ที่ยังไม่เคยเห็น

- **Divide and Conquer (แบ่งแยกและเอาชนะ)** — เทคนิคแก้ปัญหาด้วย 3 ขั้นตอนเสมอ: **Divide** (แบ่งปัญหาใหญ่เป็นปัญหาย่อยที่เล็กลงและมีลักษณะเดียวกัน) → **Conquer** (แก้ปัญหาย่อยแต่ละอันแบบ recursive จนถึง base case) → **Combine** (รวมคำตอบของปัญหาย่อยเข้าด้วยกันเป็นคำตอบของปัญหาใหญ่)
- **Recurrence Relation (สมการเวียนเกิด)** — สมการที่อธิบาย time complexity ของอัลกอริทึม D&C ในรูป T(n) = (จำนวนปัญหาย่อย) × T(ขนาดปัญหาย่อย) + (ต้นทุนของขั้นตอน Divide/Combine) เช่น Merge Sort คือ T(n) = 2T(n/2) + O(n)
- **Master Theorem** — สูตรสำเร็จรูปสำหรับแปลง Recurrence Relation ให้เป็น Big O โดยไม่ต้องวาด recursion tree เองทุกครั้ง

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **มีไว้เปลี่ยนปัญหาที่ดูซับซ้อนเกินจะแก้ตรงๆ ให้กลายเป็นปัญหาเล็กๆ ที่แก้ได้ง่าย**: ปัญหาหลายอย่าง (เรียงข้อมูลล้านตัว, คูณเลขตัวเลขยาวมาก, หาคู่จุดที่ใกล้กันที่สุดในระนาบ 2 มิติ) ยากเกินกว่าจะมองเห็นวิธีแก้ตรงๆ ทันที แต่ถ้าลองแบ่งครึ่งแล้วสมมติว่า "ถ้าแก้ครึ่งเล็กได้ ก็เอามารวมกันได้" มักจะเจอวิธีแก้ที่ทั้งถูกต้องและเร็วกว่าวิธี brute force มาก
- **การแบ่งครึ่งซ้ำๆ มักให้ผลลัพธ์ O(log n) เทอมหนึ่งเสมอ** ซึ่งเร็วกว่าการไล่ทีละตัว O(n) อย่างมีนัยสำคัญ — เหตุผลเชิงคณิตศาสตร์เดียวกับที่ทำให้ Binary Search เร็วกว่า Linear Search (บทที่ 20-22) นำมาขยายผลกับปัญหาประเภทอื่นได้อีกมาก
- **Master Theorem มีไว้ประหยัดเวลาวิเคราะห์**: แทนที่จะต้องวาด recursion tree และคำนวณผลรวมทุกชั้นด้วยมือทุกครั้งที่เจออัลกอริทึมใหม่ (เหมือนที่อธิบาย Merge Sort ในบทที่ 21) มีสูตรสำเร็จที่ใช้ได้กับ Recurrence Relation รูปแบบทั่วไปเกือบทั้งหมด

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Divide and Conquer** เหมือน **การนับคนในสนามกีฬาขนาดใหญ่โดยแบ่งงานให้ทีมงาน** — หัวหน้าแบ่งสนามเป็นโซนย่อยๆ ให้แต่ละคนนับ (Divide) แต่ละคนนับโซนของตัวเอง (Conquer) แล้วเอาตัวเลขจากทุกโซนมาบวกกัน (Combine) — เร็วกว่าคนคนเดียวนับทั้งสนามมหาศาล
- **Recurrence Relation** เหมือน **การคำนวณ "เวลารวมทั้งทัวร์นาเมนต์" ของการแข่งขันแบบแพ้คัดออก (knockout tournament)** — เวลารวมของรอบหนึ่งเท่ากับเวลาของสองสายที่แข่งขนาน (ซึ่งแต่ละสายก็แบ่งย่อยไปอีก) บวกเวลาที่ใช้ตัดสินผู้ชนะรอบนั้น
- **Master Theorem** เหมือน **ตารางสำเร็จรูปคำนวณดอกเบี้ยทบต้น** — แทนที่จะคำนวณทบต้นทีละปีด้วยมือ มีสูตรสำเร็จที่ใส่ตัวแปร (อัตราดอกเบี้ย, จำนวนปี) แล้วได้คำตอบทันทีโดยไม่ต้องไล่คำนวณทีละขั้น

## แผนภาพอธิบาย (Visual explanation)

### สามขั้นตอนของ Divide and Conquer (ใช้ Merge Sort เป็นตัวอย่าง — ทบทวนจากบทที่ 21)

```
Divide:    [5, 2, 8, 1, 9, 3]  ->  [5, 2, 8]  และ  [1, 9, 3]     (แบ่งครึ่ง)
                                        |                |
Conquer:                          แก้แบบ recursive  แก้แบบ recursive
                                    จนเหลือ 1 ตัว      จนเหลือ 1 ตัว
                                   (base case)         (base case)
                                        ↓                ↓
                                    [2, 5, 8]          [1, 3, 9]
                                        |                |
Combine:                            merge สองส่วนที่เรียงแล้วเข้าด้วยกัน
                                                ↓
                                        [1, 2, 3, 5, 8, 9]
```

### Recursion Tree ของ Merge Sort — ที่มาของ O(n log n)

```
ระดับ 0:              [n]                          ต้นทุน merge = O(n)
                      /   \
ระดับ 1:          [n/2]   [n/2]                     ต้นทุนรวม = O(n/2)+O(n/2) = O(n)
                  /   \     /   \
ระดับ 2:      [n/4] [n/4][n/4] [n/4]                ต้นทุนรวม = O(n)
                 ...  (แบ่งไปเรื่อยๆ)  ...
ระดับ log n:  [1][1][1][1]...[1]                    base case ทั้งหมด n ตัว

จำนวนระดับ = log n (แบ่งครึ่งไปเรื่อยๆ จนเหลือ 1 — หลักการเดียวกับ Binary Search บทที่ 22)
แต่ละระดับต้นทุนรวม = O(n) เท่ากันทุกระดับ (เพราะข้อมูลรวมกันแล้วเท่ากับ n เสมอ)

รวมทั้งหมด = O(n) ต่อระดับ × log n ระดับ = O(n log n)
```

### Master Theorem — สูตรสำเร็จสำหรับ T(n) = aT(n/b) + O(n^d)

```
T(n) = a T(n/b) + O(n^d)

โดย a = จำนวนปัญหาย่อยที่แบ่ง, b = ขนาดปัญหาย่อยลดลงกี่เท่า, n^d = ต้นทุนของ Divide+Combine

เปรียบเทียบ a กับ b^d:

  ถ้า a < b^d   ->  T(n) = O(n^d)              (ต้นทุน combine ครอบงำ)
  ถ้า a = b^d   ->  T(n) = O(n^d log n)         (สมดุลกันทุกระดับ)
  ถ้า a > b^d   ->  T(n) = O(n^(log_b a))       (จำนวนปัญหาย่อยครอบงำ)

ตัวอย่าง Merge Sort:  T(n) = 2T(n/2) + O(n)
  a=2, b=2, d=1  ->  b^d = 2^1 = 2  ->  a = b^d (เท่ากัน)  ->  T(n) = O(n^1 log n) = O(n log n) ✓ ตรงกับที่วิเคราะห์ด้วยมือ

ตัวอย่าง Binary Search:  T(n) = 1T(n/2) + O(1)
  a=1, b=2, d=0  ->  b^d = 2^0 = 1  ->  a = b^d (เท่ากัน)  ->  T(n) = O(n^0 log n) = O(log n) ✓ ตรงกับบทที่ 22
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== Quick Sort — D&C แบบ in-place ต่างจาก Merge Sort (ไม่ต้องสร้างอาร์เรย์ใหม่ทุก merge) =====
def quick_sort(arr, low=0, high=None):
    if high is None:
        high = len(arr) - 1
    if low < high:                                    # Base Case โดยนัย: low >= high (0 หรือ 1 ตัว)
        pivot_index = partition(arr, low, high)         # Divide: เลือก pivot แล้วจัดข้อมูลรอบๆ มัน
        quick_sort(arr, low, pivot_index - 1)             # Conquer: แก้ฝั่งซ้าย
        quick_sort(arr, pivot_index + 1, high)             # Conquer: แก้ฝั่งขวา
        # ไม่มีขั้นตอน Combine แยกต่างหาก! เพราะ partition() จัดตำแหน่งให้ถูกไปพร้อมกันแล้ว
    return arr

def partition(arr, low, high):
    pivot = arr[high]                                   # เลือกตัวสุดท้ายเป็น pivot
    i = low - 1
    for j in range(low, high):
        if arr[j] <= pivot:
            i += 1
            arr[i], arr[j] = arr[j], arr[i]
    arr[i + 1], arr[high] = arr[high], arr[i + 1]         # ย้าย pivot มาอยู่ตำแหน่งที่ถูกต้อง
    return i + 1                                          # ตำแหน่งสุดท้ายของ pivot (ทุกตัวซ้ายเล็กกว่า ทุกตัวขวาใหญ่กว่า)

# ===== Maximum Subarray — หาผลรวมต่อเนื่องที่มากที่สุดด้วย D&C =====
def max_subarray(arr, low=0, high=None):
    if high is None:
        high = len(arr) - 1
    if low == high:                                       # Base Case: เหลือตัวเดียว คำตอบคือตัวมันเอง
        return arr[low]
    mid = (low + high) // 2                                # Divide
    left_max = max_subarray(arr, low, mid)                   # Conquer ฝั่งซ้าย
    right_max = max_subarray(arr, mid + 1, high)              # Conquer ฝั่งขวา
    cross_max = max_crossing_sum(arr, low, mid, high)          # Combine: กรณีคำตอบคาบเกี่ยวจุดกึ่งกลาง
    return max(left_max, right_max, cross_max)                 # เลือกคำตอบที่ดีที่สุดจาก 3 กรณี

def max_crossing_sum(arr, low, mid, high):
    left_sum = float("-inf")
    total = 0
    for i in range(mid, low - 1, -1):                        # ไล่จากกลางไปซ้าย หาผลรวมที่มากสุดที่ติดกับ mid
        total += arr[i]
        left_sum = max(left_sum, total)
    right_sum = float("-inf")
    total = 0
    for i in range(mid + 1, high + 1):                         # ไล่จากกลาง+1 ไปขวา หาผลรวมที่มากสุดที่ติดกับ mid
        total += arr[i]
        right_sum = max(right_sum, total)
    return left_sum + right_sum                                 # รวมสองฝั่งที่ "ชนกันตรงกลางพอดี"

print(quick_sort([5, 2, 8, 1, 9, 3]))              # [1, 2, 3, 5, 8, 9]
print(max_subarray([-2, 1, -3, 4, -1, 2, 1, -5, 4]))  # 6  (มาจากช่วง [4, -1, 2, 1])
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `partition(arr, low, high)` — เลือก `pivot` (ตัวสุดท้ายในช่วง) แล้วไล่ตรวจทุกตัวในช่วง `[low, high-1]`: ถ้าตัวไหนน้อยกว่าหรือเท่ากับ pivot ให้ขยับมันมาอยู่ฝั่งซ้ายของช่วง (ใช้ pointer `i` ตามตำแหน่ง "ขอบเขตของฝั่งเล็ก") สุดท้ายสลับ pivot มาอยู่ตรงกลางพอดี — หลังจบฟังก์ชันนี้ pivot จะอยู่ **ตำแหน่งสุดท้ายที่ถูกต้อง** เสมอ (ทุกตัวซ้ายเล็กกว่า/เท่ากับ ทุกตัวขวามากกว่า) นี่คือขั้นตอน Divide ที่ทำหน้าที่ "จัดระเบียบบางส่วน" ไปพร้อมกันเลย ต่างจาก Merge Sort ที่ Divide เป็นแค่การแบ่งครึ่งเฉยๆ โดยไม่จัดอะไร
2. `quick_sort` ไม่มีขั้นตอน **Combine** แยกต่างหากเหมือน Merge Sort — เพราะ `partition()` จัดตำแหน่งของทุกตัวให้ถูกที่ไปพร้อมกับการแบ่งแล้ว เมื่อทั้งสองฝั่งถูกเรียงเสร็จแบบ recursive อาร์เรย์ทั้งหมดก็เรียงสมบูรณ์โดยอัตโนมัติไม่ต้องทำอะไรเพิ่ม — นี่คือความต่างสำคัญระหว่าง Merge Sort (Divide ง่าย, Combine หนัก) กับ Quick Sort (Divide หนัก, Combine ง่ายจนแทบไม่มี)
3. `max_subarray` — คำตอบของปัญหา "ผลรวมต่อเนื่องมากสุด" มีแค่ 3 ความเป็นไปได้เท่านั้นเสมอ: (ก) คำตอบอยู่ในครึ่งซ้ายทั้งหมด (ข) อยู่ในครึ่งขวาทั้งหมด (ค) **คาบเกี่ยวจุดกึ่งกลาง** (บางส่วนอยู่ซ้าย บางส่วนอยู่ขวา) — สองกรณีแรกแก้ด้วย recursion ตรงๆ แต่กรณีที่สามต้องมีฟังก์ชันพิเศษ `max_crossing_sum` มาจัดการ (นี่คือขั้นตอน Combine ที่ "หนัก" กว่า Merge Sort ธรรมดา เพราะต้องคำนวณเพิ่มไม่ใช่แค่รวมสองผลลัพธ์ตรงๆ)
4. `max_crossing_sum` — ไล่จาก `mid` ถอยไปทางซ้ายสะสมผลรวม เก็บค่ามากสุดที่เจอ (`left_sum`) แล้วไล่จาก `mid+1` ไปทางขวาสะสมผลรวม เก็บค่ามากสุด (`right_sum`) จากนั้น**บวกทั้งสองเข้าด้วยกันเสมอ** (ไม่ใช่ `max()`) เพราะช่วงที่คาบเกี่ยว mid ต้องต่อเนื่องกันจริงๆ ผ่านจุด mid พอดี

## Time Complexity

| Algorithm | Recurrence Relation | Time Complexity |
|---|---|---|
| Merge Sort (บทที่ 21) | T(n) = 2T(n/2) + O(n) | O(n log n) เสมอ |
| Binary Search (บทที่ 22) | T(n) = T(n/2) + O(1) | O(log n) เสมอ |
| Quick Sort (average case) | T(n) = 2T(n/2) + O(n) | O(n log n) |
| Quick Sort (worst case — pivot แย่ที่สุดทุกครั้ง) | T(n) = T(n-1) + O(n) | **O(n²)** |
| Maximum Subarray | T(n) = 2T(n/2) + O(n) | O(n log n) |

**ทำไม Quick Sort worst case เป็น O(n²)?** — ถ้าเลือก pivot แย่ที่สุดทุกครั้ง (เช่น ข้อมูลเรียงอยู่แล้วและเลือก pivot เป็นตัวสุดท้ายเสมอ) การ `partition` จะแบ่งได้ไม่สมดุลเลย (ฝั่งหนึ่งมี n-1 ตัว อีกฝั่งมี 0 ตัว) ทำให้กลายเป็น recursion ความลึก n แทนที่จะเป็น log n — สะท้อนว่า **การแบ่งที่ไม่สมดุลทำลายข้อได้เปรียบของ Divide and Conquer ไปเลย**

## Space Complexity

- Merge Sort: **O(n)** — ต้องสร้างอาร์เรย์ใหม่ตอน merge (ทบทวนจากบทที่ 21)
- Quick Sort: **O(log n)** โดยเฉลี่ย — ใช้แค่ Call Stack (บทที่ 9) เพราะ partition ทำงาน in-place ไม่สร้างอาร์เรย์ใหม่ แต่ worst case เป็น **O(n)** ถ้า recursion ลึกเท่า n (pivot แย่ที่สุดทุกครั้งเหมือนใน Time Complexity)
- Maximum Subarray: **O(log n)** — ใช้ Call Stack ตามความลึกของการแบ่งครึ่ง

## แนวทางปฏิบัติที่ดี (Best Practices)

- เมื่อเจอปัญหาใหม่ ลองถามตัวเองเสมอว่า **"ถ้าแบ่งปัญหานี้เป็นสองส่วนเล็กลง แล้วรู้คำตอบของแต่ละส่วนแล้ว จะรวมเป็นคำตอบของปัญหาใหญ่ได้อย่างไร"** — คำถามนี้คือหัวใจของการมองหาวิธีแก้แบบ D&C (ตัวอย่าง `max_subarray` แสดงให้เห็นว่าบางครั้ง "การรวม" ต้องคิดเพิ่มเรื่องกรณีคาบเกี่ยวเสมอ)
- ใช้ Master Theorem เป็นเครื่องมือตรวจสอบคำตอบเร็วๆ แต่ควรเข้าใจ recursion tree เบื้องหลังด้วย (ไม่ใช่แค่ท่องสูตร) เพราะ Master Theorem ใช้ไม่ได้กับ Recurrence Relation ทุกรูปแบบ (เช่น กรณีที่ปัญหาย่อยมีขนาดไม่เท่ากัน)
- เลือก Quick Sort เมื่อหน่วยความจำจำกัด (average case O(log n) ดีกว่า Merge Sort's O(n)) แต่เลือก Merge Sort เมื่อต้องการรับประกัน worst case ที่แน่นอน (O(n log n) เสมอ ไม่มีทางแย่ลงกว่านี้)

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ลืมกำหนด **Base Case** ที่ถูกต้อง ทำให้ recursion ไม่มีวันจบ (ย้ำจากบทที่ 9 — สำคัญมากใน D&C เพราะทุกอัลกอริทึม D&C คือ recursion ที่แบ่งปัญหาไปเรื่อยๆ)
- คิดว่าทุกอัลกอริทึมที่ใช้ recursion เป็น Divide and Conquer — ที่จริงต้องมีทั้ง 3 ขั้นตอน (Divide, Conquer, Combine) และปัญหาย่อยต้อง**เป็นอิสระจากกัน** (ถ้าปัญหาย่อยซ้ำซ้อนกัน เช่น Fibonacci คำนวณ fib(n-2) ซ้ำหลายครั้ง จะกลายเป็น Dynamic Programming แทน — จะเรียนบทถัดไป)
- เลือก pivot ใน Quick Sort แบบไม่สุ่มเสมอ (เช่น เลือกตัวแรกหรือตัวสุดท้ายทุกครั้ง) ทำให้ข้อมูลที่เรียงอยู่แล้วหรือเรียงย้อนกลับกลายเป็น worst case O(n²) โดยไม่จำเป็น — ในทางปฏิบัติควรสุ่มเลือก pivot หรือใช้ median-of-three
- ใน `max_crossing_sum` ใช้ `max()` แทนการ `+` สองผลรวมเข้าด้วยกัน ทำให้ได้คำตอบผิดเพราะช่วงที่คาบเกี่ยวต้องต่อเนื่องผ่าน mid จริงๆ ไม่ใช่เลือกฝั่งที่ดีกว่าฝั่งเดียว

## คำถามสัมภาษณ์งาน (Interview Questions)

1. อธิบายสามขั้นตอนของ Divide and Conquer พร้อมยกตัวอย่างอัลกอริทึมที่ใช้แต่ละขั้นตอนอย่างชัดเจน
2. ทำไม Quick Sort ถึงไม่มีขั้นตอน Combine ที่ชัดเจนเหมือน Merge Sort?
3. ใช้ Master Theorem วิเคราะห์ Recurrence Relation T(n) = 4T(n/2) + O(n) ว่าได้ Time Complexity เท่าไหร่ (ใบ้: เทียบ a=4 กับ b^d = 2^1 = 2)
4. ทำไม Quick Sort worst case ถึงเป็น O(n²) ทั้งที่โดยทั่วไปถือว่าเป็นอัลกอริทึม D&C ที่เร็ว? จะป้องกันได้อย่างไร?
5. Divide and Conquer ต่างจาก Dynamic Programming (ที่จะเรียนบทถัดไป) อย่างไร? (ใบ้: คิดเรื่องว่าปัญหาย่อยซ้ำซ้อนกันหรือไม่)

## แบบฝึกหัด (Practice Exercises)

1. เขียนฟังก์ชัน D&C หา**ค่ามากสุดและน้อยสุด**ในอาร์เรย์พร้อมกันในการ traverse เดียว โดยใช้หลักการแบ่งครึ่งแล้วรวมผล (เทียบ time complexity กับการหาแยกกัน 2 รอบด้วย loop ธรรมดา)
2. ใช้ Master Theorem วิเคราะห์ Recurrence Relation ต่อไปนี้ด้วยมือ: T(n) = 3T(n/3) + O(n), T(n) = T(n/2) + O(n), T(n) = 8T(n/2) + O(n²)
3. ปรับ `quick_sort` ให้เลือก pivot แบบสุ่ม (random pivot) แทนการเลือกตัวสุดท้ายเสมอ แล้วทดสอบว่าการันตี worst case เกิดขึ้นยากขึ้นจริงหรือไม่เมื่อใช้กับข้อมูลที่เรียงอยู่แล้ว

## Mini Project

**"เครื่องมือวิเคราะห์ Divide and Conquer (D&C Visualizer & Analyzer)"**: เขียนโปรแกรมที่:
1. Implement Quick Sort และ Maximum Subarray (จากตัวอย่างในบทนี้) พร้อมนับจำนวนครั้งที่ฟังก์ชัน recursive ถูกเรียก (recursion call count) ในแต่ละการทำงาน
2. แสดงผล recursion tree เป็นข้อความ (เช่น เยื้อง indent ตามความลึกของการเรียก) เพื่อให้เห็นภาพการ Divide จริงๆ ระหว่างทำงาน
3. เปรียบเทียบจำนวน recursion call จริงที่นับได้ กับค่าที่คำนวณได้จาก Master Theorem ว่าตรงกันหรือใกล้เคียงกันแค่ไหน
4. ทดสอบ Quick Sort ด้วย pivot 3 แบบ (ตัวแรก, ตัวสุดท้าย, สุ่ม) กับข้อมูล 3 แบบ (สุ่ม, เรียงแล้ว, เรียงย้อนกลับ) แสดงตารางเปรียบเทียบจำนวน recursion call เพื่อพิสูจน์ผลกระทบของการเลือก pivot ต่อ worst case

## ข้อคิดสำคัญ (Key Takeaways)

- Divide and Conquer คือเทคนิคแก้ปัญหา 3 ขั้นตอน: Divide (แบ่ง) → Conquer (แก้แบบ recursive) → Combine (รวมคำตอบ) ที่เห็นแล้วใน Merge Sort และ Binary Search ตั้งแต่บทก่อนๆ
- Recurrence Relation (เช่น T(n) = 2T(n/2) + O(n)) อธิบาย time complexity ของอัลกอริทึม D&C และ Master Theorem ช่วยแปลงมันเป็น Big O ได้เร็วโดยไม่ต้องวาด recursion tree ทุกครั้ง
- Quick Sort ต่างจาก Merge Sort ตรงที่ทำงานหนักตอน Divide (partition) แทนที่จะหนักตอน Combine ทำให้ประหยัดพื้นที่กว่า (O(log n) เทียบกับ O(n)) แต่เสี่ยง worst case O(n²) ถ้าเลือก pivot ไม่ดี
- ไม่ใช่ทุก recursion จะเป็น D&C — ต้องมีปัญหาย่อยที่**เป็นอิสระจากกัน** ถ้าปัญหาย่อยซ้ำซ้อนกัน (overlapping subproblems) จะกลายเป็นโจทย์ของ Dynamic Programming แทน ซึ่งเป็นบทถัดไป
- คำถาม "แบ่งครึ่งแล้วรวมผลได้อย่างไร" คือกรอบความคิดสำคัญที่ใช้ได้กับปัญหาใหม่ๆ อีกมากมายนอกเหนือจากตัวอย่างในบทนี้
