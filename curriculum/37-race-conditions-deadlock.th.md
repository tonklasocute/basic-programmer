# บทที่ 37: Race Conditions, Deadlock

## แนวคิดหลัก (Concept)

บทที่แล้วแนะนำ Race Condition และวิธีแก้ด้วย Mutex/Semaphore แบบเบื้องต้น แต่ก็ทิ้งคำเตือนไว้ว่า "ถ้าออกแบบลำดับการล็อกไม่ถูกต้อง" จะเกิดปัญหาใหม่ตามมา บทนี้เจาะลึกทั้งสองปัญหาให้ครบถ้วน: **Race Condition** ในรูปแบบที่ซับซ้อนกว่าตัวอย่างนับเลขธรรมดา และ **Deadlock** ซึ่งเป็นปัญหาใหม่ที่**เกิดขึ้นจากการพยายามแก้ Race Condition ด้วย Mutex อย่างไม่ระมัดระวัง**

- **Race Condition (ทบทวนและขยายความ)** — ไม่ได้จำกัดแค่ตัวแปรตัวเลข แต่เกิดกับโครงสร้างข้อมูลใดๆ ที่หลาย thread แก้ไขพร้อมกัน (list, dict, ไฟล์) รวมถึงรูปแบบที่ซับซ้อนกว่า เช่น **Check-Then-Act** (เช็คเงื่อนไขก่อนแล้วค่อยกระทำ โดยมี thread อื่นแทรกระหว่างสองขั้นตอนนี้ได้)
- **Deadlock (ภาวะติดตาย)** — สถานการณ์ที่ thread สองตัวขึ้นไป**รอกันเป็นวงกลม**ตลอดไป โดยแต่ละตัวถือกุญแจที่อีกตัวต้องการ และรอกุญแจที่อีกตัวถืออยู่ ทำให้ไม่มีใครทำงานต่อได้เลย
- **Four Conditions for Deadlock** — เงื่อนไข 4 ข้อที่ต้องเกิดขึ้นพร้อมกันทั้งหมดจึงจะเกิด Deadlock: Mutual Exclusion (ทรัพยากรใช้ได้ทีละตัว), Hold and Wait (ถือของอย่างหนึ่งไว้ขณะรออีกอย่าง), No Preemption (แย่งทรัพยากรจากคนอื่นไม่ได้), Circular Wait (รอกันเป็นวงกลม)
- **Deadlock Prevention (การป้องกัน Deadlock)** — เทคนิคออกแบบระบบให้ไม่มีทางเกิดเงื่อนไขทั้ง 4 ข้อพร้อมกัน เช่น การกำหนดลำดับการล็อกให้คงที่เสมอ

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Race Condition แบบ Check-Then-Act มีไว้อธิบายบั๊กที่ซับซ้อนกว่าการนับเลขธรรมดา**: บั๊กจริงในโปรเจกต์ขนาดใหญ่มักไม่ใช่แค่ `counter += 1` แต่เป็นรูปแบบอย่าง "เช็คว่ามีที่นั่งว่างไหม แล้วค่อยจอง" ซึ่งถ้า thread อื่นแทรกระหว่างการเช็คและการจอง จะเกิดการจองเกินจำนวนที่มีจริง (oversell) — ต้องเข้าใจรูปแบบนี้เพื่อระบุ Race Condition ในโค้ดจริงได้
- **Deadlock มีไว้เตือนว่า "การล็อกไม่ใช่คำตอบที่ปลอดภัยเสมอไป"**: บทที่แล้วสอนให้ใช้ Mutex แก้ Race Condition แต่ถ้าใช้ Mutex หลายตัวพร้อมกันโดยไม่ระวังลำดับ (เช่น การโอนเงินที่ต้องล็อกสองบัญชีพร้อมกัน ตามที่ Mini Project บทที่แล้วทิ้งคำใบ้ไว้) จะเกิดปัญหาใหม่ที่ร้ายแรงกว่าเดิม — โปรแกรมไม่ผิดพลาดแบบเงียบๆ เหมือน Race Condition แต่**ค้างสนิทตลอดไป**
- **Four Conditions มีไว้เป็นกรอบคิดสำหรับป้องกัน Deadlock อย่างเป็นระบบ**: แทนที่จะแก้ปัญหาแบบเดาสุ่ม การรู้ว่า Deadlock ต้องการทั้ง 4 เงื่อนไขพร้อมกันเสมอ ทำให้แค่ทำลายเงื่อนไขข้อใดข้อหนึ่งก็เพียงพอที่จะป้องกัน Deadlock ได้ทั้งหมด

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Check-Then-Act Race Condition** เหมือน **สองคนเช็คบัญชีธนาคารพร้อมกันแล้วต่างคนต่างถอนเงินโดยไม่รู้ว่าอีกคนก็กำลังถอนอยู่** — ทั้งคู่เห็นยอดเงิน 1,000 บาทเหมือนกัน (เช็ค) แล้วทั้งคู่ถอน 800 บาทพร้อมกัน (กระทำ) โดยไม่รู้ว่าเงินจะไม่พอสำหรับทั้งสองคน
- **Deadlock** เหมือน **สองคนเดินสวนกันในทางเดินแคบที่กว้างพอสำหรับคนเดียว** — คนหนึ่งขยับไปทางซ้ายเพื่อหลีก อีกคนก็ขยับไปทางเดียวกันพอดี (คิดว่าหลีกให้) ทั้งคู่ขยับสลับข้างไปมาตลอดโดยไม่มีใครผ่านไปได้สักที (ในกรณีเลวร้ายที่สุด ทั้งคู่หยุดนิ่งรอกันตลอดไป)
- **Four Conditions** เหมือน **สูตรผสมเคมีที่ต้องมีสารครบ 4 อย่างพร้อมกันเท่านั้นถึงจะระเบิด** — ถ้าเอาสารตัวใดตัวหนึ่งออกไป การระเบิด (Deadlock) จะไม่มีวันเกิดขึ้นเลย ไม่ว่าสารอีก 3 ตัวจะครบแค่ไหนก็ตาม

## แผนภาพอธิบาย (Visual explanation)

### Check-Then-Act Race Condition — จองตั๋วคอนเสิร์ตเกินจำนวนที่มี

```
available_seats = 1     (เหลือที่นั่งสุดท้าย 1 ที่)

Thread A (ลูกค้า 1)                    Thread B (ลูกค้า 2)

1. เช็ค: available_seats > 0? -> True (เห็น 1 ที่)
                                        1. เช็ค: available_seats > 0? -> True (เห็น 1 ที่ เหมือนกัน! แทรกก่อน A จองเสร็จ)
2. จอง! available_seats -= 1  -> 0
                                        2. จอง! available_seats -= 1  -> -1   (ติดลบ! จองเกินจำนวนจริง)

ผลลัพธ์: ขายตั๋วไป 2 ใบ ทั้งที่มีที่นั่งจริงแค่ 1 ที่ (oversell)
สาเหตุ: ช่วงเวลาระหว่าง "เช็ค" กับ "กระทำ" thread อื่นแทรกเข้ามาได้เสมอถ้าไม่มี Mutex ครอบคลุมทั้งสองขั้นตอน
```

### Deadlock — สอง Thread ล็อกกุญแจคนละดอก แล้วรอกุญแจของกันและกัน

```
Thread A ต้องการโอนเงิน: account1 -> account2       Thread B ต้องการโอนเงิน: account2 -> account1

1. lock(account1)   <- A ได้กุญแจ account1 แล้ว        1. lock(account2)   <- B ได้กุญแจ account2 แล้ว
                          (เกิดพร้อมกันโดยบังเอิญ)
2. lock(account2)   <- รอ! เพราะ B ถือกุญแจ account2   2. lock(account1)   <- รอ! เพราะ A ถือกุญแจ account1
   (A ค้างตรงนี้ตลอดไป)                                    (B ค้างตรงนี้ตลอดไป)

ผลลัพธ์: A รอ B ปล่อยกุญแจ account2, B รอ A ปล่อยกุญแจ account1
         ทั้งคู่รอกันเป็นวงกลม (Circular Wait) -> DEADLOCK ค้างตลอดไป ไม่มีใครทำงานต่อได้
```

### Four Conditions for Deadlock — ต้องเกิดครบทั้ง 4 ข้อพร้อมกัน

```
1. Mutual Exclusion:  account1/account2 ใช้ได้ทีละ thread เท่านั้น (Mutex ปกติ)
2. Hold and Wait:     A ถือ account1 (hold) ขณะรอ account2 (wait) โดยไม่ปล่อย account1 ก่อน
3. No Preemption:     ไม่มีใครมาแย่งกุญแจจาก A หรือ B ได้ ต้องรอเจ้าของปล่อยเองเท่านั้น
4. Circular Wait:     A รอ B, B รอ A -> วงจรปิด

ทำลายข้อใดข้อหนึ่ง -> Deadlock ไม่เกิดขึ้นเลย!
เช่น แก้ Circular Wait ด้วยการบังคับล็อกตามลำดับคงที่เสมอ (ดูตัวอย่างโค้ดด้านล่าง)
```

## ตัวอย่างโค้ด (Code example)

```python
import threading
import time

# ===== Check-Then-Act Race Condition: ระบบจองตั๋ว =====
available_seats = 1
seat_lock_missing = None                        # ยังไม่มี Mutex -> ไม่ปลอดภัย

def book_seat_unsafe(customer_id):
    global available_seats
    if available_seats > 0:                        # ขั้นตอน "เช็ค"
        time.sleep(0.01)                              # จำลอง delay ที่ทำให้ thread อื่นแทรกได้ง่ายขึ้น
        available_seats -= 1                          # ขั้นตอน "กระทำ" - แยกจากการเช็คโดยสิ้นเชิง!
        print(f"Customer {customer_id} booked a seat! Remaining: {available_seats}")
    else:
        print(f"Customer {customer_id} failed to book - no seats left")

# ===== แก้ด้วย Mutex ครอบคลุมทั้งขั้นตอน "เช็ค" และ "กระทำ" ในก้อนเดียว =====
available_seats_safe = 1
seat_lock = threading.Lock()

def book_seat_safe(customer_id):
    global available_seats_safe
    with seat_lock:                                 # ล็อกครอบทั้งการเช็คและการกระทำพร้อมกัน
        if available_seats_safe > 0:
            time.sleep(0.01)
            available_seats_safe -= 1
            print(f"Customer {customer_id} booked a seat! Remaining: {available_seats_safe}")
        else:
            print(f"Customer {customer_id} failed to book - no seats left")

# ===== Deadlock: ล็อกสองบัญชีตามลำดับที่ไม่สอดคล้องกัน =====
lock_a = threading.Lock()
lock_b = threading.Lock()

def transfer_deadlock_risk(from_lock, to_lock, name):
    with from_lock:
        print(f"{name}: acquired first lock")
        time.sleep(0.1)                              # เปิดโอกาสให้ thread อื่นแทรกจังหวะ (จำลองสถานการณ์จริง)
        with to_lock:                                   # ถ้า thread อื่นถือ to_lock อยู่และรอ from_lock -> DEADLOCK
            print(f"{name}: acquired second lock, transferring...")

# ===== แก้ Deadlock ด้วยการบังคับลำดับการล็อกให้คงที่เสมอ (ทำลาย Circular Wait) =====
def transfer_safe(lock1, lock2, name):
    first, second = (lock1, lock2) if id(lock1) < id(lock2) else (lock2, lock1)   # เรียงลำดับคงที่เสมอ
    with first:
        with second:
            print(f"{name}: transferred safely (no deadlock possible)")

# ทดสอบ: ทุก thread ล็อกตามลำดับเดียวกันเสมอ (ไม่ว่าจะโอนทิศทางไหน) -> ไม่มีทาง Circular Wait
t1 = threading.Thread(target=transfer_safe, args=(lock_a, lock_b, "Transfer A->B"))
t2 = threading.Thread(target=transfer_safe, args=(lock_b, lock_a, "Transfer B->A"))   # สลับพารามิเตอร์ แต่ผลลัพธ์ล็อกลำดับเดิม
t1.start(); t2.start()
t1.join(); t2.join()
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `book_seat_unsafe(customer_id)` — เงื่อนไข `if available_seats > 0` (เช็ค) และ `available_seats -= 1` (กระทำ) เป็น**คนละบรรทัด แยกจากกันโดยสิ้นเชิง** `time.sleep(0.01)` ที่แทรกไว้จงใจจำลองว่า thread อื่นมีโอกาสมาก "เช็ค" เห็นค่าเดิม (`available_seats > 0` ยังเป็น `True` อยู่) ก่อนที่ thread แรกจะ "กระทำ" (ลดค่า) เสร็จ ทำให้ทั้งสอง thread เชื่อว่าตัวเองจองได้ทั้งคู่
2. `with seat_lock:` ใน `book_seat_safe` — ครอบคลุม**ทั้งขั้นตอนเช็คและกระทำไว้ใน Critical Section เดียวกัน** ไม่ใช่ล็อกแค่บรรทัดที่แก้ไขค่าเหมือนที่อาจเข้าใจผิดได้ง่าย — ถ้าล็อกแค่ `available_seats_safe -= 1` แต่ไม่ล็อกการเช็ค `if available_seats_safe > 0` ปัญหาเดิมจะยังคงเกิดขึ้นอยู่ เพราะ Race Condition อยู่ที่**ช่วงเวลาระหว่างสองขั้นตอน** ไม่ใช่แค่ขั้นตอนใดขั้นตอนหนึ่ง
3. `transfer_deadlock_risk` — ถ้าเรียก `transfer_deadlock_risk(lock_a, lock_b, "A")` และ `transfer_deadlock_risk(lock_b, lock_a, "B")` พร้อมกันสองฝั่ง (คนละ thread) มีโอกาสที่ thread A จะได้ `lock_a` และ thread B จะได้ `lock_b` **ในเวลาไล่เลี่ยกันพอดี** จากนั้นทั้งคู่ต่างรอกุญแจของอีกฝั่ง (`lock_b` สำหรับ A, `lock_a` สำหรับ B) โดยไม่มีใครปล่อยกุญแจตัวเองก่อนเลย — เกิด Circular Wait และ Deadlock ตามแผนภาพด้านบน
4. `transfer_safe(lock1, lock2, name)` — ใช้ `id(lock1) < id(lock2)` (เปรียบเทียบ memory address ของ object ซึ่งคงที่ตลอดอายุโปรแกรม) เพื่อ**บังคับให้ล็อกตามลำดับเดียวกันเสมอไม่ว่าจะเรียกด้วยพารามิเตอร์แบบไหน** — ไม่ว่า thread ไหนจะพยายามโอนทิศทางใด ทุก thread จะต้องล็อก lock ตัวที่มี `id` น้อยกว่าก่อนเสมอ ทำให้**ไม่มีทางเกิด Circular Wait ได้เลย** เพราะไม่มี thread ไหนถือกุญแจ "ตัวหลัง" ไว้ก่อนแล้วรอ "ตัวแรก" ในสถานการณ์ใดๆ

## Time Complexity

Race Condition และ Deadlock เป็นปัญหาด้าน**ความถูกต้องของโปรแกรม (correctness)** ไม่ใช่ปัญหาด้านความเร็ว จึงไม่มี Time Complexity ในความหมายของ Big O โดยตรง — แต่มีผลกระทบทางอ้อมที่วัดได้:
- โค้ดที่มี Race Condition: ทำงานเร็ว (ไม่มีการรอคิว) แต่**ผลลัพธ์ผิดพลาด**
- โค้ดที่ป้องกัน Deadlock ด้วยการบังคับลำดับล็อก: มีต้นทุนเพิ่มขึ้นเล็กน้อยจากการเปรียบเทียบลำดับ (`id(lock1) < id(lock2)`) แต่เป็น **O(1)** ที่ไม่มีนัยสำคัญเมื่อเทียบกับความเสี่ยงที่หลีกเลี่ยงได้

## Space Complexity

- ไม่มีการใช้พื้นที่เพิ่มเติมอย่างมีนัยสำคัญจากการป้องกัน Race Condition หรือ Deadlock เอง (Mutex ใช้พื้นที่คงที่ O(1) ต่อตัวตามที่กล่าวในบทที่แล้ว)

## แนวทางปฏิบัติที่ดี (Best Practices)

- ล็อกให้ครอบคลุม**ทั้งขั้นตอนเช็คและขั้นตอนกระทำในก้อนเดียวกันเสมอ** เมื่อเจอรูปแบบ Check-Then-Act — อย่าล็อกแยกกันคนละจุด เพราะช่องว่างระหว่างสองการล็อกยังคงเป็นช่องโหว่ของ Race Condition
- เมื่อต้องล็อกทรัพยากรหลายตัวพร้อมกัน (มากกว่า 1 Mutex) **กำหนดลำดับการล็อกให้คงที่เสมอ**ในทุกที่ที่มีการล็อกทรัพยากรชุดเดียวกัน ไม่ว่าจะเรียกจากบริบทไหนก็ตาม (ตามตัวอย่าง `transfer_safe`) เพื่อทำลายเงื่อนไข Circular Wait ตั้งแต่การออกแบบ
- พิจารณาใช้ **timeout** เมื่อพยายาม `acquire()` กุญแจ (เช่น `lock.acquire(timeout=5)`) แทนการรอตลอดไปแบบไม่มีกำหนด เพื่อให้โปรแกรมตรวจจับและจัดการสถานการณ์ที่อาจเป็น Deadlock ได้ แทนที่จะค้างเงียบๆ ตลอดไป

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ล็อกแค่บรรทัดที่ "แก้ไข" ข้อมูล แต่ไม่ล็อกบรรทัดที่ "เช็คเงื่อนไข" ก่อนหน้า ทำให้ Race Condition แบบ Check-Then-Act ยังคงเกิดขึ้นได้ แม้จะคิดว่าใช้ Mutex แล้วก็ตาม
- ล็อกทรัพยากรหลายตัวโดยลำดับที่ต่างกันในแต่ละจุดของโค้ด (เช่น บางฟังก์ชันล็อก A ก่อน B แต่อีกฟังก์ชันล็อก B ก่อน A) ทำให้เสี่ยงเกิด Circular Wait และ Deadlock โดยไม่รู้ตัว
- คิดว่า Deadlock จะเกิดขึ้นแน่นอนทุกครั้งที่รันโปรแกรม ทำให้มองข้ามความเสี่ยง — ในความเป็นจริง Deadlock มักเกิดขึ้น**เป็นครั้งคราวเท่านั้น**เมื่อจังหวะเวลาของ thread สอดคล้องกันพอดี (เหมือน Race Condition) ทำให้ตรวจจับได้ยากในการทดสอบทั่วไป แต่เกิดขึ้นแน่นอนในระบบที่ใช้งานหนักเป็นเวลานาน
- ใช้ nested lock (ล็อกซ้อนล็อก) โดยไม่จำเป็น เพิ่มความเสี่ยง Deadlock โดยไม่ได้ประโยชน์เพิ่มเติมจากการออกแบบที่ง่ายกว่า

## คำถามสัมภาษณ์งาน (Interview Questions)

1. อธิบาย Check-Then-Act Race Condition คืออะไร ต่างจาก Race Condition แบบนับเลขธรรมดา (บทที่แล้ว) อย่างไร
2. อธิบาย Four Conditions for Deadlock ทั้ง 4 ข้อ พร้อมยกตัวอย่างการทำลายเงื่อนไขข้อใดข้อหนึ่งเพื่อป้องกัน Deadlock
3. ทำไมการบังคับลำดับการล็อกให้คงที่เสมอถึงป้องกัน Deadlock ได้? อธิบายด้วยหลักการ Circular Wait
4. Race Condition กับ Deadlock ต่างกันอย่างไรในแง่ของอาการที่สังเกตเห็น (ผลลัพธ์ผิดพลาด vs โปรแกรมค้าง)
5. ทำไม Deadlock ถึงเกิดขึ้น "เป็นครั้งคราว" ไม่ใช่ทุกครั้งที่รันโปรแกรม? สิ่งนี้ทำให้การทดสอบตรวจจับ Deadlock ยากขึ้นอย่างไร

3. แก้โปรแกรมในข้อ 2 ด้วยเทคนิคบังคับลำดับการล็อก (เหมือน `transfer_safe`) แล้วพิสูจน์ด้วยการรันซ้ำหลายรอบว่า Deadlock ไม่เกิดขึ้นอีกเลย

## Mini Project

**"ระบบโอนเงินระหว่างบัญชีที่ปลอดภัยจาก Race Condition และ Deadlock (Safe Multi-Account Transfer System)"**: เขียนโปรแกรมที่:
1. สร้างระบบบัญชีธนาคารหลายบัญชี (ต่อยอดจาก Mini Project บทที่แล้ว) ที่รองรับการโอนเงินระหว่างบัญชีคู่ใดๆ ก็ได้พร้อมกันจากหลาย thread
2. Implement ฟังก์ชันโอนเงินที่ป้องกันทั้ง Race Condition (ล็อกครอบคลุมการเช็คยอดและการหักเงินในก้อนเดียว) และ Deadlock (บังคับลำดับการล็อกให้คงที่ตาม `id()` ของ object เหมือนตัวอย่างในบทเรียน)
3. จำลองสถานการณ์ที่มีหลายคู่บัญชีโอนเงินไขว้กันพร้อมกัน (เช่น A โอนให้ B ขณะที่ B ก็โอนให้ A พร้อมกันพอดี) จำนวนมาก (เช่น 100 คู่ธุรกรรมพร้อมกัน) แล้วพิสูจน์ว่าโปรแกรมไม่ค้างเลยและยอดเงินรวมทั้งระบบถูกต้องเสมอ (ไม่มีเงินหายหรืองอกขึ้นมาเอง)
4. เปรียบเทียบเวอร์ชันที่ไม่ป้องกัน Deadlock (ล็อกตามลำดับการเรียกฟังก์ชันตรงๆ) กับเวอร์ชันที่ป้องกันแล้ว โดยรันด้วยจำนวน thread สูงๆ ซ้ำหลายรอบเพื่อแสดงให้เห็นว่าเวอร์ชันแรกมีโอกาสค้าง (ต้องตั้ง timeout เพื่อตรวจจับ) ในขณะที่เวอร์ชันหลังไม่ค้างเลย

## ข้อคิดสำคัญ (Key Takeaways)

- Race Condition ไม่ได้จำกัดแค่การนับเลข แต่รวมถึงรูปแบบ Check-Then-Act ที่ต้องล็อกทั้งขั้นตอนเช็คและกระทำไว้ในก้อนเดียวกันเสมอ ไม่ใช่ล็อกแค่บางส่วน
- Deadlock เกิดจากการใช้ Mutex หลายตัวพร้อมกันโดยลำดับการล็อกไม่สอดคล้องกัน ทำให้ thread รอกันเป็นวงกลม (Circular Wait) ตลอดไป
- Deadlock ต้องการ 4 เงื่อนไขครบพร้อมกัน (Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait) การทำลายเงื่อนไขข้อใดข้อหนึ่งก็เพียงพอที่จะป้องกันได้ทั้งหมด
- การบังคับลำดับการล็อกให้คงที่เสมอ (เช่น ใช้ `id()` เปรียบเทียบ) เป็นเทคนิคที่ใช้กันจริงในการป้องกัน Deadlock โดยทำลายเงื่อนไข Circular Wait
- ทั้ง Race Condition และ Deadlock มักเกิดขึ้น**เป็นครั้งคราวเท่านั้น** ขึ้นกับจังหวะเวลาที่แน่นอน ทำให้ตรวจจับได้ยากด้วยการทดสอบทั่วไป ต้องออกแบบป้องกันไว้ตั้งแต่ต้นแทนที่จะพึ่งการทดสอบเพียงอย่างเดียว
- บทถัดไปจะเรียน Goroutines, Channels, Context ซึ่งเป็นแนวทาง Concurrency อีกแบบ (ที่ใช้ในภาษา Go) ที่เน้นการสื่อสารผ่าน Channel แทนการแชร์หน่วยความจำและล็อกโดยตรง ปิดท้าย Part 8: Concurrency
