# บทที่ 34: Pure Functions, Immutability

## แนวคิดหลัก (Concept)

Part 6 สอนแนวคิด OOP ที่รวม**ข้อมูลกับพฤติกรรม**ไว้ด้วยกันใน object ที่**เปลี่ยนแปลงสถานะ (state) ได้ตลอดเวลา** (`self._balance -= amount` ในบทที่ 30) บทนี้เปิด **Part 7: Functional Programming (FP)** ซึ่งเป็นแนวคิดที่มองต่างมุมโดยสิ้นเชิง: แทนที่จะเปลี่ยนสถานะของข้อมูลเดิม FP เน้น**เขียนฟังก์ชันที่ไม่เปลี่ยนแปลงอะไรเลยนอกเหนือจากคืนค่าใหม่ออกมา** — แนวคิดนี้ไม่ได้มาแทน OOP แต่เป็นเครื่องมืออีกชิ้นที่ช่วยลดบั๊กประเภทหนึ่งที่ OOP แก้ได้ยาก

- **Pure Function (ฟังก์ชันบริสุทธิ์)** — ฟังก์ชันที่มีคุณสมบัติ 2 ข้อเสมอ: (1) **ผลลัพธ์เดียวกันทุกครั้งเมื่อ input เดียวกัน** (deterministic) และ (2) **ไม่มี Side Effect** (ไม่แก้ไขข้อมูลภายนอกตัวเอง เช่น global variable, ไฟล์, ฐานข้อมูล, หรือแม้แต่พารามิเตอร์ที่รับเข้ามา)
- **Side Effect (ผลข้างเคียง)** — การกระทำใดๆ ของฟังก์ชันที่ส่งผลกระทบต่อโลกภายนอกขอบเขตของมันเอง เช่น แก้ไขตัวแปร global, พิมพ์ข้อความ, เขียนไฟล์, หรือแก้ไข object/list ที่รับเข้ามาเป็นพารามิเตอร์
- **Immutability (ความไม่เปลี่ยนแปลง)** — หลักการที่ข้อมูลเมื่อถูกสร้างขึ้นแล้ว**ไม่ถูกแก้ไขอีกเลย** หากต้องการ "เปลี่ยนแปลง" ข้อมูล ต้อง**สร้างข้อมูลชุดใหม่**ขึ้นมาแทนที่จะแก้ของเดิม

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **มีไว้ทำให้โค้ดคาดเดาได้และเทสต์ง่ายขึ้นมาก**: Pure Function ไม่มีทางให้ผลลัพธ์ต่างกันเมื่อ input เดิม (ต่างจาก method ใน OOP ที่ผลลัพธ์อาจขึ้นกับ state ของ object ณ ขณะนั้น) ทำให้เขียน Unit Test (จะเรียนในบท Testing) ได้ตรงไปตรงมา แค่ป้อน input แล้วเช็ค output โดยไม่ต้องตั้งค่า state ที่ซับซ้อนก่อน
- **Immutability มีไว้แก้ปัญหา "ใครแก้ข้อมูลนี้กันแน่" ที่พบบ่อยมากในโปรแกรมขนาดใหญ่**: เมื่อข้อมูลแก้ไขได้จากหลายที่ (mutable) การตามหาว่า bug เกิดจากส่วนไหนแก้ข้อมูลผิดพลาดเป็นเรื่องยากมาก โดยเฉพาะในโปรแกรมที่มีหลาย thread ทำงานพร้อมกัน (เชื่อมโยงกับ Race Conditions ที่จะเรียนใน Part 8: Concurrency) — ถ้าข้อมูลแก้ไขไม่ได้เลย ปัญหานี้หายไปโดยธรรมชาติ
- **ทำให้ฟังก์ชันนำไปใช้ซ้ำและประกอบกัน (compose) ได้ง่าย**: เพราะ Pure Function ไม่ขึ้นกับ state ภายนอกใดๆ จึงย้ายไปใช้ที่ไหนก็ได้ผลลัพธ์เหมือนเดิมเสมอ ต่างจากฟังก์ชันที่มี Side Effect ซึ่งต้องระวังลำดับการเรียกและ state แวดล้อมทุกครั้งที่นำไปใช้ใหม่

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Pure Function** เหมือน **เครื่องคิดเลข** — กด `2 + 3` กี่ครั้งก็ได้ `5` เสมอ ไม่ว่าจะกดตอนไหน ไม่ว่าใครกด และการกดคำนวณครั้งนี้ไม่ทำให้เครื่องคิดเลขเครื่องอื่นหรือข้อมูลอื่นในห้องเปลี่ยนแปลงไปเลย
- **Side Effect** เหมือน **การเขียนตัวเลขลงสมุดบันทึกส่วนกลางทุกครั้งที่คำนวณ** — นอกจากได้คำตอบแล้ว ยังทิ้ง "ร่องรอย" ไว้ในสมุดที่คนอื่นเห็นได้ด้วย ทำให้ผลลัพธ์ของการคำนวณครั้งถัดไปอาจขึ้นกับสิ่งที่เขียนไว้ในสมุดจากครั้งก่อน
- **Immutability** เหมือน **เอกสารสัญญาที่เซ็นแล้วแก้ไขไม่ได้ ต้องทำฉบับใหม่แทน** — ถ้าต้องการเปลี่ยนเงื่อนไขในสัญญา ไม่ใช่การขีดฆ่าแล้วเขียนทับของเดิม แต่ต้องร่างสัญญาฉบับใหม่ทั้งหมด (ฉบับเดิมยังคงอยู่เป็นหลักฐานเดิมไม่เปลี่ยนแปลง)

## แผนภาพอธิบาย (Visual explanation)

### Pure Function vs Impure Function — ผลลัพธ์เดิมเสมอ vs ผลลัพธ์เปลี่ยนไปตาม state ภายนอก

```
Pure Function:                              Impure Function (มี Side Effect):

def add(a, b):                              total = 0                    <- global state ภายนอก
    return a + b                            def add_to_total(a):
                                                 global total
add(2, 3)  -> 5   (เรียกกี่ครั้งก็ได้ 5)             total += a               <- แก้ไข state ภายนอก!
add(2, 3)  -> 5   (เหมือนเดิมทุกครั้ง)               return total

ไม่แตะต้องอะไรนอกฟังก์ชันเลย                    add_to_total(5)  -> 5   (ครั้งแรก)
                                             add_to_total(5)  -> 10  (ครั้งที่สอง! ผลลัพธ์ต่างกัน
                                                                       ทั้งที่ input เหมือนเดิม)
```

### Mutable vs Immutable — แก้ของเดิม vs สร้างใหม่

```
Mutable (แก้ list เดิมตรงๆ):                 Immutable (สร้าง list ใหม่เสมอ):

original = [1, 2, 3]                        original = [1, 2, 3]
original.append(4)                          new_list = original + [4]

original -> [1, 2, 3, 4]                    original -> [1, 2, 3]        <- ไม่เปลี่ยนแปลงเลย!
(ข้อมูลเดิมถูกแก้ไขไปแล้ว                       new_list -> [1, 2, 3, 4]     <- ข้อมูลใหม่แยกต่างหาก
 ใครก็ตามที่ถือ reference เดิมอยู่
 จะเห็นการเปลี่ยนแปลงนี้ด้วยโดยไม่รู้ตัว!)          ใครก็ตามที่ถือ reference "original" อยู่
                                                จะยังเห็นค่าเดิม [1, 2, 3] เสมอ ปลอดภัยกว่า
```

### ปัญหาคลาสสิกของ Mutable Default Argument (กับดักที่พบบ่อยมากใน Python)

```
def add_item(item, cart=[]):        <- กับดัก! list ว่างถูกสร้างแค่ครั้งเดียวตอนนิยามฟังก์ชัน
    cart.append(item)                  ไม่ใช่ทุกครั้งที่เรียกฟังก์ชันเหมือนที่คนส่วนใหญ่คิด
    return cart

add_item("apple")   -> ["apple"]
add_item("banana")  -> ["apple", "banana"]     <- เอ๊ะ? ควรจะได้ ["banana"] เพียงอย่างเดียว!

สาเหตุ: cart=[] ถูกสร้างครั้งเดียวตอน def และถูกแชร์ (shared state) ระหว่างการเรียกทุกครั้ง
        เพราะ list เป็น mutable object ที่ append() แก้ไขของเดิมไปเรื่อยๆ
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== Pure Function vs Impure Function =====
def add_pure(a, b):                          # Pure: ไม่มี side effect, ผลลัพธ์ขึ้นกับ input เท่านั้น
    return a + b

total = 0
def add_impure(a):                            # Impure: แก้ไข global state -> side effect
    global total
    total += a
    return total

print(add_pure(2, 3))     # 5
print(add_pure(2, 3))     # 5 (เหมือนเดิมเสมอ)
print(add_impure(5))       # 5
print(add_impure(5))       # 10 (ผลลัพธ์ต่างกันทั้งที่ input เหมือนเดิม!)

# ===== Immutability: ไม่แก้ list เดิม สร้างใหม่แทน =====
def add_item_immutable(item, cart):           # Pure: คืนค่า list ใหม่ ไม่แก้ cart เดิมเลย
    return cart + [item]                        # + สร้าง list ใหม่ (ต่างจาก .append() ที่แก้ของเดิม)

original_cart = ["milk", "bread"]
new_cart = add_item_immutable("eggs", original_cart)

print(original_cart)      # ["milk", "bread"]           <- ไม่เปลี่ยนแปลงเลย
print(new_cart)             # ["milk", "bread", "eggs"]   <- ข้อมูลใหม่แยกต่างหาก

# ===== แก้กับดัก Mutable Default Argument =====
def add_item_correct(item, cart=None):        # ใช้ None เป็นค่าเริ่มต้นแทน mutable object
    if cart is None:
        cart = []                                # สร้าง list ใหม่ทุกครั้งที่เรียกฟังก์ชันจริงๆ
    return cart + [item]

print(add_item_correct("apple"))    # ["apple"]
print(add_item_correct("banana"))   # ["banana"]   <- ถูกต้องแล้ว! ไม่ใช่ ["apple", "banana"]

# ===== Immutable Data Structure ใน Python: tuple และ frozenset =====
point = (3, 4)                                # tuple แก้ไขไม่ได้เลยหลังสร้าง (immutable)
try:
    point[0] = 5
except TypeError as e:
    print(e)                                     # "'tuple' object does not support item assignment"

frozen = frozenset([1, 2, 3])                 # frozenset เหมือน set แต่แก้ไขไม่ได้
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `add_impure(5)` เรียกครั้งแรกได้ `5` แต่ครั้งที่สองได้ `10` — เพราะ `global total` ทำให้ฟังก์ชันแก้ไขตัวแปร `total` ที่อยู่**นอกขอบเขตของฟังก์ชันเอง** ทุกครั้งที่เรียก ผลลัพธ์จึงขึ้นอยู่กับ**ประวัติการเรียกฟังก์ชันก่อนหน้า** ไม่ใช่แค่ input ที่ส่งเข้ามา ณ ขณะนั้น — นี่คือเหตุผลที่ฟังก์ชันนี้ **ไม่ใช่ Pure Function**
2. `add_item_immutable(item, cart)` ใช้ `cart + [item]` แทน `cart.append(item)` — เครื่องหมาย `+` ระหว่าง list สอง list ใน Python **สร้าง list ใหม่ขึ้นมาเสมอ** โดยไม่แตะต้อง list เดิมเลย ต่างจาก `.append()` ที่**แก้ไข list เดิมตรงๆ (in-place)** — เพราะเหตุนี้ `original_cart` จึงยังคงเป็น `["milk", "bread"]` เหมือนเดิมหลังเรียกฟังก์ชัน
3. `def add_item_correct(item, cart=None)` — ค่าพารามิเตอร์เริ่มต้น (default argument) ใน Python **ถูกสร้างขึ้นแค่ครั้งเดียวตอนที่ประกาศฟังก์ชัน (ตอน `def` ทำงาน) ไม่ใช่ทุกครั้งที่เรียกใช้** ถ้าใช้ `cart=[]` ตรงๆ list ว่างตัวนั้นจะถูกสร้างครั้งเดียวและถูกใช้ซ้ำ (แชร์กัน) ในทุกการเรียกที่ไม่ได้ส่ง `cart` มาเอง — การใช้ `cart=None` แล้วเช็ค `if cart is None: cart = []` **ข้างในฟังก์ชัน** ทำให้ list ว่างถูกสร้างใหม่ทุกครั้งที่เรียกจริงๆ แก้ปัญหานี้ได้
4. `point[0] = 5` กับ `tuple` — โยน `TypeError` ทันที เพราะ `tuple` เป็น **immutable โดยธรรมชาติของภาษา** (บังคับจริงทางเทคนิค ต่างจาก "private" attribute ในบทที่ 30 ที่เป็นแค่ธรรมเนียม) การพยายามแก้ไข element ใดๆ ของ tuple หลังสร้างแล้วจะทำให้เกิด error เสมอ

## Time Complexity

- Pure Function ที่สร้างข้อมูลใหม่แทนการแก้ไขของเดิม (เช่น `cart + [item]`) มักมี Time Complexity **สูงกว่า** เวอร์ชัน mutable ที่แก้ไขในที่เดิม (`cart.append(item)`) เพราะต้องคัดลอกข้อมูลทั้งหมดไปยัง object ใหม่: `cart + [item]` คือ **O(n)** (คัดลอกทุก element) ในขณะที่ `cart.append(item)` คือ **O(1)** amortized (ทบทวนจาก Arrays บทที่ 12)
- นี่คือ **trade-off หลักของ Immutability**: แลกความปลอดภัยและคาดเดาได้ (predictability) กับ performance ที่อาจลดลงเมื่อข้อมูลมีขนาดใหญ่และต้อง "เปลี่ยนแปลง" บ่อยครั้ง

## Space Complexity

- แนวทาง Immutable ใช้พื้นที่**มากกว่า** แนวทาง Mutable เสมอ เพราะทุกครั้งที่ "เปลี่ยนแปลง" ข้อมูล ต้องสร้าง object ใหม่ทั้งชุดแทนที่จะแก้ของเดิม — ภาษาที่เน้น FP อย่างจริงจัง (เช่น Clojure, Haskell) มักใช้เทคนิคพิเศษ (Persistent Data Structure) เพื่อแชร์ส่วนที่ไม่เปลี่ยนแปลงระหว่างข้อมูลเก่ากับใหม่ ลดการสิ้นเปลืองพื้นที่ลงได้มาก แต่ Python ไม่มีกลไกนี้โดยธรรมชาติ

## แนวทางปฏิบัติที่ดี (Best Practices)

- เขียนฟังก์ชันให้เป็น Pure Function ให้ได้มากที่สุดเท่าที่ทำได้ โดยเฉพาะฟังก์ชันที่ทำหน้าที่คำนวณ/แปลงข้อมูล (business logic) — เก็บ Side Effect (การพิมพ์, การบันทึกไฟล์, การเรียก API) ไว้แค่จุดที่จำเป็นจริงๆ และแยกออกจาก logic การคำนวณให้ชัดเจน
- **ห้ามใช้ mutable object (list, dict) เป็นค่าเริ่มต้นของพารามิเตอร์** เด็ดขาด (`def f(x, items=[])`) ใช้ `None` แล้วสร้างใหม่ข้างในฟังก์ชันเสมอ (ตามตัวอย่าง `add_item_correct`)
- ใช้ `tuple` แทน `list` เมื่อข้อมูลนั้นไม่ควรถูกแก้ไขหลังสร้าง (เช่น พิกัด, ค่าคงที่ที่ประกอบกันเป็นกลุ่ม) เพื่อให้ภาษาบังคับความถูกต้องให้โดยอัตโนมัติ

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ใช้ mutable object เป็นค่าเริ่มต้นของพารามิเตอร์ (`def f(x, items=[])`) โดยไม่รู้ว่ามันถูกสร้างแค่ครั้งเดียวและแชร์กันทุกการเรียก ทำให้เกิดบั๊กที่ข้อมูลจากการเรียกครั้งก่อนหลงเหลือมาปนกับครั้งถัดไป
- แก้ไข list/dict ที่รับเข้ามาเป็นพารามิเตอร์โดยตรงในฟังก์ชัน (side effect ที่ผู้เรียกฟังก์ชันไม่คาดคิด) ทำให้ข้อมูลต้นฉบับเปลี่ยนไปโดยไม่ตั้งใจ ถ้าผู้เรียกยังคาดหวังว่าข้อมูลเดิมไม่เปลี่ยน
- คิดว่าฟังก์ชันที่ไม่มี `return` แต่แก้ไข object ที่รับเข้ามาแทน (แล้ว "return" object เดิมโดยปริยาย) ยังคงเป็น Pure Function — ที่จริงถือว่ามี Side Effect เต็มรูปแบบ เพราะแก้ไขข้อมูลนอกขอบเขตของตัวเอง
- หลงคิดว่า Immutability ไม่มี trade-off ด้าน performance เลย ทำให้เขียนโค้ดที่สร้าง object ใหม่ซ้ำๆ ในลูปขนาดใหญ่จนช้าเกินความจำเป็นโดยไม่รู้ตัว

## Mini Project

**"เครื่องมือแปลงข้อมูลแบบ Functional (Functional Data Pipeline)"**: เขียนโปรแกรมที่:
1. เขียนชุดฟังก์ชัน Pure Function สำหรับประมวลผลรายการสินค้า (list ของ dict ที่มี `name`, `price`, `category`) เช่น `filter_by_category()`, `apply_discount()`, `sort_by_price()` โดยทุกฟังก์ชันต้องคืนค่าใหม่เสมอ ไม่แก้ไข list/dict เดิมเลย
2. เชื่อมต่อฟังก์ชันเหล่านี้เข้าด้วยกันเป็น pipeline (เรียกฟังก์ชันหนึ่งต่อจากผลลัพธ์ของอีกฟังก์ชันหนึ่ง) เพื่อประมวลผลข้อมูลทีละขั้นตอน
3. เขียนเทสต์เปรียบเทียบ: เวอร์ชัน Pure Function (สร้างใหม่ทุกครั้ง) กับเวอร์ชัน Mutable (แก้ไขในที่เดิม) วัดผลต่างของเวลาและหน่วยความจำที่ใช้เมื่อข้อมูลมีขนาดใหญ่ (เช่น 100,000 รายการ)
4. พิสูจน์ว่าเมื่อเรียกฟังก์ชัน Pure Function ซ้ำด้วย input เดิม จะได้ผลลัพธ์เดิมเป๊ะทุกครั้ง (deterministic) โดยเขียนเทสต์ยืนยันอัตโนมัติ

## ข้อคิดสำคัญ (Key Takeaways)

- Pure Function ให้ผลลัพธ์เดิมเสมอเมื่อ input เดิม และไม่มี Side Effect ต่อโลกภายนอก ทำให้คาดเดาได้และเทสต์ง่าย
- Side Effect คือการกระทำใดๆ ที่ส่งผลต่อสิ่งนอกขอบเขตของฟังก์ชันเอง เช่น แก้ไข global variable หรือแก้ไขพารามิเตอร์ที่รับเข้ามาโดยตรง
- Immutability คือการไม่แก้ไขข้อมูลเดิม แต่สร้างข้อมูลชุดใหม่แทน ช่วยป้องกันบั๊กที่มาจาก "ใครแก้ข้อมูลนี้กันแน่" โดยเฉพาะในระบบที่ซับซ้อนหรือมีหลาย thread
- กับดัก Mutable Default Argument เป็นข้อผิดพลาดคลาสสิกใน Python ที่ต้องระวังเสมอ แก้ด้วยการใช้ `None` แทน mutable object เป็นค่าเริ่มต้น
- Immutability แลกมาด้วย Time/Space Complexity ที่อาจสูงกว่าเวอร์ชัน mutable เพราะต้องสร้าง object ใหม่ทุกครั้งที่ "เปลี่ยนแปลง" ข้อมูล — เป็น trade-off ที่ต้องชั่งน้ำหนักตามสถานการณ์
- บทถัดไปจะเรียน Higher Order Functions, Closures, Lambdas, และ Composition ซึ่งเป็นเครื่องมือที่ทำให้เขียน Pure Function มาประกอบกันเป็นโปรแกรมที่สมบูรณ์ได้อย่างสง่างาม ปิดท้าย Part 7: Functional Programming
