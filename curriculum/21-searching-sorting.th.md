# บทที่ 21: Searching & Sorting

## แนวคิดหลัก (Concept)

จากบทที่ 20 เรามีเครื่องมือวัดประสิทธิภาพ (Big O) แล้ว บทนี้จะนำมันมาใช้วิเคราะห์ **สองปัญหาพื้นฐานที่สุดในวงการคอมพิวเตอร์** ที่แทบทุกโปรแกรมต้องเจอ

- **Searching (การค้นหา)** — หาตำแหน่งหรือการมีอยู่ของค่าหนึ่งใน collection ของข้อมูล
- **Sorting (การเรียงลำดับ)** — จัดเรียงสมาชิกใน collection ให้อยู่ในลำดับที่ต้องการ (น้อยไปมาก หรือมากไปน้อย)

สองปัญหานี้เชื่อมโยงกันอย่างลึกซึ้ง: **การ sort ข้อมูลก่อน มักทำให้ search เร็วขึ้นอย่างมาก** (เช่น Binary Search ในบทที่ 22 ทำงานได้ก็ต่อเมื่อข้อมูลถูกเรียงแล้วเท่านั้น) บทนี้จะโฟกัสที่หลักการ Sorting หลายแบบ และภาพรวมของ Searching (รายละเอียด Binary Search จะแยกไปบทที่ 22)

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Sorting ทำให้ปัญหาอื่นๆ ง่ายขึ้นอย่างมหาศาล**: ข้อมูลที่เรียงแล้วเปิดโอกาสให้ใช้อัลกอริทึมที่เร็วกว่า (Binary Search O(log n) แทน Linear Search O(n)) หาค่ามัธยฐาน หาช่วงข้อมูล หรือแสดงผลตามลำดับ (เช่น เรียงคะแนนสอบจากสูงไปต่ำ) ล้วนต้องการข้อมูลที่ sort แล้ว
- **มีอัลกอริทึม Sort หลายแบบเพราะไม่มีแบบไหน "ดีที่สุด" ในทุกสถานการณ์**: บางแบบเขียนง่ายแต่ช้า (Bubble Sort) บางแบบซับซ้อนแต่เร็วมาก (Merge Sort, Quick Sort) การเลือกใช้ขึ้นอยู่กับขนาดข้อมูล, หน่วยความจำที่มี, และว่าข้อมูลเกือบเรียงอยู่แล้วหรือไม่
- **Search มีหลายแบบเพราะโครงสร้างข้อมูลต่างกันเหมาะกับวิธีค้นหาต่างกัน**: ข้อมูลที่ไม่เรียงต้องไล่ทีละตัว (Linear) ข้อมูลที่เรียงแล้วตัดข้อมูลทิ้งครึ่งได้ (Binary) — ทางเลือกของวิธีค้นหาจึงผูกกับว่าข้อมูลถูกจัดเก็บ/เตรียมมาอย่างไร (เชื่อมโยงกับ Part 4 ทั้งหมด)

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Linear Search** เหมือน **การหาชื่อในสมุดโทรศัพท์ที่ไม่ได้เรียงตามตัวอักษร** — ต้องพลิกดูทีละหน้าจนกว่าจะเจอ
- **Binary Search** เหมือน **การหาคำในพจนานุกรมที่เรียงตามตัวอักษรแล้ว** — เปิดตรงกลางเล่มก่อน ถ้าคำที่หาอยู่ก่อนหน้านั้นตามตัวอักษร ก็พลิกไปครึ่งแรก ถ้าอยู่หลังก็พลิกไปครึ่งหลัง ตัดทิ้งครึ่งหนึ่งทุกครั้ง
- **Sorting** เหมือน **การจัดเรียงไพ่ในมือก่อนเล่นเกม** — นักเล่นไพ่มักจัดเรียงไพ่ตามลำดับก่อนเสมอ เพราะทำให้มองหาไพ่ที่ต้องการเร็วขึ้นมากระหว่างเล่น (การลงทุนเวลาจัดเรียงล่วงหน้า คุ้มค่ากับความเร็วที่ได้กลับมาทีหลัง)

## แผนภาพอธิบาย (Visual explanation)

### Linear Search vs Binary Search

```
Linear Search: ไล่ทีละตัวจากซ้ายไปขวา
[8, 3, 1, 9, 5, 2]  หา 9
 ↑
 8≠9 -> ถัดไป
    ↑
    3≠9 -> ถัดไป
       ↑
       1≠9 -> ถัดไป
          ↑
          9=9 ✓ เจอ! (ใช้ไป 4 ครั้ง)

Binary Search: ต้องเรียงก่อนเสมอ! [1, 2, 3, 5, 8, 9]  หา 9
              mid
[1, 2, 3, 5, 8, 9]   mid=index 2 (ค่า 3) -> 3<9 -> ตัดซ้ายทิ้ง ไปทางขวา
         [5, 8, 9]   mid=index 1 (ค่า 8) -> 8<9 -> ตัดซ้ายทิ้ง ไปทางขวา
             [9]     mid=index 0 (ค่า 9) -> 9=9 ✓ เจอ! (ใช้ไปแค่ 3 ครั้ง)
```

### Bubble Sort — "ฟองอากาศลอยขึ้น" ทีละรอบ

```
[5, 2, 8, 1]  รอบที่ 1: เทียบคู่ติดกันทีละคู่ สลับถ้าลำดับผิด

[5,2,8,1] -> เทียบ(5,2): 5>2 สลับ -> [2,5,8,1]
[2,5,8,1] -> เทียบ(5,8): 5<8 ไม่สลับ -> [2,5,8,1]
[2,5,8,1] -> เทียบ(8,1): 8>1 สลับ -> [2,5,1,8]
                                        ↑ ค่ามากสุด "ลอย" ไปอยู่ท้ายสุดแล้ว (เหมือนฟองอากาศ)

รอบที่ 2: [2,5,1,8] -> เทียบ(2,5) ไม่สลับ -> เทียบ(5,1) สลับ -> [2,1,5,8]
รอบที่ 3: [2,1,5,8] -> เทียบ(2,1) สลับ -> [1,2,5,8]  ✓ เรียงเสร็จ
```

### Merge Sort — "แบ่งแล้วรวม" (Divide and Conquer)

```
                    [5, 2, 8, 1, 9, 3]
                    /                  \
              [5,2,8]                [1,9,3]        <- แบ่งครึ่งไปเรื่อยๆ (Divide)
              /     \                /      \
          [5,2]     [8]          [1,9]      [3]
          /   \                  /   \
        [5]   [2]              [1]   [9]

จากนั้น "รวม" กลับขึ้นมา โดยเรียงลำดับทุกครั้งที่รวม (Conquer/Merge):

  [5]+[2] -> merge -> [2,5]
  [1]+[9] -> merge -> [1,9]
  [2,5]+[8] -> merge -> [2,5,8]
  [1,9]+[3] -> merge -> [1,3,9]
  [2,5,8]+[1,3,9] -> merge -> [1,2,3,5,8,9]   <- ผลลัพธ์สุดท้าย เรียงสมบูรณ์
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== Linear Search - ใช้ได้กับข้อมูลไม่เรียงลำดับ =====
def linear_search(arr, target):
    for i, value in enumerate(arr):
        if value == target:
            return i
    return -1

# ===== Bubble Sort - เข้าใจง่าย แต่ช้า O(n²) =====
def bubble_sort(arr):
    n = len(arr)
    for i in range(n):
        swapped = False
        for j in range(n - i - 1):            # nested loop (บทที่ 11) -> O(n²)
            if arr[j] > arr[j + 1]:
                arr[j], arr[j + 1] = arr[j + 1], arr[j]   # สลับตำแหน่ง
                swapped = True
        if not swapped:                          # ถ้ารอบนี้ไม่มีการสลับเลย แปลว่าเรียงเสร็จแล้ว
            break                                  # ออกก่อนได้ (best case optimization)
    return arr

# ===== Merge Sort - เร็วกว่ามาก O(n log n) ใช้ Recursion (บทที่ 9) =====
def merge_sort(arr):
    if len(arr) <= 1:
        return arr                                # Base Case
    mid = len(arr) // 2
    left = merge_sort(arr[:mid])                    # Recursive Case: แบ่งครึ่งซ้าย
    right = merge_sort(arr[mid:])                    # Recursive Case: แบ่งครึ่งขวา
    return merge(left, right)

def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):          # รวมสองส่วนที่เรียงแล้วให้เป็นส่วนเดียวที่เรียง
        if left[i] <= right[j]:
            result.append(left[i]); i += 1
        else:
            result.append(right[j]); j += 1
    result.extend(left[i:])                            # เก็บส่วนที่เหลือ (ถ้ามี)
    result.extend(right[j:])
    return result

print(bubble_sort([5, 2, 8, 1]))       # [1, 2, 5, 8]
print(merge_sort([5, 2, 8, 1, 9, 3]))  # [1, 2, 3, 5, 8, 9]
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `bubble_sort` — loop ชั้นนอก (`i`) ควบคุมจำนวนรอบทั้งหมด loop ชั้นใน (`j`) เทียบคู่ที่อยู่ติดกันแล้วสลับถ้าลำดับผิด แต่ละรอบทำให้ค่าที่มากที่สุดที่เหลืออยู่ "ลอย" ไปอยู่ท้ายสุด ตัวแปร `swapped` เป็นการ optimize: ถ้ารอบใดไม่มีการสลับเลย แปลว่าข้อมูลเรียงเสร็จสมบูรณ์แล้ว จึง `break` ออกก่อนได้ทันที (ทำให้ best case เมื่อข้อมูลเรียงอยู่แล้วเป็น O(n) แทนที่จะเป็น O(n²) เต็มๆ)
2. `merge_sort([5,2,8,1,9,3])` — ตามหลัก recursion (บทที่ 9): เรียกตัวเองแบ่งครึ่งอาร์เรย์ไปเรื่อยๆ จนเหลือ 1 ตัว (base case, ซึ่งถือว่าเรียงแล้วโดยธรรมชาติ) แล้วจึง `merge()` สองส่วนที่เรียงแล้วเข้าด้วยกันทีละคู่ ไล่กลับขึ้นมาจนได้ผลลัพธ์เต็ม — สังเกตว่า **ทุกครั้งที่ merge สองส่วนที่เรียงแล้ว จะได้ผลลัพธ์ที่เรียงแล้วเสมอ** โดยไม่ต้องเทียบทุกคู่ที่เป็นไปได้เหมือน Bubble Sort
3. `merge(left, right)` — ใช้ two-pointer (`i`, `j`) เทียบสมาชิกหน้าสุดของทั้งสองฝั่งทีละคู่ เลือกตัวที่น้อยกว่าใส่ผลลัพธ์ก่อนเสมอ เดินหน้า pointer ของฝั่งนั้นไป 1 ตำแหน่ง ทำซ้ำจนกว่าฝั่งใดฝั่งหนึ่งหมด แล้วเก็บส่วนที่เหลือทั้งหมดต่อท้าย (เพราะมันเรียงอยู่แล้ว ไม่ต้องเทียบอะไรเพิ่ม)

## Time Complexity

| Algorithm | Best Case | Average Case | Worst Case |
|---|---|---|---|
| Linear Search | O(1) | O(n) | O(n) |
| Binary Search (ต้องเรียงก่อน) | O(1) | O(log n) | O(log n) |
| Bubble Sort | O(n) (ด้วย early exit) | O(n²) | O(n²) |
| Merge Sort | O(n log n) | O(n log n) | O(n log n) |

**ทำไม Merge Sort เป็น O(n log n)?** — แบ่งครึ่งข้อมูล log n ครั้ง (เหมือนหลักการ Binary Search) และในแต่ละ "ชั้น" ของการแบ่ง ต้องทำงาน merge รวมทั้งหมด O(n) (รวมทุกส่วนย่อยในชั้นนั้นแล้วเท่ากับ n เสมอ) → log n ชั้น × O(n) ต่อชั้น = **O(n log n)**

## Space Complexity

- Linear Search / Binary Search: O(1) — ไม่ต้องสร้างข้อมูลใหม่
- Bubble Sort: O(1) — สลับค่าในอาร์เรย์เดิม (in-place)
- Merge Sort: **O(n)** — ต้องสร้างอาร์เรย์ใหม่ระหว่าง merge แต่ละครั้ง (ไม่ใช่ in-place) นี่คือข้อแลกเปลี่ยน (trade-off) ที่ Merge Sort จ่ายเพื่อแลกกับความเร็ว O(n log n) ที่รับประกันเสมอ

## แนวทางปฏิบัติที่ดี (Best Practices)

- ในทางปฏิบัติ **แทบไม่มีใครเขียนอัลกอริทึม sort เองแล้ว** — ใช้ built-in function ของภาษา (`sorted()`, `.sort()`) ซึ่งมักถูก optimize ไว้อย่างดีแล้ว (Python ใช้ Timsort ซึ่งเป็นลูกผสมของ Merge Sort และ Insertion Sort)
- ใช้ Bubble Sort เฉพาะเพื่อการศึกษา/สัมภาษณ์งานเท่านั้น ไม่ควรใช้ในโค้ด production จริง เพราะช้ากว่าทางเลือกอื่นมากเมื่อข้อมูลใหญ่
- ก่อนใช้ Binary Search ต้องตรวจสอบเสมอว่าข้อมูล**เรียงลำดับแล้ว** — ถ้าไม่เรียง Binary Search จะให้ผลลัพธ์ผิดพลาดโดยไม่แจ้ง error

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ใช้ Binary Search กับข้อมูลที่ยังไม่ได้เรียงลำดับ ทำให้ได้ผลลัพธ์ผิดโดยไม่รู้ตัว (ไม่มี error แจ้งเตือน)
- คิดว่าอัลกอริทึม sort ทุกแบบมีความเร็วเท่ากัน โดยไม่พิจารณาขนาดข้อมูลจริง (Bubble Sort กับข้อมูล 100 ตัวอาจไม่ต่างจาก Merge Sort มาก แต่กับข้อมูล 1 ล้านตัวต่างกันมหาศาล)
- ลืมว่า Merge Sort ใช้พื้นที่เพิ่ม O(n) ซึ่งอาจเป็นปัญหาถ้าหน่วยความจำจำกัดมาก (ในกรณีนั้นอาจต้องพิจารณา in-place algorithm อื่นแทน)
- เขียน Bubble Sort โดยลืม early exit (`swapped` flag) ทำให้แม้ข้อมูลจะเรียงอยู่แล้วก็ยังคงวนครบทุกรอบ O(n²) โดยไม่จำเป็น

## ข้อคิดสำคัญ (Key Takeaways)

- Searching และ Sorting เป็นปัญหาพื้นฐานที่เชื่อมโยงกัน — ข้อมูลที่ sort แล้วเปิดทางให้ search ได้เร็วขึ้นมาก (Binary Search O(log n) แทน Linear Search O(n))
- Bubble Sort เข้าใจง่ายแต่ช้า O(n²) เหมาะสำหรับการศึกษาเท่านั้น ไม่เหมาะกับข้อมูลขนาดใหญ่จริง
- Merge Sort ใช้หลักการ Divide and Conquer แบ่งปัญหาให้เล็กลงด้วย recursion แล้วรวมผลลัพธ์กลับ ทำให้ได้ O(n log n) ที่เร็วกว่ามาก แลกกับการใช้พื้นที่เพิ่ม O(n)
- ควรใช้ built-in sort function ของภาษาในการเขียนโปรแกรมจริง แทนการเขียนเองเสมอ (ยกเว้นเพื่อการศึกษา)
- Divide and Conquer ที่เห็นใน Merge Sort เป็นแนวคิดสำคัญที่จะกลับมาใช้อีกในหลายอัลกอริทึมของบทถัดๆ ไป
- บทถัดไปจะเจาะลึก Binary Search โดยเฉพาะ ซึ่งเป็นรากฐานสำคัญของอัลกอริทึมการค้นหาที่มีประสิทธิภาพเกือบทั้งหมด
