# บทที่ 20: Big O, Big Theta, Big Omega

## แนวคิดหลัก (Concept)

ตลอด Part 4 (บทที่ 12-19) เราพูดถึง "O(1)", "O(n)", "O(log n)" ซ้ำๆ โดยยังไม่ได้อธิบายอย่างเป็นทางการว่ามันคืออะไร บทนี้จะรวบยอดแนวคิดนั้นให้เป็นระบบ — **Big O Notation** คือภาษากลางที่โปรแกรมเมอร์ทั่วโลกใช้อธิบายว่า **"อัลกอริทึมนี้ช้าลงเร็วแค่ไหนเมื่อข้อมูลเพิ่มขึ้น"** โดยไม่ต้องพึ่งพาความเร็วของเครื่องหรือภาษาที่ใช้เขียน

- **Big O (O)** — ขอบเขต**บนสุด** (upper bound) ของเวลา/พื้นที่ที่อัลกอริทึมใช้ในกรณีที่**แย่ที่สุด (worst case)** — เป็นสัญกรณ์ที่ใช้บ่อยที่สุดในวงการ เพราะบอก "การันตีว่าจะไม่แย่ไปกว่านี้"
- **Big Omega (Ω)** — ขอบเขต**ล่างสุด** (lower bound) ของเวลาที่อัลกอริทึมใช้ในกรณีที่**ดีที่สุด (best case)** — บอกว่า "อย่างน้อยที่สุดต้องใช้เวลาประมาณนี้"
- **Big Theta (Θ)** — ขอบเขตที่**แน่นอน** (tight bound) เมื่อ Big O และ Big Omega เท่ากันพอดี — บอกว่า "ไม่ว่ากรณีไหน อัลกอริทึมนี้ใช้เวลาประมาณนี้เสมอ"

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **มีไว้เปรียบเทียบอัลกอริทึมโดยไม่ขึ้นกับฮาร์ดแวร์**: คอมพิวเตอร์แต่ละเครื่องเร็วช้าต่างกัน (ตามบทที่ 1) การบอกว่า "โค้ดนี้รันใน 2 วินาที" ไม่มีความหมายถ้าไม่รู้ว่ารันบนเครื่องอะไร แต่การบอกว่า "อัลกอริทึมนี้เป็น O(n²)" เป็นจริงเสมอไม่ว่าจะรันบนเครื่องไหน
- **มีไว้ทำนายพฤติกรรมเมื่อข้อมูลโตขึ้นมาก**: อัลกอริทึม A อาจเร็วกว่า B เมื่อข้อมูลมีแค่ 10 ตัว แต่ช้ากว่ามากเมื่อข้อมูลมี 10 ล้านตัว — Big O สนใจ**เทรนด์การเติบโต**ไม่ใช่ตัวเลขเวลาจริง ทำให้ตัดสินใจเลือกอัลกอริทึมที่เหมาะกับสเกลของข้อมูลจริงในระบบ production ได้
- **สามแบบ (O, Ω, Θ) มีไว้ครอบคลุมทุกมุมมองของกรณีที่เป็นไปได้**: บางอัลกอริทึมเร็วมากถ้าโชคดี (best case) แต่ช้ามากถ้าโชคร้าย (worst case) — การมีทั้งสามสัญกรณ์ทำให้สื่อสารได้ครบถ้วนว่ากรณีไหนเป็นอย่างไร ไม่ใช่มองแค่ด้านเดียว

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Big O (worst case)** เหมือน **การประเมินเวลาเดินทางไปสนามบินตอนรถติดที่สุด** — "อย่างช้าที่สุดใช้เวลา 2 ชั่วโมง" คุณวางแผนตามนี้เพื่อไม่ให้พลาดเที่ยวบิน (การันตีขอบเขตบน)
- **Big Omega (best case)** เหมือน **"ถ้าโชคดีไม่ติดไฟแดงเลย ใช้เวลาแค่ 20 นาที"** — บอกขอบเขตล่างที่เป็นไปไม่ได้จะเร็วกว่านี้
- **Big Theta (tight bound)** เหมือน **เส้นทางที่มีระยะทางคงที่ไม่ว่าจะขับเวลาไหน** เช่น "ทางด่วนสายนี้ใช้เวลา 45 นาทีเสมอไม่ว่าเวลาไหน" (ไม่มีความแปรผันระหว่าง best/worst case)

## แผนภาพอธิบาย (Visual explanation)

### กราฟเปรียบเทียบอัตราการเติบโตของ Big O ทั่วไป

```
เวลาที่ใช้
    │                                              O(n²)  ← โตเร็วมาก (เช่น nested loop บทที่ 11)
    │                                         ╱
    │                                    ╱
    │                               ╱                    O(n log n) ← เร็วกว่า n² มาก
    │                          ╱          ___----
    │                     ╱      ___----
    │                ╱ ___----                            O(n) ← เชิงเส้น (loop 1 ชั้น)
    │           __----
    │      ___----------------------------------          O(log n) ← โตช้ามาก (BST บทที่ 16)
    │  ----
    │──────────────────────────────────────────           O(1) ← คงที่เสมอ (array access บทที่ 12)
    └────────────────────────────────────────── ขนาดข้อมูล (n)

ลำดับจากเร็วสุดไปช้าสุด:
O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ) < O(n!)
```

### ตัวอย่างการนับ Operation จริงเพื่อหา Big O

```python
def example(arr):              # arr มีขนาด n
    print(arr[0])                # 1 operation      -> O(1)
    for x in arr:                 # n operations
        print(x)                  #                   -> O(n)
    for x in arr:                  # n operations
        for y in arr:                # n operations ต่อรอบ
            print(x, y)                #                -> O(n * n) = O(n²)

รวมทั้งหมด: O(1) + O(n) + O(n²)
เมื่อ n ใหญ่มาก เทอม n² ครอบงำเทอมอื่นทั้งหมด (เทอมเล็กไม่มีนัยสำคัญ)
-> สรุปเป็น Big O ของทั้งฟังก์ชัน = O(n²)   (ตัดค่าคงที่และเทอมที่เล็กกว่าทิ้งเสมอ)
```

### Best / Average / Worst Case — ตัวอย่าง Linear Search

```python
def linear_search(arr, target):
    for i, value in enumerate(arr):
        if value == target:
            return i
    return -1

Best Case (Ω):   target อยู่ตำแหน่งแรกสุด -> เจอทันที       -> Ω(1)
Worst Case (O):  target อยู่ตำแหน่งสุดท้าย หรือไม่มีอยู่เลย -> ต้องไล่ทุกตัว -> O(n)
Average Case:    โดยเฉลี่ยเจอตรงกลางๆ                        -> O(n) (ยังคงเป็นเชิงเส้น)

สำหรับ linear_search: O(n) และ Ω(1) ไม่เท่ากัน -> ไม่มี Big Theta ที่ชัดเจนสำหรับทุกกรณี
(แต่ถ้าพิจารณาเฉพาะกรณีที่ target ไม่มีอยู่เลย -> Θ(n) เพราะต้องไล่ครบทุกตัวเสมอ)
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== O(1) - Constant Time =====
def get_first(arr):
    return arr[0]                    # ไม่ว่า arr จะมีกี่ล้านตัว ก็ใช้เวลาเท่าเดิม

# ===== O(n) - Linear Time =====
def sum_all(arr):
    total = 0
    for num in arr:                    # loop 1 ชั้น ผ่านทุกตัว
        total += num
    return total

# ===== O(log n) - Logarithmic Time (Binary Search - จะเรียนละเอียดบทที่ 22) =====
def binary_search(sorted_arr, target):
    low, high = 0, len(sorted_arr) - 1
    while low <= high:
        mid = (low + high) // 2
        if sorted_arr[mid] == target:
            return mid
        elif sorted_arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1                # ตัดข้อมูลทิ้งครึ่งหนึ่งทุกรอบ (เหมือน BST บทที่ 16)
    return -1

# ===== O(n²) - Quadratic Time =====
def has_duplicate_slow(arr):
    for i in range(len(arr)):
        for j in range(i + 1, len(arr)):     # nested loop - บทที่ 11
            if arr[i] == arr[j]:
                return True
    return False

# ===== O(n) - เวอร์ชันที่ดีกว่าด้วย Set (บทที่ 15) =====
def has_duplicate_fast(arr):
    seen = set()
    for num in arr:
        if num in seen:                        # O(1) โดยเฉลี่ยต่อครั้ง
            return True
        seen.add(num)
    return False
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `binary_search` — ทุกรอบของ `while` จะ**ตัดข้อมูลทิ้งครึ่งหนึ่ง**เสมอ (เชื่อมโยงกับ BST บทที่ 16) ถ้าเริ่มด้วยข้อมูล 1,000 ตัว รอบแรกเหลือ 500 ตัว รอบสองเหลือ 250 ตัว ไปเรื่อยๆ จนเหลือ 1 ตัว — จำนวนรอบที่ต้องใช้คือ log₂(1000) ≈ 10 รอบเท่านั้น (ไม่ใช่ 1,000 รอบ) นี่คือที่มาของ **O(log n)**
2. `has_duplicate_slow` เทียบกับ `has_duplicate_fast` — ทั้งสองฟังก์ชันแก้ปัญหาเดียวกัน (หาว่ามีค่าซ้ำหรือไม่) แต่ `has_duplicate_slow` ใช้ nested loop (O(n²)) ขณะที่ `has_duplicate_fast` ใช้ Set (O(n)) — เมื่อ n = 10,000: เวอร์ชันช้าต้องเทียบประมาณ 50 ล้านครั้ง ส่วนเวอร์ชันเร็วเทียบแค่ 10,000 ครั้ง **นี่คือเหตุผลที่ Big O สำคัญในทางปฏิบัติ ไม่ใช่แค่ทฤษฎี** — ความต่างระหว่าง O(n) กับ O(n²) ที่ n ใหญ่ๆ อาจหมายถึงความต่างระหว่าง "เร็วทันใจ" กับ "โปรแกรมค้าง"
3. เมื่อวิเคราะห์ `example(arr)` ในแผนภาพด้านบน เราคำนวณ operation ของแต่ละส่วนแยกกันก่อน (O(1), O(n), O(n²)) แล้ว**เลือกเทอมที่โตเร็วที่สุดเป็นตัวแทนทั้งหมด** เพราะเมื่อ n มีค่ามากพอ เทอมที่โตช้ากว่าจะมีผลกระทบเล็กน้อยจนไม่มีนัยสำคัญเมื่อเทียบกับเทอมที่โตเร็วที่สุด — กฎนี้เรียกว่า "การตัดเทอมที่ไม่มีนัยสำคัญ (drop non-dominant terms)"

## Time Complexity — สรุปเปรียบเทียบ (เชื่อมโยงกับทุกบทที่ผ่านมา)

| Big O | ชื่อเรียก | ตัวอย่างจากบทที่ผ่านมา |
|---|---|---|
| O(1) | Constant | เข้าถึง array ด้วย index (บทที่ 12), Hash Table lookup โดยเฉลี่ย (บทที่ 15) |
| O(log n) | Logarithmic | Binary Search, ค้นหาใน BST/AVL ที่สมดุล (บทที่ 16) |
| O(n) | Linear | Loop ผ่านทุกสมาชิก 1 ชั้น (บทที่ 11), ค้นหาใน Linked List (บทที่ 13) |
| O(n log n) | Linearithmic | อัลกอริทึม sorting ที่ดี เช่น Merge Sort (บทที่ 21) |
| O(n²) | Quadratic | Nested loop 2 ชั้น (บทที่ 11), Bubble Sort |
| O(2ⁿ) | Exponential | Recursive Fibonacci ตรงไปตรงมา (บทที่ 9) |

## Space Complexity

หลักการเดียวกับ Time Complexity แต่วัด**หน่วยความจำที่ใช้เพิ่มขึ้น**แทนเวลา เช่น การสร้าง array ใหม่ขนาด n ใช้ Space Complexity O(n) ส่วนการใช้แค่ตัวแปรนับจำนวนคงที่ (ไม่ว่าข้อมูลจะใหญ่แค่ไหน) ใช้ O(1) — Recursion ที่ลึก n ชั้นใช้ Space Complexity O(n) บน Call Stack (เชื่อมโยงกับบทที่ 3 และ 9)

## แนวทางปฏิบัติที่ดี (Best Practices)

- วิเคราะห์ Big O ของโค้ดก่อนนำไปใช้กับข้อมูลขนาดใหญ่จริง ไม่ใช่แค่ทดสอบกับข้อมูลตัวอย่างเล็กๆ ที่ไม่สะท้อนปัญหาที่จะเกิดขึ้นจริง
- เมื่อเจอ nested loop ให้ตั้งคำถามเสมอว่า "มีวิธีลด complexity ลงได้หรือไม่" (เช่น เปลี่ยนจาก O(n²) เป็น O(n) ด้วย Hash Table ตามตัวอย่าง `has_duplicate_fast`)
- อย่าเพิ่ง optimize ทุกอย่างให้เร็วที่สุดโดยไม่วิเคราะห์ก่อนว่าส่วนไหนคือคอขวดจริง (บาง O(n²) ที่ n เล็กมากๆ อาจเร็วกว่า O(n) ที่มี constant factor สูงในทางปฏิบัติ — Big O บอกเทรนด์ระยะยาว ไม่ใช่ความเร็วจริงเสมอไปเมื่อ n เล็ก)

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- สับสนระหว่าง Big O (worst case) กับความเร็วจริงเฉลี่ย — บางอัลกอริทึมมี worst case แย่แต่ average case ดีมาก (เช่น Quick Sort ที่จะเรียนบทที่ 21)
- ลืมตัดค่าคงที่และเทอมที่ไม่มีนัยสำคัญทิ้ง เช่น เขียน O(2n + 100) แทนที่จะสรุปเป็น O(n) ตามหลักการ Big O ที่แท้จริง
- คิดว่า Big O เดียวกันเสมอแปลว่าเร็วเท่ากันจริง — O(n) สองอัลกอริทึมอาจมี constant factor ต่างกันมาก ทำให้ความเร็วจริงต่างกันได้ (Big O บอกแค่เทรนด์การเติบโต ไม่ใช่ตัวเลขเวลาจริง)
- นับ Big O ของ nested loop ผิด โดยเฉพาะเมื่อ loop ชั้นในไม่ได้วนเต็มความยาวเสมอ (เช่นในตัวอย่าง `find_pair`/`has_duplicate_slow` ที่ loop ในเริ่มจาก `i+1` — ยังคงเป็น O(n²) แม้จะวนน้อยกว่า n เต็มๆ เพราะสัดส่วนยังโตแบบกำลังสอง)

3. วิเคราะห์ Big O ของโค้ดที่มี nested loop ที่ loop ชั้นในไม่ได้ขึ้นกับขนาดของ loop ชั้นนอก (เช่น loop นอกวน n รอบ loop ในวนคงที่ 100 รอบเสมอ) — Big O ของทั้งหมดคืออะไร?

## ข้อคิดสำคัญ (Key Takeaways)

- Big O (worst case), Big Omega (best case), และ Big Theta (tight bound) คือภาษากลางในการอธิบายว่าอัลกอริทึมช้าลงเร็วแค่ไหนเมื่อข้อมูลเพิ่มขึ้น โดยไม่ขึ้นกับฮาร์ดแวร์หรือภาษาที่ใช้
- การวิเคราะห์ Big O ทำโดยนับ operation ของแต่ละส่วน ตัดค่าคงที่และเทอมที่ไม่มีนัยสำคัญทิ้ง แล้วเลือกเทอมที่โตเร็วที่สุดเป็นตัวแทน
- Big O ไม่ได้บอกความเร็วจริง แต่บอกเทรนด์การเติบโตในระยะยาว — สำคัญมากเมื่อข้อมูลมีขนาดใหญ่ในระบบ production จริง
- ทุกโครงสร้างข้อมูลและอัลกอริทึมที่เรียนมาใน Part 4 ล้วนถูกอธิบายด้วยภาษานี้ ทำให้เปรียบเทียบและเลือกใช้ได้อย่างมีหลักการ
- บทนี้เป็นเครื่องมือสำคัญที่จะใช้ตลอดไปในบท Algorithms ถัดจากนี้ ซึ่งจะเริ่มจาก Searching และ Sorting — อัลกอริทึมพื้นฐานที่สุดสองแบบที่ใช้ Big O วิเคราะห์ประสิทธิภาพโดยตรง
