# บทที่ 22: Binary Search

## แนวคิดหลัก (Concept)

บทที่แล้วแนะนำ Binary Search แบบภาพรวม บทนี้จะเจาะลึกมันในฐานะอัลกอริทึมที่**สำคัญที่สุดอันหนึ่งที่ทุกวิศวกรซอฟต์แวร์ต้องเขียนได้อย่างถูกต้อง 100%** — แม้แนวคิดจะง่าย แต่รายละเอียดปลีกย่อย (edge case, off-by-one error) ทำให้เป็นหนึ่งในอัลกอริทึมที่คนเขียนผิดบ่อยที่สุดในการสัมภาษณ์งานจริง

- **Binary Search** — อัลกอริทึมค้นหาค่าใน**ข้อมูลที่เรียงลำดับแล้วเท่านั้น** โดยเทียบกับค่าตรงกลาง (mid) แล้ว**ตัดข้อมูลทิ้งครึ่งหนึ่ง**ทุกครั้ง ทำซ้ำจนกว่าจะเจอค่าหรือไม่เหลือข้อมูลให้ค้นหาแล้ว
- **Search Space (พื้นที่การค้นหา)** — ช่วงของข้อมูลที่ยังไม่ถูกตัดทิ้ง แทนด้วยขอบเขต `low` และ `high` ที่หดตัวลงทุกรอบ
- **Binary Search บน "คำตอบ" (Binary Search on Answer)** — เทคนิคขั้นสูงที่ใช้หลักการเดียวกัน แต่ไม่ได้ค้นหาใน array โดยตรง กลับใช้ค้นหา "คำตอบที่ดีที่สุด" ในช่วงตัวเลขที่เป็นไปได้ (จะยกตัวอย่างด้านล่าง)

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **มีไว้เปลี่ยน O(n) ให้เป็น O(log n)**: เมื่อข้อมูลเรียงลำดับแล้ว การไล่ทีละตัว (Linear Search) เป็นการเสียโอกาสมหาศาล เพราะทุกครั้งที่เทียบค่าที่ตำแหน่งหนึ่ง เรารู้ทันทีว่าคำตอบอยู่ฝั่งไหน (ซ้ายหรือขวา) — Binary Search ใช้ข้อมูลนี้ตัดข้อมูลทิ้งครึ่งหนึ่งทุกครั้ง ต่างจาก Linear Search ที่ทิ้งข้อมูลไปแค่ 1 ตัวต่อรอบ
- **เป็นรากฐานของ Divide and Conquer**: หลักการ "แบ่งปัญหาให้เล็กลงครึ่งหนึ่งซ้ำๆ" ที่เห็นใน Binary Search เป็นแนวคิดเดียวกับ Merge Sort (บทที่แล้ว) และจะกลับมาอีกในบท Divide and Conquer โดยเฉพาะ
- **"Binary Search on Answer" มีไว้แก้ปัญหาที่ดูไม่เหมือนการค้นหาเลยแต่จริงๆ ใช้หลักการเดียวกันได้**: หลายปัญหาการเพิ่มประสิทธิภาพ (optimization) มีคุณสมบัติ "monotonic" (ถ้าคำตอบ X ใช้ได้ คำตอบที่มากกว่า/น้อยกว่า X ก็มักใช้ได้ด้วยในทิศทางเดียวกันเสมอ) ทำให้ใช้ Binary Search หาคำตอบที่ดีที่สุดได้ แม้ปัญหาจะไม่ใช่การค้นหาใน array ตรงๆ

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Binary Search พื้นฐาน** เหมือน **เกมทาย "สูงไป-ต่ำไป"** (เหมือนที่เคยทำใน Mini Project บทที่ 11) — ทายตรงกลางช่วงที่เป็นไปได้เสมอ แล้วตัดครึ่งที่ไม่เกี่ยวข้องทิ้งตามคำใบ้
- **Binary Search on Answer** เหมือน **การหาน้ำหนักสูงสุดที่ลิฟต์รับได้โดยการทดสอบ** — ถ้าใส่น้ำหนัก 500kg แล้วลิฟต์ยังทำงานปกติ ก็ไม่จำเป็นต้องทดสอบน้ำหนักที่น้อยกว่า 500 อีก (เพราะรู้แน่นอนว่าใช้ได้อยู่แล้ว) ทดสอบแค่ค่าตรงกลางระหว่างจุดที่ "รู้ว่าใช้ได้" กับ "รู้ว่าใช้ไม่ได้" ซ้ำๆ จนกว่าจะเจอขีดจำกัดที่แน่นอน

### Search Space ที่หดตัวลงทุกรอบ

index:  0  1  2  3  4   5   6   7

รอบ 1:  low=0, high=7, mid=(0+7)//2=3  -> arr[3]=7 < 13 -> ตัดซ้ายทิ้ง -> low=4
        [1, 3, 5, 7, |9, 11, 13, 15]
                       └─── search space ใหม่ ───┘

รอบ 2:  low=4, high=7, mid=(4+7)//2=5  -> arr[5]=11 < 13 -> ตัดซ้ายทิ้ง -> low=6
        [9, 11, |13, 15]
                 └── search space ใหม่ ──┘

รอบ 3:  low=6, high=7, mid=(6+7)//2=6  -> arr[6]=13 = 13 ✓ เจอที่ index 6!

ใช้ไปแค่ 3 รอบ จากข้อมูล 8 ตัว (log₂8 = 3 พอดี)

### จุดที่มือใหม่เขียนผิดบ่อยที่สุด: เงื่อนไข while และการอัปเดต low/high

```python
# ผิด: ใช้ low < high (ไม่ใช่ <=) -> พลาดกรณีที่ low == high คือคำตอบพอดี
while low < high:   # ✗ ถ้า search space เหลือแค่ 1 ตัวพอดี จะไม่เข้า loop เลย!
    ...

# ถูก:
while low <= high:  # ✓ ต้องตรวจสอบแม้ search space เหลือแค่ 1 ตัว
    mid = (low + high) // 2
    if arr[mid] == target:
        return mid
    elif arr[mid] < target:
        low = mid + 1     # ✓ ต้อง +1 ไม่ใช่ mid เฉยๆ (ไม่งั้นวนไม่จบ - infinite loop!)
    else:
        high = mid - 1     # ✓ ต้อง -1 ไม่ใช่ mid เฉยๆ
```

### Binary Search on Answer — ตัวอย่าง "หาค่ารากที่สอง (Integer Square Root)"

```
หา floor(sqrt(28))  โดยไม่ใช้ math.sqrt() -> ใช้ Binary Search บนช่วงคำตอบที่เป็นไปได้ (0 ถึง 28)

ช่วงคำตอบ:  low=0, high=28

mid=14 -> 14²=196 > 28 -> คำตอบต้องน้อยกว่า 14 -> high=13
mid=6  (จาก 0-13)-> 6²=36 > 28 -> high=5
mid=2  (จาก 0-5) -> 2²=4 < 28 -> low=3
mid=4  (จาก 3-5) -> 4²=16 < 28 -> low=5
mid=5  (จาก 5-5) -> 5²=25 < 28 -> low=6 -> low>high หยุด

คำตอบ = high = 5   (เพราะ 5²=25 ≤ 28 แต่ 6²=36 > 28)

สังเกต: เราไม่ได้ค้นหาใน array เลย! แต่ค้นหา "ตัวเลขคำตอบ" ในช่วงที่เป็นไปได้
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== Binary Search แบบมาตรฐาน (Iterative) =====
def binary_search(arr, target):
    low, high = 0, len(arr) - 1
    while low <= high:                     # ต้องเป็น <= ไม่ใช่ <
        mid = low + (high - low) // 2       # ป้องกัน integer overflow (สำคัญในภาษาที่มีขอบเขต int เช่น Java/C++)
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1                                 # ไม่เจอ

# ===== Binary Search แบบ Recursive (เชื่อมโยงบทที่ 9) =====
def binary_search_recursive(arr, target, low=0, high=None):
    if high is None:
        high = len(arr) - 1
    if low > high:                             # Base Case: search space หมดแล้ว
        return -1
    mid = low + (high - low) // 2
    if arr[mid] == target:
        return mid
    elif arr[mid] < target:
        return binary_search_recursive(arr, target, mid + 1, high)   # Recursive Case
    else:
        return binary_search_recursive(arr, target, low, mid - 1)

# ===== Binary Search on Answer: หาค่ารากที่สอง (Integer Square Root) =====
def integer_sqrt(n):
    if n < 2:
        return n
    low, high = 1, n
    result = 0
    while low <= high:
        mid = low + (high - low) // 2
        if mid * mid <= n:
            result = mid          # เก็บคำตอบล่าสุดที่ "ใช้ได้" ไว้
            low = mid + 1          # ลองหาค่าที่มากกว่านี้ต่อ
        else:
            high = mid - 1
    return result

print(binary_search([1,3,5,7,9,11,13,15], 13))   # 6
print(integer_sqrt(28))                            # 5
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `mid = low + (high - low) // 2` — เขียนแบบนี้แทน `(low + high) // 2` เพื่อ**ป้องกัน integer overflow** ในภาษาที่ int มีขอบเขตจำกัด (เช่น Java, C++) เพราะถ้า `low` และ `high` ต่างก็มีค่ามากใกล้ขอบเขตสูงสุดของ int การบวกกันตรงๆ ก่อนหารอาจล้นขอบเขตได้ — ใน Python ไม่มีปัญหานี้ (int ไม่มีขอบเขตตายตัว) แต่เป็นนิสัยที่ดีที่ควรเขียนแบบนี้เสมอเพื่อความปลอดภัยข้ามภาษา
2. `while low <= high` — เงื่อนไขนี้ต้องเป็น `<=` เสมอ เพราะเมื่อ `low == high` ยังเหลือข้อมูล **1 ตัว**ที่ต้องตรวจสอบอยู่ ถ้าใช้ `<` (ผิด) จะข้ามการตรวจสอบตัวสุดท้ายไปเฉยๆ ทำให้พลาดคำตอบที่ถูกต้อง
3. `integer_sqrt(28)` — ใช้เทคนิค "เก็บคำตอบล่าสุดที่ใช้ได้ไว้ (`result = mid`) แล้วลองหาค่าที่ดีกว่าต่อไป" แทนที่จะ `return` ทันทีที่เจอเงื่อนไข เพราะโจทย์นี้ไม่ได้หา "ค่าที่เท่ากันพอดี" (ซึ่งอาจไม่มีจริง เช่น 28 ไม่มีรากที่สองเป็นจำนวนเต็มพอดี) แต่หา "ค่าที่ดีที่สุดที่ยังอยู่ในเงื่อนไข" — เป็นรูปแบบทั่วไปของ Binary Search on Answer ที่ต่างจาก Binary Search มาตรฐานที่หาค่า "ตรงเป๊ะ"

## Time Complexity

- Binary Search มาตรฐาน (ทั้ง iterative และ recursive): **O(log n)** — ตัดข้อมูลทิ้งครึ่งหนึ่งทุกรอบ
- Binary Search on Answer: **O(log(range) × cost_per_check)** โดย range คือขนาดของช่วงคำตอบที่เป็นไปได้ และ cost_per_check คือค่าใช้จ่ายในการตรวจสอบว่าคำตอบหนึ่งใช้ได้หรือไม่ (เช่น ในตัวอย่าง `integer_sqrt` ตรวจสอบด้วย `mid * mid <= n` ซึ่งเป็น O(1) ทำให้รวมเป็น O(log n))

## Space Complexity

- Binary Search แบบ Iterative: **O(1)** — ใช้แค่ตัวแปร `low`, `high`, `mid` คงที่ ไม่ว่าข้อมูลจะใหญ่แค่ไหน
- Binary Search แบบ Recursive: **O(log n)** — ใช้ Call Stack ตามความลึกของการเรียกซ้ำ (เชื่อมโยงกับบทที่ 3 และ 9) ซึ่งเท่ากับจำนวนรอบที่ใช้ตัดข้อมูลทิ้งครึ่งหนึ่งไปเรื่อยๆ

## แนวทางปฏิบัติที่ดี (Best Practices)

- ใช้เวอร์ชัน iterative แทน recursive เมื่อคำนึงถึงหน่วยความจำ (O(1) ดีกว่า O(log n)) เว้นแต่ recursive จะทำให้โค้ดอ่านง่ายขึ้นชัดเจนในบริบทนั้น
- เขียน `low + (high - low) // 2` แทน `(low + high) // 2` เป็นนิสัยเสมอ แม้ในภาษาที่ไม่มีปัญหา overflow เพื่อความสม่ำเสมอข้ามภาษา
- เมื่อเจอปัญหาที่มีคุณสมบัติ "monotonic" (ยิ่งมาก/น้อย ยิ่งมีคุณสมบัติบางอย่างเปลี่ยนทิศทางเดียว) ให้พิจารณา Binary Search on Answer เป็นตัวเลือกแรกๆ แทนการไล่ตรวจทุกค่าที่เป็นไปได้ (brute force)

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ใช้ `while low < high` แทน `while low <= high` ทำให้พลาดกรณีที่ search space เหลือแค่ 1 ตัว
- ลืม `+1`/`-1` ตอนอัปเดต `low`/`high` (เขียน `low = mid` แทน `low = mid + 1`) ทำให้เกิด **infinite loop** เพราะ search space ไม่หดตัวลงจริง
- ใช้ Binary Search กับข้อมูลที่ยังไม่ได้เรียงลำดับ ได้ผลลัพธ์ผิดโดยไม่มี error แจ้งเตือน (ย้ำจากบทที่แล้ว เพราะเป็นข้อผิดพลาดที่พบบ่อยมาก)
- เขียน `(low + high) // 2` ในภาษาที่มีขอบเขต integer จำกัด โดยไม่ระวังปัญหา overflow เมื่อ index มีค่ามากๆ

## ข้อคิดสำคัญ (Key Takeaways)

- Binary Search ค้นหาข้อมูลที่เรียงแล้วด้วยการตัดข้อมูลทิ้งครึ่งหนึ่งทุกรอบ ทำให้ได้ O(log n) แทนที่จะเป็น O(n)
- รายละเอียดเล็กๆ (เงื่อนไข `<=`, การอัปเดต `low`/`high` ด้วย `+1`/`-1`) สำคัญมาก การเขียนผิดแม้เล็กน้อยทำให้เกิด infinite loop หรือพลาดคำตอบ
- Binary Search on Answer ขยายหลักการเดียวกันไปใช้กับปัญหาที่ไม่ใช่การค้นหาใน array โดยตรง แต่ค้นหา "คำตอบที่ดีที่สุด" ในช่วงตัวเลขที่มีคุณสมบัติ monotonic
- เวอร์ชัน iterative ประหยัดหน่วยความจำกว่าเวอร์ชัน recursive (O(1) เทียบกับ O(log n))
- Binary Search เป็นรากฐานสำคัญที่จะเชื่อมโยงกับ BFS/DFS และ Divide and Conquer ในบทถัดไป ซึ่งล้วนใช้หลักการ "แบ่งปัญหาให้เล็กลง" แบบเดียวกัน
