# บทที่ 55: Scalability, Load Balancing, Caching, Redis, CDN

## แนวคิดหลัก (Concept)

ตลอดหลักสูตรที่ผ่านมาเราเรียนรู้วิธีสร้างระบบให้**ถูกต้อง** (correctness) — ทำงานได้ตามที่ออกแบบไว้ บทนี้เปิด **Part 16: System Design** โดยเปลี่ยนโฟกัสไปที่คำถาม: **ทำอย่างไรให้ระบบรองรับผู้ใช้เป็นล้านคนพร้อมกันได้** เมื่อเซิร์ฟเวอร์เดียวไม่พอ ต้องมีเทคนิคขยายระบบ (Scale) อย่างเป็นระบบ

- **Scalability (ความสามารถในการขยายตัว)** — ความสามารถของระบบในการรองรับปริมาณงานที่เพิ่มขึ้น แบ่งเป็น **Vertical Scaling** (เพิ่มพลังให้เครื่องเดิม — CPU/RAM มากขึ้น) และ **Horizontal Scaling** (เพิ่มจำนวนเครื่อง)
- **Load Balancer (ตัวกระจายโหลด)** — ตัวกลางที่กระจาย request ที่เข้ามาไปยังเซิร์ฟเวอร์หลายเครื่อง ทำให้ไม่มีเครื่องไหนรับภาระหนักเกินไปเครื่องเดียว
- **Caching (การแคช)** — เทคนิคเก็บผลลัพธ์ที่คำนวณ/ดึงมาแล้วไว้ใช้ซ้ำ แทนที่จะคำนวณหรือ query ฐานข้อมูลใหม่ทุกครั้ง (เชื่อมโยงกับ Memoization บทที่ 25 แต่ประยุกต์ใช้ระดับระบบทั้งหมด)
- **Redis** — ฐานข้อมูลแบบ **in-memory** (เก็บข้อมูลใน RAM ไม่ใช่ disk) ที่นิยมใช้เป็น cache เพราะเร็วมาก (เชื่อมโยงกับ speed hierarchy จากบทที่ 1: RAM เร็วกว่า disk มาก)
- **CDN (Content Delivery Network)** — เครือข่ายเซิร์ฟเวอร์ที่กระจายอยู่หลายที่ทั่วโลก เก็บสำเนาของไฟล์ static (รูปภาพ, video, CSS/JS) ไว้ใกล้ผู้ใช้ปลายทางที่สุด

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Scalability มีไว้เพราะเซิร์ฟเวอร์เดียวมีขีดจำกัดทางฟิสิกส์**: ไม่ว่าจะซื้อเครื่องแรงแค่ไหน (Vertical Scaling) ก็มีเพดานสูงสุดที่ทำไม่ได้มากกว่านั้น และการอัปเกรดเครื่องเดียวมักต้องปิดระบบชั่วคราว — Horizontal Scaling (เพิ่มเครื่อง) แก้ปัญหานี้โดยไม่มีเพดานตายตัว (เพิ่มเครื่องได้เรื่อยๆ) แต่ต้องมีระบบจัดการหลายเครื่องที่ดี
- **Load Balancer มีไว้เป็นเงื่อนไขที่ทำให้ Horizontal Scaling ใช้งานได้จริง**: ถ้ามีหลายเครื่องแต่ไม่มีใครกระจายงานให้ ผู้ใช้ต้องรู้เองว่าเครื่องไหนว่าง — Load Balancer ทำหน้าที่นี้อัตโนมัติ ทำให้ผู้ใช้เห็นระบบเป็น "จุดเดียว" (single entry point) แม้เบื้องหลังจะมีหลายเครื่องทำงานอยู่
- **Caching มีไว้ลดภาระของฐานข้อมูลและเพิ่มความเร็วในการตอบสนอง**: การ query ฐานข้อมูลทุกครั้งที่มีคนขอข้อมูลเดียวกันซ้ำๆ (เช่น หน้าแรกของเว็บที่ทุกคนเห็นเหมือนกัน) เป็นการสิ้นเปลืองที่ไม่จำเป็น (เชื่อมโยงกับปัญหาเดียวกับที่ Memoization บทที่ 25 แก้ไข) — Cache เก็บผลลัพธ์ไว้ใช้ซ้ำ ลดภาระฐานข้อมูลลงมาก
- **Redis มีไว้เป็นเครื่องมือ Caching ที่เร็วที่สุดในทางปฏิบัติ**: เพราะเก็บข้อมูลใน RAM (เร็วกว่า disk หลายพันเท่าตามบทที่ 1) Redis ตอบคำถามได้ในเสี้ยวมิลลิวินาที เหมาะกับข้อมูลที่ถูกอ่านบ่อยและไม่จำเป็นต้อง persist ถาวรเหมือนฐานข้อมูลหลัก
- **CDN มีไว้ลดเวลาแฝง (latency) จากระยะทางทางภูมิศาสตร์**: ถ้าเซิร์ฟเวอร์อยู่ที่สหรัฐฯ แต่ผู้ใช้อยู่ไทย ทุก request ต้องเดินทางข้ามครึ่งโลก (เชื่อมโยงกับ TCP/IP บทที่ 42 ที่ latency ขึ้นกับระยะทางจริง) — CDN เก็บสำเนาไฟล์ไว้ที่เซิร์ฟเวอร์ใกล้ผู้ใช้ที่สุด ลดเวลาเดินทางของข้อมูลได้มาก

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Vertical vs Horizontal Scaling** เหมือน **การจ้างพนักงานคนเดียวให้เก่งขึ้น (อบรมเพิ่ม) เทียบกับการจ้างพนักงานเพิ่มหลายคน** — คนเดียวเก่งแค่ไหนก็มีเพดาน แต่จ้างเพิ่มได้เรื่อยๆ ตามงานที่มากขึ้น
- **Load Balancer** เหมือน **พนักงานต้อนรับที่คอยจัดคิวลูกค้าไปยังพนักงานขายที่ว่างที่สุด** — ลูกค้าไม่ต้องรู้เองว่าพนักงานคนไหนว่าง แค่เข้าคิวเดียวแล้วถูกส่งไปหาคนที่เหมาะสม
- **Caching** เหมือน **การจดสูตรอาหารยอดนิยมติดไว้หน้าครัวแทนที่จะเปิดตำราใหม่ทุกครั้งที่มีคนสั่ง** — สูตรที่ถูกถามบ่อยเก็บไว้ใกล้มือ หยิบใช้ได้ทันทีโดยไม่ต้องเดินไปห้องสมุด (ฐานข้อมูล) ทุกครั้ง
- **CDN** เหมือน **เครือข่ายสาขาของร้านสะดวกซื้อที่กระจายอยู่ทุกมุมเมือง** — แทนที่ทุกคนต้องเดินทางไปโกดังใหญ่แห่งเดียว (เซิร์ฟเวอร์หลัก) แต่ละคนแค่เดินไปสาขาใกล้บ้านตัวเอง (CDN edge server) ที่มีสินค้าเหมือนกันวางไว้แล้ว

## แผนภาพอธิบาย (Visual explanation)

### Vertical vs Horizontal Scaling

```
Vertical Scaling (Scale Up):              Horizontal Scaling (Scale Out):

   [Server]                                [Server 1] [Server 2] [Server 3]
   2 CPU, 4GB RAM                           2 CPU, 4GB RAM (แต่ละเครื่อง)
        |
        v (อัปเกรด)
   [Server]                                เพิ่มเครื่องได้เรื่อยๆ ไม่มีเพดาน
   16 CPU, 64GB RAM                         แต่ต้องมี Load Balancer กระจายงาน
        |
        v (อัปเกรดต่อ)
   มีเพดานสูงสุดที่ฮาร์ดแวร์ทำได้
```

### Load Balancer — กระจาย Request ไปยังหลายเซิร์ฟเวอร์

```
                        ┌──────────────┐
   Client Requests ---> │Load Balancer │
                        └───┬──┬──┬────┘
                    ┌────────┘  │  └────────┐
                    v            v            v
              [Server 1]   [Server 2]   [Server 3]
              (กำลังทำงาน   (ว่าง - รับ    (กำลังทำงาน
               ปานกลาง)      request ใหม่)   หนัก)

Load Balancer เลือกเซิร์ฟเวอร์ตาม algorithm เช่น:
- Round Robin: หมุนเวียนส่งทีละเครื่องเรียงกัน (คล้าย Round Robin Scheduling บทที่ 44)
- Least Connections: ส่งไปเครื่องที่มีงานค้างน้อยที่สุด
```

### Caching Flow — Cache Hit vs Cache Miss

```
Request: GET /product/123

Cache Hit (เจอใน cache):                   Cache Miss (ไม่เจอใน cache):

Client -> Cache (Redis)                    Client -> Cache (Redis) -> ไม่เจอ!
   เจอข้อมูล! ตอบกลับทันที                          -> Database -> ดึงข้อมูลจริง
   (เร็วมาก, ไม่ต้องแตะฐานข้อมูลเลย)                  -> เก็บผลลัพธ์ลง Cache ด้วย (สำหรับครั้งถัดไป)
                                                    -> ตอบกลับ Client
                                                    (ช้ากว่า Cache Hit แต่ครั้งถัดไปจะเร็ว)
```

### CDN — เก็บสำเนาไฟล์ไว้ใกล้ผู้ใช้ทั่วโลก

```
Origin Server (สหรัฐฯ)
        |
        | กระจายสำเนาไฟล์ static (รูปภาพ, video, CSS/JS)
        |
   ┌────┼────┬─────────┬──────────┐
   v    v    v         v          v
[Edge  [Edge  [Edge    [Edge     [Edge
 US]    EU]   Asia]    Thailand]  Australia]

ผู้ใช้ในไทยขอไฟล์ -> เชื่อมต่อกับ Edge Server ที่ไทย (ใกล้ที่สุด) -> เร็วกว่าไปสหรัฐฯ มาก
ผู้ใช้ในยุโรปขอไฟล์เดียวกัน -> เชื่อมต่อกับ Edge Server ที่ยุโรปแทน
```

## ตัวอย่างโค้ด (Code example)

```python
import redis
import time
import json

# ===== Redis: ใช้เป็น Cache สำหรับ query ที่ทำบ่อย =====
cache = redis.Redis(host='localhost', port=6379, db=0)

def get_product_slow(product_id, database):                # จำลอง query ฐานข้อมูลที่ใช้เวลานาน
    time.sleep(1)                                              # จำลอง network/disk I/O ที่ช้า (บทที่ 1, 42)
    return database.get(product_id)

def get_product_with_cache(product_id, database):
    cache_key = f"product:{product_id}"
    cached = cache.get(cache_key)                               # เช็ค cache ก่อนเสมอ
    if cached:
        print("Cache HIT")
        return json.loads(cached)                                 # เจอใน cache -> คืนค่าทันที ไม่ต้องรอ 1 วินาที

    print("Cache MISS")
    product = get_product_slow(product_id, database)              # ไม่เจอ -> query ฐานข้อมูลจริง (ช้า)
    cache.setex(cache_key, 300, json.dumps(product))                 # เก็บลง cache หมดอายุใน 300 วินาที (5 นาที)
    return product

# เรียกครั้งแรก: Cache MISS -> รอ 1 วินาที
# เรียกครั้งที่สอง (ภายใน 5 นาที): Cache HIT -> ได้ผลลัพธ์ทันทีโดยไม่รอเลย

# ===== Load Balancer แบบ Round Robin (จำลองแนวคิด) =====
class RoundRobinLoadBalancer:
    def __init__(self, servers):
        self.servers = servers
        self.current_index = 0

    def get_next_server(self):
        server = self.servers[self.current_index]
        self.current_index = (self.current_index + 1) % len(self.servers)   # วนกลับไปตัวแรกเมื่อครบ
        return server

lb = RoundRobinLoadBalancer(["server1", "server2", "server3"])
for _ in range(5):
    print(f"Routing request to: {lb.get_next_server()}")
# server1, server2, server3, server1, server2 (วนไปเรื่อยๆ)

# ===== Cache Invalidation: ล้าง cache เมื่อข้อมูลเปลี่ยน =====
def update_product(product_id, new_data, database):
    database.update(product_id, new_data)                        # อัปเดตข้อมูลจริงในฐานข้อมูลก่อน
    cache.delete(f"product:{product_id}")                          # ล้าง cache เก่าทิ้ง (สำคัญมาก!)
    # ครั้งถัดไปที่มีคนขอสินค้านี้ จะเป็น Cache Miss -> ดึงข้อมูลใหม่ล่าสุดมา cache ใหม่
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `get_product_with_cache` — เช็ค `cache.get(cache_key)` **ก่อนเสมอ**: ถ้าเจอข้อมูล (**Cache Hit**) คืนค่ากลับทันทีโดยไม่แตะฐานข้อมูลเลย ถ้าไม่เจอ (**Cache Miss**) จึงเรียก `get_product_slow` (จำลองการ query ฐานข้อมูลที่ช้า) แล้ว**เก็บผลลัพธ์นั้นลง cache ด้วย** (`cache.setex(...)`) เพื่อให้การเรียกครั้งถัดไปเป็น Cache Hit แทน — นี่คือรูปแบบ **Cache-Aside Pattern** ที่นิยมใช้มากที่สุด
2. `cache.setex(cache_key, 300, json.dumps(product))` — `setex` ตั้งค่าพร้อม**เวลาหมดอายุ (TTL — Time To Live)** ที่ 300 วินาที หลังจากนั้น Redis จะลบข้อมูลนี้ทิ้งอัตโนมัติ — การตั้ง TTL สำคัญมากเพราะป้องกันไม่ให้ cache เก็บข้อมูลเก่าไว้ตลอดไปโดยไม่มีวันอัปเดต (ถ้าไม่ตั้ง TTL และไม่มีกลไก invalidate ข้อมูลใน cache อาจ "เก่า" กว่าความเป็นจริงในฐานข้อมูลนานเกินไป)
3. `RoundRobinLoadBalancer.get_next_server()` — ใช้ `self.current_index` ไล่เลือกเซิร์ฟเวอร์ทีละตัวเรียงกัน แล้วใช้ `% len(self.servers)` (modulo — ทบทวนจากบทที่ 6) เพื่อ**วนกลับไปเริ่มต้นใหม่**เมื่อไล่ครบทุกเครื่องแล้ว — เป็น algorithm ที่ง่ายที่สุดในบรรดา Load Balancing algorithm ทั้งหมด แต่ไม่คำนึงว่าเครื่องไหนกำลังทำงานหนักอยู่ (algorithm ที่ซับซ้อนกว่าอย่าง Least Connections จะพิจารณาภาระงานจริงของแต่ละเครื่องก่อนตัดสินใจ)
4. `update_product` — ขั้นตอนสำคัญที่มักถูกลืมคือ `cache.delete(...)` **ทันทีหลังอัปเดตข้อมูลจริง** เรียกว่า **Cache Invalidation** — ถ้าลืมขั้นตอนนี้ ผู้ใช้จะยังคงเห็นข้อมูลเก่าจาก cache ต่อไปจนกว่า TTL จะหมดอายุ แม้ข้อมูลจริงในฐานข้อมูลจะเปลี่ยนไปแล้วก็ตาม (ปัญหานี้เรียกกันติดตลกในวงการว่า **"There are only two hard things in Computer Science: cache invalidation and naming things"**)

## Time Complexity

- Cache Hit (Redis): **O(1)** โดยประมาณ — Redis ใช้ Hash Table ภายใน (บทที่ 15) ทำให้ค้นหาข้อมูลได้เร็วมาก บวกกับข้อมูลอยู่ใน RAM ทั้งหมด (เร็วกว่า disk มากตามบทที่ 1)
- Cache Miss: ช้ากว่า Cache Hit มาก เพราะต้อง query ฐานข้อมูลจริง (เชื่อมโยงกับ Index จากบทที่ 40 — ยิ่งฐานข้อมูลมี Index ที่ดี Cache Miss ก็ยิ่งเร็วขึ้น)
- Round Robin Load Balancer: **O(1)** ต่อการเลือกเซิร์ฟเวอร์หนึ่งครั้ง

## Space Complexity

- Redis Cache ใช้ RAM ตามปริมาณข้อมูลที่ cache ไว้ — ต้องตั้ง TTL และ**นโยบายการลบข้อมูลเก่า** (eviction policy เช่น LRU จากบทที่ 45) เมื่อ RAM เต็ม เพราะ RAM มีจำกัดกว่า disk มาก
- CDN ใช้พื้นที่จัดเก็บกระจายไปยังหลาย edge server ทั่วโลก แต่ละแห่งเก็บแค่ไฟล์ที่ผู้ใช้ในพื้นที่นั้นเข้าถึงบ่อย (ไม่จำเป็นต้องมีสำเนาทุกไฟล์ในทุก edge server)

## แนวทางปฏิบัติที่ดี (Best Practices)

- Cache เฉพาะข้อมูลที่ **อ่านบ่อยกว่าที่เขียน** มาก (read-heavy) เช่น ข้อมูลสินค้า, หน้าแรกของเว็บ — ข้อมูลที่เปลี่ยนแปลงบ่อยมาก (เช่น ยอดเงินในบัญชีธนาคารแบบเรียลไทม์) ไม่เหมาะกับการ cache เพราะเสี่ยงข้อมูลเก่าเกินไป
- ตั้ง TTL ให้เหมาะสมกับความถี่ในการเปลี่ยนแปลงของข้อมูล และ**ทำ Cache Invalidation ทุกครั้งที่มีการอัปเดตข้อมูลต้นฉบับ** อย่าพึ่งพา TTL เพียงอย่างเดียว
- เลือก Load Balancing algorithm ให้เหมาะกับลักษณะงาน (Round Robin เหมาะกับงานที่ใช้เวลาใกล้เคียงกัน, Least Connections เหมาะกับงานที่ใช้เวลาต่างกันมาก) และตรวจสอบสุขภาพของเซิร์ฟเวอร์ (Health Check) เพื่อไม่ส่ง request ไปยังเครื่องที่ล่มแล้ว

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ลืมทำ Cache Invalidation หลังอัปเดตข้อมูล ทำให้ผู้ใช้เห็นข้อมูลเก่าค้างอยู่นานเกินไป (แม้ข้อมูลจริงในฐานข้อมูลจะเปลี่ยนแล้ว)
- Cache ข้อมูลที่เปลี่ยนแปลงบ่อยเกินไปโดยไม่จำเป็น ทำให้ Cache Hit Rate ต่ำ (ข้อมูลหมดอายุเร็วกว่าจะได้ใช้ประโยชน์) เสียทรัพยากร RAM โดยไม่คุ้มค่า
- คิดว่า Horizontal Scaling แก้ปัญหาได้ทุกอย่างโดยไม่พิจารณาว่าแอปพลิเคชันต้อง**ออกแบบให้ไม่มี state ผูกติดกับเครื่องใดเครื่องหนึ่ง** (Stateless — เชื่อมโยงกับ JWT บทที่ 52) ถ้าแอปเก็บ session ไว้ในหน่วยความจำของเครื่องใดเครื่องหนึ่งโดยเฉพาะ Load Balancer ที่กระจายไปเครื่องอื่นจะทำให้ผู้ใช้ "หลุด" การล็อกอิน
- ไม่ตั้งค่า eviction policy ของ Redis เมื่อ RAM เต็ม ทำให้ Redis ปฏิเสธการเขียนข้อมูลใหม่ทั้งหมดแทนที่จะลบข้อมูลเก่าออกอัตโนมัติ

## คำถามสัมภาษณ์งาน (Interview Questions)

1. อธิบายความแตกต่างระหว่าง Vertical Scaling และ Horizontal Scaling พร้อมข้อดี-ข้อเสียของแต่ละแบบ
2. Load Balancer ทำงานอย่างไร ยกตัวอย่าง algorithm ที่ใช้เลือกเซิร์ฟเวอร์ปลายทาง
3. Cache Invalidation คืออะไร ทำไมถึงเป็นปัญหาที่ยากในวงการ Computer Science
4. ทำไม Redis ถึงเร็วกว่าฐานข้อมูลทั่วไปมาก เชื่อมโยงกับความรู้เรื่อง speed hierarchy จากบทที่ 1
5. CDN ช่วยลด latency ได้อย่างไร เหมาะกับข้อมูลประเภทไหน (และไม่เหมาะกับประเภทไหน)

## แบบฝึกหัด (Practice Exercises)

1. เขียนโปรแกรมเปรียบเทียบเวลาที่ใช้ query ข้อมูลเดียวกัน 100 ครั้งโดยไม่มี cache กับมี Redis cache แล้ววัดผลต่างของเวลารวม
2. Implement Load Balancer แบบ **Least Connections** (เลือกเครื่องที่มี connection ที่ยังทำงานค้างอยู่น้อยที่สุด) แล้วเปรียบเทียบกับ Round Robin ในสถานการณ์ที่แต่ละ request ใช้เวลาต่างกันมาก
3. ออกแบบระบบ Cache ที่มี TTL และ Cache Invalidation ที่ถูกต้องสำหรับระบบร้านค้าออนไลน์ (สินค้า, ราคา, สต็อก) แล้วทดสอบว่าเมื่ออัปเดตราคาสินค้า ผู้ใช้เห็นราคาใหม่ทันทีหรือไม่

## Mini Project

**"ระบบจำลองเว็บไซต์ขนาดใหญ่พร้อม Load Balancer, Cache, และ CDN (Scalable Web System Simulator)"**: เขียนโปรแกรมที่:
1. จำลองเซิร์ฟเวอร์หลายเครื่อง (ใช้ Class/Thread แทนเครื่องจริง) พร้อม Load Balancer ที่รองรับทั้ง Round Robin และ Least Connections ให้เลือกใช้ได้
2. เพิ่ม Redis Cache Layer สำหรับข้อมูลที่ query บ่อย พร้อมระบบ Cache Invalidation ที่ถูกต้องเมื่อข้อมูลเปลี่ยนแปลง
3. จำลอง CDN โดยสร้าง "edge server" หลายตัวที่เก็บสำเนาไฟล์ static แยกตาม "ภูมิภาค" จำลอง แล้วให้ผู้ใช้จำลองจากภูมิภาคต่างๆ เชื่อมต่อกับ edge server ที่ใกล้ที่สุด
4. ทดสอบระบบด้วยการจำลอง traffic จำนวนมาก (หลายพัน request พร้อมกัน) แล้วเปรียบเทียบประสิทธิภาพระหว่างระบบที่มี Load Balancer+Cache+CDN ครบ กับระบบที่ไม่มีเลย (เซิร์ฟเวอร์เดียว ไม่มี cache) แสดงผลเป็นตารางเปรียบเทียบ

## ข้อคิดสำคัญ (Key Takeaways)

- Scalability แบ่งเป็น Vertical Scaling (เพิ่มพลังเครื่องเดิม มีเพดาน) และ Horizontal Scaling (เพิ่มจำนวนเครื่อง ไม่มีเพดานตายตัว แต่ต้องออกแบบให้ Stateless)
- Load Balancer กระจาย request ไปยังหลายเซิร์ฟเวอร์ ทำให้ Horizontal Scaling ใช้งานได้จริง ด้วย algorithm หลายแบบ (Round Robin, Least Connections)
- Caching เก็บผลลัพธ์ที่คำนวณ/ดึงมาแล้วไว้ใช้ซ้ำ ลดภาระฐานข้อมูลและเพิ่มความเร็ว แต่ต้องจัดการ Cache Invalidation อย่างถูกต้องเสมอ
- Redis เป็น in-memory database ที่นิยมใช้เป็น cache เพราะเร็วมาก (RAM เร็วกว่า disk ตามบทที่ 1)
- CDN กระจายสำเนาไฟล์ static ไปยังเซิร์ฟเวอร์ใกล้ผู้ใช้ทั่วโลก ลด latency จากระยะทางทางภูมิศาสตร์
- ทั้งหมดนี้คือเครื่องมือพื้นฐานที่ใช้ประกอบกันในการออกแบบระบบขนาดใหญ่ที่รองรับผู้ใช้จำนวนมาก บทถัดไปจะเรียน Message Queues, Kafka, RabbitMQ ซึ่งเป็นอีกเครื่องมือสำคัญที่ช่วยให้ระบบขนาดใหญ่ประมวลผลงานจำนวนมากได้อย่างเสถียร ต่อยอดจาก Event-Driven Architecture ที่เรียนไปแล้วในบทที่ 49
