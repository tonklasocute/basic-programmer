# บทที่ 50: Git — branch, merge, rebase, cherry-pick, conflicts

## แนวคิดหลัก (Concept)

Part 12 สอนวิธีออกแบบโค้ดและระบบให้ดี แต่ในโลกจริงโค้ดถูกเขียนโดย**หลายคนพร้อมกัน**และเปลี่ยนแปลงตลอดเวลา บทนี้เปิด **Part 13: Version Control** ด้วย **Git** ซึ่งเป็นเครื่องมือที่ใช้ทุกวันในการทำงานร่วมกันของทีมพัฒนาซอฟต์แวร์เกือบทุกที่ในโลก — Git บันทึกประวัติการเปลี่ยนแปลงของโค้ดทุกจุด ทำให้ย้อนกลับ เปรียบเทียบ และรวมงานจากหลายคนเข้าด้วยกันได้อย่างปลอดภัย

- **Commit** — จุดบันทึกสถานะของโค้ดทั้งหมด ณ ขณะหนึ่ง พร้อมข้อความอธิบายว่าเปลี่ยนอะไรไปบ้าง แต่ละ commit ชี้ไปยัง commit ก่อนหน้าเสมอ (ทำให้ประวัติทั้งหมดเป็นเหมือน **Linked List** จากบทที่ 13 ที่เชื่อมย้อนกลับไปในอดีต)
- **Branch** — เส้นทางการพัฒนาที่แยกออกจากกัน ทำให้พัฒนาฟีเจอร์ใหม่หรือทดลองอะไรบางอย่างโดยไม่กระทบโค้ดหลัก (`main`) จนกว่าจะพร้อม
- **Merge** — การรวมการเปลี่ยนแปลงจาก branch หนึ่งกลับเข้า branch อื่น (มักเป็น `main`) โดยสร้าง commit ใหม่ที่มี**พ่อแม่สองฝั่ง** (merge commit)
- **Rebase** — วิธีรวมการเปลี่ยนแปลงอีกแบบหนึ่งที่**เขียนประวัติใหม่** ให้ดูเหมือนว่า commit ของ branch หนึ่งถูกสร้างขึ้นต่อจาก branch อื่นตั้งแต่แรก (ประวัติเป็นเส้นตรง ไม่มี merge commit)
- **Cherry-pick** — การหยิบ commit เฉพาะตัวจาก branch หนึ่งมาใส่ใน branch อื่น โดยไม่เอา commit อื่นๆ ทั้งหมดมาด้วย
- **Merge Conflict** — สถานการณ์ที่ Git ไม่สามารถรวมการเปลี่ยนแปลงจากสอง branch ได้อัตโนมัติ เพราะทั้งสองฝั่งแก้ไข**บรรทัดเดียวกัน**ต่างกัน (คล้ายหลักการ Race Condition จากบทที่ 37 แต่เกิดกับโค้ด ไม่ใช่ข้อมูล runtime)

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Commit มีไว้ให้ย้อนกลับไปดูหรือกู้คืนสถานะเก่าของโค้ดได้เสมอ**: ถ้าไม่มีระบบบันทึกประวัติ การแก้บั๊กที่เพิ่งเกิดขึ้นจากการเปลี่ยนแปลงล่าสุดจะทำได้ยากมาก (ต้องจำเองว่าแก้อะไรไปบ้าง) — commit ทำหน้าที่เหมือน "เซฟพอยต์" ที่กลับไปดูหรือย้อนกลับได้ทุกจุด
- **Branch มีไว้ให้หลายคน (หรือหลายฟีเจอร์) พัฒนาพร้อมกันโดยไม่ชนกัน**: ถ้าทุกคนแก้โค้ดใน `main` โดยตรงพร้อมกัน จะเกิดสถานการณ์ที่โค้ดของคนหนึ่งเขียนทับของอีกคน (คล้าย Race Condition) — Branch แยกพื้นที่ทำงานของแต่ละคน/ฟีเจอร์ออกจากกันจนกว่าจะพร้อมรวมกลับ
- **Merge/Rebase มีไว้ให้เลือกวิธีรวมประวัติที่เหมาะกับสถานการณ์**: Merge เก็บประวัติที่แท้จริงไว้ครบ (รู้ว่า branch ไหนแตกจากไหนเมื่อไหร่) เหมาะกับการทำงานเป็นทีมที่ต้องการความโปร่งใส ส่วน Rebase ทำให้ประวัติเป็นเส้นตรงสะอาดตา อ่านง่ายกว่าเมื่อดูย้อนหลัง แต่แลกกับการ "เขียนประวัติใหม่" ที่ต้องระวังเป็นพิเศษ
- **Cherry-pick มีไว้เมื่อต้องการแค่บางส่วนของงาน ไม่ใช่ทั้งหมด**: เช่น มีการแก้บั๊กเร่งด่วนอยู่ใน branch ที่ยังพัฒนาไม่เสร็จ (มี commit อื่นที่ยังไม่พร้อม) — cherry-pick ให้หยิบเฉพาะ commit ที่แก้บั๊กนั้นไปใส่ใน branch อื่นได้ทันทีโดยไม่ต้องรอ branch ทั้งหมดเสร็จ
- **Merge Conflict มีไว้เป็นกลไกความปลอดภัยป้องกันการเขียนทับข้อมูลโดยไม่ตั้งใจ**: ถ้า Git รวมโค้ดที่ขัดแย้งกันแบบอัตโนมัติโดยไม่ถามใครเลย อาจทำให้โค้ดที่คนหนึ่งตั้งใจเขียนหายไปเงียบๆ — การบังคับให้มนุษย์ตัดสินใจเองเมื่อเกิดความขัดแย้งเป็นการป้องกันที่จำเป็น

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Commit** เหมือน **การเซฟเกมที่มีชื่อบอกว่าเซฟตอนไหน** — กลับมาเล่นจากจุดเซฟไหนก็ได้ พร้อมรู้ว่าแต่ละจุดคือช่วงไหนของเกม
- **Branch** เหมือน **การถ่ายเอกสารต้นฉบับมาแก้ไขแยกกันหลายชุด** — แต่ละคนแก้ไขสำเนาของตัวเองได้อิสระ โดยต้นฉบับ (`main`) ยังคงเดิมจนกว่าจะเลือกรวมฉบับแก้ไขกลับเข้าไป
- **Merge** เหมือน **การรวมความคิดเห็นจากหลายคนที่แก้เอกสารคนละสำเนากลับเข้าต้นฉบับเดียว** — เก็บร่องรอยไว้ว่าใครแก้อะไรตรงไหนบ้าง
- **Rebase** เหมือน **การเขียนรายงานใหม่ให้ดูเหมือนเขียนต่อจากฉบับล่าสุดตั้งแต่แรก** แทนที่จะแปะส่วนที่แก้ไว้ต่อท้าย — ได้เอกสารที่อ่านลื่นเป็นเรื่องเดียวกัน แต่เสียร่องรอยว่าจริงๆ แล้วมันถูกเขียนแยกกันตอนไหน
- **Cherry-pick** เหมือน **การถ่ายเอกสารแค่หน้าเดียวจากเล่มรายงานทั้งเล่มมาแนบกับเอกสารอื่น** — ไม่เอาทุกหน้าของรายงานเล่มนั้นมาทั้งหมด
- **Merge Conflict** เหมือน **สองคนแก้ประโยคเดียวกันในเอกสารเดียวกันคนละแบบ** — ไม่มีทางรู้ได้เองว่าควรใช้แบบไหน ต้องให้คนตัดสินใจเลือกหรือรวมสองแบบเข้าด้วยกันเอง

## แผนภาพอธิบาย (Visual explanation)

### Commit History — แต่ละ Commit ชี้กลับไปยัง Commit ก่อนหน้า (เหมือน Linked List บทที่ 13)

```
A ---> B ---> C ---> D    (main branch)

A: "Initial commit"
B: "Add user login"          <- ชี้กลับไปหา A
C: "Fix login bug"           <- ชี้กลับไปหา B
D: "Add password reset"      <- ชี้กลับไปหา C

HEAD (ตำแหน่งปัจจุบัน) ชี้ไปที่ D เสมอเมื่ออยู่บน main
```

### Branch และ Merge — แยกทางแล้วรวมกลับ

```
                  E ---> F              (feature/login branch)
                 /            \
A ---> B ---> C                G        (G = merge commit, มีพ่อแม่ 2 ฝั่ง: C และ F)
                                 \
                                  main ชี้มาที่ G

git checkout -b feature/login    <- สร้าง branch ใหม่จาก C
(ทำงานใน feature/login: commit E, F)
git checkout main
git merge feature/login           <- สร้าง G ที่รวม C กับ F เข้าด้วยกัน
```

### Rebase — เขียนประวัติใหม่ให้เป็นเส้นตรง

```
ก่อน rebase:                              หลัง rebase (feature ย้ายไปต่อท้าย main ใหม่):

      E ---> F        (feature)                              E' ---> F'   (feature, commit ใหม่!)
     /                                                       /
A -> B -> C -> D       (main)              A -> B -> C -> D              (main เดิม)

git checkout feature
git rebase main

E', F' คือ "สำเนา" ของ E, F ที่ถูกสร้างใหม่ต่อจาก D (ไม่ใช่ commit เดิม - นี่คือ "เขียนประวัติใหม่")
ผลลัพธ์: ประวัติเป็นเส้นตรงเดียว A->B->C->D->E'->F' ไม่มี merge commit เลย
```

### Cherry-pick — หยิบ Commit เดียวข้าม Branch

```
feature branch:   A -> B -> X(fix urgent bug) -> C -> D

main branch:      A -> B

git checkout main
git cherry-pick X    <- หยิบแค่ commit X มาใส่ใน main

ผลลัพธ์:
main:             A -> B -> X'   (สำเนาของ X มาอยู่ใน main โดยไม่มี C, D ตามมาด้วยเลย)
```

### Merge Conflict — เมื่อ Git รวมอัตโนมัติไม่ได้

```
main:                          feature:
line 5: "Hello World"          line 5: "Hello Thailand"

git merge feature  ->  CONFLICT!

ไฟล์จะมีเครื่องหมายแสดงความขัดแย้ง:
<<<<<<< HEAD
Hello World
=======
Hello Thailand
>>>>>>> feature

ต้องแก้ไขด้วยมือ (เลือกอันใดอันหนึ่ง หรือรวมทั้งสอง) แล้ว git add + git commit เพื่อยืนยันคำตอบ
```

## ตัวอย่างโค้ด (Code example)

```bash
# ===== Branch: สร้างและสลับไปทำงานบน branch ใหม่ =====
git checkout -b feature/login          # สร้าง branch ใหม่ + สลับไปทำงานที่นั่นทันที
# ... แก้ไขโค้ด ...
git add login.py
git commit -m "Add user login feature"

# ===== Merge: รวม branch กลับเข้า main =====
git checkout main
git merge feature/login                 # สร้าง merge commit ที่มีพ่อแม่ 2 ฝั่ง

# ===== Rebase: เขียนประวัติให้เป็นเส้นตรง =====
git checkout feature/login
git rebase main                          # ย้าย commit ของ feature ไปต่อท้าย main ล่าสุด
# ถ้า main เปลี่ยนไปหลังจากแตก branch มา rebase จะ "เล่น" commit ของ feature ใหม่ทีละตัวบน main ล่าสุด

# ===== Cherry-pick: หยิบ commit เฉพาะตัวข้าม branch =====
git log feature/login --oneline          # ดูรายการ commit เพื่อหา hash ที่ต้องการ
git checkout main
git cherry-pick a1b2c3d                   # หยิบ commit ที่มี hash นี้มาใส่ใน main

# ===== Merge Conflict: แก้ไขด้วยมือเมื่อเกิดขึ้น =====
git merge feature/login
# CONFLICT (content): Merge conflict in app.py

# เปิดไฟล์ app.py แก้ไขส่วนที่มี <<<<<<< ======= >>>>>>> ด้วยมือ แล้ว:
git add app.py                             # บอก Git ว่าแก้ conflict นี้เสร็จแล้ว
git commit                                  # ยืนยัน merge commit พร้อมคำตอบที่แก้ไขแล้ว

# ===== คำสั่งช่วยตรวจสอบสถานะที่ใช้บ่อย =====
git status                                  # ดูว่ามีไฟล์ไหนเปลี่ยนแปลง/conflict อยู่
git log --graph --oneline --all             # ดูประวัติ commit แบบกราฟ เห็น branch แยก/รวมชัดเจน
git diff main feature/login                 # เปรียบเทียบความต่างระหว่างสอง branch
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `git checkout -b feature/login` — สร้าง**ตัวชี้ใหม่** (branch) ที่ชี้ไปยัง commit ปัจจุบัน แล้วย้าย `HEAD` (ตำแหน่งที่กำลังทำงานอยู่) ไปที่ branch ใหม่นี้ทันที — ทุก commit ที่สร้างขึ้นต่อจากนี้จะทำให้ `feature/login` ขยับไปข้างหน้า โดยที่ `main` ยังคงอยู่ที่ตำแหน่งเดิมไม่เปลี่ยนแปลง
2. `git merge feature/login` (ขณะอยู่บน `main`) — Git หา**จุดร่วมล่าสุด (common ancestor)** ของทั้งสอง branch แล้วสร้าง**merge commit ใหม่** ที่มีพ่อแม่ 2 ฝั่ง (commit ล่าสุดของ `main` และ commit ล่าสุดของ `feature/login`) — ถ้าการเปลี่ยนแปลงของทั้งสองฝั่งไม่ชนกัน (แก้คนละไฟล์หรือคนละบรรทัด) Git รวมให้อัตโนมัติโดยไม่ต้องถามอะไรเลย
3. `git rebase main` (ขณะอยู่บน `feature/login`) — Git **หา commit ทั้งหมดที่มีเฉพาะใน `feature/login`** (ที่ไม่มีใน `main`) แล้ว**เล่นซ้ำ (replay)** commit เหล่านั้นทีละตัวโดยเริ่มจากปลายของ `main` ล่าสุด — ผลลัพธ์คือ commit ใหม่ทั้งหมด (hash ต่างจากเดิม แม้เนื้อหาการเปลี่ยนแปลงจะเหมือนเดิม) ที่ต่อจาก `main` เป็นเส้นตรง **ไม่มี merge commit เกิดขึ้นเลย**
4. `git cherry-pick a1b2c3d` — Git หยิบ**เฉพาะการเปลี่ยนแปลง (diff)** ที่ commit `a1b2c3d` สร้างขึ้น แล้วนำมาสร้างเป็น commit ใหม่บน branch ปัจจุบัน (`main` ในตัวอย่าง) โดย**ไม่แตะต้อง commit อื่นๆ ที่อยู่ก่อนหรือหลัง `a1b2c3d` ใน `feature/login` เลย** — เหมาะกับการดึงเฉพาะการแก้บั๊กเร่งด่วนที่บังเอิญอยู่ใน branch ที่ยังพัฒนาไม่เสร็จ
5. เมื่อเกิด **Merge Conflict** — Git แทรกเครื่องหมาย `<<<<<<<`, `=======`, `>>>>>>>` ลงในไฟล์ตรงจุดที่ขัดแย้งกัน โดยแสดงทั้งสองเวอร์ชัน (`HEAD` คือฝั่งปัจจุบัน, ชื่อ branch อีกฝั่งคือฝั่งที่กำลัง merge เข้ามา) — ผู้พัฒนาต้อง**แก้ไขด้วยมือ**ให้เหลือแค่โค้ดที่ถูกต้อง (ลบเครื่องหมายทั้งหมดออก) แล้วเรียก `git add` เพื่อบอกว่า "แก้ conflict นี้เสร็จแล้ว" ก่อนจะ `git commit` เพื่อยืนยัน merge commit ให้สมบูรณ์

## Time Complexity

Git เป็นเครื่องมือจัดการเวอร์ชัน ไม่ใช่อัลกอริทึมที่วัดด้วย Big O โดยตรง แต่โครงสร้างข้อมูลภายในเชื่อมโยงกับความรู้ที่เรียนมา:
- **Commit History** เป็น **Directed Acyclic Graph (DAG)** — คล้าย Linked List (บทที่ 13) แต่แต่ละ node อาจมีมากกว่าหนึ่งพ่อแม่ได้ (merge commit) และไม่มี cycle เลย (เชื่อมโยงกับ Graph บทที่ 19)
- การหา common ancestor สำหรับ `merge`/`rebase` ใช้หลักการคล้าย **BFS/DFS** (บทที่ 23) ไล่ตามกราฟของ commit ย้อนกลับไป
- `git log`, `git diff` ทำงานเร็วเพราะ Git เก็บข้อมูลแบบ content-addressable (ใช้ hash เป็น key คล้าย Hash Table บทที่ 15) ทำให้ค้นหา commit/object ได้เกือบ O(1)

## Space Complexity

- Git เก็บ**สแนปช็อตของทั้งโปรเจกต์**ในแต่ละ commit แต่ใช้เทคนิค**แชร์ object ที่ไม่เปลี่ยนแปลง**ระหว่าง commit (คล้ายหลักการ Persistent Data Structure ที่กล่าวถึงใน Immutability บทที่ 34) ทำให้ประหยัดพื้นที่มากแม้จะเก็บสแนปช็อตทั้งหมดในทุก commit

## แนวทางปฏิบัติที่ดี (Best Practices)

- ใช้ `merge` เมื่อทำงานเป็นทีมและต้องการรักษาประวัติที่แท้จริงไว้ (รู้ว่าใครทำอะไรตอนไหนจริงๆ) ใช้ `rebase` เมื่อต้องการทำความสะอาดประวัติของ branch ส่วนตัวก่อน merge เข้า `main` (ให้ดูเป็นเส้นตรง อ่านง่าย)
- **ห้าม rebase branch ที่คนอื่นกำลังใช้งานร่วมกันอยู่** (เช่น `main` ที่แชร์กับทีม) เพราะ rebase เขียน commit ใหม่ทั้งหมด ทำให้ประวัติของคนอื่นที่อ้างอิง commit เดิมพังทันที — ใช้ rebase ได้อย่างปลอดภัยเฉพาะกับ branch ส่วนตัวที่ยังไม่ได้แชร์กับใคร
- Commit บ่อยๆ ด้วยข้อความที่ชัดเจนสื่อความหมาย (เชื่อมโยงกับ Meaningful Naming จากบทที่ 47 แต่ใช้กับข้อความ commit แทน) ทำให้ประวัติที่ย้อนดูภายหลังมีประโยชน์จริง

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- Rebase branch สาธารณะที่แชร์กับทีม ทำให้เพื่อนร่วมทีมที่ pull โค้ดไปแล้วเจอประวัติที่ขัดแย้งกันอย่างสับสน (เพราะ commit hash เปลี่ยนไปหมด)
- แก้ Merge Conflict โดยลบเครื่องหมาย `<<<<<<<`/`=======`/`>>>>>>>` ออกไม่ครบ ทำให้เครื่องหมายเหล่านี้หลงเหลือในโค้ดจริงโดยไม่ตั้งใจ (โปรแกรมพังเพราะ syntax error)
- Cherry-pick commit ที่พึ่งพา commit อื่นก่อนหน้าที่ไม่ได้ถูกหยิบมาด้วย ทำให้โค้ดที่ได้ไม่สมบูรณ์หรือพังเพราะขาดส่วนที่จำเป็น
- Commit ข้อความที่ไม่สื่อความหมาย (เช่น "fix", "update", "asdf") ทำให้ประวัติที่ย้อนดูภายหลังไม่มีประโยชน์เลยเมื่อพยายามหาว่า bug เกิดจาก commit ไหน

## คำถามสัมภาษณ์งาน (Interview Questions)

1. อธิบายความแตกต่างระหว่าง Merge และ Rebase ทั้งในแง่ผลลัพธ์ของประวัติและความเสี่ยง
2. ทำไมถึงไม่ควร rebase branch ที่แชร์กับทีม (public branch)
3. Cherry-pick ใช้ในสถานการณ์ไหนบ้าง ต่างจากการ merge ทั้ง branch อย่างไร
4. อธิบายว่า Merge Conflict เกิดขึ้นได้อย่างไร และขั้นตอนการแก้ไขที่ถูกต้องคืออะไร
5. Git เก็บประวัติ commit ในรูปแบบโครงสร้างข้อมูลอะไร เชื่อมโยงกับความรู้เรื่อง Graph/Linked List ที่เคยเรียนมาอย่างไร

## แบบฝึกหัด (Practice Exercises)

1. สร้างโปรเจกต์ทดสอบ สร้าง branch ใหม่ แก้ไขไฟล์เดียวกันทั้งใน `main` และ branch ใหม่ให้ต่างกันในบรรทัดเดียวกัน แล้วลอง `git merge` เพื่อดู Merge Conflict เกิดขึ้นจริงและฝึกแก้ไขด้วยมือ
2. ทดลอง `git rebase` กับ branch ทดสอบที่มีหลาย commit แล้วใช้ `git log --graph --oneline --all` เปรียบเทียบรูปร่างของประวัติก่อนและหลัง rebase
3. สร้าง branch ที่มีหลาย commit แล้วลองใช้ `git cherry-pick` หยิบแค่ commit ตรงกลางมาใส่ใน branch อื่น สังเกตว่า commit อื่นที่เหลือไม่ถูกนำมาด้วย

## Mini Project

**"คู่มือ Git Workflow สำหรับทีมพัฒนา (Team Git Workflow Playbook)"**: เขียนเอกสาร/สคริปต์ทดสอบที่:
1. จำลองสถานการณ์ทีม 2-3 คนทำงานพร้อมกันบนโปรเจกต์เดียว (ใช้ branch คนละอันจำลองแต่ละคน) ที่ต้องมีการ merge, rebase, และ cherry-pick เกิดขึ้นจริงตามสถานการณ์ที่กำหนด (เช่น "คนที่ 1 ต้องหยิบ hotfix จากคนที่ 2 มาใช้ด่วน")
2. จงใจสร้าง Merge Conflict อย่างน้อย 2 สถานการณ์ (แก้ไขบรรทัดเดียวกัน, ลบไฟล์ที่อีกฝั่งแก้ไข) แล้วเขียนขั้นตอนการแก้ไขที่ถูกต้องสำหรับแต่ละสถานการณ์
3. เขียนแนวทาง (guideline) ว่าทีมควรใช้ merge หรือ rebase ในสถานการณ์ไหนบ้าง พร้อมเหตุผลจากประสบการณ์ที่ทดลองจริง
4. สร้างสคริปต์ตรวจสอบสถานะ (`git status`, `git log --graph`) ที่ช่วยให้เห็นภาพรวมของ branch ทั้งหมดในโปรเจกต์ได้ง่ายในคำสั่งเดียว

## ข้อคิดสำคัญ (Key Takeaways)

- Git บันทึกประวัติของโค้ดเป็น commit ที่เชื่อมโยงกันเป็น DAG (Directed Acyclic Graph) ทำให้ย้อนกลับ เปรียบเทียบ และรวมงานจากหลายคนได้อย่างปลอดภัย
- Branch แยกพื้นที่ทำงานออกจากกัน ทำให้พัฒนาฟีเจอร์ใหม่โดยไม่กระทบโค้ดหลักจนกว่าจะพร้อม
- Merge เก็บประวัติที่แท้จริงไว้ครบด้วย merge commit ส่วน Rebase เขียนประวัติใหม่ให้เป็นเส้นตรง — ทั้งสองมีที่ใช้ต่างกัน และห้าม rebase branch ที่แชร์กับทีม
- Cherry-pick หยิบ commit เฉพาะตัวข้าม branch โดยไม่เอา commit อื่นมาด้วย เหมาะกับการดึงการแก้ไขเร่งด่วน
- Merge Conflict เกิดเมื่อ Git รวมการเปลี่ยนแปลงอัตโนมัติไม่ได้ ต้องแก้ไขด้วยมือเสมอเพื่อป้องกันการเขียนทับข้อมูลโดยไม่ตั้งใจ
- Git เป็นเครื่องมือที่ใช้ทุกวันในการทำงานจริง ความเข้าใจกลไกภายในช่วยให้แก้ปัญหาที่ซับซ้อน (conflict, ประวัติที่ยุ่งเหยิง) ได้อย่างมั่นใจแทนที่จะท่องจำคำสั่งโดยไม่เข้าใจ
