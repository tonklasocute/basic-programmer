# บทที่ 27: Backtracking

## แนวคิดหลัก (Concept)

บทที่แล้วปิดท้ายด้วยคำถาม: ถ้า Greedy ตัดสินใจแล้วเดินหน้าต่อโดยไม่ย้อนกลับ แล้วถ้าปัญหาต้องการ**ลองทางเลือกหลายทางและย้อนกลับได้เมื่อพบว่าทางนั้นผิด**ล่ะ? นี่คือหน้าที่ของ **Backtracking** — เทคนิคที่สร้างคำตอบทีละขั้นตอน (คล้าย DFS จากบทที่ 23) แต่เพิ่มความสามารถพิเศษคือ**ตรวจสอบทันทีว่าทางที่เลือกยังมีโอกาสถูกต้องหรือไม่** ถ้าพบว่าผิดแน่นอนแล้วให้**ถอยกลับ (backtrack)** ทันทีโดยไม่ต้องสำรวจทางนั้นต่อให้จบ

- **Backtracking** — เทคนิคแก้ปัญหาแบบ "ลองแล้วถอย" (try and undo) สร้างคำตอบทีละส่วน ตรวจสอบเงื่อนไขความถูกต้องระหว่างทาง ถ้าพบว่าทางที่เลือกไม่มีทางนำไปสู่คำตอบที่ถูกต้องได้ (invalid) ให้ยกเลิกการเลือกล่าสุดแล้วย้อนกลับไปลองทางเลือกอื่น
- **Pruning (การตัดกิ่ง)** — การหยุดสำรวจเส้นทางที่รู้แน่ชัดแล้วว่าไม่มีทางถูกต้อง โดยไม่ต้องสำรวจต่อจนสุด — หัวใจสำคัญที่ทำให้ Backtracking เร็วกว่า Brute Force ที่ลองทุกความเป็นไปได้แบบไม่เลือก
- **State Space Tree** — ต้นไม้ของทุกความเป็นไปได้ในการสร้างคำตอบทีละขั้น โดย Backtracking คือการทำ DFS บนต้นไม้นี้พร้อม pruning กิ่งที่รู้แล้วว่าผิด

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **มีไว้แก้ปัญหาที่ต้องหา "คำตอบที่เป็นไปได้ทั้งหมด" หรือ "คำตอบใดคำตอบหนึ่งที่ถูกต้อง" ไม่ใช่แค่ค่าที่ดีที่สุด**: ต่างจาก DP และ Greedy (สองบทที่แล้ว) ที่หา "ค่าที่ดีที่สุด" หนึ่งค่า Backtracking เหมาะกับปัญหาประเภท "จัดวาง" หรือ "เลือกชุด" ที่ต้องตรวจสอบเงื่อนไขซับซ้อน เช่น N-Queens, Sudoku, การจัดสรร้ายชื่อ — ปัญหาที่ DP ทำไม่ได้เพราะไม่มี Optimal Substructure ที่ชัดเจนแบบเดียวกัน
- **Pruning มีไว้ประหยัดเวลามหาศาลเทียบกับ Brute Force**: ถ้าลองทุกความเป็นไปได้แบบไม่เลือก (Brute Force เต็มรูปแบบ) จำนวนความเป็นไปได้มักเป็น exponential (เช่น N-Queens มี N^N แบบวางที่เป็นไปได้ทั้งหมด) แต่การตัดกิ่งที่รู้แน่ว่าผิดตั้งแต่เนิ่นๆ ลดจำนวนที่ต้องสำรวจจริงลงมหาศาล แม้ worst case ทางทฤษฎียังคง exponential อยู่ก็ตาม
- **เชื่อมโยง DFS (บทที่ 23) เข้ากับการตัดสินใจแบบมีเงื่อนไข**: Backtracking คือ DFS ที่ฉลาดขึ้น — แทนที่จะเดินลึกไปเรื่อยๆ โดยไม่สนใจอะไร มันตรวจสอบเงื่อนไขที่จุดตัดสินใจทุกจุด ทำให้เป็นสะพานเชื่อมระหว่างการ traverse ธรรมดา (บทที่ 23) กับการแก้ปัญหาเชิงจัดวาง (Combinatorial Problems)

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Backtracking** เหมือน **การเดินเขาวงกตที่จดทางเดินไว้ทุกจุด และหันหลังกลับทันทีเมื่อเจอทางตัน** — ต่างจากการเดินสุ่มไปเรื่อยๆ เพราะทันทีที่รู้ว่าทางข้างหน้าคือทางตันแน่นอน ก็ถอยกลับไปจุดแยกล่าสุดทันทีแทนที่จะเดินต่อไปดูให้ถึงจุดตันจริงๆ ก่อน
- **Pruning** เหมือน **การเล่นซูโดกุแล้วข้ามช่องที่เห็นชัดว่าใส่เลขนี้ไม่ได้ทันที** — ไม่ต้องลองใส่แล้วไล่ตรวจทั้งกระดานทุกครั้ง แค่มองแถว/คอลัมน์/บล็อกเดียวกันก็รู้ทันทีว่าเลขนี้ซ้ำแน่นอน ตัดทิ้งได้เลยโดยไม่ต้องลองจริง
- **N-Queens (จะยกตัวอย่างด้านล่าง)** เหมือน **การจัดที่นั่งแขกในงานแต่งงานที่ห้ามให้คนที่ไม่ถูกกันนั่งแถวเดียว/แนวทแยงเดียวกัน** — จัดทีละคนไปเรื่อยๆ พอเจอว่าคนใหม่ที่จะจัดขัดกับคนที่จัดไปแล้ว ก็ต้องย้ายที่คนใหม่หรือถอยไปจัดคนก่อนหน้าใหม่

### เปรียบเทียบ Brute Force vs Backtracking (การตัดกิ่ง)

```
Brute Force: ลองวางราชินีทุกตำแหน่งที่เป็นไปได้ทั้งหมดก่อน (N^N แบบ) แล้วค่อยตรวจสอบทีหลังว่าถูกหรือไม่
             N=8 -> 8^8 = 16,777,216 แบบที่ต้องสร้างและตรวจสอบทั้งหมด

Backtracking: ตรวจสอบทันทีหลังวางราชินีแต่ละตัว ถ้าชนกับตัวก่อนหน้า -> ตัดทิ้งทันที ไม่วางตัวถัดไปเลย
              N=8 -> สำรวจจริงแค่หลักหมื่นแบบเท่านั้น (ตัดกิ่งผิดตั้งแต่เนิ่นๆ)

ยิ่งตัดกิ่งเร็ว (ตรวจสอบเงื่อนไขทันทีหลังตัดสินใจแต่ละขั้น) ยิ่งประหยัดเวลามากขึ้นเท่านั้น
```

### โครงสร้างทั่วไปของ Backtracking

```
function backtrack(สถานะปัจจุบัน):
    if สถานะปัจจุบัน คือคำตอบที่สมบูรณ์:
        บันทึกคำตอบ
        return

    for ทุกตัวเลือกที่เป็นไปได้ในขั้นตอนนี้:
        if ตัวเลือกนี้ valid (ไม่ขัดเงื่อนไข):
            เลือกตัวเลือกนี้                    <- Choose
            backtrack(สถานะใหม่)                 <- Explore (recursive)
            ยกเลิกตัวเลือกนี้                    <- Un-choose (backtrack!)
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== N-Queens — หาคำตอบทั้งหมด =====
def solve_n_queens(n):
    solutions = []
    columns = set()          # คอลัมน์ที่ถูกใช้แล้ว
    diagonals1 = set()       # แนวทแยง "\" ใช้ (row - col) เป็นตัวระบุที่ไม่ซ้ำ
    diagonals2 = set()       # แนวทแยง "/" ใช้ (row + col) เป็นตัวระบุที่ไม่ซ้ำ
    board = []               # เก็บคอลัมน์ที่วางไว้ในแต่ละแถว

    def backtrack(row):
        if row == n:                              # Base Case: วางครบทุกแถวแล้ว = คำตอบสมบูรณ์
            solutions.append(board[:])
            return
        for col in range(n):
            if col in columns or (row - col) in diagonals1 or (row + col) in diagonals2:
                continue                            # Pruning: ตัดทิ้งทันทีถ้าขัดเงื่อนไข ไม่ลองต่อ
            # Choose
            columns.add(col); diagonals1.add(row - col); diagonals2.add(row + col)
            board.append(col)
            # Explore
            backtrack(row + 1)
            # Un-choose (backtrack!)
            columns.remove(col); diagonals1.remove(row - col); diagonals2.remove(row + col)
            board.pop()

    backtrack(0)
    return solutions

# ===== Subsets — หา subset ทั้งหมดของเซตหนึ่ง (Power Set) =====
def subsets(nums):
    result = []
    current = []

    def backtrack(start):
        result.append(current[:])                  # ทุกสถานะระหว่างทางคือคำตอบที่ valid (ไม่ต้องรอถึง base case)
        for i in range(start, len(nums)):
            current.append(nums[i])                 # Choose
            backtrack(i + 1)                          # Explore
            current.pop()                            # Un-choose (backtrack!)

    backtrack(0)
    return result

print(len(solve_n_queens(4)))    # 2 (มี 2 คำตอบสำหรับ N=4)
print(subsets([1, 2, 3]))        # [[], [1], [1,2], [1,2,3], [1,3], [2], [2,3], [3]]
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `solve_n_queens` — ใช้ 3 set (`columns`, `diagonals1`, `diagonals2`) แทนการไล่ตรวจกระดานทั้งหมดทุกครั้ง เพื่อเช็คว่าตำแหน่ง (row, col) ชนกับราชินีตัวก่อนหน้าหรือไม่แบบ **O(1)** — `row - col` คงที่เสมอสำหรับทุกจุดบนแนวทแยง "\" เดียวกัน และ `row + col` คงที่เสมอสำหรับแนวทแยง "/" เดียวกัน (เทคนิคนี้ใช้ hash set จากบทที่ 15 แทนการไล่ตรวจ O(n) ทุกครั้ง)
2. รูปแบบ **Choose → Explore → Un-choose** คือหัวใจของ Backtracking ทุกปัญหา — `columns.add(col)` ฯลฯ คือ Choose (ทำเครื่องหมายว่าเลือกแล้ว), `backtrack(row+1)` คือ Explore (ลองต่อแบบ recursive จากสถานะใหม่), และ `columns.remove(col)` ฯลฯ คือ **Un-choose** ซึ่งเป็นขั้นตอนที่ทำให้เป็น Backtracking จริงๆ — ถ้าลืมขั้นตอนนี้ สถานะจากเส้นทางหนึ่งจะเปื้อนไปยังเส้นทางอื่นที่ยังไม่ได้ลอง (ดู Common Mistakes)
3. `subsets` — ต่างจาก N-Queens ตรงที่ **ทุกสถานะระหว่างทางคือคำตอบที่ valid ได้เลย** ไม่ต้องรอให้ถึง base case ก่อน (`result.append(current[:])` อยู่บรรทัดแรกของฟังก์ชัน ไม่ใช่หลัง `if` เหมือน N-Queens) เพราะ subset ทุกขนาด (รวมถึง subset ว่างเปล่า) ล้วนเป็นคำตอบที่ถูกต้องของปัญหานี้ — สะท้อนว่ารูปแบบ "จุดที่ถือว่าเป็นคำตอบ" ต้องออกแบบให้ตรงกับธรรมชาติของแต่ละปัญหา
4. `current[:]` (ไม่ใช่ `current` ตรงๆ) — ต้องสร้าง**สำเนาใหม่**ของ list ทุกครั้งที่บันทึกผลลัพธ์ เพราะ `current` เป็น object เดียวกันที่ถูกแก้ไขต่อไปเรื่อยๆ ตลอดการ backtrack ถ้าเก็บ reference ตรงๆ (`result.append(current)`) ผลลัพธ์ที่บันทึกไว้ก่อนหน้าทั้งหมดจะถูกแก้ไขตามไปด้วยเมื่อ `current` เปลี่ยนแปลงในภายหลัง

## Time Complexity

| Algorithm | Time Complexity |
|---|---|
| N-Queens (worst case ทางทฤษฎี) | O(N!) — แต่ pruning ลดจำนวนที่สำรวจจริงลงมหาศาล |
| Subsets | O(2^n) — จำนวน subset ทั้งหมดของเซต n สมาชิกมี 2^n แบบเสมอ (ไม่มีทาง pruning ได้เพราะทุก subset คือคำตอบ) |

**ทำไม Backtracking ยังคง exponential ในทางทฤษฎี?** — เพราะ worst case (ปัญหาที่ pruning แทบไม่ช่วยอะไรเลย) ยังต้องสำรวจ State Space Tree เกือบทั้งหมด แต่ **ในทางปฏิบัติ pruning ช่วยลดเวลาจริงลงมหาศาล** เมื่อเทียบกับ Brute Force ที่ไม่ตัดกิ่งเลย (เช่น N-Queens N=8 จาก Brute Force ล้านกว่าแบบ เหลือสำรวจจริงหลักหมื่นแบบเท่านั้น)

## Space Complexity

- N-Queens: **O(N)** — ความลึกของ Call Stack เท่ากับจำนวนแถว (N) บวกกับพื้นที่ของ 3 set ที่ใช้ตรวจสอบ ซึ่งก็เป็น O(N) เช่นกัน
- Subsets: **O(n)** สำหรับ Call Stack ระหว่างทำงาน (ไม่นับพื้นที่เก็บผลลัพธ์ทั้งหมดซึ่งเป็น O(n × 2^n) เพราะมี 2^n subset แต่ละอันยาวได้ถึง n)

## แนวทางปฏิบัติที่ดี (Best Practices)

- ออกแบบเงื่อนไข pruning ให้ตรวจสอบ**เร็วที่สุดเท่าที่จะทำได้** (เช่น ใช้ Hash Set แทนการไล่ตรวจ array) เพราะเงื่อนไขนี้ถูกเรียกซ้ำมหาศาลตลอดการ backtrack — ยิ่งตรวจสอบเร็ว ยิ่งประหยัดเวลารวมมาก
- ใช้รูปแบบ **Choose → Explore → Un-choose** เป็นโครงสร้างมาตรฐานเสมอเมื่อเขียน Backtracking เพื่อไม่ให้ลืมขั้นตอน "คืนสถานะ" ก่อนลองทางเลือกถัดไป
- ตัดกิ่ง (pruning) ให้เร็วที่สุดเท่าที่จะเป็นไปได้ — ตรวจสอบเงื่อนไขทันทีหลังตัดสินใจแต่ละขั้น อย่ารอไปตรวจสอบตอนสร้างคำตอบครบสมบูรณ์แล้ว เพราะจะเสียเวลาสำรวจกิ่งที่ผิดไปแล้วโดยเปล่าประโยชน์

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ลืมขั้นตอน **Un-choose** (เช่น ลืม `columns.remove(col)` หรือ `current.pop()`) ทำให้สถานะจากเส้นทางหนึ่งเปื้อนไปยังเส้นทางอื่นที่ยังไม่ได้ลอง ได้ผลลัพธ์ผิดทั้งหมด
- เก็บ reference ของ mutable object (เช่น `list`) ตรงๆ ลงผลลัพธ์ (`result.append(current)`) แทนการสร้างสำเนา (`result.append(current[:])`) ทำให้ผลลัพธ์ทั้งหมดที่บันทึกไว้ถูกแก้ไขย้อนหลังโดยไม่ตั้งใจ
- ไม่ทำ pruning เลย (ตรวจสอบเงื่อนไขแค่ตอนคำตอบสมบูรณ์แล้ว) ทำให้ Backtracking กลายเป็น Brute Force เต็มรูปแบบโดยไม่รู้ตัว เสียประโยชน์หลักของเทคนิคนี้ไปทั้งหมด
- สับสนระหว่าง Backtracking กับ DP — พยายามใช้ Backtracking กับปัญหาที่มีปัญหาย่อยซ้ำซ้อนกันมาก (overlapping subproblems) โดยไม่มี memoization ทำให้คำนวณซ้ำเหมือนปัญหาของ Fibonacci ธรรมดาในบทที่ 25

## ข้อคิดสำคัญ (Key Takeaways)

- Backtracking คือ DFS ที่ฉลาดขึ้นด้วยการตรวจสอบเงื่อนไขระหว่างทางและตัดกิ่ง (pruning) ทันทีที่รู้ว่าทางนั้นผิดแน่นอน แทนที่จะสำรวจจนสุดเหมือน Brute Force
- รูปแบบ Choose → Explore → Un-choose คือโครงสร้างมาตรฐานของ Backtracking ทุกปัญหา ขั้นตอน Un-choose สำคัญมากเพื่อคืนสถานะก่อนลองทางเลือกอื่น
- แม้ worst case ทางทฤษฎียังคง exponential แต่ pruning ช่วยลดเวลาทำงานจริงลงมหาศาลเมื่อเทียบกับ Brute Force เต็มรูปแบบ
- Backtracking เหมาะกับปัญหาประเภท "หาคำตอบทั้งหมด" หรือ "หาการจัดวางที่ถูกต้อง" ต่างจาก DP/Greedy ที่หา "ค่าที่ดีที่สุด" หนึ่งค่า
- N-Queens และ Subsets แสดงให้เห็นสองรูปแบบของ "จุดที่ถือเป็นคำตอบ" — บางปัญหาต้องรอถึง base case (N-Queens) บางปัญหาทุกสถานะระหว่างทางคือคำตอบได้เลย (Subsets)
- บทถัดไปจะเรียน Sliding Window, Two Pointer, และ Prefix Sum ซึ่งเป็นเทคนิคที่เบากว่าและเร็วกว่า (มักเป็น O(n)) เหมาะกับปัญหาที่มีโครงสร้างเรียบง่ายกว่าที่ Backtracking แก้ ซึ่งเป็นทักษะสำคัญมากสำหรับการสัมภาษณ์งานจริง
