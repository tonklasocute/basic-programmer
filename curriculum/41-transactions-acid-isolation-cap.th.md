# บทที่ 41: Transactions, ACID, Isolation Levels, CAP

## แนวคิดหลัก (Concept)

บทที่แล้วปิดท้ายด้วยการชี้ให้เห็นว่าปัญหา Race Condition (บทที่ 37) เกิดขึ้นในฐานข้อมูลได้เช่นกันเมื่อหลาย query แก้ไขข้อมูลพร้อมกัน บทนี้เป็นบทปิดท้าย **Part 9: Databases** โดยอธิบายเครื่องมือที่ฐานข้อมูลใช้แก้ปัญหานี้อย่างเป็นระบบ — **Transaction** และชุดคุณสมบัติ **ACID** ที่รับประกันความถูกต้องของข้อมูล รวมถึงข้อจำกัดที่หลีกเลี่ยงไม่ได้เมื่อระบบฐานข้อมูลกระจายไปหลายเครื่อง (**CAP Theorem**)

- **Transaction (ธุรกรรม)** — กลุ่มของการกระทำ (เช่น หลายคำสั่ง SQL) ที่ถูกปฏิบัติเป็น**หน่วยเดียวที่แบ่งแยกไม่ได้** ทำสำเร็จทั้งหมดหรือไม่สำเร็จเลยแม้แต่ส่วนเดียว
- **ACID** — ชุดคุณสมบัติ 4 ข้อที่ Transaction ต้องมี: **Atomicity** (ทำครบทุกขั้นตอนหรือไม่ทำเลย), **Consistency** (ข้อมูลต้องถูกต้องตามกฎเสมอทั้งก่อนและหลัง), **Isolation** (Transaction ที่ทำงานพร้อมกันต้องไม่รบกวนกัน), **Durability** (เมื่อ commit สำเร็จแล้ว ข้อมูลต้องคงอยู่ถาวรแม้ไฟดับ)
- **Isolation Levels** — ระดับความเข้มงวดของการแยก Transaction ออกจากกัน มีหลายระดับที่แลก "ความถูกต้อง" กับ "ความเร็ว" ต่างกัน
- **CAP Theorem** — ทฤษฎีที่บอกว่าระบบฐานข้อมูลแบบกระจาย (distributed database) **เลือกได้แค่ 2 ใน 3 อย่างพร้อมกัน**: Consistency (ข้อมูลตรงกันทุกเครื่อง), Availability (ระบบตอบสนองได้เสมอ), Partition Tolerance (ทำงานต่อได้แม้เครือข่ายขาดการเชื่อมต่อบางส่วน)

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Transaction มีไว้ป้องกันข้อมูลอยู่ในสถานะ "ทำไปครึ่งทาง" ที่ไม่สมเหตุสมผล**: การโอนเงินระหว่างบัญชี (ทบทวนจาก Mini Project บทที่ 37) ต้องมีทั้งการหักเงินจากบัญชีหนึ่งและเพิ่มเงินอีกบัญชีหนึ่ง — ถ้าระบบล่มหลังหักเงินแต่ก่อนเพิ่มเงิน (ไม่มี Transaction ป้องกัน) เงินจะ "หายไป" จากระบบทั้งหมด Transaction รับประกันว่าเหตุการณ์แบบนี้ไม่มีทางเกิดขึ้น
- **ACID มีไว้เป็นสัญญาที่ชัดเจนระหว่างฐานข้อมูลกับโปรแกรมเมอร์**: แทนที่จะต้องเขียนโค้ดตรวจสอบความถูกต้องของข้อมูลเองทุกกรณี (เช่น เช็คว่าระบบล่มกลางทางหรือไม่) โปรแกรมเมอร์วางใจได้ว่าฐานข้อมูลที่รองรับ ACID จะจัดการให้ Transaction ทุกตัวเป็นไปตามคุณสมบัติทั้ง 4 ข้อเสมอ
- **Isolation Levels มีไว้ให้เลือก trade-off ตามความต้องการจริง**: การแยก Transaction ให้เข้มงวดที่สุด (เห็นเหมือนทำงานทีละตัว) ปลอดภัยที่สุดแต่**ช้าที่สุด**เพราะต้องล็อกข้อมูลมาก (เชื่อมโยงกับ Mutex บทที่ 36) — บางแอปพลิเคชันยอมรับความเสี่ยงเล็กน้อยเพื่อแลกกับความเร็วที่มากขึ้น
- **CAP Theorem มีไว้อธิบายว่าทำไมฐานข้อมูลแบบกระจายไม่มีทาง "สมบูรณ์แบบ"**: เมื่อข้อมูลกระจายอยู่หลายเครื่อง (เพื่อรองรับผู้ใช้จำนวนมากทั่วโลก) เครือข่ายระหว่างเครื่องมีโอกาสขาดการเชื่อมต่อเสมอ (Partition) — CAP Theorem พิสูจน์ว่าเมื่อเกิด Partition ขึ้นจริง ระบบต้อง**เลือก**ระหว่างตอบสนองแม้ข้อมูลอาจไม่ตรงกัน (Availability) หรือรอจนข้อมูลตรงกันก่อนตอบ (Consistency) เท่านั้น เลือกทั้งคู่พร้อมกันไม่ได้

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Transaction** เหมือน **การจองตั๋วเครื่องบินพร้อมที่นั่งและอาหารในคำสั่งเดียว** — ถ้าจองที่นั่งสำเร็จแต่จองอาหารไม่สำเร็จ (เมนูหมด) ระบบที่ดีจะยกเลิกการจองที่นั่งด้วย ไม่ปล่อยให้อยู่ในสถานะ "จองที่นั่งได้แต่ไม่มีอาหาร" ที่ไม่ตรงกับที่ลูกค้าต้องการ
- **Atomicity** เหมือน **สัญญาซื้อขายที่ต้องเซ็นครบทุกหน้าถึงจะมีผล** — เซ็นแค่บางหน้าไม่มีผลทางกฎหมายเลย ต้องเซ็นครบหรือไม่เซ็นเลย
- **Isolation** เหมือน **ห้องสอบที่กั้นม่านระหว่างผู้เข้าสอบแต่ละคน** — แม้จะสอบพร้อมกันในห้องเดียวกัน (concurrent) แต่ผู้สอบแต่ละคนไม่เห็นกระดาษคำตอบของคนอื่นเลย
- **CAP Theorem** เหมือน **สาขาธนาคารสองแห่งที่สายโทรศัพท์ระหว่างกันขาด (Partition)** — สาขา A จะเลือกอย่างใดอย่างหนึ่ง: หยุดให้บริการจนกว่าจะติดต่อสาขา B ได้เพื่อยืนยันยอดเงินตรงกัน (เลือก Consistency) หรือให้บริการลูกค้าต่อไปโดยใช้ข้อมูลล่าสุดที่มี แม้อาจไม่ตรงกับสาขา B เป๊ะ (เลือก Availability)

## แผนภาพอธิบาย (Visual explanation)

### Atomicity — โอนเงินสำเร็จทั้งหมดหรือย้อนกลับทั้งหมด (ไม่มีสถานะครึ่งๆ กลางๆ)

```
BEGIN TRANSACTION;
  UPDATE Accounts SET balance = balance - 100 WHERE id = 1;   -- หักเงินจาก A
  UPDATE Accounts SET balance = balance + 100 WHERE id = 2;   -- เพิ่มเงินให้ B
COMMIT;                                                        -- ยืนยันทั้งหมดพร้อมกัน

ถ้าระบบล่มระหว่างสองคำสั่ง (หลังหักเงิน A แต่ก่อนเพิ่มเงิน B):

ไม่มี Transaction:                          มี Transaction (Atomicity):
A เสียเงินไปแล้ว, B ไม่ได้รับเลย                 ROLLBACK อัตโนมัติ -> A ได้เงินคืนเหมือนไม่มีอะไรเกิดขึ้น
เงิน 100 บาทหายไปจากระบบทั้งหมด!               ไม่มีทางเกิดสถานะ "หักไปแล้วแต่ยังไม่เพิ่ม" ค้างอยู่เลย
```

### Isolation Levels — ยิ่งเข้มงวด ยิ่งปลอดภัยแต่ยิ่งช้า

```
ระดับ (จากหลวมสุดไปเข้มสุด):

READ UNCOMMITTED  -> เห็นข้อมูลที่ transaction อื่นยังไม่ commit ได้ (Dirty Read - อันตรายที่สุด)
READ COMMITTED    -> เห็นเฉพาะข้อมูลที่ commit แล้วเท่านั้น (แก้ Dirty Read แต่ยังมี Non-Repeatable Read)
REPEATABLE READ   -> อ่านค่าเดิมซ้ำได้ผลเหมือนเดิมเสมอตลอด transaction (แก้ Non-Repeatable Read)
SERIALIZABLE      -> เข้มงวดสุด เสมือนทุก transaction ทำงานทีละตัวเรียงกัน (ปลอดภัยสุดแต่ช้าสุด)

ยิ่งลงล่าง -> ยิ่งล็อกข้อมูลมากขึ้น (เชื่อมโยง Mutex บทที่ 36) -> ยิ่งปลอดภัยแต่ยิ่งรองรับ concurrency ได้น้อยลง
```

### Dirty Read — ปัญหาที่เกิดจาก Isolation ที่หลวมเกินไป

```
Transaction A                          Transaction B

BEGIN
UPDATE balance = 500 (ยังไม่ commit)
                                        BEGIN
                                        SELECT balance -> เห็น 500!  (Dirty Read - อ่านค่าที่ยังไม่ยืนยัน)
ROLLBACK (ยกเลิก! กลับไปเป็น 1000)
                                        ใช้ค่า 500 ไปตัดสินใจต่อ -> ผิดพลาด! เพราะค่าจริงคือ 1000
```

### CAP Theorem — เลือกได้แค่ 2 ใน 3 เมื่อเกิด Network Partition

```
                    Consistency
                        /\
                       /  \
                      /    \
                     / เลือก \
                    /  ไม่ได้  \
                   /  ครบทั้ง 3  \
                  /______________\
        Availability        Partition Tolerance

เมื่อเครือข่ายขาดการเชื่อมต่อจริง (Partition เกิดขึ้นแน่นอนในระบบกระจายจริง):

CP (เลือก Consistency): หยุดตอบสนองจนกว่าข้อมูลจะตรงกัน (เช่น ธนาคาร - ยอมรอ ดีกว่าให้ข้อมูลผิด)
AP (เลือก Availability): ตอบสนองต่อไปด้วยข้อมูลที่มี แม้อาจไม่ตรงกันชั่วคราว (เช่น โซเชียลมีเดีย - ตอบช้าแย่กว่า)
```

## ตัวอย่างโค้ด (Code example)

```sql
-- ===== Transaction พื้นฐาน: โอนเงินระหว่างบัญชี =====
BEGIN TRANSACTION;
    UPDATE Accounts SET balance = balance - 100 WHERE id = 1;
    UPDATE Accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                          -- ยืนยันทั้งสองคำสั่งพร้อมกัน (Atomicity)

-- ===== ROLLBACK เมื่อเงื่อนไขไม่ผ่าน =====
BEGIN TRANSACTION;
    UPDATE Accounts SET balance = balance - 100 WHERE id = 1;

    -- ตรวจสอบว่ายอดเงินติดลบหรือไม่ (Consistency: ห้ามยอดเงินติดลบ)
    -- ถ้าติดลบ:
    ROLLBACK;                      -- ยกเลิกทั้งหมด กลับไปสถานะก่อน BEGIN TRANSACTION ทันที
    -- ถ้าไม่ติดลบ:
    -- UPDATE Accounts SET balance = balance + 100 WHERE id = 2;
    -- COMMIT;

-- ===== ตั้งค่า Isolation Level =====
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;      -- ระดับที่นิยมใช้เป็นค่าเริ่มต้นในหลายฐานข้อมูล
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;        -- เข้มงวดสุด ใช้เมื่อความถูกต้องสำคัญกว่าความเร็วมาก

-- ===== ตัวอย่าง Non-Repeatable Read (ปัญหาที่ SERIALIZABLE ป้องกันได้) =====
-- Transaction A:
BEGIN;
SELECT balance FROM Accounts WHERE id = 1;    -- ได้ 1000
-- (ระหว่างนี้ Transaction B แก้ไขและ commit ค่าเป็น 500)
SELECT balance FROM Accounts WHERE id = 1;    -- ได้ 500!  ค่าเปลี่ยนกลางทาง (Non-Repeatable Read)
COMMIT;
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `BEGIN TRANSACTION` — เริ่มต้นกลุ่มคำสั่งที่จะถูกปฏิบัติเป็นหน่วยเดียว ฐานข้อมูลจะ**ไม่ยืนยันการเปลี่ยนแปลงใดๆ ให้ transaction อื่นเห็นถาวร** จนกว่าจะเจอ `COMMIT` — ถ้าเกิดปัญหาระหว่างทาง (ระบบล่ม, เงื่อนไขไม่ผ่าน) สามารถเรียก `ROLLBACK` เพื่อยกเลิกทุกการเปลี่ยนแปลงที่ทำไปตั้งแต่ `BEGIN TRANSACTION` กลับสู่สถานะเดิมทุกประการ
2. `COMMIT` — ยืนยันว่าทุกคำสั่งภายใน transaction สำเร็จและถูกต้องตามกฎ (Consistency) ทั้งหมด ฐานข้อมูลจะบันทึกการเปลี่ยนแปลงลง disk อย่างถาวร (**Durability** — แม้ไฟดับทันทีหลัง `COMMIT` สำเร็จ ข้อมูลก็จะไม่หายเพราะถูกเขียนลง disk แล้ว) และเปิดให้ transaction อื่นเห็นข้อมูลใหม่นี้ได้
3. `ROLLBACK` — ยกเลิกทุกการเปลี่ยนแปลงที่เกิดขึ้นตั้งแต่ `BEGIN TRANSACTION` ราวกับไม่มีอะไรเกิดขึ้นเลย — นี่คือกลไกที่ทำให้ **Atomicity** เป็นจริง: ถ้าคำสั่งที่สองในกลุ่ม (`UPDATE ... id = 2`) ไม่สามารถทำได้ (เช่น ยอดเงินจะติดลบ) โปรแกรมสามารถเรียก `ROLLBACK` เพื่อยกเลิกคำสั่งแรกที่ทำไปแล้วด้วย (`UPDATE ... id = 1`) ทำให้ไม่มีทางเกิดสถานะ "หักเงินไปแล้วแต่ไม่ได้เพิ่มให้อีกฝั่ง" ค้างอยู่
4. Non-Repeatable Read ในตัวอย่างสุดท้าย — เกิดขึ้นเพราะ **Isolation Level ที่ไม่เข้มงวดพอ** (ต่ำกว่า `REPEATABLE READ`) อนุญาตให้ Transaction A เห็นการเปลี่ยนแปลงที่ Transaction B commit ไปแล้ว**ระหว่างที่ A ยังทำงานอยู่** ทำให้ `SELECT` คำสั่งเดียวกันในทรานแซคชันเดียวกันให้ผลลัพธ์ต่างกันสองครั้ง — ถ้าตั้ง Isolation Level เป็น `REPEATABLE READ` หรือสูงกว่า Transaction A จะยังคงเห็นค่า 1000 ในทั้งสอง `SELECT` เสมอ (ฐานข้อมูลจะ "ล็อก" มุมมองข้อมูลไว้ตั้งแต่เริ่ม transaction)

## Time Complexity

Transaction และ ACID เป็นเรื่องของ**ความถูกต้องของข้อมูล (correctness)** เช่นเดียวกับ Race Condition/Deadlock ในบทที่ 37 ไม่ใช่ Big O ของอัลกอริทึม แต่มีผลกระทบเชิงประสิทธิภาพที่วัดได้ทางอ้อม:
- Isolation Level ที่เข้มงวดกว่า (เช่น `SERIALIZABLE`) ต้องการการล็อกข้อมูลมากกว่า ทำให้ transaction อื่นที่ต้องการเข้าถึงข้อมูลเดียวกัน**รอคิวนานขึ้น** (คล้าย Critical Section ที่ใหญ่เกินไปในบทที่ 36) — throughput ของระบบโดยรวมลดลงเมื่อ Isolation เข้มงวดขึ้น

## Space Complexity

- ฐานข้อมูลต้องเก็บ **transaction log** (บันทึกการเปลี่ยนแปลงทุกขั้นตอนก่อน commit จริง) เพื่อรองรับ Durability และ Atomicity ใช้พื้นที่เพิ่มเติมตามจำนวนและขนาดของ transaction ที่กำลังทำงานอยู่

## แนวทางปฏิบัติที่ดี (Best Practices)

- ทำ transaction ให้**สั้นและเร็วที่สุดเท่าที่จำเป็น** (เหมือนหลักการทำ Critical Section ให้เล็กในบทที่ 36) เพื่อลดเวลาที่ข้อมูลถูกล็อกและปล่อยให้ transaction อื่นทำงานต่อได้เร็ว
- เลือก Isolation Level ให้เหมาะกับความต้องการจริง: ใช้ `READ COMMITTED` (ค่าเริ่มต้นทั่วไป) สำหรับงานส่วนใหญ่ ใช้ `SERIALIZABLE` เฉพาะเมื่อความถูกต้องสัมบูรณ์สำคัญมาก (เช่น ระบบการเงิน) เพราะมันช้ากว่ามาก
- เมื่อออกแบบระบบแบบกระจาย (distributed system) ให้ตัดสินใจล่วงหน้าว่าจะเลือก **CP** (สอดคล้องกับข้อมูลทางการเงินที่ต้องแม่นยำ) หรือ **AP** (สอดคล้องกับระบบที่ต้องตอบสนองเสมอ เช่น โซเชียลมีเดีย) ตามลักษณะของแอปพลิเคชันจริง ไม่ใช่พยายามเอาทั้งสองอย่างพร้อมกัน

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ลืม `COMMIT` หรือ `ROLLBACK` ทำให้ transaction ค้างอยู่นาน (ล็อกข้อมูลไว้โดยไม่จำเป็น) ส่งผลให้ transaction อื่นรอคิวนานเกินควร
- เขียนคำสั่งหลายคำสั่งที่ควรอยู่ใน transaction เดียวกันแยกกันโดยไม่มี `BEGIN TRANSACTION`/`COMMIT` ครอบ ทำให้เสี่ยงเกิดสถานะ "ทำไปครึ่งทาง" เมื่อระบบล่มกลางทาง (เหมือนตัวอย่างการโอนเงินที่ไม่มี Atomicity)
- ใช้ Isolation Level ต่ำเกินไป (`READ UNCOMMITTED`) ในระบบที่ต้องการความถูกต้องสูง ทำให้เกิด Dirty Read ที่นำไปสู่การตัดสินใจผิดพลาดจากข้อมูลที่ยังไม่ยืนยันจริง
- คิดว่าระบบแบบกระจายสามารถมี Consistency, Availability, และ Partition Tolerance ครบทั้ง 3 อย่างพร้อมกันได้ ทั้งที่ CAP Theorem พิสูจน์แล้วว่าเป็นไปไม่ได้เมื่อเกิด Partition จริง

## คำถามสัมภาษณ์งาน (Interview Questions)

1. อธิบาย ACID ทั้ง 4 ข้อ พร้อมยกตัวอย่างสถานการณ์ที่แสดงให้เห็นว่าแต่ละข้อสำคัญอย่างไร
2. Dirty Read, Non-Repeatable Read คืออะไร แต่ละปัญหาป้องกันได้ด้วย Isolation Level ระดับไหน
3. อธิบาย CAP Theorem พร้อมยกตัวอย่างระบบจริงที่เลือก CP และระบบที่เลือก AP
4. ทำไม Isolation Level ที่เข้มงวดกว่าถึงทำให้ระบบช้าลง? เชื่อมโยงกับหลักการ Mutex/Critical Section จากบทที่ 36
5. Transaction แก้ปัญหาอะไรที่การรันคำสั่ง SQL แยกกันทีละคำสั่งแก้ไม่ได้

## แบบฝึกหัด (Practice Exercises)

1. เขียน SQL จำลองการโอนเงินที่ใช้ `BEGIN TRANSACTION`/`ROLLBACK` เพื่อป้องกันไม่ให้ยอดเงินติดลบ (เช็คเงื่อนไขก่อน `COMMIT` ถ้าไม่ผ่านให้ `ROLLBACK` ทันที)
2. จำลอง Dirty Read ด้วยสอง connection ไปยังฐานข้อมูลเดียวกัน (หนึ่งตั้ง Isolation Level เป็น `READ UNCOMMITTED`) แล้วสังเกตว่าเห็นข้อมูลที่ยังไม่ commit ได้จริงหรือไม่
3. เปรียบเทียบเวลาที่ใช้ทำ transaction จำนวนมากพร้อมกัน (concurrent) ภายใต้ Isolation Level ต่างกัน (`READ COMMITTED` vs `SERIALIZABLE`) แล้ววัดผลต่างของ throughput

## Mini Project

**"ระบบจำลองการโอนเงินที่ปลอดภัยระดับธนาคาร (Bank-Grade Transfer Simulation)"**: เขียนโปรแกรมที่:
1. สร้างฐานข้อมูลจำลองบัญชีธนาคารหลายบัญชี พร้อมฟังก์ชันโอนเงินที่ใช้ Transaction ครอบคลุมทั้งการหักและเพิ่มเงิน (Atomicity) พร้อมตรวจสอบยอดเงินไม่ติดลบ (Consistency)
2. จำลองสถานการณ์ระบบล่มกลางทาง (เช่น จงใจโยน exception หลังหักเงินแต่ก่อนเพิ่มเงิน) แล้วพิสูจน์ว่า `ROLLBACK` ทำให้ยอดเงินกลับสู่สถานะถูกต้องเสมอ
3. ทดสอบหลาย transaction พร้อมกันภายใต้ Isolation Level ต่างกัน แล้วบันทึกว่าเกิด Dirty Read หรือ Non-Repeatable Read ในระดับไหนบ้าง
4. เขียนรายงานเปรียบเทียบว่าถ้าออกแบบระบบนี้เป็นแบบกระจาย (หลายเซิร์ฟเวอร์ในหลายประเทศ) ควรเลือก CP หรือ AP ตาม CAP Theorem พร้อมให้เหตุผลจากลักษณะของระบบธนาคารที่ต้องการความถูกต้องของยอดเงินสูงสุด

## ข้อคิดสำคัญ (Key Takeaways)

- Transaction รวมหลายคำสั่งเป็นหน่วยเดียวที่ทำครบทั้งหมดหรือไม่ทำเลย ป้องกันข้อมูลอยู่ในสถานะ "ทำไปครึ่งทาง" ที่ไม่สมเหตุสมผล
- ACID (Atomicity, Consistency, Isolation, Durability) คือสัญญา 4 ข้อที่ฐานข้อมูลให้ไว้เพื่อรับประกันความถูกต้องของ Transaction
- Isolation Levels ให้เลือก trade-off ระหว่างความถูกต้อง (ป้องกัน Dirty Read, Non-Repeatable Read) กับความเร็ว — ยิ่งเข้มงวดยิ่งปลอดภัยแต่ยิ่งช้า เชื่อมโยงกับหลักการ Critical Section จากบทที่ 36
- CAP Theorem พิสูจน์ว่าระบบฐานข้อมูลแบบกระจายเลือกได้แค่ 2 ใน 3 ระหว่าง Consistency, Availability, Partition Tolerance เมื่อเกิด Network Partition จริง
- ปัญหาความถูกต้องของข้อมูลในฐานข้อมูล (Race Condition ระดับ Transaction) เป็นปัญหาแบบเดียวกับที่เรียนใน Part 8: Concurrency เพียงเกิดในบริบทที่ต่างกัน
- นี่คือบทปิดท้าย **Part 9: Databases** — บทถัดไปจะเข้าสู่ **Part 10: Networking** ซึ่งอธิบายว่าข้อมูลเดินทางจากเครื่องหนึ่งไปอีกเครื่องหนึ่งผ่านอินเทอร์เน็ตได้อย่างไร โดยเริ่มจาก TCP/IP, DNS, HTTP/HTTPS, SSL/TLS
