# บทที่ 53: Encryption, Hashing

## แนวคิดหลัก (Concept)

บทที่แล้วทิ้งท้ายด้วยคำถาม: JWT signature และการเก็บรหัสผ่านอย่างปลอดภัยทำงานได้อย่างไรในทางคณิตศาสตร์? บทนี้เจาะลึกสองเทคนิคพื้นฐานที่เป็นรากฐานของความปลอดภัยเกือบทุกระบบ — **Encryption** (การเข้ารหัสที่ถอดรหัสกลับได้) และ **Hashing** (การแปลงข้อมูลที่ถอดกลับไม่ได้) ซึ่งมักถูกสับสนกันบ่อย ทั้งที่ใช้แก้ปัญหาคนละแบบโดยสิ้นเชิง

- **Encryption (การเข้ารหัส)** — แปลงข้อมูลต้นฉบับ (plaintext) ให้เป็นข้อมูลที่อ่านไม่ออก (ciphertext) โดย**ถอดรหัสกลับเป็นต้นฉบับได้เสมอ**ถ้ามีกุญแจที่ถูกต้อง แบ่งเป็น **Symmetric Encryption** (ใช้กุญแจเดียวกันทั้งเข้ารหัสและถอดรหัส) และ **Asymmetric Encryption** (ใช้กุญแจคู่: Public Key เข้ารหัส, Private Key ถอดรหัส — ที่ SSL/TLS บทที่ 42 ใช้จริง)
- **Hashing (การแฮช)** — แปลงข้อมูลใดๆ ให้เป็นค่าที่มีความยาวคงที่ (hash/digest) โดย**ไม่มีทางถอดกลับเป็นต้นฉบับได้เลย** (One-way function) ต่างจาก Encryption อย่างสิ้นเชิง — เชื่อมโยงกับ Hash Table จากบทที่ 15 ที่ใช้หลักการเดียวกันแต่เป้าหมายต่างกัน (ที่นั่นใช้เพื่อความเร็ว ที่นี่ใช้เพื่อความปลอดภัย)
- **Salt (เกลือ)** — ค่าสุ่มที่เพิ่มเข้าไปก่อน hash รหัสผ่าน เพื่อป้องกันการโจมตีแบบ **Rainbow Table** (ตารางคำตอบ hash ที่เตรียมไว้ล่วงหน้า)

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Encryption มีไว้ปกป้องข้อมูลที่ต้อง "อ่านกลับได้" ในภายหลัง**: ข้อมูลอย่างเบอร์บัตรเครดิตหรือข้อความส่วนตัวต้องถูกอ่านออกมาใช้งานจริงในบางจุด (เช่น ตอนเรียกเก็บเงิน) — Encryption ทำให้ข้อมูลปลอดภัยระหว่างการเก็บ/ส่ง แต่ยังคงกู้กลับมาใช้งานได้เมื่อจำเป็น
- **Hashing มีไว้สำหรับข้อมูลที่ "ไม่ต้องอ่านกลับ" แต่ต้อง "ตรวจสอบว่าตรงกันหรือไม่"**: รหัสผ่านเป็นตัวอย่างที่ชัดเจนที่สุด — ระบบไม่จำเป็นต้องรู้ว่ารหัสผ่านจริงของผู้ใช้คืออะไร แค่ต้องตรวจสอบว่ารหัสผ่านที่กรอกเข้ามา "ตรงกับที่ตั้งไว้หรือไม่" ถ้าเก็บรหัสผ่านด้วย Encryption (ถอดกลับได้) แล้วฐานข้อมูลรั่วไหล ผู้โจมตีจะได้รหัสผ่านจริงของทุกคนทันที แต่ถ้าเก็บด้วย Hash (ถอดกลับไม่ได้) แม้ฐานข้อมูลรั่วก็ยังไม่มีทางรู้รหัสผ่านจริง
- **Salt มีไว้ป้องกันจุดอ่อนของ Hash ธรรมดา**: Hash function เดียวกันให้ผลลัพธ์เดียวกันเสมอสำหรับ input เดียวกัน (deterministic — เชื่อมโยงกับ Pure Function บทที่ 34) ทำให้ผู้โจมตีสร้างตาราง hash ของรหัสผ่านยอดนิยมไว้ล่วงหน้าได้ (Rainbow Table) แล้วเทียบหา match ได้ทันทีโดยไม่ต้องคำนวณใหม่ — Salt ที่สุ่มไม่ซ้ำกันในแต่ละผู้ใช้ทำให้ผลลัพธ์ hash ต่างกันแม้รหัสผ่านจะเหมือนกันทุกประการ ทำลายประโยชน์ของ Rainbow Table ที่เตรียมไว้ล่วงหน้าไปเลย

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Encryption** เหมือน **กล่องเซฟที่ล็อกด้วยกุญแจ** — ใส่ของมีค่าเข้าไป (เข้ารหัส) แล้วเปิดออกมาดูของเดิมได้เสมอถ้ามีกุญแจที่ถูกต้อง (ถอดรหัส)
- **Hashing** เหมือน **เครื่องปั่นผลไม้ที่ปั่นแอปเปิ้ลให้กลายเป็นน้ำผลไม้** — ไม่มีทางเอาน้ำผลไม้กลับมาเป็นแอปเปิ้ลลูกเดิมได้อีกเลย แต่ถ้าใครเอาแอปเปิ้ลลูกเดียวกันมาปั่นซ้ำ จะได้น้ำผลไม้ที่มีลักษณะเหมือนเดิมเป๊ะ (ใช้เทียบว่า "แอปเปิ้ลลูกนี้เหมือนลูกเดิมหรือไม่" โดยไม่ต้องเก็บแอปเปิ้ลลูกจริงไว้เลย)
- **Symmetric vs Asymmetric Encryption** เหมือน **กุญแจบ้านที่มีดอกเดียวใช้ได้ทั้งล็อกและปลดล็อก (Symmetric) เทียบกับตู้ไปรษณีย์ที่ใครก็ใส่จดหมายเข้าได้ (กุญแจสาธารณะ) แต่เปิดอ่านได้แค่เจ้าของที่มีกุญแจส่วนตัว (Asymmetric)**
- **Salt** เหมือน **การเติมเครื่องปรุงลับเฉพาะตัวก่อนใส่ในเครื่องปั่น** — แม้สองคนใช้วัตถุดิบตั้งต้นเหมือนกัน (รหัสผ่านเดียวกัน) แต่ถ้าเติมเครื่องปรุงคนละแบบ (salt คนละค่า) ผลลัพธ์ที่ปั่นออกมาจะต่างกันโดยสิ้นเชิง ทำให้ใครก็ตามที่มีตารางผลลัพธ์เตรียมไว้ล่วงหน้าใช้ไม่ได้ผลอีกต่อไป

## แผนภาพอธิบาย (Visual explanation)

### Encryption vs Hashing — ความต่างที่สำคัญที่สุด

```
Encryption (ถอดรหัสกลับได้เสมอ):              Hashing (ถอดกลับไม่ได้เด็ดขาด):

"Hello World"                                "Hello World"
      │ เข้ารหัสด้วย key                              │ hash (SHA-256)
      v                                              v
"U2FsdGVkX1..."  <── ถอดรหัสกลับด้วย key ──   "a591a6d40bf420..."  ✗ ไม่มีทางย้อนกลับได้เลย
      │                                              │
      v                                              v
"Hello World"  (ได้ต้นฉบับกลับมาแน่นอน)          (จบแค่นี้ ไม่มีฟังก์ชัน "decrypt" สำหรับ hash)

ใช้กับ: ข้อมูลที่ต้องอ่านกลับ (บัตรเครดิต, ข้อความส่วนตัว)  ใช้กับ: รหัสผ่าน, ตรวจสอบความถูกต้องของไฟล์
```

### Symmetric vs Asymmetric Encryption

```
Symmetric Encryption:                        Asymmetric Encryption:

     [Secret Key เดียวกัน]                        Public Key (แจกได้ทุกคน)      Private Key (เก็บเป็นความลับ)
    /                    \                              │                              │
Encrypt                Decrypt                       Encrypt                        Decrypt
(ผู้ส่ง)                (ผู้รับ)                       (ใครก็เข้ารหัสได้)                (เจ้าของเท่านั้นถอดได้)

เร็วกว่า แต่ต้องแชร์ key ล่วงหน้า              ช้ากว่า แต่ไม่ต้องแชร์ key ลับเลย
                                             (นี่คือหลักการที่ SSL/TLS บทที่ 42 ใช้ตอน Handshake)
```

### Salt ป้องกัน Rainbow Table Attack

```
ไม่มี Salt (อันตราย!):                         มี Salt (ปลอดภัย):

hash("password123") = "ef92b778..."          salt_alice = "x7k2"
hash("password123") = "ef92b778..."          hash("x7k2" + "password123") = "9a8f3e1c..."
   (ผลลัพธ์เดียวกันเสมอ!)
                                              salt_bob = "m4p9"
ผู้โจมตีเตรียม Rainbow Table ไว้ล่วงหน้า:        hash("m4p9" + "password123") = "5d2c7b0a..."
"ef92b778..." -> "password123"  (เปิดตาราง)
                                                 (Alice กับ Bob รหัสผ่านเดียวกัน แต่ hash ต่างกันสิ้นเชิง!
เจอ match ทันที ไม่ต้องคำนวณอะไรเลย                Rainbow Table ที่เตรียมไว้ใช้ไม่ได้ผลอีกต่อไป)
```

## ตัวอย่างโค้ด (Code example)

```python
import hashlib
import bcrypt                                            # pip install bcrypt (ออกแบบมาเพื่อ hash รหัสผ่านโดยเฉพาะ)
from cryptography.fernet import Fernet                     # pip install cryptography (Symmetric Encryption)

# ===== Hashing: ใช้ SHA-256 ตรวจสอบความถูกต้องของไฟล์ (Integrity Check) =====
def calculate_file_hash(content):
    return hashlib.sha256(content.encode()).hexdigest()      # ผลลัพธ์ยาวคงที่ 64 ตัวอักษรเสมอ ไม่ว่า input จะยาวแค่ไหน

original_hash = calculate_file_hash("Important document content")
tampered_hash = calculate_file_hash("Important document content!")  # เปลี่ยนแค่ตัวอักษรเดียว
print(original_hash)   # a591a6d40bf420...
print(tampered_hash)    # ค่าต่างไปโดยสิ้นเชิง (Avalanche Effect) -> ตรวจจับการแก้ไขได้ทันที
print(original_hash == tampered_hash)   # False

# ===== Hashing รหัสผ่านที่ถูกต้อง: ใช้ bcrypt (มี Salt ในตัวอัตโนมัติ) =====
def hash_password(plain_password):
    salt = bcrypt.gensalt()                                    # สุ่ม salt ใหม่ทุกครั้ง (ไม่ซ้ำกันเลยแม้รหัสผ่านเดียวกัน)
    return bcrypt.hashpw(plain_password.encode(), salt)

def verify_password(plain_password, hashed_password):
    return bcrypt.checkpw(plain_password.encode(), hashed_password)   # เทียบโดยไม่ต้อง "ถอดรหัส" กลับมาเลย

stored_hash = hash_password("MySecureP@ss123")
print(verify_password("MySecureP@ss123", stored_hash))      # True -- รหัสผ่านถูกต้อง
print(verify_password("WrongPassword", stored_hash))          # False -- ไม่มีทางถอด stored_hash กลับเป็นรหัสจริงได้เลย

# ===== Encryption: Symmetric Encryption ที่ถอดรหัสกลับได้ =====
key = Fernet.generate_key()                                   # สร้าง secret key (ต้องเก็บไว้อย่างปลอดภัย)
cipher = Fernet(key)

credit_card = "4111-1111-1111-1111"
encrypted = cipher.encrypt(credit_card.encode())
print(encrypted)                                                 # b'gAAAAABm...' -- อ่านไม่ออกเลย

decrypted = cipher.decrypt(encrypted).decode()
print(decrypted)                                                  # "4111-1111-1111-1111" -- ได้ต้นฉบับกลับมาแน่นอน
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `calculate_file_hash(content)` — `hashlib.sha256(...)` แปลงข้อความที่ยาวเท่าไหร่ก็ได้ให้เป็นค่า hash ที่มี**ความยาวคงที่เสมอ** (256 บิต, 64 ตัวอักษรในรูป hex) — เมื่อเปลี่ยน input แม้แค่ตัวอักษรเดียว (`content` -> `content!`) ค่า hash ที่ได้**เปลี่ยนไปโดยสิ้นเชิง** (เรียกว่า **Avalanche Effect**) ทำให้ใช้ตรวจสอบว่าไฟล์ถูกแก้ไขระหว่างทางหรือไม่ได้อย่างแม่นยำ (เช่น ตรวจสอบว่าไฟล์ที่ดาวน์โหลดมาตรงกับต้นฉบับหรือไม่)
2. `hash_password(plain_password)` — `bcrypt.gensalt()` สุ่ม salt ใหม่**ทุกครั้งที่เรียก** แม้จะ hash รหัสผ่านเดียวกันซ้ำสองครั้งก็จะได้ผลลัพธ์ต่างกัน (เพราะ salt ต่างกัน) — `bcrypt.hashpw(...)` รวม salt เข้ากับรหัสผ่านก่อน hash และ**เก็บ salt ไว้เป็นส่วนหนึ่งของผลลัพธ์ที่คืนมาด้วย** (ไม่ต้องเก็บ salt แยกต่างหาก) ทำให้ `verify_password` ดึง salt เดิมออกมาใช้ตรวจสอบได้ถูกต้องในภายหลัง
3. `verify_password(plain_password, hashed_password)` — `bcrypt.checkpw(...)` **ไม่ได้ "ถอดรหัส" `hashed_password` กลับเป็นรหัสผ่านจริงเลย** (เป็นไปไม่ได้ตามธรรมชาติของ Hash function) แต่ทำสิ่งที่ตรงกันข้าม: **hash `plain_password` ที่ผู้ใช้กรอกเข้ามาด้วย salt เดิมที่ฝังอยู่ใน `hashed_password`** แล้วเทียบว่าผลลัพธ์ตรงกันหรือไม่ — นี่คือวิธีที่ระบบยืนยันรหัสผ่านได้โดยไม่เคยรู้รหัสผ่านจริงเลยสักครั้งหลังจากตอนสมัครสมาชิก
4. `Fernet.generate_key()` และ `cipher.encrypt()/decrypt()` — ต่างจาก bcrypt โดยสิ้นเชิง เพราะ `Fernet` เป็น **Symmetric Encryption** ที่ **ถอดรหัสกลับได้เสมอ** ถ้ามี `key` ที่ถูกต้อง — เหมาะกับข้อมูลอย่างเลขบัตรเครดิตที่ระบบจำเป็นต้อง**อ่านค่าจริงกลับมาใช้งาน**ในภายหลัง (เช่น ตอนเรียกเก็บเงินจริง) ซึ่งเป็นสิ่งที่ Hashing ทำไม่ได้เลยตามธรรมชาติของมัน

## Time Complexity

- **Hashing (SHA-256)**: **O(n)** โดย n คือความยาวของข้อมูล input — คำนวณครั้งเดียวจบ เร็วมาก
- **bcrypt**: ถูกออกแบบมาให้**ช้ากว่า SHA-256 โดยเจตนา** (ปรับ "cost factor" ได้) เพื่อทำให้การลองสุ่มรหัสผ่านจำนวนมาก (Brute Force) ใช้เวลานานเกินคุ้มค่าสำหรับผู้โจมตี แม้จะช้าลงเล็กน้อยสำหรับผู้ใช้จริงที่ล็อกอินแค่ครั้งเดียว
- **Symmetric Encryption**: **O(n)** เร็วกว่า Asymmetric มาก เพราะใช้การคำนวณที่เบากว่า
- **Asymmetric Encryption**: ช้ากว่า Symmetric มาก (การคำนวณทางคณิตศาสตร์ซับซ้อนกว่า เช่น RSA ใช้เลขจำนวนเฉพาะขนาดใหญ่) — เหตุผลที่ SSL/TLS (บทที่ 42) ใช้ Asymmetric แค่ตอน Handshake เพื่อแลกกุญแจ Symmetric ที่ใช้เข้ารหัสข้อมูลจริงต่อไป (ผสมสองแบบเข้าด้วยกันเพื่อความเร็วและความปลอดภัย)

## Space Complexity

- Hash output มีขนาด**คงที่เสมอ** (เช่น SHA-256 ให้ผลลัพธ์ 256 บิตเสมอ ไม่ว่า input จะเป็นไฟล์ 1 KB หรือ 1 GB)
- Encrypted output มีขนาด**ใกล้เคียงกับ input เดิม** (บวก overhead เล็กน้อยจาก IV/padding ที่ใช้ในกระบวนการเข้ารหัส)

## แนวทางปฏิบัติที่ดี (Best Practices)

- ใช้ **bcrypt, scrypt, หรือ Argon2** สำหรับ hash รหัสผ่านเสมอ (ไม่ใช่ SHA-256/MD5 ตรงๆ) เพราะถูกออกแบบมาให้ช้าโดยเจตนาเพื่อต้านทาน Brute Force และมี Salt ในตัวอัตโนมัติ
- ใช้ SHA-256 (หรือรุ่นใหม่กว่า) สำหรับ **ตรวจสอบความถูกต้องของข้อมูล** (Integrity Check) เช่น ตรวจว่าไฟล์ดาวน์โหลดมาไม่ถูกแก้ไข — ไม่ใช่สำหรับ hash รหัสผ่าน (เร็วเกินไปสำหรับจุดประสงค์นั้น)
- เก็บ key ของ Encryption ไว้อย่างปลอดภัยเสมอ (ไม่ hardcode ในโค้ด, ไม่ commit ลง Git) เพราะถ้า key รั่วไหล ข้อมูลที่เข้ารหัสไว้ทั้งหมดจะถูกถอดรหัสได้ทันที (ต่างจาก Hash ที่แม้ algorithm รู้กันทั่วไปก็ยังปลอดภัยถ้ามี salt ที่ดี)

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- เก็บรหัสผ่านด้วย Encryption แทน Hashing เพราะเข้าใจผิดว่า "ปลอดภัยเหมือนกัน" — ถ้าฐานข้อมูลรั่วไหลและ key ของ Encryption ก็รั่วไหลไปด้วย (มักเก็บไว้ใกล้กัน) ผู้โจมตีจะถอดรหัสผ่านจริงของทุกคนได้ทันที ต่างจาก Hash ที่ถอดกลับไม่ได้เลยไม่ว่ากรณีใด
- ใช้ Hash function ธรรมดา (MD5, SHA-1) โดยไม่มี Salt สำหรับรหัสผ่าน ทำให้เสี่ยงต่อ Rainbow Table Attack อย่างมาก
- ใช้ Salt เดียวกันสำหรับทุกผู้ใช้ (Global Salt) แทนที่จะสุ่มใหม่ทุกครั้งต่อผู้ใช้ ทำให้ผู้โจมตียังคงสร้าง Rainbow Table เฉพาะสำหรับ salt นั้นได้ (แม้จะยากกว่าไม่มี salt เลยก็ตาม)
- ใช้ MD5/SHA-1 สำหรับความปลอดภัยที่สำคัญ (แม้จะเร็วดี) โดยไม่รู้ว่าทั้งสอง algorithm นี้ถูกพิสูจน์แล้วว่ามีจุดอ่อนที่ทำให้เกิด Hash Collision ได้ง่ายกว่าที่ควรจะเป็น

## คำถามสัมภาษณ์งาน (Interview Questions)

1. อธิบายความแตกต่างระหว่าง Encryption และ Hashing พร้อมยกตัวอย่างสถานการณ์ที่เหมาะกับแต่ละแบบ
2. ทำไมถึงไม่ควรเก็บรหัสผ่านด้วย Encryption แม้จะดูปลอดภัยกว่าเก็บเป็น plain text
3. Salt คืออะไร ป้องกันการโจมตีแบบไหน ทำงานอย่างไร
4. Symmetric Encryption ต่างจาก Asymmetric Encryption อย่างไร แต่ละแบบมีข้อดี-ข้อเสียอะไรบ้าง
5. ทำไม bcrypt ถึงเหมาะกับการ hash รหัสผ่านมากกว่า SHA-256 ทั้งที่ SHA-256 ดูปลอดภัยกว่าในแง่ความยาวของ output

## แบบฝึกหัด (Practice Exercises)

1. เขียนโปรแกรมเปรียบเทียบเวลาที่ใช้ hash รหัสผ่านเดียวกันด้วย SHA-256 กับ bcrypt แล้ววิเคราะห์ว่าทำไม bcrypt ถึงช้ากว่ามากทั้งที่ดูเหมือนทำงานคล้ายกัน
2. เขียนระบบตรวจสอบความถูกต้องของไฟล์ (File Integrity Checker) ที่คำนวณ SHA-256 hash ของไฟล์ก่อนและหลังการดาวน์โหลดจำลอง แล้วแจ้งเตือนถ้า hash ไม่ตรงกัน
3. เขียนโปรแกรมที่เข้ารหัสข้อความด้วย Symmetric Encryption (Fernet) แล้วจงใจเปลี่ยน key ก่อนถอดรหัส พิสูจน์ว่าถอดรหัสไม่สำเร็จเมื่อ key ไม่ตรงกัน

## Mini Project

**"ระบบจัดเก็บข้อมูลผู้ใช้ที่ปลอดภัย (Secure User Data Vault)"**: เขียนโปรแกรมที่:
1. สร้างระบบสมัครสมาชิกที่ hash รหัสผ่านด้วย bcrypt (พร้อม Salt อัตโนมัติ) ก่อนบันทึกลงฐานข้อมูลจำลอง
2. เข้ารหัสข้อมูลละเอียดอ่อนอื่น (เช่น เลขบัตรประชาชนจำลอง) ด้วย Symmetric Encryption แยกจากรหัสผ่าน โดยเก็บ encryption key ไว้แยกต่างหากอย่างปลอดภัย (ไม่ปนกับข้อมูลที่เข้ารหัส)
3. สร้างระบบตรวจสอบความถูกต้องของ backup ไฟล์ด้วย SHA-256 hash ก่อนและหลังการสำรองข้อมูล เพื่อยืนยันว่าข้อมูลไม่เสียหายระหว่างทาง
4. เขียนรายงานเปรียบเทียบว่าถ้าฐานข้อมูลทั้งหมดรั่วไหล ผู้โจมตีจะได้อะไรบ้าง (ไม่ได้รหัสผ่านจริงเพราะเป็น hash, ต้องมี encryption key แยกต่างหากถึงจะถอดข้อมูลบัตรประชาชนได้) เพื่อแสดงให้เห็นคุณค่าของการแยกใช้ Hashing และ Encryption ให้ถูกจุด

## ข้อคิดสำคัญ (Key Takeaways)

- Encryption ถอดรหัสกลับเป็นต้นฉบับได้เสมอถ้ามีกุญแจถูกต้อง เหมาะกับข้อมูลที่ต้องอ่านกลับมาใช้งานในภายหลัง
- Hashing แปลงข้อมูลเป็นค่าที่ถอดกลับไม่ได้เลย เหมาะกับข้อมูลที่แค่ต้องตรวจสอบว่าตรงกันหรือไม่ (เช่น รหัสผ่าน)
- Salt คือค่าสุ่มที่เพิ่มก่อน hash เพื่อป้องกัน Rainbow Table Attack ทำให้รหัสผ่านเดียวกันได้ hash ต่างกันในแต่ละผู้ใช้
- bcrypt/scrypt/Argon2 เหมาะกับ hash รหัสผ่านเพราะช้าโดยเจตนา (ต้าน Brute Force) ส่วน SHA-256 เหมาะกับตรวจสอบความถูกต้องของข้อมูลเพราะเร็วและมี Avalanche Effect ชัดเจน
- Symmetric Encryption เร็วแต่ต้องแชร์ key ล่วงหน้า ส่วน Asymmetric Encryption ช้ากว่าแต่ไม่ต้องแชร์ key ลับเลย — SSL/TLS (บทที่ 42) ผสมทั้งสองแบบเพื่อความเร็วและความปลอดภัย
- บทถัดไปจะเรียน SQL Injection, XSS, CSRF ซึ่งเป็นช่องโหว่ความปลอดภัยที่พบบ่อยที่สุดในเว็บแอปพลิเคชัน ปิดท้าย Part 15: Security
