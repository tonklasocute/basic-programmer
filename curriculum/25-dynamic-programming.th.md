# บทที่ 25: Dynamic Programming

## แนวคิดหลัก (Concept)

บทที่แล้วปิดท้ายด้วยคำถามสำคัญ: "ถ้าปัญหาย่อยซ้ำซ้อนกัน (overlapping subproblems) จะเกิดอะไรขึ้น?" — Fibonacci คือตัวอย่างคลาสสิกที่สุด: `fib(5)` เรียก `fib(3)` สองครั้งแยกกันโดยไม่รู้ตัว ทำให้เสียเวลาคำนวณซ้ำโดยใช่เหตุ **Dynamic Programming (DP)** คือเทคนิคที่แก้ปัญหานี้ตรงๆ ด้วยการ**จำคำตอบของปัญหาย่อยที่เคยแก้แล้วไว้** แทนที่จะคำนวณซ้ำทุกครั้ง

- **Dynamic Programming** — เทคนิคแก้ปัญหาที่มีคุณสมบัติ 2 ข้อคือ **Overlapping Subproblems** (ปัญหาย่อยซ้ำกัน) และ **Optimal Substructure** (คำตอบที่ดีที่สุดของปัญหาใหญ่ สร้างได้จากคำตอบที่ดีที่สุดของปัญหาย่อย) โดยเก็บผลลัพธ์ของปัญหาย่อยไว้ใช้ซ้ำ ไม่คำนวณใหม่ทุกครั้ง
- **Memoization (Top-Down)** — เขียนแบบ recursive ตามปกติ (เชื่อมโยงบทที่ 9) แต่เพิ่ม cache (ปกติใช้ Hash Table จากบทที่ 15) เก็บผลลัพธ์ที่เคยคำนวณแล้ว ก่อนคำนวณใหม่ให้เช็ค cache ก่อนเสมอ
- **Tabulation (Bottom-Up)** — เขียนแบบ iterative ด้วย loop สร้างตาราง (array) เก็บคำตอบของปัญหาย่อยไล่จากเล็กที่สุดขึ้นไปใหญ่ที่สุด จนได้คำตอบสุดท้าย

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **มีไว้กำจัดการคำนวณซ้ำที่สิ้นเปลืองมหาศาลจาก Recursion ธรรมดา**: `fib(n)` แบบ recursive ล้วนๆ มี time complexity ถึง **O(2^n)** เพราะคำนวณปัญหาย่อยเดิมซ้ำเลขชี้กำลัง แต่ด้วย DP ลดเหลือแค่ **O(n)** — ต่างกันมหาศาลเมื่อ n มีค่ามาก (n=40: recursive ธรรมดาใช้เวลาเป็นวินาทีถึงนาที ส่วน DP ใช้เวลาน้อยกว่ามิลลิวินาที)
- **แก้ปัญหาที่ Divide and Conquer (บทที่แล้ว) แก้ไม่ได้ดี**: D&C ใช้ได้ดีเมื่อปัญหาย่อย**เป็นอิสระจากกัน** แต่หลายปัญหาจริง (การเดินทางที่ประหยัดสุด, การจัดกระเป๋าเดินทางให้ได้มูลค่าสูงสุดภายในน้ำหนักจำกัด) มีปัญหาย่อยที่**ซ้อนทับกัน** ซึ่งถ้าใช้ D&C ตรงๆ จะคำนวณซ้ำเหมือน Fibonacci
- **Optimal Substructure มีไว้รับประกันว่า "แก้ปัญหาย่อยให้ดีที่สุด" นำไปสู่ "คำตอบใหญ่ที่ดีที่สุด" ได้จริง**: ถ้าปัญหาไม่มีคุณสมบัตินี้ (เช่น บางปัญหาที่ทางเลือกที่ดีที่สุดของปัญหาย่อย ไม่ได้นำไปสู่คำตอบที่ดีที่สุดของปัญหาใหญ่เสมอ) DP จะใช้ไม่ได้ผล ต้องใช้เทคนิคอื่นแทน (เช่น Backtracking ที่จะเรียนในบทถัดๆ ไป)

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Memoization** เหมือน **การจดคำตอบข้อสอบที่เคยคำนวณไว้ในกระดาษทด** — ถ้าโจทย์ข้อถัดไปถามซ้ำกับที่เคยคำนวณแล้ว แค่พลิกดูกระดาษทดแทนที่จะคำนวณใหม่ทั้งหมด
- **Tabulation** เหมือน **การสร้างตารางสูตรคูณแม่ 2 ถึง 12 ไว้ล่วงหน้าทั้งเล่ม** — สร้างจากค่าน้อยไปมาก (2×1, 2×2, 2×3, ...) ทีละขั้น แล้วเปิดดูค่าที่ต้องการได้ทันทีโดยไม่ต้องคำนวณใหม่
- **Overlapping Subproblems** เหมือน **หลายคนในครอบครัวถามเส้นทางไปสนามบินแยกกัน** — แทนที่จะหาเส้นทางใหม่ทุกครั้งที่มีคนถาม ก็จดเส้นทางไว้ครั้งเดียวแล้วบอกทุกคนที่ถามซ้ำ

## แผนภาพอธิบาย (Visual explanation)

### Fibonacci แบบ Recursive ธรรมดา — เห็นปัญหาซ้ำซ้อนชัดเจน

```
                          fib(5)
                        /        \
                   fib(4)          fib(3)
                  /      \        /      \
             fib(3)    fib(2)  fib(2)   fib(1)
            /     \    /    \   /    \
        fib(2)  fib(1)fib(1)fib(0)fib(1)fib(0)
        /    \
    fib(1) fib(0)

สังเกต: fib(3) ถูกคำนวณ 2 ครั้ง, fib(2) ถูกคำนวณ 3 ครั้ง, fib(1) ถูกคำนวณ 5 ครั้ง!
ยิ่ง n ใหญ่ขึ้น การคำนวณซ้ำยิ่งเพิ่มแบบ exponential -> O(2^n)
```

### Memoization (Top-Down) — จำคำตอบไว้ ไม่คำนวณซ้ำ

```
                          fib(5)
                        /        \
                   fib(4)          fib(3) ← เจอใน cache แล้ว! คืนค่าทันที ไม่คำนวณซ้ำ
                  /      \
             fib(3)    fib(2)
            /     \
        fib(2)  fib(1) ← เจอใน cache แล้ว!
        /    \
    fib(1) fib(0)

cache = {0: 0, 1: 1, 2: 1, 3: 2, 4: 3, 5: 5}   (เติมทีละตัวตอนคำนวณครั้งแรก)

ผลลัพธ์: คำนวณแต่ละ fib(k) แค่ครั้งเดียว -> O(n) แทนที่จะเป็น O(2^n)
```

### Tabulation (Bottom-Up) — สร้างตารางไล่จากเล็กไปใหญ่

```
dp[0] = 0
dp[1] = 1
dp[2] = dp[1] + dp[0] = 1
dp[3] = dp[2] + dp[1] = 2
dp[4] = dp[3] + dp[2] = 3
dp[5] = dp[4] + dp[3] = 5

ตาราง:  index  0  1  2  3  4  5
        dp[]   0  1  1  2  3  5
                          ↑
                   คำตอบสุดท้าย dp[5] = 5

ไม่มี recursion เลย ไล่ loop ธรรมดาจากซ้ายไปขวา ใช้ผลลัพธ์ที่เพิ่งคำนวณเสร็จมาต่อยอดทันที
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== Fibonacci: Recursive ธรรมดา (ช้ามาก O(2^n)) — สำหรับเปรียบเทียบ =====
def fib_naive(n):
    if n <= 1:
        return n
    return fib_naive(n - 1) + fib_naive(n - 2)     # คำนวณ fib(n-2) ซ้ำซ้อนหลายครั้ง

# ===== Fibonacci: Memoization (Top-Down) — O(n) =====
def fib_memo(n, cache=None):
    if cache is None:
        cache = {}
    if n <= 1:
        return n
    if n in cache:                    # เช็ค cache ก่อนเสมอ - หัวใจของ memoization
        return cache[n]
    cache[n] = fib_memo(n - 1, cache) + fib_memo(n - 2, cache)   # คำนวณแล้วเก็บลง cache
    return cache[n]

# ===== Fibonacci: Tabulation (Bottom-Up) — O(n) เวลา, O(1) พื้นที่ =====
def fib_tabulation(n):
    if n <= 1:
        return n
    prev2, prev1 = 0, 1                # เก็บแค่ 2 ค่าล่าสุด ไม่ต้องเก็บทั้งตาราง
    for i in range(2, n + 1):
        current = prev1 + prev2
        prev2, prev1 = prev1, current
    return prev1

# ===== 0/1 Knapsack — ตัวอย่าง DP คลาสสิกที่ใช้ Optimal Substructure ชัดเจน =====
def knapsack(weights, values, capacity):
    n = len(weights)
    dp = [[0] * (capacity + 1) for _ in range(n + 1)]   # dp[i][w] = มูลค่าสูงสุดจากของ i ชิ้นแรก ที่น้ำหนักไม่เกิน w

    for i in range(1, n + 1):
        for w in range(capacity + 1):
            if weights[i - 1] > w:
                dp[i][w] = dp[i - 1][w]                    # ของชิ้นนี้หนักเกิน w -> ไม่หยิบ ใช้คำตอบเดิม
            else:
                dp[i][w] = max(
                    dp[i - 1][w],                             # ไม่หยิบของชิ้นนี้
                    dp[i - 1][w - weights[i - 1]] + values[i - 1]   # หยิบของชิ้นนี้ + คำตอบที่ดีที่สุดของน้ำหนักที่เหลือ
                )
    return dp[n][capacity]

print(fib_memo(10))          # 55
print(fib_tabulation(10))    # 55
print(knapsack([2, 3, 4, 5], [3, 4, 5, 6], 5))   # 7 (หยิบของชิ้นที่น้ำหนัก 2+3=5, มูลค่า 3+4=7)
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `fib_memo(5, {})` — ก่อนคำนวณ `fib(n-1) + fib(n-2)` เช็คก่อนเสมอว่า `n` เคยถูกคำนวณแล้วหรือยังผ่าน `if n in cache` ถ้าเคยแล้ว **คืนค่าจาก cache ทันทีโดยไม่เรียก recursion ต่อเลย** — เช่นตอนเรียก `fib(3)` ครั้งที่สอง (จากฝั่ง `fib(4)` ที่แตกออกมา) จะเจอใน cache ทันทีเพราะถูกคำนวณไปแล้วตอนแตกจาก `fib(5)` ฝั่งซ้าย ทำให้ไม่ต้องไล่แตก recursion ซ้ำอีกรอบ
2. `fib_tabulation(10)` — ไม่ใช้ recursion เลย ใช้ตัวแปรแค่ 2 ตัว (`prev2`, `prev1`) แทนอาร์เรย์เต็ม เพราะ Fibonacci แต่ละค่าต้องการแค่ 2 ค่าก่อนหน้าเท่านั้น ไม่ต้องเก็บย้อนหลังไปไกลกว่านั้น — เทคนิคนี้เรียกว่า **Space Optimization** ลด Space Complexity จาก O(n) เหลือ O(1) (จะอธิบายเพิ่มด้านล่าง)
3. `knapsack` — สร้างตาราง 2 มิติ `dp[i][w]` แทน "มูลค่าสูงสุดที่ได้ ถ้าเลือกได้จากของ `i` ชิ้นแรกเท่านั้น และน้ำหนักรวมต้องไม่เกิน `w`" สำหรับของแต่ละชิ้น มีแค่ 2 ทางเลือกเสมอ: **ไม่หยิบ** (ใช้คำตอบเดิมจากแถวก่อนหน้า `dp[i-1][w]`) หรือ **หยิบ** (มูลค่าของชิ้นนี้ + คำตอบที่ดีที่สุดของน้ำหนักที่เหลือจากของ `i-1` ชิ้นก่อนหน้า `dp[i-1][w-weights[i-1]]`) — เลือกทางที่ให้มูลค่ามากกว่าเก็บไว้ นี่คือ **Optimal Substructure**: คำตอบของ `dp[i][w]` สร้างจากคำตอบที่ดีที่สุดของปัญหาย่อย `dp[i-1][...]` โดยตรง
4. เงื่อนไข `if weights[i-1] > w` — ถ้าของชิ้นปัจจุบันหนักเกินความจุที่เหลือ `w` **ไม่มีทางเลือกอื่นนอกจากไม่หยิบ** จึงใช้ `dp[i-1][w]` ตรงๆ โดยไม่ต้องเทียบกับกรณีหยิบเลย (เพราะหยิบไม่ได้จริงๆ)

## Time Complexity

| Approach | Time Complexity |
|---|---|
| Fibonacci — Recursive ธรรมดา | O(2^n) |
| Fibonacci — Memoization | **O(n)** |
| Fibonacci — Tabulation | **O(n)** |
| 0/1 Knapsack — DP | **O(n × capacity)** โดย n = จำนวนของ, capacity = ความจุกระเป๋า |

**ทำไม Memoization ถึงลด O(2^n) เหลือ O(n)?** — เพราะมีค่า `n` ที่เป็นไปได้แค่ `n` แบบเท่านั้น (0 ถึง n) และแต่ละค่าถูกคำนวณจริงแค่ครั้งเดียว (ครั้งต่อๆ ไปดึงจาก cache ซึ่งเป็น O(1)) จำนวนการคำนวณจริงทั้งหมดจึงเป็น O(n) ไม่ใช่ O(2^n)

## Space Complexity

- Fibonacci — Recursive ธรรมดา: **O(n)** — ความลึกของ Call Stack (เชื่อมโยงบทที่ 3, 9)
- Fibonacci — Memoization: **O(n)** — ทั้ง cache และ Call Stack ใช้ O(n)
- Fibonacci — Tabulation (แบบ optimize แล้ว): **O(1)** — เก็บแค่ 2 ค่าล่าสุด ไม่ต้องใช้ Call Stack เลยเพราะไม่มี recursion
- 0/1 Knapsack: **O(n × capacity)** — ขนาดตาราง 2 มิติที่สร้างขึ้น

## แนวทางปฏิบัติที่ดี (Best Practices)

- ก่อนใช้ DP เสมอ ตรวจสอบว่าปัญหามีทั้ง **Overlapping Subproblems** และ **Optimal Substructure** จริง ถ้าไม่มีข้อใดข้อหนึ่ง DP อาจไม่ใช่เครื่องมือที่เหมาะสม (ลองพิจารณา D&C ธรรมดาหรือ Greedy แทน — จะเรียนในบทถัดๆ ไป)
- เริ่มต้นด้วย Memoization (Top-Down) ก่อนเสมอเมื่อคิดวิธีแก้ เพราะเขียนจากโครงสร้าง recursive ที่คิดออกได้ง่ายกว่า แล้วค่อยแปลงเป็น Tabulation (Bottom-Up) ทีหลังถ้าต้องการประสิทธิภาพเพิ่ม (หลีกเลี่ยง Call Stack, บาง compiler/interpreter optimize loop ได้ดีกว่า recursion)
- มองหาโอกาส **Space Optimization** เสมอเมื่อใช้ Tabulation — ถ้าคำตอบของ `dp[i]` ต้องการแค่ไม่กี่แถวก่อนหน้า (เหมือน Fibonacci ที่ต้องการแค่ 2 ค่า) ไม่จำเป็นต้องเก็บตารางเต็มทั้งหมด

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ลืมเช็ค cache ก่อนคำนวณใน Memoization ทำให้ยังคงคำนวณซ้ำเหมือนเดิม (cache มีอยู่แต่ไม่ได้ใช้ประโยชน์จริง)
- ใช้ DP กับปัญหาที่ไม่มี Optimal Substructure จริง ได้คำตอบผิดโดยไม่รู้ตัว (เช่น ปัญหาที่ทางเลือกที่ดีที่สุดของปัญหาย่อยขัดแย้งกับคำตอบที่ดีที่สุดของปัญหาใหญ่)
- สร้างตาราง DP ขนาดใหญ่เกินจำเป็นโดยไม่มองหาโอกาส Space Optimization (เช่น เก็บตาราง 2 มิติเต็มทั้งที่ต้องการแค่แถวก่อนหน้าแถวเดียว) ทำให้เสียหน่วยความจำมหาศาลโดยไม่จำเป็นเมื่อข้อมูลใหญ่
- สับสนระหว่าง DP กับ D&C ธรรมดา — พยายามใช้ D&C ตรงๆ (ไม่มี cache) กับปัญหาที่มีปัญหาย่อยซ้ำซ้อน ทำให้ได้ time complexity แย่แบบ exponential โดยไม่รู้ตัว (เหมือน `fib_naive`)

## คำถามสัมภาษณ์งาน (Interview Questions)

1. อธิบาย Overlapping Subproblems และ Optimal Substructure คืออะไร ทำไมทั้งสองข้อถึงจำเป็นสำหรับ DP
2. Memoization กับ Tabulation ต่างกันอย่างไร แต่ละแบบมีข้อดี-ข้อเสียอะไรบ้าง
3. ทำไม Fibonacci แบบ recursive ธรรมดาถึงมี time complexity O(2^n)? อธิบายด้วย recursion tree
4. อธิบายว่า 0/1 Knapsack ใช้หลักการ Optimal Substructure อย่างไร (ทำไม `dp[i][w]` ถึงคำนวณจาก `dp[i-1][...]` ได้)
5. DP ต่างจาก Divide and Conquer (บทที่แล้ว) อย่างไร ยกตัวอย่างปัญหาที่เหมาะกับแต่ละเทคนิค

## แบบฝึกหัด (Practice Exercises)

1. เขียน DP หา**จำนวนวิธีทั้งหมด**ในการเดินขึ้นบันได n ขั้น โดยแต่ละครั้งก้าวได้ 1 หรือ 2 ขั้น (ใบ้: `ways(n) = ways(n-1) + ways(n-2)` คล้าย Fibonacci มาก)
2. เขียน DP หา**ผลรวมย่อยที่ยาวที่สุดที่เพิ่มขึ้นต่อเนื่อง (Longest Increasing Subsequence)** ในอาร์เรย์ที่กำหนด
3. แปลง `knapsack` (Tabulation แบบตาราง 2 มิติ) ให้ใช้แค่อาร์เรย์ 1 มิติแทน (Space Optimization) แล้วอธิบายว่าทำไมยังได้คำตอบถูกต้องอยู่ (ใบ้: ต้องไล่ `w` จากมากไปน้อยแทนน้อยไปมาก)

**"เครื่องมือเปรียบเทียบ Recursive vs Memoization vs Tabulation (DP Performance Benchmark)"**: เขียนโปรแกรมที่:
1. Implement Fibonacci ทั้ง 3 แบบ (recursive ธรรมดา, memoization, tabulation) พร้อมวัดเวลาจริงที่ n = 10, 20, 30, 35
2. แสดงกราฟ/ตารางเปรียบเทียบเวลาที่ใช้ พิสูจน์ว่า recursive ธรรมดาช้าลงแบบ exponential ขณะที่อีกสองแบบช้าลงแบบ linear
3. Implement 0/1 Knapsack แล้วสร้างระบบ "แนะนำของที่ควรหยิบ" ไม่ใช่แค่บอกมูลค่าสูงสุด แต่ต้อง**ย้อนรอย (backtrack) จากตาราง dp** เพื่อบอกว่าหยิบของชิ้นไหนบ้าง
4. ทดสอบกับข้อมูลของจริง (เช่น รายการสินค้าพร้อมน้ำหนักและราคา) ที่มีของมากกว่า 20 ชิ้น เพื่อดูว่า DP ยังทำงานได้เร็วในขณะที่ brute force (ลองทุกวิธีเลือกของ) ทำไม่ได้เลยเพราะ 2^20 มีค่ามากเกินไป

## ข้อคิดสำคัญ (Key Takeaways)

- Dynamic Programming แก้ปัญหาที่มี Overlapping Subproblems และ Optimal Substructure โดยจำคำตอบของปัญหาย่อยไว้ใช้ซ้ำ แทนที่จะคำนวณใหม่ทุกครั้ง
- Memoization (Top-Down) ใช้ recursion + cache เขียนง่ายจากโครงสร้าง recursive เดิม ส่วน Tabulation (Bottom-Up) ใช้ loop สร้างตารางไล่จากเล็กไปใหญ่ ประหยัดกว่าเพราะไม่มี Call Stack
- Fibonacci คือตัวอย่างที่ชัดเจนที่สุดว่า DP ลด time complexity จาก O(2^n) เหลือ O(n) ได้อย่างมหาศาล
- 0/1 Knapsack แสดงให้เห็นรูปแบบทั่วไปของ DP: สร้างตารางที่แต่ละช่องมี "ทางเลือก" จำกัด (หยิบ/ไม่หยิบ) แล้วเลือกทางที่ดีที่สุดจากคำตอบของปัญหาย่อยที่เล็กกว่า
- DP ต่างจาก Divide and Conquer ตรงที่ D&C เหมาะกับปัญหาย่อยที่เป็นอิสระจากกัน ส่วน DP เหมาะกับปัญหาย่อยที่ซ้อนทับกัน — การแยกแยะสองแบบนี้ได้คือทักษะสำคัญในการเลือกเทคนิคที่ถูกต้อง
- บทถัดไปจะเรียน Greedy Algorithm ซึ่งเป็นอีกเทคนิคหนึ่งที่บางครั้งดูคล้าย DP แต่ตัดสินใจแบบ "เลือกที่ดีที่สุด ณ ตอนนั้นทันที" โดยไม่ย้อนกลับมาพิจารณาใหม่ — ต่างจาก DP ที่พิจารณาทุกความเป็นไปได้ผ่านตาราง
