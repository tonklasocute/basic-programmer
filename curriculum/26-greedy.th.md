# บทที่ 26: Greedy

## แนวคิดหลัก (Concept)

บทที่แล้วจบด้วยการทิ้งคำถามไว้: มีเทคนิคไหนที่ตัดสินใจแบบ "เลือกดีที่สุด ณ ตอนนั้นทันที" โดยไม่ต้องสร้างตารางพิจารณาทุกความเป็นไปได้เหมือน DP หรือไม่? คำตอบคือ **Greedy Algorithm** — เทคนิคที่ในแต่ละขั้นตอนเลือกตัวเลือกที่ดูดีที่สุด ณ ขณะนั้น (local optimum) โดยไม่ย้อนกลับมาทบทวนการตัดสินใจเดิม แล้วหวังว่าผลรวมทั้งหมดจะออกมาดีที่สุด (global optimum) — ซึ่ง**ใช้ได้ผลจริงกับบางปัญหาเท่านั้น** ไม่ใช่ทุกปัญหา

- **Greedy Algorithm** — อัลกอริทึมที่ตัดสินใจทีละขั้น โดยเลือกตัวเลือกที่ดีที่สุด ณ ขณะนั้นเสมอ (Local Optimum) โดยไม่พิจารณาผลกระทบต่ออนาคตหรือย้อนกลับไปแก้การตัดสินใจเดิม
- **Local Optimum vs Global Optimum** — Local Optimum คือคำตอบที่ดีที่สุดในสถานการณ์ตรงหน้า ณ ขั้นตอนนั้น ส่วน Global Optimum คือคำตอบที่ดีที่สุดของปัญหาทั้งหมด — Greedy ใช้ได้ผลก็ต่อเมื่อการเลือก Local Optimum ทุกขั้นตอน นำไปสู่ Global Optimum เสมอ
- **Greedy Choice Property** — คุณสมบัติของปัญหาที่ทำให้ Greedy ใช้ได้ผลจริง: การตัดสินใจที่ดีที่สุด ณ ขั้นตอนหนึ่ง ไม่มีวันถูก "ทำลาย" โดยการตัดสินใจในขั้นตอนถัดไป (ต่างจาก DP ที่ต้องพิจารณาทุกทางเลือกเพราะบางครั้งทางเลือกที่ดูดีตอนนี้อาจแย่กว่าในภาพรวม)

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **มีไว้แก้ปัญหาที่ DP "แรงเกินความจำเป็น"**: DP (บทที่แล้ว) รับประกันคำตอบที่ดีที่สุดเสมอ แต่ต้องแลกด้วยการสร้างตารางพิจารณาทุกความเป็นไปได้ (time/space complexity สูงกว่า) ถ้าปัญหามี Greedy Choice Property จริง Greedy จะให้คำตอบที่ดีที่สุดเท่ากับ DP แต่**เร็วกว่ามาก** (มักเป็น O(n log n) จากการ sort ครั้งเดียว แทนที่จะเป็น O(n × capacity) แบบ Knapsack)
- **สะท้อนวิธีตัดสินใจของมนุษย์ในชีวิตจริงหลายสถานการณ์**: เวลาเราทอนเงิน มักหยิบเหรียญ/แบงก์มูลค่าสูงสุดที่ไม่เกินจำนวนที่ต้องทอนก่อนเสมอ โดยไม่คิดย้อนกลับไปทบทวน — เป็นสัญชาตญาณที่ตรงกับหลักการ Greedy พอดี (แม้จะไม่ใช่ทุกกรณีที่ใช้ได้ผล ต้องระวัง)
- **เป็นรากฐานของอัลกอริทึม Graph สำคัญหลายตัว**: Dijkstra's Algorithm (หาเส้นทางสั้นที่สุดแบบมีน้ำหนัก), Kruskal's/Prim's Algorithm (หา Minimum Spanning Tree) ล้วนเป็น Greedy Algorithm ที่ใช้กันจริงในระบบเครือข่ายและแผนที่นำทาง

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Greedy** เหมือน **การทอนเงินแบบหยิบเหรียญมูลค่าสูงสุดก่อนเสมอ** — ถ้าต้องทอน 67 บาท จะหยิบแบงก์ 50 ก่อน (เหลือ 17) แล้วหยิบเหรียญ 10 (เหลือ 7) แล้วหยิบเหรียญ 5 (เหลือ 2) แล้วหยิบเหรียญ 2 บาท — แต่ละขั้นเลือกมูลค่าสูงสุดที่ไม่เกินจำนวนคงเหลือ ไม่คิดย้อนกลับ
- **Greedy ที่ล้มเหลว** เหมือน **การเดินเลือกทางที่ดูสั้นที่สุดในทุกแยกโดยไม่ดูแผนที่รวม** — บางครั้งทางที่ดูสั้นในแยกแรกอาจนำไปสู่ทางตันหรือทางอ้อมไกลในภาพรวม ในขณะที่ทางที่ดูยาวกว่าในแยกแรกอาจนำไปสู่เส้นทางรวมที่สั้นกว่า — นี่คือเหตุผลที่ Greedy ไม่ใช่คำตอบสำหรับทุกปัญหา
- **Activity Selection (จะยกตัวอย่างด้านล่าง)** เหมือน **การจองห้องประชุมให้ได้จำนวนครั้งมากที่สุดในหนึ่งวัน** — เลือกประชุมที่**จบเร็วที่สุดก่อนเสมอ** เพื่อเปิดโอกาสให้จองครั้งถัดไปได้มากที่สุดเท่าที่จะเป็นไปได้

## แผนภาพอธิบาย (Visual explanation)

### Coin Change แบบ Greedy — กรณีที่ใช้ได้ผล (เหรียญไทย)

```
ทอนเงิน 67 บาท ด้วยเหรียญ/แบงก์ [50, 20, 10, 5, 2, 1]

ขั้น 1: เหลือ 67  -> หยิบ 50 (มากสุดที่ไม่เกิน 67)  -> เหลือ 17
ขั้น 2: เหลือ 17  -> หยิบ 10 (มากสุดที่ไม่เกิน 17)  -> เหลือ 7
ขั้น 3: เหลือ 7   -> หยิบ 5  (มากสุดที่ไม่เกิน 7)   -> เหลือ 2
ขั้น 4: เหลือ 2   -> หยิบ 2  (มากสุดที่ไม่เกิน 2)   -> เหลือ 0  ✓ จบ

ผลลัพธ์: [50, 10, 5, 2] = 4 เหรียญ  (นี่คือจำนวนน้อยที่สุดที่เป็นไปได้จริง ระบบเหรียญไทยเอื้อให้ Greedy ใช้ได้ผล)
```

### Coin Change แบบ Greedy — กรณีที่ "ล้มเหลว" (ระบบเหรียญสมมติ)

```
ทอนเงิน 6 หน่วย ด้วยเหรียญสมมติ [1, 3, 4]

Greedy: เหลือ 6 -> หยิบ 4 (มากสุดที่ไม่เกิน 6) -> เหลือ 2
        เหลือ 2 -> หยิบ 1 (มากสุดที่ไม่เกิน 2) -> เหลือ 1
        เหลือ 1 -> หยิบ 1                      -> เหลือ 0
        ผลลัพธ์ Greedy: [4, 1, 1] = 3 เหรียญ

คำตอบจริงที่ดีที่สุด: [3, 3] = 2 เหรียญ  ← Greedy พลาด! เพราะระบบเหรียญนี้ไม่มี Greedy Choice Property

สรุป: Coin Change ใช้ Greedy ได้ผลเฉพาะระบบเหรียญบางแบบเท่านั้น (เช่น เหรียญไทย/สหรัฐ)
      ถ้าไม่แน่ใจว่าระบบเหรียญมีคุณสมบัตินี้หรือไม่ ต้องใช้ DP (บทที่แล้ว) เพื่อรับประกันคำตอบที่ถูกต้องเสมอ
```

### Activity Selection — เลือกกิจกรรมให้ได้จำนวนมากที่สุดโดยไม่ทับซ้อนเวลา

```
กิจกรรม (เริ่ม, จบ):  A(1,4)  B(3,5)  C(0,6)  D(5,7)  E(3,9)  F(5,9)  G(6,10)  H(8,11)

ขั้นตอน Greedy: เรียงตาม "เวลาจบ" ก่อนเสมอ -> A(1,4) B(3,5) C(0,6) D(5,7) E(3,9) F(5,9) G(6,10) H(8,11)

เลือก A(1,4) ก่อน (จบเร็วสุด)         -> เลือกแล้ว: [A]
ข้าม B(3,5) เพราะเริ่ม 3 < จบของ A(4)  -> ทับซ้อน
ข้าม C(0,6) เพราะเริ่ม 0 < จบของ A(4)  -> ทับซ้อน
เลือก D(5,7) เพราะเริ่ม 5 >= จบของ A(4) -> เลือกแล้ว: [A, D]
ข้าม E(3,9) เพราะเริ่ม 3 < จบของ D(7)  -> ทับซ้อน
ข้าม F(5,9) เพราะเริ่ม 5 < จบของ D(7)  -> ทับซ้อน
เลือก G(6,10) เพราะเริ่ม 6... รอก่อน 6 < 7 ทับซ้อน -> ข้าม
เลือก H(8,11) เพราะเริ่ม 8 >= จบของ D(7) -> เลือกแล้ว: [A, D, H]

ผลลัพธ์: [A, D, H] = 3 กิจกรรม (มากที่สุดเท่าที่เป็นไปได้จริง)
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== Coin Change แบบ Greedy — ใช้ได้ผลกับระบบเหรียญไทย/สหรัฐ =====
def coin_change_greedy(coins, amount):
    coins = sorted(coins, reverse=True)    # เรียงจากมากไปน้อยก่อนเสมอ
    result = []
    for coin in coins:
        while amount >= coin:               # หยิบเหรียญนี้ซ้ำๆ จนกว่าจะเกินจำนวนคงเหลือ
            amount -= coin
            result.append(coin)
    return result if amount == 0 else None   # None = ทอนไม่ได้พอดีด้วยเหรียญชุดนี้

# ===== Activity Selection — Greedy โดยเรียงตาม "เวลาจบ" =====
def activity_selection(activities):
    # activities = list ของ (start, end)
    activities = sorted(activities, key=lambda a: a[1])   # หัวใจสำคัญ: เรียงตามเวลาจบ ไม่ใช่เวลาเริ่ม!
    selected = [activities[0]]
    last_end = activities[0][1]
    for start, end in activities[1:]:
        if start >= last_end:               # ไม่ทับซ้อนกับกิจกรรมล่าสุดที่เลือกไว้
            selected.append((start, end))
            last_end = end
    return selected

# ===== Fractional Knapsack — Greedy โดยเรียงตาม "มูลค่าต่อหน่วยน้ำหนัก" =====
def fractional_knapsack(items, capacity):
    # items = list ของ (weight, value)
    items = sorted(items, key=lambda x: x[1] / x[0], reverse=True)   # เรียงตาม value/weight มากไปน้อย
    total_value = 0.0
    for weight, value in items:
        if capacity >= weight:
            capacity -= weight
            total_value += value            # หยิบทั้งชิ้น
        else:
            total_value += value * (capacity / weight)   # หยิบแค่บางส่วนตามสัดส่วนที่เหลือ
            break                            # กระเป๋าเต็มพอดี จบทันที
    return total_value

print(coin_change_greedy([50, 20, 10, 5, 2, 1], 67))          # [50, 10, 5, 2]
print(activity_selection([(1,4),(3,5),(0,6),(5,7),(3,9),(5,9),(6,10),(8,11)]))  # [(1,4),(5,7),(8,11)]
print(fractional_knapsack([(2,3),(3,4),(4,5)], 5))            # 7.0 (หยิบของ value/weight สูงสุดก่อน)
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `coin_change_greedy` — เรียงเหรียญจากมากไปน้อยก่อน แล้วใช้ `while amount >= coin` หยิบเหรียญมูลค่าสูงสุดซ้ำๆ จนกว่าจะหยิบต่อไม่ได้ (เกินจำนวนคงเหลือ) แล้วขยับไปเหรียญที่เล็กกว่าถัดไป — **ไม่มีการย้อนกลับมาทบทวน**เลยว่าถ้าหยิบเหรียญที่เล็กกว่าตั้งแต่ต้นจะได้ผลลัพธ์ที่ดีกว่าหรือไม่ (นี่คือความหมายของ "Greedy" — ตัดสินใจแล้วเดินหน้าต่อเสมอ)
2. `activity_selection` — ขั้นตอนที่สำคัญที่สุดคือ `sorted(activities, key=lambda a: a[1])` **เรียงตามเวลาจบ ไม่ใช่เวลาเริ่มหรือความยาว** เพราะกิจกรรมที่จบเร็วที่สุดเปิดโอกาสให้เหลือเวลามากที่สุดสำหรับกิจกรรมถัดไป — ถ้าเรียงผิด (เช่น เรียงตามเวลาเริ่ม) จะได้คำตอบที่ไม่ใช่ค่าที่ดีที่สุดเสมอไป
3. `fractional_knapsack` — ต่างจาก 0/1 Knapsack (บทที่แล้ว) ตรงที่**หยิบของบางส่วนได้** (เช่น หยิบทองคำ 2.5 กก. จาก 4 กก. ได้) ทำให้ Greedy ใช้ได้ผลจริงในกรณีนี้ (ต่างจาก 0/1 Knapsack ที่ต้องใช้ DP) เพราะเรียงตาม "มูลค่าต่อหน่วยน้ำหนัก" (`value/weight`) แล้วหยิบของที่คุ้มค่าที่สุดก่อนเสมอ รับประกันว่าได้มูลค่ารวมสูงสุดจริง — บรรทัด `total_value += value * (capacity / weight)` คือการหยิบ "เศษส่วน" ของชิ้นสุดท้ายที่พอดีกับพื้นที่ที่เหลือ

## Time Complexity

| Algorithm | Time Complexity |
|---|---|
| Coin Change — Greedy | O(amount / min_coin) ในกรณีทั่วไป |
| Activity Selection | O(n log n) — ต้นทุนหลักคือการ sort |
| Fractional Knapsack | O(n log n) — ต้นทุนหลักคือการ sort |
| (เทียบ) 0/1 Knapsack — DP จากบทที่แล้ว | O(n × capacity) |

**ทำไม Greedy เร็วกว่า DP มาก?** — เพราะ Greedy ตัดสินใจแค่ครั้งเดียวต่อขั้นตอน (มักหลัง sort ข้อมูลแล้ว) โดยไม่ต้องสร้างตารางพิจารณาทุกความเป็นไปได้เหมือน DP — แต่แลกมาด้วยการที่ **ใช้ได้เฉพาะปัญหาที่มี Greedy Choice Property เท่านั้น**

## Space Complexity

- Coin Change — Greedy: **O(1)** เพิ่มเติมนอกจาก output (ไม่นับพื้นที่เก็บผลลัพธ์)
- Activity Selection: **O(n)** สำหรับ list ผลลัพธ์ที่เลือก (หรือ O(log n) ถ้านับแค่พื้นที่ใช้ในการ sort)
- Fractional Knapsack: **O(1)** เพิ่มเติมนอกจากการ sort — ต่างจาก 0/1 Knapsack ที่ต้องใช้ O(n × capacity) สำหรับตาราง DP

## แนวทางปฏิบัติที่ดี (Best Practices)

- ก่อนใช้ Greedy เสมอ ต้อง**พิสูจน์ (หรืออย่างน้อยตรวจสอบด้วยตัวอย่างหลายกรณี) ว่าปัญหามี Greedy Choice Property จริง** — อย่าสมมติเอาเองว่า Greedy ใช้ได้ผลเพียงเพราะมันดูสมเหตุสมผล (ดูตัวอย่าง Coin Change ที่ล้มเหลวด้านบน)
- เมื่อไม่แน่ใจว่าปัญหาเหมาะกับ Greedy หรือไม่ ให้เริ่มจาก DP ก่อนเสมอเพราะรับประกันความถูกต้อง แล้วค่อยพิจารณาเปลี่ยนเป็น Greedy ทีหลังถ้าพิสูจน์ได้ว่าใช้ได้ผลจริงและต้องการความเร็วเพิ่ม
- สังเกตว่าปัญหา Greedy ส่วนใหญ่เริ่มต้นด้วยการ **sort ข้อมูลตามเกณฑ์บางอย่าง** เสมอ (เวลาจบ, มูลค่าต่อหน่วยน้ำหนัก, มูลค่าเหรียญ) — การเลือกเกณฑ์ sort ที่ถูกต้องคือหัวใจสำคัญที่สุดของการออกแบบ Greedy Algorithm

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ใช้ Greedy กับปัญหาที่ไม่มี Greedy Choice Property โดยไม่ตรวจสอบก่อน ได้คำตอบที่ผิด (ไม่ใช่ค่าที่ดีที่สุดจริง) โดยไม่มี error แจ้งเตือนเลย — เหมือนตัวอย่าง Coin Change ด้วยเหรียญ [1,3,4]
- เรียงข้อมูลผิดเกณฑ์ใน Activity Selection (เรียงตามเวลาเริ่มหรือความยาวกิจกรรม แทนที่จะเป็นเวลาจบ) ทำให้ได้จำนวนกิจกรรมน้อยกว่าค่าที่ดีที่สุดจริง
- ใช้ Fractional Knapsack logic (เรียงตาม value/weight) กับปัญหา 0/1 Knapsack ที่หยิบของบางส่วนไม่ได้ — สองปัญหานี้ต้องใช้เทคนิคต่างกัน (Greedy ใช้ได้กับ Fractional เท่านั้น 0/1 ต้องใช้ DP)
- คิดว่า Greedy ต้องเร็วกว่า DP เสมอโดยไม่พิจารณาความถูกต้อง — ความเร็วไม่มีประโยชน์ถ้าคำตอบผิด ต้องพิสูจน์ความถูกต้องก่อนเสมอ ไม่ใช่แค่ดูความเร็ว

2. ทำไม Activity Selection ต้องเรียงตาม "เวลาจบ" ไม่ใช่ "เวลาเริ่ม" หรือ "ความยาวกิจกรรม"?
3. ยกตัวอย่างระบบเหรียญที่ Greedy Coin Change ให้คำตอบผิด พร้อมอธิบายว่าทำไมถึงผิด
4. Fractional Knapsack ต่างจาก 0/1 Knapsack (บทที่แล้ว) อย่างไร ทำไม Greedy ถึงใช้ได้กับแบบแรกแต่ใช้ไม่ได้กับแบบหลัง?
5. เมื่อไหร่ควรเลือกใช้ Greedy แทน DP และเมื่อไหร่ควรเลือก DP แทน Greedy?

## Mini Project

**"ระบบจัดตารางประชุมอัตโนมัติ (Meeting Room Scheduler)"**: เขียนโปรแกรมที่:
1. Implement `activity_selection` เพื่อเลือกประชุมให้ได้จำนวนมากที่สุดในห้องประชุม 1 ห้อง จากรายการคำขอจองที่มี (เวลาเริ่ม, เวลาจบ) จำนวนมาก
2. ขยายให้รองรับ**ห้องประชุมหลายห้อง** (เช่น k ห้อง) โดยใช้หลักการ Greedy ร่วมกับ Min-Heap (ทบทวนจากบทที่ 17) เพื่อติดตามว่าห้องไหนว่างเร็วที่สุด
3. เปรียบเทียบผลลัพธ์กับการแก้ปัญหาแบบ Brute Force (ลองทุกชุดย่อยที่เป็นไปได้) เพื่อพิสูจน์ว่า Greedy ให้คำตอบที่ดีที่สุดจริงสำหรับปัญหานี้
4. เพิ่มฟีเจอร์รายงานสรุป: ประชุมที่ถูกปฏิเสธทั้งหมด (ทับซ้อนจนจัดไม่ได้) พร้อมเหตุผล

## ข้อคิดสำคัญ (Key Takeaways)

- Greedy Algorithm ตัดสินใจเลือก Local Optimum ทีละขั้นตอนโดยไม่ย้อนกลับ ใช้ได้ผลก็ต่อเมื่อปัญหามี Greedy Choice Property เท่านั้น
- Greedy เร็วกว่า DP มาก (มักเป็น O(n log n) จากการ sort) แต่ไม่รับประกันคำตอบที่ดีที่สุดเสมอไปเหมือน DP — ต้องพิสูจน์ก่อนใช้เสมอ ไม่ใช่สมมติเอาเอง
- Activity Selection และ Fractional Knapsack เป็นตัวอย่างคลาสสิกที่ Greedy ใช้ได้ผลจริง ส่วน Coin Change (บางระบบเหรียญ) และ 0/1 Knapsack เป็นตัวอย่างที่ Greedy ใช้ไม่ได้ผล ต้องใช้ DP แทน
- การเลือกเกณฑ์ sort ที่ถูกต้อง (เวลาจบ, มูลค่าต่อหน่วยน้ำหนัก ฯลฯ) คือหัวใจสำคัญที่สุดในการออกแบบ Greedy Algorithm ให้ถูกต้อง
- Greedy เป็นรากฐานของอัลกอริทึม Graph สำคัญ (Dijkstra's, Kruskal's, Prim's) ที่จะเชื่อมโยงกับ Graph (บทที่ 19) และ Heap (บทที่ 17) ในการประยุกต์ใช้จริงต่อไป
- บทถัดไปจะเรียน Backtracking ซึ่งต่างจาก Greedy ตรงที่**ย้อนกลับได้**เมื่อพบว่าทางเลือกที่เลือกไว้ไม่นำไปสู่คำตอบที่ถูกต้อง เหมาะกับปัญหาที่ Greedy ใช้ไม่ได้ผลและ DP ก็ยังไม่พอ
