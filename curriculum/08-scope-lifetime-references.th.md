# บทที่ 8: Scope, Lifetime, References, Pointers

## แนวคิดหลัก (Concept)

ทุกตัวแปรที่เราสร้างขึ้น (บทที่ 5) มีคำถามสำคัญ 2 ข้อที่ต้องตอบเสมอ: **"ที่ไหนบ้างในโค้ดที่มองเห็นตัวแปรนี้ได้?"** และ **"ตัวแปรนี้มีชีวิตอยู่นานแค่ไหน?"** สองคำถามนี้คือแนวคิด **Scope** และ **Lifetime**

- **Scope (ขอบเขตการมองเห็น)** — บริเวณของโค้ดที่สามารถเข้าถึง (อ้างอิงถึง) ตัวแปรได้ เช่น ตัวแปรที่สร้างในฟังก์ชันหนึ่ง มักมองไม่เห็นจากฟังก์ชันอื่น (local scope) ในขณะที่ตัวแปรระดับบนสุดของไฟล์อาจมองเห็นได้ทุกที่ (global scope)
- **Lifetime (อายุการใช้งาน)** — ช่วงเวลาที่ตัวแปรนั้นยังมีอยู่จริงในหน่วยความจำ ตั้งแต่ถูกสร้างจนถูกทำลาย (เชื่อมโยงโดยตรงกับ Stack/Heap จากบทที่ 3 — ตัวแปรบน Stack มักตายทันทีที่ฟังก์ชันจบ)
- **Reference (การอ้างอิง)** — ตัวแปรที่ไม่ได้เก็บค่าโดยตรง แต่เก็บ "ที่อยู่" ของค่าจริงที่อยู่ที่อื่น (มักอยู่ใน Heap) การแก้ไขผ่าน reference จะกระทบค่าจริงต้นทางด้วย
- **Pointer (ตัวชี้)** — แนวคิดคล้าย reference แต่ชัดเจนกว่า คือตัวแปรที่เก็บ **ที่อยู่หน่วยความจำ (memory address)** ของข้อมูลอื่นโดยตรง และในบางภาษา (C, C++, Rust) สามารถคำนวณ/ขยับที่อยู่นั้นได้ (pointer arithmetic)

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Scope มีไว้ป้องกันชื่อตัวแปรชนกัน (naming collision) และจำกัดผลกระทบของบั๊ก**: ถ้าทุกตัวแปรในโปรแกรมมองเห็นกันหมด (global ทั้งหมด) โปรแกรมขนาดใหญ่จะจัดการไม่ได้เลย เพราะฟังก์ชันหนึ่งอาจไปแก้ตัวแปรที่ฟังก์ชันอื่นกำลังใช้อยู่โดยไม่ตั้งใจ
- **Lifetime มีไว้จัดการหน่วยความจำอย่างมีประสิทธิภาพ**: ถ้าตัวแปรทุกตัวอยู่ตลอดไปไม่มีวันตาย หน่วยความจำจะเต็มอย่างรวดเร็ว การที่ตัวแปร local ตายเมื่อฟังก์ชันจบ (ตามกลไก Stack) ทำให้หน่วยความจำถูกนำกลับมาใช้ใหม่ได้อัตโนมัติ
- **Reference/Pointer มีไว้ให้ข้อมูลขนาดใหญ่ถูกส่งต่อได้อย่างมีประสิทธิภาพ**: การส่ง object ขนาดใหญ่ (เช่น list ล้านตัว) เข้าฟังก์ชันโดย **copy ค่าทั้งหมด** จะช้ามากและสิ้นเปลืองหน่วยความจำ การส่งแค่ "ที่อยู่" (reference/pointer) แทน ทำให้ฟังก์ชันเข้าถึงข้อมูลเดิมได้โดยไม่ต้องคัดลอก

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Scope** เหมือน **ห้องต่างๆ ในบ้าน** — ของในห้องนอนของคุณ (local scope) คนในห้องนอนอื่นมองไม่เห็น แต่ของในห้องนั่งเล่นกลาง (global scope) ทุกคนในบ้านมองเห็นและใช้ร่วมกันได้
- **Lifetime** เหมือน **อายุของลูกโป่งในงานปาร์ตี้** — ลูกโป่งถูกเป่าตอนงานเริ่ม (สร้างตัวแปร) และแตก/ถูกทิ้งเมื่องานเลิก (ฟังก์ชันจบ) ไม่มีทางเก็บลูกโป่งไว้ใช้ในงานถัดไปได้ถ้ามันผูกกับงานนี้เท่านั้น
- **Reference/Pointer** เหมือน **ที่อยู่บ้านบนซองจดหมาย** — ซองจดหมายไม่ได้เก็บ "ตัวบ้าน" ไว้ในซอง แต่เก็บแค่ที่อยู่ ทำให้ส่งซอง (ที่อยู่) ให้เพื่อนได้ง่ายกว่าการยกบ้านทั้งหลังไปให้ ถ้าเพื่อนไปที่บ้านตามที่อยู่นั้นแล้วทาสีใหม่ บ้านจริงก็เปลี่ยนสี ไม่ใช่แค่สำเนา

## แผนภาพอธิบาย (Visual explanation)

### Scope แบบซ้อนกัน (Nested Scope / Lexical Scope)

```python
x = "global"                 # Global Scope

def outer():
    y = "outer local"        # Local Scope ของ outer()
    def inner():
        z = "inner local"    # Local Scope ของ inner()
        print(x)             # เข้าถึง global ได้ -> "global"
        print(y)             # เข้าถึง outer's local ได้ (closure) -> "outer local"
        print(z)             # เข้าถึงตัวเองได้ -> "inner local"
    inner()

# นอก inner()/outer() มองเห็น z, y ไม่ได้ (อยู่นอกขอบเขต)
```

```
┌─────────────────────────────────────┐
│ GLOBAL SCOPE (x)                      │
│  ┌───────────────────────────────┐   │
│  │ outer() SCOPE (y)               │  │
│  │  ┌───────────────────────────┐ │  │
│  │  │ inner() SCOPE (z)          │ │  │
│  │  │  มองเห็น: z, y, x (ทั้งหมด) │ │  │
│  │  └───────────────────────────┘ │  │
│  │  มองเห็น: y, x (ไม่เห็น z)      │  │
│  └───────────────────────────────┘   │
│  มองเห็น: x เท่านั้น (ไม่เห็น y, z)     │
└─────────────────────────────────────┘
```

### Value vs Reference

```
Pass by Value (ค่าถูกคัดลอก):
    def modify(n):
        n = n + 1          # แก้ไขสำเนา ไม่กระทบต้นฉบับ
    x = 5
    modify(x)
    print(x)   # ยังคงเป็น 5

Pass by Reference (ส่งที่อยู่ของ Heap object ไป — บทที่ 3):
    def modify_list(lst):
        lst.append(4)      # แก้ไขผ่านที่อยู่เดียวกัน -> กระทบต้นฉบับ!
    my_list = [1, 2, 3]
    modify_list(my_list)
    print(my_list)   # [1, 2, 3, 4]  <- เปลี่ยนไปจริง!
```

### Pointer (แนวคิดใน C) — ที่อยู่หน่วยความจำโดยตรง

```c
int age = 25;
int *p = &age;     // p เก็บ "ที่อยู่" ของ age ไม่ใช่ค่า 25 โดยตรง

//  ตัวแปร age  ──┐
//                ▼
//   Memory: [0x7ffee1: 25]
//   ตัวแปร p    ──► ชี้ไปที่ 0x7ffee1

*p = 30;           // "ไปที่ที่อยู่ที่ p ชี้อยู่ แล้วเปลี่ยนค่าเป็น 30"
printf("%d", age); // พิมพ์ 30 -> เพราะ p ชี้ไปที่ age โดยตรง
```

## ตัวอย่างโค้ด (Code example)

```python
counter = 0                       # Global scope

def increment():
    global counter                # ต้องประกาศ global ชัดเจนถ้าจะแก้ไขตัวแปร global จากในฟังก์ชัน
    counter += 1

increment()
increment()
print(counter)                    # 2

def make_counter():
    count = 0                     # Local scope ของ make_counter
    def inner():
        nonlocal count            # อ้างถึงตัวแปรใน scope ของฟังก์ชันแม่ (closure)
        count += 1
        return count
    return inner

my_counter = make_counter()
print(my_counter())    # 1  (count "รอด" อยู่ได้แม้ make_counter() จะจบไปแล้ว!)
print(my_counter())    # 2

# ===== Reference semantics ของ mutable object =====
def add_item(items):
    items.append("new item")      # แก้ไข list ต้นฉบับผ่าน reference

shopping_list = ["milk", "eggs"]
add_item(shopping_list)
print(shopping_list)   # ['milk', 'eggs', 'new item']
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `increment()` ครั้งแรก — Python เห็นคำสั่ง `global counter` จึงรู้ว่าเวลาเขียน `counter += 1` ให้แก้ไข**ตัวแปร global** ไม่ใช่สร้างตัวแปร local ใหม่ที่ซ้อนทับชื่อเดียวกัน (ถ้าไม่มี `global` ไว้ Python จะ error เพราะคิดว่าเรากำลังใช้ตัวแปร local ที่ยังไม่ถูกกำหนดค่า)
2. `make_counter()` ถูกเรียก — สร้างตัวแปร `count = 0` ใน Local scope ของมัน แล้วสร้างฟังก์ชัน `inner` ที่**จดจำ scope ของ `make_counter` ไว้** (เรียกว่า **closure**) แม้ `make_counter()` จะ return และ Stack frame ของมันถูก pop ไปแล้ว (ตามหลักการบทที่ 3) ตัวแปร `count` ก็ยัง**ไม่ตาย** เพราะยังมี `inner` อ้างอิงถึงมันอยู่ — Python (และภาษาที่รองรับ closure) จะย้ายตัวแปรนี้ไปอยู่ใน Heap แทน Stack เพื่อให้มันอยู่รอดได้นานกว่าฟังก์ชันที่สร้างมัน
3. `add_item(shopping_list)` — พารามิเตอร์ `items` ไม่ได้รับสำเนาของ list แต่รับ **reference** (ที่อยู่ของ list object ใน Heap) เดียวกับ `shopping_list` ดังนั้น `items.append(...)` จึงแก้ไข object ตัวเดียวกันกับที่ `shopping_list` ชี้อยู่ — ผลลัพธ์คือต้นฉบับเปลี่ยนไปจริง

## Time Complexity

การเข้าถึงตัวแปรผ่าน scope (local/global lookup) โดยทั่วไปเป็น **O(1)** ในภาษาสมัยใหม่ส่วนใหญ่ (ใช้ตาราง/สัญลักษณ์ที่คอมไพล์ไว้ล่วงหน้า) แม้บางภาษาแบบ dynamic (เช่น การค้นหาผ่านหลายชั้น scope ที่ซ้อนลึก) อาจมีค่าใช้จ่ายเพิ่มขึ้นตามจำนวนชั้นของ scope ที่ต้องไล่ค้นหา

## Space Complexity

Closure ที่ยึดตัวแปรจาก scope ภายนอกไว้ ทำให้ตัวแปรนั้นไม่ถูกคืนหน่วยความจำแม้ฟังก์ชันแม่จะจบไปแล้ว (ตามตัวอย่าง `make_counter`) — ถ้าใช้ closure จำนวนมากโดยไม่ระวัง อาจทำให้หน่วยความจำถูกใช้ค้างไว้นานเกินจำเป็น (คล้าย memory leak ในภาษาที่มี garbage collector)

## แนวทางปฏิบัติที่ดี (Best Practices)

- จำกัดขอบเขตตัวแปรให้แคบที่สุดเท่าที่จำเป็น (local ดีกว่า global เสมอถ้าเป็นไปได้) เพื่อลดความเสี่ยงจากการแก้ไขโดยไม่ตั้งใจข้ามฟังก์ชัน
- หลีกเลี่ยงการใช้ตัวแปร global สำหรับ state ที่เปลี่ยนแปลงบ่อย เพราะทำให้ debug ยาก (ไม่รู้ว่าฟังก์ชันไหนแก้ไขมันบ้าง)
- เมื่อส่ง mutable object (list, dict, object) เข้าฟังก์ชัน ต้องตระหนักเสมอว่ากำลังส่ง reference ไม่ใช่สำเนา — ถ้าต้องการสำเนาจริงๆ ให้ copy อย่างชัดเจน (เช่น `list(original)` หรือ `copy.deepcopy()`)
- ในภาษาที่มี pointer โดยตรง (C/C++) ต้องระวัง **dangling pointer** (ตัวชี้ที่ชี้ไปยังหน่วยความจำที่ถูกคืนไปแล้ว) ซึ่งเป็นสาเหตุบั๊กร้ายแรงและช่องโหว่ความปลอดภัยที่พบบ่อย

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- แก้ไข mutable object ที่ส่งเข้าฟังก์ชันโดยไม่ตั้งใจ แล้วงงว่าทำไมตัวแปรต้นฉบับข้างนอกเปลี่ยนไปด้วย (ลืมว่าเป็น reference ไม่ใช่สำเนา)
- ใช้ตัวแปร global มากเกินไปจนโปรแกรมกลายเป็น "spaghetti code" ที่ตามรอยยาก ว่าฟังก์ชันไหนแก้ค่าตอนไหน
- เข้าใจผิดว่าตัวแปรทุกชนิดพฤติกรรมเหมือนกันเวลาส่งเข้าฟังก์ชัน (บางชนิด เช่น int, string, tuple ใน Python เป็น **immutable** — แก้ไขในฟังก์ชันจะไม่กระทบต้นฉบับ ต่างจาก list/dict ที่เป็น **mutable**)
- ในภาษาที่มี pointer ตรงๆ ลืม initialize pointer ก่อนใช้ (wild pointer) หรือใช้ pointer หลังจากหน่วยความจำที่มันชี้ไปถูก free แล้ว (dangling pointer)

## ข้อคิดสำคัญ (Key Takeaways)

- Scope กำหนดว่าตัวแปรมองเห็นได้จากที่ไหนบ้าง ส่วน Lifetime กำหนดว่าตัวแปรมีชีวิตอยู่นานแค่ไหน — สองเรื่องนี้เกี่ยวข้องกันแต่ไม่ใช่เรื่องเดียวกัน
- Reference/Pointer คือการเก็บ "ที่อยู่" แทนค่าจริง ทำให้ส่งข้อมูลขนาดใหญ่เข้าฟังก์ชันได้อย่างมีประสิทธิภาพ แต่ต้องระวังผลข้างเคียงจากการแก้ไขข้อมูลต้นฉบับโดยไม่ตั้งใจ
- Closure คือกลไกที่ทำให้ตัวแปรจาก scope ภายนอก "รอด" อยู่ได้นานกว่าฟังก์ชันที่สร้างมัน โดยการย้ายไปเก็บใน Heap แทน Stack
- Mutable object (list, dict) ถูกแก้ไขผ่าน reference ได้ ขณะที่ Immutable object (int, string, tuple) การ "แก้ไข" จะสร้างค่าใหม่แทนเสมอ ไม่กระทบต้นฉบับ
- ความเข้าใจเรื่องนี้เป็นพื้นฐานสำคัญก่อนเข้าสู่บทถัดไป: Functions, Parameters, Return Values, Recursion ซึ่งใช้แนวคิด scope/lifetime/reference ตลอดเวลา
