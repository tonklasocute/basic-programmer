# บทที่ 4: Compiler, Interpreter และ Virtual Machine //ต้องดู

## แนวคิดหลัก (Concept)

โค้ดที่เราเขียน (เช่น Python, Java, C++) เป็น **ภาษาที่มนุษย์อ่านเข้าใจ** แต่ CPU เข้าใจได้แค่ **เลขฐาน 2 (machine code)** ตามที่เรียนในบทที่ 2 ดังนั้นต้องมีตัวกลางที่แปลงโค้ดของเราให้กลายเป็นสิ่งที่เครื่องรันได้จริง ตัวกลางนี้มี 3 รูปแบบหลัก:

- **Compiler (คอมไพเลอร์)** — แปลซอร์สโค้ด**ทั้งหมด**เป็น machine code (หรือภาษาระดับต่ำอื่น) ล่วงหน้า **ก่อน**รันจริง ได้ไฟล์ executable ออกมา แล้วค่อยรันไฟล์นั้นตรงๆ (เช่น C, C++, Go, Rust)
- **Interpreter (อินเทอร์พรีเตอร์)** — อ่านและรันโค้ด **ทีละบรรทัด** ขณะโปรแกรมทำงาน ไม่ต้องแปลงเป็นไฟล์ executable ล่วงหน้า (เช่น Python, Ruby แบบดั้งเดิม)
- **Virtual Machine (VM)** — เครื่องจำลอง (software) ที่รัน "bytecode" ตัวกลาง ซึ่งภาษานั้นถูกคอมไพล์มาก่อนระดับหนึ่ง (ไม่ถึง machine code) แล้ว VM จะตีความ/แปล bytecode นั้นให้กลายเป็นคำสั่งที่ CPU จริงเข้าใจอีกที (เช่น JVM สำหรับ Java, CLR สำหรับ C#, และ Python เองก็ใช้ bytecode + VM ภายใน)

ภาษาสมัยใหม่จำนวนมาก (Java, C#, Python, JavaScript แบบ V8) จริงๆ แล้วใช้วิธีผสมระหว่างทั้งสามแบบ ไม่ใช่แบบใดแบบหนึ่งล้วนๆ

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Compiler มีไว้เพื่อความเร็วตอนรัน**: เพราะแปลงเป็น machine code ล่วงหน้าหมดแล้ว ตอนรันจริงไม่ต้องเสียเวลาแปลภาษาอีก จึงเร็วที่สุด แต่แลกมาด้วยเวลาคอมไพล์ก่อนรัน และไฟล์ที่ได้ผูกกับ OS/CPU เฉพาะแบบ (ต้องคอมไพล์ใหม่ถ้าย้ายแพลตฟอร์ม)
- **Interpreter มีไว้เพื่อความยืดหยุ่นและพัฒนาไว**: ไม่ต้องรอคอมไพล์ เขียนโค้ดแล้วรันได้ทันที เหมาะกับการทดลอง แก้บั๊กไว แต่รันช้ากว่าเพราะต้องแปลภาษาซ้ำทุกครั้งที่รัน (แม้เป็นบรรทัดเดิม)
- **VM มีไว้เพื่อ "เขียนครั้งเดียว รันได้ทุกที่" (Write Once, Run Anywhere)**: bytecode ตัวกลางไม่ผูกกับ OS/CPU ใดๆ ตราบใดที่เครื่องนั้นมี VM ที่ถูกต้องติดตั้งอยู่ ก็รัน bytecode เดียวกันได้ ทำให้ portable กว่า compiler ล้วนๆ และยังเร็วกว่า interpreter ล้วนๆ เพราะ bytecode ผ่านการแปลงมาระดับหนึ่งแล้ว

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Compiler** เหมือน **นักแปลหนังสือทั้งเล่ม** — แปลหนังสือทั้งเล่มจากภาษาไทยเป็นภาษาอังกฤษให้เสร็จก่อน แล้วค่อยส่งหนังสือ (ที่แปลเสร็จแล้ว) ให้คนอ่าน คนอ่านอ่านได้ลื่นไหลเร็วมาก เพราะไม่มีการแปลคั่นระหว่างอ่าน แต่ต้องรอนักแปลทำงานให้เสร็จก่อน
- **Interpreter** เหมือน **ล่ามแปลสด** — แปลทีละประโยคขณะที่ผู้พูดพูด ผู้ฟังได้ยินทันที ไม่ต้องรอ แต่ล่ามต้องแปลซ้ำทุกครั้งที่มีการพูดประโยคเดิม (ถ้าพูดวนซ้ำ)
- **Virtual Machine** เหมือน **ปลั๊กแปลงไฟสากล (universal adapter)** — อุปกรณ์ไฟฟ้า (โปรแกรม) ถูกออกแบบให้เสียบกับปลั๊กมาตรฐานเดียว (bytecode) แล้วปลั๊กแปลงไฟ (VM) ที่ติดตั้งในแต่ละประเทศ (แต่ละ OS/CPU) จะแปลงไฟให้เข้ากับเต้ารับท้องถิ่นเอง อุปกรณ์ตัวเดียวใช้ได้ทั่วโลกโดยไม่ต้องออกแบบใหม่

## แผนภาพอธิบาย (Visual explanation)

### เส้นทางของ Compiler (เช่น C, Go)

```
Source Code (.c)  ──► Compiler ──► Machine Code (.exe) ──► CPU รันตรงๆ
   (มนุษย์เขียน)        (แปลล่วงหน้า      (เฉพาะ OS/CPU นั้นๆ)     (เร็วที่สุด)
                          ครั้งเดียว)
```

### เส้นทางของ Interpreter (เช่น Python แบบดั้งเดิม, Bash)

```
Source Code  ──► Interpreter อ่านทีละบรรทัด ──► รันทันที
                  (แปล + รัน พร้อมกัน            (ไม่มีไฟล์ executable
                   ทุกครั้งที่รัน)                  แยกต่างหาก)
```

### เส้นทางของ Virtual Machine (เช่น Java, C#, และ Python จริงๆ)

```
Source Code (.java)  ──► Compiler ──► Bytecode (.class)  ──► VM (JVM) ──► Machine Code
                          (แปลครั้งเดียว   (ตัวกลาง ไม่ผูก      (ตีความ/แปล      (CPU รัน)
                           เป็น bytecode)   OS/CPU ใดๆ)         ตอนรันจริง)

              เครื่อง Windows: ติดตั้ง JVM สำหรับ Windows → รัน .class ไฟล์เดียวกันได้
              เครื่อง Mac:     ติดตั้ง JVM สำหรับ Mac     → รัน .class ไฟล์เดียวกันได้
              เครื่อง Linux:   ติดตั้ง JVM สำหรับ Linux   → รัน .class ไฟล์เดียวกันได้
```

### เปรียบเทียบความเร็วเทียบกับความยืดหยุ่น

```
เร็วที่สุด (แต่ portable น้อยสุด)              ช้าที่สุด (แต่ยืดหยุ่นสุด, dev ไว)
     │                                                              │
  Compiler ────────────── Virtual Machine ──────────── Interpreter
  (C, Rust, Go)            (Java, C#, Python*)            (Bash, PHP ดั้งเดิม)

* Python ใช้ทั้ง VM (bytecode + PVM) และมีลักษณะ interpreter ในเชิงพัฒนา/debug
```

## ตัวอย่างโค้ด (Code example)

```python
# ตัวอย่าง: ดู bytecode ที่ Python สร้างขึ้นจากซอร์สโค้ด
# (Python คอมไพล์เป็น bytecode ก่อน แล้วค่อยรันบน Python VM / PVM)
import dis

def add(a, b):
    return a + b

dis.dis(add)
```

ผลลัพธ์ที่ได้ (ประมาณนี้):

```
  2           0 LOAD_FAST                0 (a)
              2 LOAD_FAST                1 (b)
              4 BINARY_ADD
              6 RETURN_VALUE
```

```c
// ตัวอย่างภาษา C (compiled language) — ต้องคอมไพล์ก่อนรัน
#include <stdio.h>

int add(int a, int b) {
    return a + b;
}

int main() {
    printf("%d\n", add(3, 4));
    return 0;
}
```

```bash
# ขั้นตอนคอมไพล์ C: แปลงเป็น machine code (.exe) ก่อน แล้วค่อยรัน
gcc program.c -o program     # ขั้นตอน "compile" (ทำครั้งเดียว)
./program                     # ขั้นตอน "run" (รัน machine code ตรงๆ เร็วมาก)
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. **ฝั่ง Python (VM-based)**: เมื่อรัน `python script.py` — Python จะคอมไพล์ซอร์สโค้ดเป็น **bytecode** ก่อน (ไฟล์ `.pyc` แคชไว้) ขั้นตอนนี้เร็วและทำเบื้องหลังอัตโนมัติ จากนั้น **Python Virtual Machine (PVM)** จะอ่าน bytecode ทีละคำสั่ง (เช่น `LOAD_FAST`, `BINARY_ADD`) แล้วตีความให้กลายเป็นการทำงานจริงบน CPU
2. **ฝั่ง C (Compiler-based)**: คำสั่ง `gcc program.c -o program` จะแปลซอร์สโค้ดทั้งไฟล์เป็น **machine code** ที่จำเพาะกับ CPU/OS ของเครื่องที่คอมไพล์ ได้ไฟล์ `program` (หรือ `.exe`) ออกมา
3. เมื่อรัน `./program` — OS โหลดไฟล์ machine code เข้า RAM แล้วส่งให้ CPU รันได้ทันที **ไม่มีการแปลภาษาใดๆ อีก** ต่างจาก Python ที่ต้องผ่าน VM ตีความทุกครั้งที่รัน
4. ถ้านำไฟล์ `program` (ที่คอมไพล์บน Windows) ไปรันบน Mac จะรันไม่ได้ (ต้องคอมไพล์ใหม่) แต่ไฟล์ bytecode ของ Java (`.class`) รันได้ทั้งสองเครื่อง ตราบใดที่มี JVM ติดตั้งอยู่ — นี่คือหัวใจของ "Write Once, Run Anywhere"

## Time Complexity

ไม่ใช่แนวคิดที่วัดด้วย Big O โดยตรง แต่สามารถเปรียบเทียบ **overhead ตอนรัน (runtime overhead)** ได้เชิงคุณภาพ:
- Compiled code: overhead ตอนรัน ≈ 0 (ทำงานเป็น machine code ล้วนๆ)
- VM-based (bytecode): overhead ตอนรัน = ต้องตีความ/แปล bytecode ทุกคำสั่ง (มักมี JIT — Just-In-Time compilation — มาช่วยแปลงส่วนที่รันบ่อยให้เป็น machine code ระหว่างรัน เพื่อลด overhead นี้)
- Pure interpreted: overhead ตอนรัน สูงสุด เพราะแปลจากซอร์สโค้ดดิบทุกครั้ง

## Space Complexity

โปรแกรมที่ผ่าน compiler ได้ไฟล์ executable ที่มักมีขนาดใหญ่กว่าซอร์สโค้ดเล็กน้อย (รวม machine code + metadata) ส่วนโปรแกรมแบบ VM/interpreter ต้องพก runtime (เช่น JVM, PVM) แยกต่างหากติดตั้งบนเครื่องเสมอ ซึ่งกินพื้นที่และหน่วยความจำเพิ่มเติมขณะรัน (VM เองก็ใช้ RAM)

## แนวทางปฏิบัติที่ดี (Best Practices)

- เลือกภาษาที่เหมาะกับงาน: งานที่ต้องการประสิทธิภาพสูงสุด (เช่น game engine, ระบบฝังตัว) มักใช้ compiled language (C++, Rust) ส่วนงานที่ต้องการพัฒนาไวหรือ prototype (สคริปต์, data science) มักใช้ interpreted/VM language (Python, JavaScript)
- เข้าใจว่า "ภาษาตีความช้ากว่า" เป็นภาพรวมกว้างๆ เท่านั้น — ภาษาสมัยใหม่จำนวนมาก (Java, JavaScript V8, Python ผ่าน PyPy) มี JIT compiler ที่ช่วยให้เร็วใกล้เคียง compiled code ในหลายกรณี
- เมื่อ deploy โปรแกรมที่ต้องใช้ VM (Java, .NET) ต้องมั่นใจว่าเครื่องปลายทางมี runtime ที่ถูกต้องติดตั้งไว้

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- เข้าใจผิดว่า Python เป็น "pure interpreter" ล้วนๆ — จริงๆ แล้ว Python คอมไพล์เป็น bytecode ก่อนเสมอ (มีขั้นตอน compile ซ่อนอยู่) แล้วค่อยรันผ่าน VM
- คิดว่า compiled language เร็วกว่า VM-based เสมอในทุกกรณี — ในทางปฏิบัติ JIT compiler ที่ดี (เช่นใน JVM) อาจเร็วใกล้เคียงหรือบางกรณีเร็วกว่า code ที่คอมไพล์แบบ static เพราะ JIT ปรับ optimize ตาม runtime behavior จริงได้
- ลืมว่าไฟล์ executable ที่คอมไพล์แล้วผูกกับ OS/CPU สถาปัตยกรรมนั้นๆ (เช่น คอมไพล์บน ARM รันบน x86 ไม่ได้)

## ข้อคิดสำคัญ (Key Takeaways)

- Compiler แปลซอร์สโค้ดทั้งหมดเป็น machine code ล่วงหน้า รันเร็วที่สุดแต่ผูกกับ OS/CPU เฉพาะ
- Interpreter แปล+รันทีละบรรทัดขณะทำงาน ยืดหยุ่นและพัฒนาไว แต่รันช้ากว่า
- Virtual Machine ใช้ bytecode ตัวกลางที่ portable ข้าม OS/CPU ได้ โดยแลกกับ overhead จากการตีความ/แปลตอนรัน (ซึ่งบรรเทาได้ด้วย JIT)
- ภาษาสมัยใหม่ส่วนใหญ่ผสมผสานทั้งสามแนวคิดเข้าด้วยกัน ไม่ใช่แบบใดแบบหนึ่งล้วนๆ
- ความเข้าใจเรื่องนี้เป็นการปิดท้าย "พื้นฐาน CS" ก่อนจะเข้าสู่การเขียนโปรแกรมจริงในบทถัดไป (ตัวแปร, ชนิดข้อมูล, ฟังก์ชัน)
