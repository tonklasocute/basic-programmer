# บทที่ 29: Union Find

## แนวคิดหลัก (Concept)

บทที่ 26 (Greedy) กล่าวถึง Kruskal's Algorithm ไว้เป็นตัวอย่างของ Greedy บน Graph โดยยังไม่ได้อธิบายว่ามันตรวจสอบ "จะเกิด cycle หรือไม่ถ้าเพิ่ม edge นี้" ได้เร็วขนาด O(1)-เกือบคงที่ได้อย่างไร — คำตอบคือโครงสร้างข้อมูลชื่อ **Union Find** (หรือเรียกอีกชื่อว่า **Disjoint Set Union / DSU**) บทนี้เป็นบทปิดท้ายของ Part 5: Algorithms โดยแนะนำโครงสร้างข้อมูลเฉพาะทางที่ตอบคำถาม **"สองสิ่งนี้อยู่กลุ่มเดียวกันหรือไม่"** ได้เร็วกว่าการใช้ BFS/DFS (บทที่ 23) ไล่ตรวจทุกครั้งมาก

- **Union Find (Disjoint Set Union)** — โครงสร้างข้อมูลที่จัดการ**เซตที่ไม่ทับซ้อนกัน (disjoint sets)** จำนวนหนึ่ง รองรับ 2 operation หลัก: **Find** (หาว่าสมาชิกหนึ่งอยู่เซตไหน) และ **Union** (รวมสองเซตเข้าด้วยกัน)
- **Representative / Root** — สมาชิกตัวแทนของแต่ละเซต ใช้บอกว่าสองสมาชิกอยู่เซตเดียวกันหรือไม่ (ถ้า Find คืนค่า root เดียวกัน แปลว่าอยู่เซตเดียวกัน)
- **Union by Rank/Size** — เทคนิคเพิ่มประสิทธิภาพตอนรวมสองเซต โดยเลือกให้ต้นไม้ที่เล็กกว่าไปติดอยู่ใต้ต้นไม้ที่ใหญ่กว่าเสมอ ป้องกันไม่ให้โครงสร้างสูงเกินไป
- **Path Compression** — เทคนิคเพิ่มประสิทธิภาพตอน Find โดยทำให้ทุก node ที่ผ่านระหว่างทางไปหา root ชี้ตรงไปที่ root ทันที ทำให้การ Find ครั้งถัดไปเร็วขึ้นมาก

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **มีไว้ตอบคำถาม "อยู่กลุ่มเดียวกันหรือไม่" เร็วกว่า BFS/DFS มาก เมื่อต้องถามซ้ำหลายครั้ง**: ถ้าใช้ BFS/DFS ตรวจสอบว่าสอง vertex เชื่อมกันหรือไม่ ต้อง traverse ใหม่ทุกครั้ง O(V+E) ต่อคำถาม แต่ Union Find เตรียมโครงสร้างไว้แล้วตอบแต่ละคำถามได้เกือบ O(1) (แม่นยำคือ O(α(n)) ซึ่งเป็นฟังก์ชันที่โตช้ามากจนถือว่าคงที่ในทางปฏิบัติ)
- **เป็นหัวใจของ Kruskal's Algorithm (Minimum Spanning Tree)**: การหา MST ต้องเพิ่ม edge ทีละเส้นโดยหลีกเลี่ยง cycle เสมอ — Union Find ตรวจสอบได้ทันทีว่า edge ใหม่จะทำให้เกิด cycle หรือไม่ (ถ้าปลายทั้งสองของ edge อยู่เซตเดียวกันแล้ว = จะเกิด cycle แน่นอน) โดยไม่ต้อง traverse ทั้ง graph ใหม่
- **ใช้แก้ปัญหา "จัดกลุ่ม/connectivity" ได้กว้างกว่าแค่ Graph โดยตรง**: เช่น ตรวจสอบว่าเครือข่ายคอมพิวเตอร์แบ่งเป็นกี่กลุ่มที่แยกจากกัน, ตรวจจับว่าเพื่อนสองคนอยู่ในเครือข่ายสังคมเดียวกันหรือไม่ (โดยไม่สนใจเส้นทางที่แน่นอน แค่ต้องการรู้ว่าเชื่อมกันหรือไม่)

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Union Find** เหมือน **ระบบสมาชิกกลุ่มไลน์ที่ควบรวมกันได้** — แต่ละกลุ่มมี "หัวหน้ากลุ่ม" (representative) เป็นตัวแทน เมื่อสองกลุ่มควบรวมกัน หัวหน้ากลุ่มหนึ่งจะยอมรับอีกกลุ่มเป็นหัวหน้าใหญ่ ถ้าอยากรู้ว่าคนสองคนอยู่กลุ่มเดียวกันหรือไม่ แค่เช็คว่าหัวหน้ากลุ่มสุดท้ายของทั้งคู่เป็นคนเดียวกันหรือเปล่า
- **Path Compression** เหมือน **การจำทางลัดตรงไปหาหัวหน้าใหญ่ทันทีหลังถามทางครั้งแรก** — แทนที่จะต้องถามต่อๆ กันไปหลายชั้น (A ถามหัวหน้าเล็ก B, B ถามหัวหน้าใหญ่ C) ครั้งถัดไป A จำทางลัดไปหา C ได้เลยโดยไม่ต้องผ่าน B อีก
- **Union by Rank** เหมือน **การควบรวมบริษัทเล็กเข้ากับบริษัทใหญ่เสมอ (ไม่ใช่กลับกัน)** — ทำให้โครงสร้างองค์กรโดยรวมไม่ลึกเกินไป ประหยัดเวลาไล่สายบังคับบัญชาเมื่อต้องหาผู้บริหารสูงสุด

## แผนภาพอธิบาย (Visual explanation)

### เริ่มต้น: ทุกสมาชิกเป็นเซตของตัวเองแยกกัน

```
A   B   C   D   E   F

parent[A]=A, parent[B]=B, parent[C]=C, parent[D]=D, parent[E]=E, parent[F]=F
(ทุกตัวเป็น root ของตัวเอง — 6 เซตแยกกันทั้งหมด)
```

### Union ทีละคู่ — สร้างต้นไม้ขึ้นเรื่อยๆ

```
union(A, B):        union(C, D):        union(A, C):  <- รวม 2 เซตที่มีอยู่แล้ว (ไม่ใช่แค่สมาชิกเดี่ยว)

   A                    C                     A
   |                    |                   / | \
   B                    D                  B  C  (union by size: root ที่มีสมาชิกน้อยกว่าไปอยู่ใต้)
                                               |
                                               D

หลัง union(A,C): เซตของ A มี {A,B} (size=2) และเซตของ C มี {C,D} (size=2)
ขนาดเท่ากัน -> เลือกให้ C ไปอยู่ใต้ A ตามธรรมเนียม (Union by Size)
```

### Find พร้อม Path Compression — ทางลัดหลัง Find ครั้งแรก

```
ก่อน Path Compression:            หลังเรียก find(D) ครั้งแรก (ต้องไล่ D->C->A):
        A                                    A
      / | \                                / | \
     B  C  (root)                         B  C  D   <- D ชี้ตรงไปหา A ทันที (ทางลัด!)
        |
        D

find(D) ครั้งถัดไป: D->A โดยตรง (1 ก้าว) แทนที่จะเป็น D->C->A (2 ก้าว) เหมือนเดิม
ยิ่งเรียก find บ่อย โครงสร้างยิ่งแบนลงเรื่อยๆ ทำให้เร็วขึ้นเรื่อยๆ
```

### ตรวจสอบ Cycle ด้วย Union Find (หลักการของ Kruskal's Algorithm)

```
Edge ที่จะเพิ่ม: (A, D)

find(A) = A (root ปัจจุบันของ A หลัง path compression)
find(D) = A (root ปัจจุบันของ D)

find(A) == find(D)  -> อยู่เซตเดียวกันอยู่แล้ว! ถ้าเพิ่ม edge นี้จะเกิด CYCLE
                        -> Kruskal's Algorithm จะข้าม edge นี้ทิ้งทันที ไม่ต้อง traverse graph เลย
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== Union Find พร้อม Path Compression และ Union by Size =====
class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))       # แต่ละตัวเป็น root ของตัวเองตอนเริ่มต้น
        self.size = [1] * n                 # ขนาดของแต่ละเซต ใช้สำหรับ Union by Size

    def find(self, x):
        if self.parent[x] != x:
            self.parent[x] = self.find(self.parent[x])   # Path Compression: ชี้ตรงไปหา root ทันที
        return self.parent[x]

    def union(self, x, y):
        root_x, root_y = self.find(x), self.find(y)
        if root_x == root_y:
            return False                     # อยู่เซตเดียวกันอยู่แล้ว -> union ไม่ได้ผล (จะเกิด cycle ถ้าเป็น graph)
        if self.size[root_x] < self.size[root_y]:         # Union by Size: เล็กไปอยู่ใต้ใหญ่เสมอ
            root_x, root_y = root_y, root_x
        self.parent[root_y] = root_x
        self.size[root_x] += self.size[root_y]
        return True

    def connected(self, x, y):
        return self.find(x) == self.find(y)

# ===== ตัวอย่างการใช้งาน: ตรวจสอบเครือข่ายเพื่อน =====
uf = UnionFind(6)                # สมาชิก 0-5
uf.union(0, 1)                    # 0 กับ 1 เป็นเพื่อนกัน
uf.union(2, 3)
uf.union(0, 2)                    # รวมกลุ่ม {0,1} กับ {2,3}
print(uf.connected(1, 3))         # True (1 กับ 3 อยู่กลุ่มเดียวกันผ่าน 0)
print(uf.connected(1, 4))         # False (4 ยังไม่เชื่อมกับใครเลย)

# ===== Kruskal's Algorithm (โครงร่าง) — ใช้ Union Find ตรวจ cycle =====
def kruskal_mst(n, edges):
    # edges = list ของ (weight, u, v)
    edges.sort()                              # Greedy: เรียงตามน้ำหนักน้อยไปมากก่อนเสมอ (ทบทวนบทที่ 26)
    uf = UnionFind(n)
    mst_weight = 0
    mst_edges = []
    for weight, u, v in edges:
        if uf.union(u, v):                    # union คืน True แปลว่าไม่เกิด cycle -> เพิ่ม edge นี้ได้
            mst_weight += weight
            mst_edges.append((u, v))
    return mst_weight, mst_edges

print(kruskal_mst(4, [(1,0,1), (3,0,2), (4,1,2), (2,1,3), (5,2,3)]))
# (6, [(0,1), (1,3), (0,2)]) -> MST น้ำหนักรวมน้อยที่สุด = 6
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `find(x)` — ถ้า `x` ไม่ใช่ root ของตัวเอง (`self.parent[x] != x`) เรียก `find` แบบ recursive ไปยัง parent ของมันต่อไปเรื่อยๆ จนเจอ root แล้ว**เขียนทับ `self.parent[x]` ให้ชี้ตรงไปที่ root ทันที** (`self.parent[x] = self.find(self.parent[x])`) — บรรทัดนี้คือ Path Compression: ทุก node ที่อยู่บนเส้นทางจาก `x` ไปหา root จะถูกทำให้ชี้ตรงไปที่ root โดยตรงในการเรียกครั้งนี้ ทำให้การเรียก `find` ครั้งถัดไปสำหรับ node เหล่านั้นเร็วขึ้นมาก
2. `union(x, y)` — หา root ของทั้งสองฝั่งก่อน ถ้าเป็น root เดียวกันแปลว่าอยู่เซตเดียวกันแล้ว **คืน `False` ทันทีโดยไม่ทำอะไรต่อ** (สำคัญมากสำหรับ Kruskal's Algorithm เพราะนี่คือสัญญาณว่าจะเกิด cycle) ถ้า root ต่างกัน เปรียบเทียบ `self.size` ของทั้งสองเซต แล้วให้เซตที่**เล็กกว่า**ไปอยู่ใต้เซตที่ใหญ่กว่าเสมอ (Union by Size) เพื่อป้องกันไม่ให้ต้นไม้สูงเกินความจำเป็น
3. `kruskal_mst` — เรียง edge ทั้งหมดตามน้ำหนักน้อยไปมากก่อน (หลักการ Greedy จากบทที่ 26) แล้วไล่พิจารณาทีละ edge จากน้อยไปมาก ถ้า `uf.union(u, v)` คืนค่า `True` (แปลว่ายังไม่เชื่อมกันมาก่อน ไม่เกิด cycle) จึงรับ edge นั้นเข้า MST — นี่คือจุดที่ Union Find กับ Greedy Choice Property (บทที่ 26) มาบรรจบกัน: การเลือก edge ที่เบาที่สุดก่อนเสมอ (Greedy) และใช้ Union Find ตรวจสอบ cycle แบบเกือบ O(1) ทำให้ได้ MST ที่ถูกต้องอย่างมีประสิทธิภาพ

## Time Complexity

| Operation | ไม่มี Optimization | Path Compression อย่างเดียว | Path Compression + Union by Size |
|---|---|---|---|
| Find | O(n) worst case (ต้นไม้เป็นเส้นตรง) | O(log n) amortized | **O(α(n))** — เกือบคงที่ |
| Union | O(n) worst case | O(log n) amortized | **O(α(n))** — เกือบคงที่ |
| Kruskal's Algorithm ทั้งหมด | — | — | **O(E log E)** (ต้นทุนหลักคือการ sort edges) |

โดย **α(n)** คือ **Inverse Ackermann Function** ซึ่งโตช้ามากจนสำหรับข้อมูลจริงทุกขนาดที่เป็นไปได้ (แม้แต่ n ที่มีเลขศูนย์เป็นร้อยหลัก) ค่า α(n) ยังคงน้อยกว่า 5 เสมอ — ในทางปฏิบัติจึงถือว่า Find และ Union ทำงานแบบ **เกือบคงที่ O(1)** เมื่อใช้ทั้งสอง optimization ร่วมกัน

## Space Complexity

- Union Find: **O(n)** — ใช้อาร์เรย์ `parent` และ `size` ขนาด n ทั้งคู่

## แนวทางปฏิบัติที่ดี (Best Practices)

- ใช้ Path Compression และ Union by Size/Rank **ร่วมกันเสมอ** ไม่ใช้แค่อย่างใดอย่างหนึ่ง เพราะการใช้ทั้งสองร่วมกันเท่านั้นที่ให้ complexity เกือบคงที่ O(α(n)) ที่แท้จริง
- เลือก Union Find แทน BFS/DFS เมื่อโจทย์ต้องการตอบคำถาม **"เชื่อมกันหรือไม่"** ซ้ำหลายครั้งบน graph ที่ edge ถูกเพิ่มเข้ามาเรื่อยๆ (ไม่ใช่ graph คงที่ที่ query แค่ครั้งเดียว) เพราะ Union Find ออกแบบมาสำหรับ dynamic connectivity โดยเฉพาะ
- ถ้าโจทย์ต้องการ**เส้นทาง**จริงๆ (ไม่ใช่แค่ตอบว่าเชื่อมกันหรือไม่) Union Find ใช้ไม่ได้ ต้องกลับไปใช้ BFS/DFS (บทที่ 23) แทน เพราะ Union Find ไม่เก็บข้อมูลเส้นทาง เก็บแค่ว่าอยู่กลุ่มเดียวกันหรือไม่เท่านั้น

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ลืมทำ Path Compression ใน `find()` ทำให้ต้นไม้สูงขึ้นเรื่อยๆ จนกลายเป็นเส้นตรง (worst case O(n) ต่อการเรียก) โดยเฉพาะเมื่อ union เป็นลำดับต่อเนื่องกันไปเรื่อยๆ
- Union แบบไม่สนใจขนาด (`self.parent[root_y] = root_x` เสมอโดยไม่เทียบ size) ทำให้ต้นไม้เอนไปด้านเดียวและสูงเกินจำเป็น เสียประโยชน์ของ Union by Size ไป
- คิดว่า `find(x) == find(y)` เท่ากับการหาว่า "x กับ y มี edge เชื่อมกันโดยตรง" — ที่จริงมันหมายถึง **x กับ y อยู่กลุ่มเดียวกัน** (อาจเชื่อมกันทางอ้อมผ่านสมาชิกอื่นก็ได้) ไม่ใช่แค่เชื่อมตรง
- ใช้ Union Find แทน BFS/DFS ทั้งที่โจทย์ต้องการรู้ **เส้นทางที่แท้จริง** ไม่ใช่แค่ว่าเชื่อมกันหรือไม่ — ทำให้แก้ปัญหาผิดประเภทเพราะ Union Find ไม่มีข้อมูลเส้นทางเก็บไว้เลย

## คำถามสัมภาษณ์งาน (Interview Questions)

1. อธิบาย Path Compression และ Union by Rank/Size คืออะไร ทำไมต้องใช้ทั้งสองเทคนิคร่วมกันถึงจะได้ประสิทธิภาพดีที่สุด
2. Union Find ต่างจาก BFS/DFS ในการตรวจสอบ connectivity อย่างไร แต่ละแบบเหมาะกับสถานการณ์ไหน
3. อธิบายว่า Union Find ช่วยตรวจสอบ cycle ใน Kruskal's Algorithm ได้อย่างไร โดยไม่ต้อง traverse graph ใหม่ทุกครั้ง
4. Inverse Ackermann Function (α(n)) คืออะไรในบริบทนี้ ทำไมถึงถือว่า Find/Union เป็น "เกือบคงที่" ในทางปฏิบัติ
5. ยกตัวอย่างปัญหาจริงที่เหมาะกับ Union Find มากกว่า BFS/DFS พร้อมอธิบายเหตุผล

2. เขียนฟังก์ชันใช้ Union Find ตรวจสอบว่าการเพิ่ม edge ทีละเส้นใน list ที่กำหนด จะทำให้เกิด **Redundant Connection** (edge ที่ทำให้เกิด cycle) เส้นไหนบ้าง โดยคืนค่า edge แรกที่ทำให้เกิด cycle
3. Implement `UnionFind` แบบไม่มี Path Compression และไม่มี Union by Size แล้ววัดเวลาเทียบกับเวอร์ชันที่มีทั้งสอง optimization เมื่อ union ต่อเนื่องกันเป็นเส้นตรง (0-1, 1-2, 2-3, ..., n-1 คู่) เพื่อดูความแตกต่างของ worst case ชัดๆ

## Mini Project

**"ระบบตรวจจับเครือข่ายและป้องกันวงจรซ้ำ (Network Cluster & Cycle Detector)"**: เขียนโปรแกรมที่:
1. Implement `UnionFind` แบบเต็มรูปแบบพร้อม Path Compression และ Union by Size
2. สร้างระบบจำลองเครือข่ายคอมพิวเตอร์ (Union Find บนรายการการเชื่อมต่อ) แล้วรายงานว่าเครือข่ายทั้งหมดแบ่งเป็นกี่กลุ่มย่อยที่แยกจากกัน (isolated clusters)
3. Implement Kruskal's Algorithm แบบเต็มรูปแบบ หา Minimum Spanning Tree ของเครือข่ายที่มีต้นทุนการเชื่อมต่อ (weighted edges) แสดงรายการ edge ที่เลือกและต้นทุนรวม
4. เปรียบเทียบเวลาที่ใช้ตรวจสอบ "เชื่อมกันหรือไม่" ระหว่าง Union Find กับ BFS/DFS เมื่อต้องตอบคำถามแบบนี้ซ้ำๆ กันหลายพันครั้งบนเครือข่ายเดิม แสดงผลเป็นตารางเปรียบเทียบ

## ข้อคิดสำคัญ (Key Takeaways)

- Union Find (Disjoint Set Union) จัดการเซตที่ไม่ทับซ้อนกัน รองรับ Find (หากลุ่ม) และ Union (รวมกลุ่ม) อย่างมีประสิทธิภาพสูง
- Path Compression (แบนโครงสร้างระหว่าง Find) และ Union by Rank/Size (เล็กไปอยู่ใต้ใหญ่เสมอ) เมื่อใช้ร่วมกันทำให้ Find/Union มี complexity เกือบคงที่ O(α(n))
- Union Find คือหัวใจสำคัญของ Kruskal's Algorithm ที่ใช้ตรวจสอบ cycle แบบรวดเร็วโดยไม่ต้อง traverse graph ใหม่ทุกครั้ง เชื่อมโยงกับ Greedy (บทที่ 26) โดยตรง
- เลือก Union Find เมื่อต้องตอบคำถาม "เชื่อมกันหรือไม่" ซ้ำหลายครั้งบน graph ที่เปลี่ยนแปลง (dynamic connectivity) แต่เลือก BFS/DFS เมื่อต้องการเส้นทางจริงหรือ graph คงที่ที่ query แค่ครั้งเดียว
- นี่คือบทสุดท้ายของ **Part 5: Algorithms** — ตลอด 10 บทที่ผ่านมา (Big O ถึง Union Find) ได้วางรากฐานอัลกอริทึมสำคัญเกือบทั้งหมดที่ใช้ในงานวิศวกรรมซอฟต์แวร์จริง บทถัดไปจะเข้าสู่ **Part 6: Object-Oriented Programming** ซึ่งเปลี่ยนโฟกัสจาก "การแก้ปัญหาด้วยอัลกอริทึม" ไปสู่ "การออกแบบโครงสร้างโค้ดให้จัดการและขยายง่าย"
