# บทที่ 7: Input/Output, Type Conversion

## แนวคิดหลัก (Concept)

โปรแกรมที่มีประโยชน์ต้อง **รับข้อมูลจากภายนอก** และ **ส่งผลลัพธ์ออกไป** — สองแนวคิดนี้เรียกว่า **Input/Output (I/O)** นอกจากนี้ ข้อมูลที่รับเข้ามามักไม่ตรงชนิดกับที่โปรแกรมต้องการใช้คำนวณ จึงต้องมี **Type Conversion (การแปลงชนิดข้อมูล)** มาเชื่อมสองฝั่งเข้าด้วยกัน

- **Input** — ข้อมูลที่โปรแกรมรับเข้ามาจากภายนอก เช่น คีย์บอร์ด, ไฟล์, เครือข่าย (API), ฐานข้อมูล, เซนเซอร์
- **Output** — ผลลัพธ์ที่โปรแกรมส่งออกไป เช่น พิมพ์หน้าจอ, เขียนไฟล์, ส่งผ่านเครือข่าย
- **Type Conversion** — การเปลี่ยนค่าจากชนิดข้อมูลหนึ่งไปเป็นอีกชนิดหนึ่ง แบ่งเป็น 2 แบบ:
  - **Implicit Conversion (Type Coercion)** — ภาษาแปลงให้อัตโนมัติโดยไม่ต้องสั่ง เช่น `1 + 2.5` ได้ `3.5` (int ถูกแปลงเป็น float โดยอัตโนมัติ)
  - **Explicit Conversion (Type Casting)** — โปรแกรมเมอร์สั่งแปลงเองชัดเจน เช่น `int("42")`, `str(3.14)`

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **I/O มีไว้เพื่อให้โปรแกรมมีประโยชน์ในโลกจริง**: โปรแกรมที่คำนวณอย่างเดียวโดยไม่รับ/ส่งข้อมูลกับภายนอกเลยแทบไม่มีประโยชน์ — ทุกแอปที่ใช้งานจริง (เว็บ, เกม, แอปมือถือ) ล้วนต้องรับ input จากผู้ใช้และแสดง output กลับ
- **ข้อมูล Input ทุกอย่างเข้ามาเป็น "ข้อความ" หรือ "bytes" เสมอในตอนแรก**: ไม่ว่าจะพิมพ์ตัวเลขจากคีย์บอร์ด หรืออ่านค่าจากไฟล์ ระบบจะได้รับมันมาเป็นลำดับตัวอักษร/ไบต์ก่อนเสมอ (ตามที่เรียนเรื่อง ASCII/Unicode ในบทที่ 2) ต้องแปลงเป็นชนิดข้อมูลที่ต้องการ (int, float) ก่อนถึงจะนำไปคำนวณได้ — นี่คือเหตุผลที่ Type Conversion จำเป็นคู่กับ I/O เสมอ
- **Type Conversion มีไว้เชื่อมโลกของข้อมูลดิบกับโลกของตรรกะการคำนวณ**: ถ้าไม่มีการแปลงชนิด โปรแกรมจะไม่สามารถนำข้อมูลจากภายนอก (ซึ่งเป็น text/bytes เสมอ) มาคำนวณทางคณิตศาสตร์ได้เลย

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Input** เหมือน **การสั่งอาหารที่เคาน์เตอร์** — ลูกค้าพูดคำสั่งซื้อ (input) ให้พนักงาน
- **Output** เหมือน **การเสิร์ฟอาหาร** — ครัวส่งจานอาหาร (output) กลับมาให้ลูกค้า
- **Type Conversion** เหมือน **ล่ามแปลภาษา** — ลูกค้าพูดภาษาหนึ่ง (ข้อความดิบ) ล่ามต้องแปลเป็นภาษาที่ครัวเข้าใจ (ตัวเลข/คำสั่งที่ระบบประมวลผลได้) ก่อนจะดำเนินการต่อได้

## แผนภาพอธิบาย (Visual explanation)

### วงจร Input → Process → Output

```
┌─────────┐     ┌──────────────┐     ┌─────────┐
│  INPUT  │ ──► │   PROCESS    │ ──► │ OUTPUT  │
│ (text/  │     │ (แปลงชนิด +   │     │ (text/  │
│  bytes) │     │  คำนวณ)       │     │  bytes) │
└─────────┘     └──────────────┘     └─────────┘
 คีย์บอร์ด            ตรรกะโปรแกรม         หน้าจอ
 ไฟล์                                     ไฟล์
 เครือข่าย                                 เครือข่าย
```

### Implicit vs Explicit Conversion

```
Implicit (ภาษาแปลงให้เอง):
   1 + 2.5           →  int ถูกยกระดับเป็น float โดยอัตโนมัติ  →  3.5
   "5" + "3"         →  string บวก string (ต่อกัน)             →  "53"

Explicit (สั่งแปลงเอง):
   int("42")         →  แปลง string เป็น int                   →  42
   float("3.14")     →  แปลง string เป็น float                 →  3.14
   str(100)          →  แปลง int เป็น string                    →  "100"
   int("abc")        →  แปลงไม่ได้!  เกิด ValueError/Exception
```

### ทำไม Input ต้องแปลงชนิดก่อนคำนวณเสมอ

```
ผู้ใช้พิมพ์:  "25"      ← นี่คือ STRING เสมอ ไม่ว่าผู้ใช้จะตั้งใจพิมพ์ตัวเลขแค่ไหน
                │
                ▼  ต้อง explicit convert
              int("25") = 25   ← ตอนนี้เป็น int แล้ว คำนวณได้

ถ้าลืมแปลง:  age = "25"
             age + 1     ← Error! (string บวก int ไม่ได้ในหลายภาษา)
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== Input =====
name = input("กรุณาใส่ชื่อของคุณ: ")     # input() คืนค่าเป็น string เสมอ
age_text = input("กรุณาใส่อายุของคุณ: ")  # ก็เป็น string เช่นกัน แม้พิมพ์ตัวเลข

# ===== Type Conversion (Explicit) =====
age = int(age_text)          # แปลง string -> int เพื่อนำไปคำนวณ
next_year_age = age + 1       # ตอนนี้บวกได้แล้ว เพราะเป็น int ทั้งคู่

# ===== Output =====
print("สวัสดีคุณ " + name)                     # string + string ต่อกันได้
print(f"ปีหน้าคุณจะอายุ {next_year_age} ปี")    # f-string แปลงค่าเป็น string ให้อัตโนมัติตอนแสดงผล

# ===== Error Handling สำหรับ Input ที่ไม่ถูกต้อง =====
user_input = input("ใส่ตัวเลข: ")
try:
    number = int(user_input)   # ถ้าผู้ใช้พิมพ์ "abc" จะเกิด ValueError
    print(f"สองเท่าของค่านี้คือ {number * 2}")
except ValueError:
    print("กรุณาใส่ตัวเลขที่ถูกต้อง")

# ===== File I/O =====
with open("output.txt", "w", encoding="utf-8") as f:
    f.write("บันทึกข้อมูลลงไฟล์\n")   # Output ไปยังไฟล์แทนหน้าจอ

with open("output.txt", "r", encoding="utf-8") as f:
    content = f.read()             # Input จากไฟล์
    print(content)
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `input("กรุณาใส่อายุของคุณ: ")` — โปรแกรมหยุดรอผู้ใช้พิมพ์ กดคีย์บอร์ด ระบบปฏิบัติการส่งตัวอักษรที่พิมพ์ (เป็นไบต์ ตามหลักการบทที่ 2) เข้าสู่โปรแกรม แล้ว Python ห่อค่านั้นเป็น **string** เสมอ ไม่ว่าผู้ใช้จะพิมพ์อะไรก็ตาม
2. `int(age_text)` — Python พยายามตีความ string นั้นเป็นตัวเลขฐาน 10 ถ้าตีความได้ (เช่น `"25"`) จะคืนค่า int `25` ถ้าตีความไม่ได้ (เช่น `"abc"` หรือ `"25.5"`) จะโยน exception `ValueError` ทันที
3. `age + 1` — ตอนนี้ทั้งสองฝั่งเป็น int แล้ว จึงคำนวณได้ตามปกติ (ถ้าไม่แปลงก่อน ขั้นตอนนี้จะ error เพราะ Python ไม่ยอมบวก string กับ int โดยอัตโนมัติ)
4. `f"...{next_year_age}..."` — f-string ทำ **implicit conversion** ให้อัตโนมัติตอนแสดงผล แปลงค่า int กลับเป็น string เพื่อนำไปต่อกับข้อความอื่นก่อนพิมพ์ออกทางหน้าจอ (output)
5. บล็อก `try/except` — ป้องกันโปรแกรม crash เมื่อผู้ใช้ป้อน input ที่แปลงชนิดไม่ได้ เป็นรูปแบบมาตรฐานในการรับมือกับ input ที่ไม่น่าเชื่อถือ (input จากผู้ใช้ไม่ควรถูกไว้ใจว่าจะถูกฟอร์แมตเสมอ)

## Time Complexity

- การอ่าน/เขียน input-output พื้นฐาน (คีย์บอร์ด, หน้าจอ) มีค่าใช้จ่ายคงที่ต่อการเรียกหนึ่งครั้ง แต่ในทางปฏิบัติ **I/O คือส่วนที่ช้าที่สุด** เมื่อเทียบกับการคำนวณในหน่วยความจำ (ตามลำดับความเร็วในบทที่ 1: RAM เร็วกว่า Disk/Network หลายพันถึงหลายแสนเท่า)
- Type conversion ของค่าพื้นฐาน (string สั้น → number) เป็น O(n) ตามความยาวของ string ที่ต้องอ่านทีละตัวอักษรเพื่อตีความ

## Space Complexity

การอ่านไฟล์ทั้งไฟล์เข้าหน่วยความจำในครั้งเดียว (`f.read()`) ใช้พื้นที่ O(n) ตามขนาดไฟล์ — ถ้าไฟล์ใหญ่มาก (เช่น หลาย GB) อาจทำให้ RAM ไม่พอ จึงมักใช้เทคนิคอ่านทีละบรรทัด/ทีละส่วน (streaming) แทนเพื่อควบคุมการใช้หน่วยความจำ

## แนวทางปฏิบัติที่ดี (Best Practices)

- **ไม่เคยไว้ใจ input จากภายนอกโดยไม่ตรวจสอบ** — ครอบด้วย try/except หรือ validation เสมอ เพราะผู้ใช้ (หรือไฟล์/API ภายนอก) อาจส่งข้อมูลที่ไม่ตรงรูปแบบที่คาดไว้
- ใช้ `with open(...)` แทนการเปิดไฟล์แบบ manual (`open()` ตรงๆ) เพราะ `with` รับประกันว่าไฟล์จะถูกปิดอัตโนมัติแม้เกิด error ระหว่างทาง (ป้องกัน resource leak)
- ระบุ encoding อย่างชัดเจนเสมอเมื่ออ่าน/เขียนไฟล์ (เช่น `encoding="utf-8"`) เพื่อป้องกันปัญหาตัวอักษรเพี้ยนตามที่เรียนในบทที่ 2
- แยกส่วนรับ input/ทำ output ออกจากส่วนตรรกะคำนวณหลักของโปรแกรม (ช่วยให้ทดสอบ/debug ง่ายขึ้น เพราะตรรกะไม่ผูกกับแหล่งข้อมูลเฉพาะ)

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ลืมว่า `input()` คืนค่าเป็น string เสมอ แล้วพยายามเอาไปคำนวณตรงๆ โดยไม่แปลงชนิดก่อน
- ไม่ครอบ error handling รอบการแปลงชนิดข้อมูลจาก input ทำให้โปรแกรม crash ทันทีที่ผู้ใช้พิมพ์ผิดรูปแบบ
- เปิดไฟล์แล้วลืมปิด (ไม่ใช้ `with`) ทำให้เกิด resource leak โดยเฉพาะเมื่อเปิดไฟล์จำนวนมากในลูป
- อ่านไฟล์ขนาดใหญ่ทั้งไฟล์เข้าหน่วยความจำในครั้งเดียวโดยไม่จำเป็น ทำให้โปรแกรมใช้ RAM สูงเกินควรหรือ crash จาก out-of-memory

## ข้อคิดสำคัญ (Key Takeaways)

- Input/Output คือช่องทางที่โปรแกรมสื่อสารกับโลกภายนอก (ผู้ใช้, ไฟล์, เครือข่าย) ทำให้โปรแกรมมีประโยชน์จริง
- ข้อมูล Input เข้ามาเป็นข้อความ/ไบต์เสมอในตอนแรก ต้องผ่าน Type Conversion (explicit) ก่อนนำไปคำนวณ
- Implicit conversion เกิดขึ้นอัตโนมัติโดยภาษา ส่วน Explicit conversion ต้องสั่งเองชัดเจน — ควรรู้ว่ากำลังใช้แบบไหนอยู่เสมอ
- Input จากภายนอกไม่ควรถูกไว้ใจว่าถูกต้องเสมอ ต้องมีการตรวจสอบ/จัดการ error เสมอ
- I/O เป็นส่วนที่ช้าที่สุดในโปรแกรมเมื่อเทียบกับการคำนวณในหน่วยความจำ (ตามลำดับความเร็วจากบทที่ 1) ควรออกแบบให้ทำ I/O เท่าที่จำเป็น
- บทถัดไปจะต่อยอดเรื่อง Scope, Lifetime, References, Pointers ซึ่งเกี่ยวข้องกับว่าตัวแปรที่รับ input เข้ามานั้น "มองเห็นได้" และ "มีชีวิตอยู่" ที่ไหนบ้างในโปรแกรม
