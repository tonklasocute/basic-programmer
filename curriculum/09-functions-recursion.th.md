# บทที่ 9: Functions, Parameters, Return Values, Recursion

## แนวคิดหลัก (Concept)

**Function (ฟังก์ชัน)** คือกลุ่มของ statement ที่ถูกตั้งชื่อและเก็บไว้เป็นหน่วยเดียว สามารถถูก "เรียกใช้" ซ้ำได้จากหลายจุดในโปรแกรม โดยไม่ต้องเขียนโค้ดเดิมซ้ำ

- **Parameter (พารามิเตอร์)** — ช่องรับค่าที่ฟังก์ชันประกาศไว้ล่วงหน้า ทำหน้าที่เป็น "ตัวแปร local" ที่รับค่าจากผู้เรียก
- **Argument (อาร์กิวเมนต์)** — ค่าจริงที่ส่งเข้าไปตอนเรียกฟังก์ชัน (คนละคำกับ parameter แต่มักใช้ปนกัน)
- **Return Value (ค่าที่คืนกลับ)** — ผลลัพธ์ที่ฟังก์ชันส่งกลับไปให้จุดที่เรียกมัน ผ่านคำสั่ง `return`
- **Recursion (การเรียกซ้ำตัวเอง)** — ฟังก์ชันที่เรียกตัวเองภายในนิยามของมันเอง เพื่อแก้ปัญหาที่แตกย่อยเป็นปัญหาย่อยแบบเดียวกันได้ (self-similar)

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Function มีไว้เพื่อ "DRY" (Don't Repeat Yourself)**: ถ้าไม่มีฟังก์ชัน โค้ดที่ต้องทำงานซ้ำๆ (เช่น คำนวณภาษี, ตรวจสอบ email) ต้อง copy-paste ทุกจุดที่ใช้ ทำให้แก้บั๊กครั้งเดียวไม่พอ ต้องไล่แก้ทุกจุดที่ copy ไว้
- **Parameter/Return มีไว้ให้ฟังก์ชันสื่อสารกับโลกภายนอกได้โดยไม่ผูกติดกับ context เฉพาะ**: ฟังก์ชันที่ดีควรทำงานเหมือนกล่องดำ (black box) — รับ input ทางเดียว (parameter) ส่ง output ทางเดียว (return) โดยไม่ต้องรู้ว่าใครเรียกมันหรือเรียกจากที่ไหน ทำให้นำไปใช้ซ้ำได้ในบริบทต่างๆ
- **Recursion มีไว้แก้ปัญหาที่มีโครงสร้างแบบ "ปัญหาย่อยเหมือนปัญหาใหญ่"**: ปัญหาบางอย่าง (เช่น การไล่โครงสร้างต้นไม้, การคำนวณแฟกทอเรียล) เขียนด้วย recursion จะสั้นและตรงกับธรรมชาติของปัญหามากกว่าเขียนด้วย loop ตรงๆ

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Function** เหมือน **เครื่องชงกาแฟอัตโนมัติ** — คุณใส่เมล็ดกาแฟและน้ำเข้าไป (parameter) กดปุ่ม (เรียกฟังก์ชัน) แล้วได้กาแฟออกมา (return value) โดยไม่ต้องรู้กลไกภายในเครื่องว่าทำงานอย่างไร และเครื่องเดียวกันนี้ใช้ชงกาแฟให้ใครก็ได้ กี่ครั้งก็ได้
- **Recursion** เหมือน **กระจกเงาสองบานหันเข้าหากัน** — ภาพในกระจกบานหนึ่งมีภาพสะท้อนของกระจกอีกบานซ้อนอยู่ข้างใน ซึ่งก็มีภาพสะท้อนซ้อนอยู่ข้างในอีกไปเรื่อยๆ จนกว่าจะถึงขีดจำกัด (เช่น ความละเอียดของแสง) — เปรียบได้กับ **base case** ที่ทำให้ recursion หยุดในที่สุด

## แผนภาพอธิบาย (Visual explanation)

### โครงสร้างฟังก์ชัน

```python
def calculate_area(width, height):   # "calculate_area" = ชื่อ, width/height = parameters
    area = width * height             # ตรรกะภายใน
    return area                       # return value ส่งกลับไปให้ผู้เรียก

result = calculate_area(5, 3)        # 5, 3 = arguments; result รับค่าที่ return กลับมา
#         └───┬───┘
#             └── เรียกฟังก์ชัน (function call)
```

### Recursion — ตัวอย่างแฟกทอเรียล (factorial)

```
factorial(4) = 4 * factorial(3)
             = 4 * (3 * factorial(2))
             = 4 * (3 * (2 * factorial(1)))
             = 4 * (3 * (2 * 1))              ← base case: factorial(1) = 1
             = 4 * (3 * 2)
             = 4 * 6
             = 24
```

```
Call Stack (ตามหลักการบทที่ 3 — LIFO):

┌─────────────────────┐
│ factorial(1) -> 1     │  ← เรียกล่าสุด, จบก่อน (base case)
├─────────────────────┤
│ factorial(2) -> 2*1   │
├─────────────────────┤
│ factorial(3) -> 3*2   │
├─────────────────────┤
│ factorial(4) -> 4*6   │  ← เรียกก่อน, จบสุดท้าย
└─────────────────────┘
        STACK
```

### ส่วนประกอบที่ recursion ทุกตัวต้องมี

```
1. Base Case (เงื่อนไขหยุด)   — ถ้าไม่มี จะเรียกตัวเองไม่จบ -> Stack Overflow (บทที่ 3)
2. Recursive Case (เรียกตัวเอง) — ต้องทำให้ปัญหา "เล็กลง" ทุกครั้งที่เรียก เพื่อให้ไปถึง base case ได้จริง
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== Function พื้นฐาน =====
def greet(name, greeting="สวัสดี"):    # greeting มีค่า default -> parameter ไม่บังคับ
    return f"{greeting}, {name}!"

print(greet("Alice"))                  # ใช้ default -> "สวัสดี, Alice!"
print(greet("Bob", "หวัดดี"))            # override default -> "หวัดดี, Bob!"

# ===== Multiple Return Values =====
def get_min_max(numbers):
    return min(numbers), max(numbers)   # คืนค่าหลายตัวพร้อมกัน (tuple)

low, high = get_min_max([4, 1, 9, 2])
print(low, high)                        # 1 9

# ===== Recursion: Factorial =====
def factorial(n):
    if n <= 1:            # Base Case
        return 1
    return n * factorial(n - 1)   # Recursive Case: ปัญหาเล็กลงทุกครั้ง (n-1)

print(factorial(4))       # 24

# ===== Recursion: Fibonacci (แสดงปัญหาประสิทธิภาพ) =====
def fibonacci(n):
    if n <= 1:
        return n
    return fibonacci(n - 1) + fibonacci(n - 2)

print(fibonacci(10))      # 55 (แต่ช้ามากถ้า n ใหญ่ — ดู Time Complexity ด้านล่าง)
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `greet("Alice")` — เมื่อไม่ส่ง argument ตัวที่สอง Python ใช้ **default parameter value** (`"สวัสดี"`) แทน พารามิเตอร์ที่มีค่า default ต้องอยู่**หลัง**พารามิเตอร์ที่ไม่มีค่า default เสมอในการประกาศฟังก์ชัน
2. `factorial(4)` — ตามหลักการ Stack ในบทที่ 3: เรียก `factorial(4)` จะ push stack frame ใหม่ที่ยังไม่จบ (รอผลจาก `factorial(3)`) แล้วเรียก `factorial(3)` ซ้อนเข้าไปอีก ไปเรื่อยๆ จนถึง `factorial(1)` ที่ชน **base case** (`n <= 1`) แล้ว return `1` ทันที จากนั้น stack frame จะถูก pop กลับขึ้นมาทีละชั้น คูณค่าไปเรื่อยๆ จนได้ `24`
3. `fibonacci(10)` — แต่ละการเรียกแตกออกเป็น **2 การเรียกย่อย** (`fibonacci(n-1)` และ `fibonacci(n-2)`) ทำให้จำนวนการเรียกฟังก์ชันทั้งหมดโตแบบ exponential เพราะค่าเดิมถูกคำนวณซ้ำหลายรอบ (เช่น `fibonacci(8)` ถูกเรียกซ้ำหลายครั้งจากกิ่งต่างๆ) — นี่คือตัวอย่างคลาสสิกที่แสดงให้เห็นว่า recursion ที่เขียนตรงไปตรงมาอาจไม่มีประสิทธิภาพ (จะแก้ด้วย memoization ในบท Dynamic Programming ภายหลัง)

## Time Complexity

- ฟังก์ชันทั่วไปที่ไม่มี loop/recursion ข้างใน: **O(1)** ต่อการเรียกหนึ่งครั้ง (ไม่นับตรรกะภายใน)
- `factorial(n)` แบบ recursive: **O(n)** — เรียกตัวเองลดค่าทีละ 1 จนถึง base case รวม n ครั้ง
- `fibonacci(n)` แบบ recursive ตรงไปตรงมา (ไม่มี memoization): **O(2ⁿ)** — เติบโตแบบ exponential เพราะคำนวณค่าเดิมซ้ำซ้อนจำนวนมาก ถือเป็นตัวอย่างสำคัญที่แสดงให้เห็นว่า recursion ไม่ได้มีประสิทธิภาพเสมอไป

## Space Complexity

- Recursion ทุกตัวใช้พื้นที่ **Stack** เพิ่มขึ้นตามความลึกของการเรียกซ้อน (**O(depth)**) — `factorial(n)` ใช้ Stack ลึก O(n) ส่วน `fibonacci(n)` แบบตรงไปตรงมาใช้ Stack ลึกสูงสุด O(n) เช่นกัน (แม้จำนวนการเรียกทั้งหมดจะเป็น O(2ⁿ) แต่ความลึกสูงสุด ณ เวลาใดเวลาหนึ่งไม่เกิน n)
- นี่คือเหตุผลที่ recursion ลึกเกินไปทำให้เกิด **Stack Overflow** ตามที่เรียนในบทที่ 3 — เมื่อ n ใหญ่มาก การเปลี่ยนมาเขียนด้วย loop (iteration) แทนอาจจำเป็น เพราะ loop ใช้พื้นที่ Stack คงที่ O(1) ไม่ว่าจะวนกี่รอบ

## แนวทางปฏิบัติที่ดี (Best Practices)

- ตั้งชื่อฟังก์ชันให้สื่อถึงสิ่งที่มันทำ (มักเป็นคำกริยา เช่น `calculate_total`, `is_valid_email`)
- ให้ฟังก์ชันทำหน้าที่เดียว (Single Responsibility) — ฟังก์ชันสั้นและโฟกัสเรื่องเดียวจะทดสอบและแก้บั๊กง่ายกว่า
- เขียน **base case ก่อนเสมอ** เมื่อออกแบบ recursive function และตรวจสอบว่าทุก recursive call ทำให้ปัญหา "เล็กลง" จริง เพื่อรับประกันว่าจะถึง base case ในที่สุด
- ถ้า recursion อาจลึกมาก (เช่น ประมวลผลข้อมูลนับล้านรายการ) ให้พิจารณาเขียนเป็น loop (iteration) แทน เพื่อหลีกเลี่ยง Stack Overflow

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ลืมเขียน base case หรือเขียนเงื่อนไข base case ผิด ทำให้ recursion เรียกตัวเองไม่มีที่สิ้นสุด → Stack Overflow
- recursive case ไม่ได้ทำให้ปัญหาเล็กลงจริง (เช่น เผลอเรียก `factorial(n)` แทน `factorial(n-1)`) ทำให้วนซ้ำไม่จบ
- เขียน recursive function อย่าง fibonacci โดยไม่ตระหนักถึงปัญหาประสิทธิภาพ exponential เมื่อ n มีค่ามาก ทำให้โปรแกรมค้าง
- ใช้ mutable default parameter (เช่น `def f(items=[])`) ในภาษาอย่าง Python ซึ่งเป็นกับดักชื่อดัง เพราะ list เริ่มต้นนั้นถูกสร้างครั้งเดียวและใช้ร่วมกันทุกครั้งที่เรียกฟังก์ชันโดยไม่ระบุ argument นั้น

**"เครื่องคำนวณ Fibonacci ที่มีประสิทธิภาพ (Memoized Fibonacci)"**: เขียนโปรแกรมที่:

3. วัดและเปรียบเทียบเวลาทำงานของทั้งสองฟังก์ชันเมื่อ n = 10, 20, 30, 35 แสดงเป็นตารางหรือกราฟง่ายๆ พร้อมอธิบายผลลัพธ์ที่เห็น (เชื่อมโยงกับ Time Complexity ด้านบน)

## ข้อคิดสำคัญ (Key Takeaways)

- ฟังก์ชันคือหน่วยของโค้ดที่นำกลับมาใช้ซ้ำได้ ช่วยลดการเขียนโค้ดซ้ำและทำให้โปรแกรมจัดระเบียบง่ายขึ้น
- Parameter/Argument/Return Value คือช่องทางสื่อสารระหว่างฟังก์ชันกับผู้เรียก โดยไม่ต้องผูกกับ context เฉพาะ
- Recursion คือฟังก์ชันที่เรียกตัวเอง ต้องมี base case (จุดหยุด) และ recursive case ที่ทำให้ปัญหาเล็กลงเสมอ
- Recursion ใช้พื้นที่ Stack ตามความลึกของการเรียก — ลึกเกินไปจะเกิด Stack Overflow (เชื่อมโยงกับบทที่ 3)
- Recursive function บางแบบ (เช่น fibonacci ตรงไปตรงมา) มีปัญหาประสิทธิภาพร้ายแรง (exponential time) ซึ่งต้องเข้าใจ Big O (บทที่ 20) เพื่อวิเคราะห์และแก้ไขด้วยเทคนิคอย่าง memoization
- บทถัดไปจะเข้าสู่ Part 3: Control Flow (if/else/switch/loop) ซึ่งเป็นอีกเครื่องมือสำคัญที่ทำงานร่วมกับฟังก์ชันในการควบคุมทิศทางของโปรแกรม
