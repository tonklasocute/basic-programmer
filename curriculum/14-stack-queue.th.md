# บทที่ 14: Stack & Queue //ต้องดู

## แนวคิดหลัก (Concept)

Array (บทที่ 12) และ Linked List (บทที่ 13) เป็นโครงสร้างข้อมูล "อเนกประสงค์" ที่เข้าถึงตำแหน่งไหนก็ได้ แต่บางครั้งเราต้อง**จำกัด**วิธีเข้าถึงข้อมูลให้เฉพาะเจาะจงมากขึ้น เพื่อสะท้อนกฎของปัญหาจริงและป้องกันการใช้งานผิดวิธี — **Stack** และ **Queue** คือโครงสร้างข้อมูลที่สร้างขึ้นจาก Array หรือ Linked List แต่บังคับกฎการเข้า-ออกที่ต่างกัน

- **Stack (สแตก)** — โครงสร้างข้อมูลแบบ **LIFO (Last In, First Out)** สิ่งที่ใส่เข้าไปล่าสุดจะถูกหยิบออกมาก่อนเสมอ (เหมือนที่เรียนเรื่อง Call Stack ในบทที่ 3 — นั่นคือ Stack ในความหมายนี้เป๊ะๆ)
  - `push(x)` — ใส่ค่าเข้าไปบนสุด
  - `pop()` — หยิบค่าบนสุดออก
  - `peek()`/`top()` — ดูค่าบนสุดโดยไม่หยิบออก
- **Queue (คิว)** — โครงสร้างข้อมูลแบบ **FIFO (First In, First Out)** สิ่งที่ใส่เข้าไปก่อนจะถูกหยิบออกมาก่อนเสมอ
  - `enqueue(x)` — ใส่ค่าเข้าไปท้ายคิว
  - `dequeue()` — หยิบค่าจากหัวคิวออก
  - `peek()`/`front()` — ดูค่าหัวคิวโดยไม่หยิบออก

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Stack มีไว้แก้ปัญหาที่มีธรรมชาติ "ย้อนกลับ" (undo/backtrack)**: หลายปัญหาในโลกจริงต้องจัดการสิ่งที่ทำล่าสุดก่อนเสมอ เช่น ปุ่ม Undo ในโปรแกรม (ย้อนการกระทำล่าสุดก่อน), การเรียกฟังก์ชันซ้อนกัน (function call ล่าสุดต้องจบก่อนถึงจะกลับไปทำฟังก์ชันที่เรียกมันได้ — ตามบทที่ 3), การตรวจสอบวงเล็บที่เปิด-ปิดถูกต้อง
- **Queue มีไว้แก้ปัญหาที่ต้อง "ยุติธรรม" ตามลำดับมาก่อน-หลัง**: เช่น คิวรอคิวธนาคาร (คนมาก่อนต้องได้บริการก่อน), งานพิมพ์เอกสารที่ส่งเข้าคิว printer, การประมวลผลข้อความ/request ตามลำดับที่เข้ามา
- **การจำกัดวิธีเข้าถึงข้อมูลไม่ใช่ข้อจำกัด แต่คือฟีเจอร์**: การบังคับว่า "เข้าถึงได้แค่ปลายด้านเดียว/สองด้านที่กำหนด" ทำให้โค้ดที่ใช้ Stack/Queue สื่อเจตนาชัดเจนกว่า และป้องกันบั๊กจากการเข้าถึงข้อมูลผิดตำแหน่งโดยไม่ตั้งใจ (เทียบกับ Array ที่เข้าถึงตำแหน่งไหนก็ได้ ซึ่งบางครั้งยืดหยุ่นเกินความจำเป็น)

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Stack** เหมือน **กองจานในบทที่ 3** (Stack Memory) — วางจานใหม่ทับบนสุด หยิบจานบนสุดออกก่อนเสมอ ไม่มีทางหยิบจานล่างสุดออกโดยไม่หยิบจานด้านบนออกก่อนทั้งหมด
- **Queue** เหมือน **แถวต่อคิวซื้อตั๋วหนัง** — คนที่มาต่อคิวก่อนจะได้ซื้อตั๋วก่อนเสมอ คนที่มาใหม่ต้องต่อท้ายแถว ไม่มีใครแซงคิวได้ (ถ้าไม่โกง)

### Stack กับ Call Stack (เชื่อมโยงบทที่ 3 และ 9)

```
เรียก a() -> b() -> c()   คือการ push stack frame ตามลำดับ
c() จบ -> pop c() ออกก่อน (LIFO)  -> b() จบ -> pop b() -> a() จบ -> pop a()

นี่คือเหตุผลที่ recursion (บทที่ 9) และ Stack เป็นเรื่องเดียวกันโดยธรรมชาติ
```

## ตัวอย่างโค้ด (Code example)

```python
# ===== Stack (ใช้ Python list ธรรมดา - append/pop ที่ท้ายคือ O(1)) =====
stack = []
stack.append(1)     # push
stack.append(2)
stack.append(3)
print(stack.pop())   # 3  (LIFO - ตัวล่าสุดออกก่อน)
print(stack.pop())   # 2

# ===== Queue (ห้ามใช้ list.pop(0) เพราะช้า O(n) - ใช้ collections.deque แทน) =====
from collections import deque
queue = deque()
queue.append(1)       # enqueue
queue.append(2)
queue.append(3)
print(queue.popleft())   # 1  (FIFO - ตัวแรกสุดออกก่อน)
print(queue.popleft())   # 2

# ===== ตัวอย่างจริง: ตรวจสอบวงเล็บเปิด-ปิดถูกต้องหรือไม่ (ใช้ Stack) =====
def is_balanced(expression):
    stack = []
    pairs = {")": "(", "]": "[", "}": "{"}
    for char in expression:
        if char in "([{":
            stack.append(char)             # push วงเล็บเปิด
        elif char in ")]}":
            if not stack or stack.pop() != pairs[char]:   # pop เทียบกับวงเล็บปิด
                return False
    return len(stack) == 0                  # ต้องไม่เหลือวงเล็บเปิดค้าง

print(is_balanced("({[]})"))   # True
print(is_balanced("({[}])"))   # False (ลำดับปิดผิด)

# ===== ตัวอย่างจริง: ประมวลผลงานตามลำดับ (ใช้ Queue) =====
print_jobs = deque(["doc1.pdf", "doc2.pdf", "doc3.pdf"])
while print_jobs:
    job = print_jobs.popleft()               # หยิบงานที่ส่งมาก่อนสุดมาพิมพ์ก่อน
    print(f"กำลังพิมพ์: {job}")
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `is_balanced("({[]})")` — ไล่ทีละตัวอักษร: เจอ `(` → push เข้า stack `["("]`, เจอ `{` → push `["(", "{"]`, เจอ `[` → push `["(", "{", "["]`, เจอ `]` (วงเล็บปิด) → `pop()` ได้ `[` ตรงกับที่ต้องการพอดี → เจอ `}` → `pop()` ได้ `{` ตรงกัน → เจอ `)` → `pop()` ได้ `(` ตรงกัน → stack ว่างพอดี (`len(stack) == 0`) → คืนค่า `True`
2. `is_balanced("({[}])")` — ไล่ไปจนเจอ `}` (ตัวที่ 4) แต่ `stack.pop()` ในตอนนั้นได้ `[` ไม่ตรงกับ `{` ที่ควรจะเป็น → คืนค่า `False` ทันที — นี่แสดงให้เห็นว่า **Stack เหมาะกับปัญหาที่ต้อง "จับคู่จากด้านในสุดออกมาด้านนอก" ตามธรรมชาติ** (ล่าสุดที่เปิดไว้ ต้องปิดก่อนเสมอ)
3. `queue.popleft()` ใน `deque` — ต่างจาก `list.pop(0)` ที่ต้องเลื่อนสมาชิกทั้งหมด O(n) (ตามบทที่ 12) `deque` ถูกออกแบบมาเป็น **Doubly Linked List ภายใน** (ตามบทที่ 13) ทำให้ทั้งการหยิบจากหัวและท้ายเป็น O(1) เหมือนกันหมด — นี่คือเหตุผลที่ควรใช้ `deque` แทน `list` เมื่อต้องทำ Queue จริงจัง

## Time Complexity

| Operation | Stack (list) | Queue (deque) | Queue (list — ไม่ควรใช้) |
|---|---|---|---|
| push/enqueue | O(1) | O(1) | O(1) |
| pop/dequeue | O(1) | O(1) | O(n) ← ต้องเลื่อนสมาชิกทั้งหมด |
| peek | O(1) | O(1) | O(1) |

ตารางนี้แสดงให้เห็นชัดเจนว่า **การเลือกโครงสร้างข้อมูลภายใน (implementation) มีผลต่อประสิทธิภาพโดยตรง** แม้แนวคิดระดับสูง (Queue) จะเหมือนกัน — ใช้ `list.pop(0)` ทำ Queue เป็นความผิดพลาดด้านประสิทธิภาพที่พบบ่อยมาก

## Space Complexity

ทั้ง Stack และ Queue ใช้พื้นที่ **O(n)** ตามจำนวนสมาชิกที่เก็บอยู่ เช่นเดียวกับ Array/Linked List ที่เป็นฐานราก

## ข้อดี (Advantages)

- Stack: จัดการปัญหาแบบ "ย้อนกลับ/ซ้อนกัน" ได้เป็นธรรมชาติ (undo, backtracking, recursion)
- Queue: รับประกันความยุติธรรมตามลำดับเวลาที่เข้ามา (FIFO) เหมาะกับงานที่ต้องประมวลผลตามคิว
- ทั้งสองแบบมี operation หลักที่ทำงานได้เร็ว O(1) เมื่อ implement ถูกวิธี

## ข้อเสีย (Disadvantages)

- ทั้งสองแบบ**ไม่รองรับการเข้าถึงข้อมูลตรงกลาง**โดยตรง (ต้อง pop/dequeue ออกมาทีละตัวถ้าต้องการเข้าถึงตัวที่ไม่ใช่ปลาย) — เป็นข้อจำกัดที่ตั้งใจ เพื่อบังคับวินัยการเข้าถึงข้อมูล
- ถ้า implement Queue ผิดวิธี (ใช้ Array ธรรมดาแล้ว dequeue จากต้น) จะช้ามาก O(n)

## การใช้งานจริง (Real-world usage)

- **Stack**: ปุ่ม Undo/Redo, การตรวจสอบ syntax วงเล็บในคอมไพเลอร์, Browser back button, Call Stack ของทุกภาษาโปรแกรม (บทที่ 3), Depth-First Search (DFS — บทอัลกอริทึม)
- **Queue**: ระบบคิวรอประมวลผลงาน (task queue เช่น Celery, RabbitMQ — บท System Design), Breadth-First Search (BFS — บทอัลกอริทึม), การจัดการ request ที่เข้ามาที่ server ตามลำดับ, buffer ของข้อมูล streaming

## แนวทางปฏิบัติที่ดี (Best Practices)

- ใช้ `list.append()`/`list.pop()` (ไม่มี argument) สำหรับ Stack ใน Python เพราะทั้งคู่ทำงานที่ท้าย list ซึ่งเป็น O(1)
- ใช้ `collections.deque` แทน `list` เสมอเมื่อต้องทำ Queue จริงจังใน Python เพื่อหลีกเลี่ยง O(n) จาก `pop(0)`
- เลือก Stack เมื่อโจทย์มีคำว่า "ล่าสุด", "ย้อนกลับ", "ซ้อนกัน" และเลือก Queue เมื่อโจทย์มีคำว่า "ตามลำดับ", "คิว", "ก่อน-หลัง"

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ใช้ `list.pop(0)` ทำ Queue ใน Python โดยไม่รู้ว่าเป็น O(n) ทำให้โปรแกรมช้าลงอย่างเห็นได้ชัดเมื่อข้อมูลมีจำนวนมาก
- พยายาม `pop()`/`dequeue()` จาก Stack/Queue ที่ว่างเปล่า ทำให้เกิด error ถ้าไม่ตรวจสอบก่อน (`if not stack:`)
- สับสนทิศทาง LIFO กับ FIFO เมื่อออกแบบอัลกอริทึม ทำให้ผลลัพธ์ผิดลำดับ (เช่น ใช้ Stack ทั้งที่โจทย์ต้องการ FIFO)
- ในการตรวจสอบวงเล็บ ลืมตรวจกรณี stack ว่างตอนเจอวงเล็บปิด (`if not stack or ...`) ทำให้ error เมื่อ input เริ่มต้นด้วยวงเล็บปิด

## ข้อคิดสำคัญ (Key Takeaways)

- Stack ทำงานแบบ LIFO (ล่าสุดเข้า-ออกก่อน) เหมาะกับปัญหาที่มีธรรมชาติย้อนกลับหรือซ้อนกัน เช่น undo, การเรียกฟังก์ชัน, ตรวจวงเล็บ
- Queue ทำงานแบบ FIFO (มาก่อนออกก่อน) เหมาะกับปัญหาที่ต้องประมวลผลตามลำดับเวลาที่เข้ามาอย่างยุติธรรม
- ทั้งสองแบบสร้างขึ้นจาก Array หรือ Linked List ที่เรียนมาก่อนหน้า แต่จำกัดวิธีเข้าถึงข้อมูลเพื่อสื่อเจตนาและป้องกันบั๊ก
- การเลือก implementation ที่ถูกต้อง (เช่น `deque` แทน `list` สำหรับ Queue) มีผลอย่างมากต่อ time complexity ในทางปฏิบัติ
- ทั้งสองโครงสร้างนี้เป็นรากฐานสำคัญของอัลกอริทึมที่จะเรียนภายหลัง โดยเฉพาะ DFS (ใช้ Stack) และ BFS (ใช้ Queue) ในบท Algorithms
- บทถัดไปจะเรียน Hash Table / Map / Set ซึ่งแก้ปัญหาคนละแบบ: การค้นหาข้อมูลให้เร็วโดยไม่ต้องไล่ทีละตัว
