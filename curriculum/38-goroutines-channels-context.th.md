# บทที่ 38: Goroutines, Channels, Context

## แนวคิดหลัก (Concept)

สองบทที่ผ่านมาสอน Concurrency แบบดั้งเดิม (Thread + Mutex/Semaphore) ที่**แชร์หน่วยความจำแล้วใช้กุญแจป้องกัน** ซึ่งเป็นแนวทางที่ใช้ในภาษาส่วนใหญ่ (Python, Java, C++) บทนี้ปิดท้าย **Part 8: Concurrency** ด้วยแนวทางที่ต่างออกไปโดยสิ้นเชิงจากภาษา **Go**: แทนที่จะแชร์หน่วยความจำแล้วล็อก ปรัชญาของ Go คือ **"อย่าสื่อสารด้วยการแชร์หน่วยความจำ ให้แชร์หน่วยความจำด้วยการสื่อสารแทน"** (Don't communicate by sharing memory; share memory by communicating)

- **Goroutine** — หน่วยการทำงานแบบ concurrent ของภาษา Go เบากว่า Thread ของระบบปฏิบัติการมาก (ใช้หน่วยความจำเริ่มต้นเพียงไม่กี่ KB เทียบกับ Thread ปกติที่ใช้เป็น MB) ทำให้สร้างได้เป็นหมื่นเป็นแสนตัวพร้อมกันโดยไม่มีปัญหา
- **Channel** — "ท่อ" สำหรับส่งข้อมูลระหว่าง Goroutine อย่างปลอดภัย แทนที่จะให้ Goroutine หลายตัวแก้ไขตัวแปรร่วมกันโดยตรง (ซึ่งต้องใช้ Mutex ตามบทที่ 36) ข้อมูลจะถูก "ส่งผ่าน" Channel จาก Goroutine หนึ่งไปอีกตัวหนึ่งแทน
- **Context** — กลไกสำหรับส่งสัญญาณ "ยกเลิก" หรือ "หมดเวลา" ข้ามหลาย Goroutine พร้อมกัน ทำให้ยกเลิกงานที่กำลังทำอยู่ได้อย่างเป็นระบบ โดยเฉพาะเมื่องานนั้นแตกออกเป็นหลาย Goroutine ย่อย

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Goroutine มีไว้แก้ปัญหา Thread ของระบบปฏิบัติการที่ "หนักเกินไป" สำหรับงานที่ต้องการ concurrency จำนวนมาก**: การสร้าง OS Thread แต่ละตัวมีต้นทุนสูง (หน่วยความจำ, เวลาสร้าง/สลับบริบท) ทำให้สร้างได้จำกัดจำนวน (หลักพันตัว) แต่เว็บเซิร์ฟเวอร์สมัยใหม่อาจต้องรับหลักหมื่นการเชื่อมต่อพร้อมกัน — Goroutine (จัดการโดย Go runtime เอง ไม่ใช่ OS โดยตรง) เบากว่ามากจึงรองรับจำนวนมหาศาลได้
- **Channel มีไว้กำจัดความจำเป็นในการใช้ Mutex ในหลายสถานการณ์**: บทที่ 36-37 แสดงให้เห็นว่าการแชร์หน่วยความจำแล้วล็อกด้วย Mutex เสี่ยงต่อ Race Condition และ Deadlock ถ้าใช้ไม่ระวัง — Channel เปลี่ยนวิธีคิดใหม่: ถ้าข้อมูล**ไม่เคยถูกแชร์เลย**แต่ถูก**ส่งต่อ**จาก Goroutine หนึ่งไปอีกตัวหนึ่งแทน (มีเจ้าของแค่ตัวเดียวเสมอในแต่ละขณะ) ปัญหา Race Condition จากการแชร์หน่วยความจำก็หายไปโดยธรรมชาติ
- **Context มีไว้จัดการการยกเลิกงานที่ซับซ้อนข้ามหลาย Goroutine อย่างเป็นระบบ**: เมื่องานหนึ่งแตกออกเป็นหลาย Goroutine ย่อย (เช่น เรียก API หลายตัวพร้อมกัน) ถ้าผู้ใช้ยกเลิกคำขอหรือหมดเวลา (timeout) ต้องมีวิธีบอกทุก Goroutine ย่อยให้หยุดทำงานพร้อมกันได้ ไม่ใช่ปล่อยให้ทำงานต่อไปโดยไม่มีประโยชน์ (สิ้นเปลืองทรัพยากร)

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Goroutine เทียบกับ Thread** เหมือน **นกกระจอกเทียบกับช้าง** — ทั้งคู่เป็นสิ่งมีชีวิตที่เคลื่อนที่ได้ (ทำงานแบบ concurrent ได้) แต่นกกระจอกตัวเล็กและเบากว่ามาก ทำให้เลี้ยงนกกระจอกได้เป็นฝูงใหญ่ในพื้นที่เดียวกับที่เลี้ยงช้างได้แค่ไม่กี่ตัว
- **Channel** เหมือน **สายพานลำเลียงระหว่างสถานีงานในโรงงาน** — แทนที่คนงานสองคนจะแย่งกันหยิบชิ้นงานจากกล่องเดียวกัน (แชร์หน่วยความจำ) คนงานคนแรกวางชิ้นงานบนสายพาน (ส่งเข้า Channel) แล้วคนงานคนที่สองหยิบจากสายพานไปทำงานต่อ (รับจาก Channel) — ไม่มีทางแย่งกันหยิบชิ้นงานเดียวกันพร้อมกันได้เลย เพราะสายพานส่งต่อให้ทีละชิ้น
- **Context** เหมือน **สัญญาณไฟไหม้ที่กระจายไปทุกชั้นของตึกพร้อมกัน** — เมื่อมีเหตุฉุกเฉิน (ยกเลิก/หมดเวลา) สัญญาณส่งไปถึงทุกคนในตึก (ทุก Goroutine) พร้อมกันทันที ไม่ต้องเดินไปบอกทีละชั้นทีละคน

## แผนภาพอธิบาย (Visual explanation)

### Goroutine เทียบกับ OS Thread — น้ำหนักที่ต่างกันมาก

```
OS Thread:                              Goroutine:
- หน่วยความจำเริ่มต้น ~1-8 MB ต่อตัว        - หน่วยความจำเริ่มต้น ~2 KB ต่อตัว (ขยายได้ตามต้องการ)
- OS จัดการ scheduling                  - Go runtime จัดการ scheduling เอง (เบากว่า)
- สร้างได้จริงหลักพันตัว                    - สร้างได้จริงหลักแสน-ล้านตัวในเครื่องเดียว

go doSomething()    <- คำสั่งง่ายๆ แค่คำเดียว (keyword "go") สร้าง Goroutine ใหม่ทันที
```

### Channel — ส่งข้อมูลระหว่าง Goroutine โดยไม่ต้องแชร์หน่วยความจำ

```
Goroutine A (Producer)                Channel                Goroutine B (Consumer)

data := compute()
ch <- data          -------------->  [ data ]  -------------->  received := <-ch
(ส่งเข้า channel)                      (ท่อส่งข้อมูล)                (รับจาก channel)

ไม่มีตัวแปรใดที่ทั้ง A และ B เข้าถึงพร้อมกันเลย -> ไม่มี Race Condition จากการแชร์หน่วยความจำ
ข้อมูลมีเจ้าของแค่ฝั่งเดียวในแต่ละขณะ: ก่อนส่งเป็นของ A, หลังส่งเป็นของ B เท่านั้น
```

### Fan-out/Fan-in Pattern — หลาย Goroutine ทำงานพร้อมกัน แล้วรวมผลลัพธ์

```
                     ┌──> Worker 1 ──┐
jobs channel  ──────>├──> Worker 2 ──┼──> results channel ──> รวบรวมผลลัพธ์ทั้งหมด
                     └──> Worker 3 ──┘

Fan-out: งานจาก jobs channel กระจายไปให้ Worker หลายตัวทำงานพร้อมกัน (ขนานกัน)
Fan-in:  ผลลัพธ์จากทุก Worker ไหลกลับมารวมกันที่ results channel เดียว
```

### Context — ยกเลิกหลาย Goroutine พร้อมกันด้วยสัญญาณเดียว

```
context.WithTimeout(parentCtx, 5*time.Second)
        |
        ├──> Goroutine 1: เช็ค ctx.Done() ทุกรอบ loop
        ├──> Goroutine 2: เช็ค ctx.Done() ทุกรอบ loop
        └──> Goroutine 3: เช็ค ctx.Done() ทุกรอบ loop

เมื่อครบ 5 วินาที (หรือถูก cancel() เรียกจากที่ไหนก็ได้):
ctx.Done() channel ถูกปิด -> ทุก Goroutine ที่เช็คอยู่เห็นสัญญาณพร้อมกันทันที -> หยุดทำงานทั้งหมด
```

## ตัวอย่างโค้ด (Code example)

```go
package main

import (
    "context"
    "fmt"
    "sync"
    "time"
)

// ===== Goroutine พื้นฐาน — สร้างง่ายด้วย keyword "go" =====
func sayHello(name string, wg *sync.WaitGroup) {
    defer wg.Done()                              // บอกว่างานนี้เสร็จแล้ว (เทียบเท่า t.join() ในบทที่ 36)
    fmt.Printf("Hello, %s!\n", name)
}

func main() {
    var wg sync.WaitGroup
    for _, name := range []string{"Alice", "Bob", "Charlie"} {
        wg.Add(1)                                   // เพิ่มตัวนับก่อนเริ่ม goroutine ใหม่
        go sayHello(name, &wg)                        // สร้าง goroutine ใหม่ทันที ทำงานแบบ concurrent
    }
    wg.Wait()                                       // รอทุก goroutine ทำงานเสร็จ

    // ===== Channel — ส่งข้อมูลระหว่าง Goroutine โดยไม่ต้องล็อก =====
    ch := make(chan int)                            // สร้าง channel สำหรับส่งค่า int
    go func() {
        result := 2 + 3                               // Goroutine คำนวณผลลัพธ์
        ch <- result                                    // ส่งเข้า channel (block จนกว่าจะมีคนรับ)
    }()
    received := <-ch                                  // รับค่าจาก channel (block จนกว่าจะมีข้อมูลส่งมา)
    fmt.Println("Received:", received)                // 5

    // ===== Fan-out/Fan-in: หลาย Worker ทำงานพร้อมกันผ่าน Channel =====
    jobs := make(chan int, 5)
    results := make(chan int, 5)

    for w := 1; w <= 3; w++ {                       // สร้าง Worker 3 ตัว (fan-out)
        go worker(w, jobs, results)
    }
    for j := 1; j <= 5; j++ {
        jobs <- j                                       // ส่งงานเข้า channel
    }
    close(jobs)                                       // ปิด channel เมื่อไม่มีงานเพิ่มแล้ว

    for a := 1; a <= 5; a++ {
        fmt.Println("Result:", <-results)               // รับผลลัพธ์กลับมา (fan-in)
    }

    // ===== Context — ยกเลิกงานที่ใช้เวลานานเกินไป =====
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()                                    // ปล่อยทรัพยากรของ context เมื่อจบฟังก์ชันเสมอ
    doLongTask(ctx)
}

func worker(id int, jobs <-chan int, results chan<- int) {
    for j := range jobs {                            // วนรับงานจาก jobs channel จนกว่าจะถูกปิด
        results <- j * 2                                // ประมวลผลแล้วส่งผลลัพธ์เข้า results channel
    }
}

func doLongTask(ctx context.Context) {
    select {
    case <-time.After(5 * time.Second):              // งานที่ใช้เวลา 5 วินาที
        fmt.Println("Task completed")
    case <-ctx.Done():                                 // แต่ context timeout ไว้แค่ 2 วินาที
        fmt.Println("Task cancelled:", ctx.Err())        // "context deadline exceeded" -> ยกเลิกก่อนงานเสร็จ
    }
}
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `go sayHello(name, &wg)` — คีย์เวิร์ด `go` วางไว้หน้าการเรียกฟังก์ชันใดๆ ทำให้ Go runtime สร้าง **Goroutine ใหม่** ทันทีเพื่อรันฟังก์ชันนั้นแบบ concurrent กับโค้ดส่วนที่เหลือ โดยไม่รอให้ฟังก์ชันทำงานเสร็จก่อน (ต่างจากการเรียกฟังก์ชันปกติที่ต้องรอ) — `sync.WaitGroup` ทำหน้าที่คล้าย `t.join()` ในบทที่ 36: `wg.Add(1)` เพิ่มตัวนับก่อนเริ่มงาน, `wg.Done()` (เรียกผ่าน `defer` ให้ทำงานอัตโนมัติเมื่อฟังก์ชันจบ) ลดตัวนับ, `wg.Wait()` บล็อกจนกว่าตัวนับจะกลับมาเป็น 0 (ทุก Goroutine เสร็จหมดแล้ว)
2. `ch <- result` และ `received := <-ch` — ตัวดำเนินการ `<-` ใช้ทั้งส่งและรับข้อมูลผ่าน channel: `ch <- result` **ส่ง** ค่าเข้า channel (ฝั่งซ้ายคือ channel ฝั่งขวาคือค่าที่ส่ง) ส่วน `<-ch` **รับ** ค่าจาก channel (ไม่มี object ฝั่งซ้ายก็ได้ถ้าไม่ต้องการเก็บค่า) — โดยดีฟอลต์ (unbuffered channel อย่าง `make(chan int)`) การส่งจะ**บล็อก**จนกว่าจะมีอีกฝั่งพร้อมรับ และการรับก็บล็อกจนกว่าจะมีข้อมูลส่งมา ทำให้ทั้งสอง Goroutine **ซิงค์กันโดยอัตโนมัติ**ผ่านการส่ง/รับนี้เอง โดยไม่ต้องใช้ Mutex เลย
3. `worker(id, jobs, results)` — พารามิเตอร์ `jobs <-chan int` (รับได้อย่างเดียว) และ `results chan<- int` (ส่งได้อย่างเดียว) คือการระบุทิศทางของ channel อย่างชัดเจนในระดับ type system ป้องกันไม่ให้ Worker ส่งเข้า `jobs` หรือรับจาก `results` โดยไม่ตั้งใจ — `for j := range jobs` วนรับงานจาก channel ไปเรื่อยๆ จน**channel ถูกปิด** (`close(jobs)` ในฟังก์ชันหลัก) จึงจะออกจาก loop โดยอัตโนมัติ ซึ่งเป็นวิธีมาตรฐานในการบอก Goroutine ว่า "ไม่มีงานเพิ่มแล้ว"
4. `select { case <-time.After(5*time.Second): ... case <-ctx.Done(): ... }` — คำสั่ง `select` รอ**หลาย channel พร้อมกัน** แล้วทำงานตาม case ของ channel ที่**พร้อมก่อน**ตัวอื่น ในตัวอย่างนี้ `time.After(5*time.Second)` จำลองงานที่ใช้เวลา 5 วินาที แต่ `ctx.Done()` (จาก `context.WithTimeout(..., 2*time.Second)`) พร้อมก่อนที่ 2 วินาที เพราะตั้ง timeout ไว้สั้นกว่า จึงเข้า case `ctx.Done()` และพิมพ์ข้อความยกเลิกแทนที่จะรอจนงานเสร็จ

## Time Complexity

- การสร้าง Goroutine ใหม่ (`go func()`): **O(1)** และเร็วกว่าการสร้าง OS Thread มาก เพราะ Go runtime จัดการ scheduling เองโดยไม่ต้องผ่าน system call ของ OS ทุกครั้ง
- การส่ง/รับผ่าน Channel: **O(1)** ต่อการดำเนินการหนึ่งครั้ง (ไม่นับเวลาที่อาจต้องรอบล็อกจนกว่าอีกฝั่งพร้อม)
- Fan-out/Fan-in ด้วย k Worker ประมวลผล n งาน: **O(n/k)** ต่อ Worker โดยประมาณ (ถ้างานแบ่งเท่าๆ กัน) รวมเป็น **O(n)** total work แต่ทำงานแบบขนานจริงบน CPU หลายคอร์

## Space Complexity

- Goroutine แต่ละตัวใช้พื้นที่เริ่มต้นเพียง **~2 KB** (ขยายอัตโนมัติเมื่อจำเป็น) เทียบกับ OS Thread ที่ใช้ **~1-8 MB** ต่อตัว — ทำให้สร้าง Goroutine จำนวนมาก (หลักแสน) ยังคงใช้หน่วยความจำรวมน้อยกว่าการสร้าง OS Thread จำนวนเท่ากันมาก
- Buffered Channel (`make(chan int, 5)`) ใช้พื้นที่ **O(buffer size)** สำหรับเก็บข้อมูลที่รอการรับ

## แนวทางปฏิบัติที่ดี (Best Practices)

- ใช้ Channel เป็นทางเลือกแรกสำหรับการสื่อสารระหว่าง Goroutine แทน Mutex เมื่อเป็นไปได้ (ตามปรัชญาของ Go) แต่ถ้าแค่ต้องการป้องกันการเข้าถึงตัวแปรร่วมกันแบบง่ายๆ (เช่น counter) การใช้ Mutex ยังคงเหมาะสมกว่าในบางกรณี — ไม่มีกฎตายตัวว่าต้องใช้ Channel เสมอ
- ปิด Channel (`close()`) เสมอเมื่อไม่มีข้อมูลจะส่งเพิ่มแล้ว เพื่อให้ฝั่งที่ `range` รับข้อมูลรู้ว่าควรหยุด loop — แต่**ห้ามปิด Channel มากกว่าหนึ่งครั้ง** หรือส่งข้อมูลเข้า Channel ที่ปิดแล้ว เพราะจะทำให้โปรแกรม panic
- ใช้ `context.WithTimeout` หรือ `context.WithCancel` เสมอสำหรับงานที่อาจใช้เวลานานหรือเรียก network/API ภายนอก เพื่อป้องกันไม่ให้ Goroutine ทำงานค้างตลอดไปโดยไม่มีทางยกเลิก

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ลืม `wg.Wait()` (หรือกลไกรออื่นๆ) ทำให้โปรแกรมหลัก (`main`) จบการทำงานก่อนที่ Goroutine ย่อยจะทำงานเสร็จ ผลลัพธ์จาก Goroutine เหล่านั้นจึงไม่ถูกแสดงเลย
- ส่งข้อมูลเข้า unbuffered channel โดยไม่มีใครรอรับอยู่ฝั่งตรงข้าม ทำให้เกิด **Deadlock** ทันที (โปรแกรมค้าง) เพราะการส่งจะบล็อกตลอดไปถ้าไม่มีคนรับ
- ปิด Channel ที่ยังมี Goroutine อื่นพยายามส่งข้อมูลเข้าอยู่ ทำให้เกิด panic "send on closed channel"
- ลืมเรียก `cancel()` (ที่ได้จาก `context.WithCancel`/`WithTimeout`) ทำให้ทรัพยากรที่ผูกกับ context ไม่ถูกปล่อยคืนอย่างถูกต้อง (ควรใช้ `defer cancel()` เสมอทันทีหลังสร้าง context)

## คำถามสัมภาษณ์งาน (Interview Questions)

1. Goroutine ต่างจาก OS Thread อย่างไร ทำไมถึงสร้างได้จำนวนมากกว่ามาก
2. อธิบายปรัชญา "Don't communicate by sharing memory; share memory by communicating" ของภาษา Go
3. Unbuffered Channel ต่างจาก Buffered Channel อย่างไร แต่ละแบบมีพฤติกรรมการบล็อกต่างกันอย่างไร
4. Context มีไว้แก้ปัญหาอะไร ทำไมถึงสำคัญเมื่องานหนึ่งแตกออกเป็นหลาย Goroutine ย่อย
5. Channel-based concurrency (แนวทางของ Go) แก้ปัญหา Race Condition ได้อย่างไร เทียบกับแนวทาง Mutex/Semaphore (บทที่ 36) ที่เรียนมาก่อนหน้า

## แบบฝึกหัด (Practice Exercises)

1. เขียนโปรแกรม Go ที่สร้าง Goroutine 10 ตัว แต่ละตัวคำนวณผลรวมของตัวเลขในช่วงที่ต่างกัน แล้วส่งผลลัพธ์กลับผ่าน Channel มารวมกันเป็นผลรวมสุดท้าย
2. เขียนระบบ Fan-out/Fan-in (ตามตัวอย่างในบทเรียน) ที่มี Worker จำนวนปรับได้ ประมวลผลงาน 100 ชิ้น แล้ววัดเวลาที่ใช้เมื่อมี Worker 1, 5, 10 ตัว เปรียบเทียบกัน
3. เขียนฟังก์ชันที่เรียก "API จำลอง" (ใช้ `time.Sleep` แทนการเรียกจริง) ผ่าน Context ที่มี timeout 3 วินาที แล้วทดสอบทั้งกรณีที่ API ตอบเร็วกว่า timeout และช้ากว่า timeout

4. แสดงรายงานสรุป: ไฟล์ไหนดาวน์โหลดสำเร็จ, ไฟล์ไหนถูกยกเลิกเพราะ timeout, ใช้เวลารวมทั้งหมดเท่าไหร่ เปรียบเทียบกับการดาวน์โหลดทีละไฟล์แบบ sequential

## ข้อคิดสำคัญ (Key Takeaways)

- Goroutine เป็นหน่วยการทำงาน concurrent ที่เบากว่า OS Thread มาก (จัดการโดย Go runtime เอง) ทำให้สร้างได้จำนวนมหาศาลในโปรแกรมเดียว
- Channel เปลี่ยนวิธีจัดการ concurrency จาก "แชร์หน่วยความจำแล้วล็อก" (Mutex ในบทที่ 36) เป็น "ส่งข้อมูลผ่านท่อ" ทำให้ข้อมูลมีเจ้าของแค่ฝั่งเดียวเสมอ ลดความเสี่ยง Race Condition โดยธรรมชาติ
- Fan-out/Fan-in Pattern ใช้ Channel กระจายงานให้หลาย Goroutine ทำงานพร้อมกัน แล้วรวมผลลัพธ์กลับมาที่เดียว
- Context ใช้ส่งสัญญาณยกเลิกหรือ timeout ข้ามหลาย Goroutine พร้อมกันอย่างเป็นระบบ ป้องกันการทำงานค้างโดยไม่มีประโยชน์
- ปรัชญาของ Go ("อย่าสื่อสารด้วยการแชร์หน่วยความจำ ให้แชร์หน่วยความจำด้วยการสื่อสารแทน") เป็นแนวทางที่ต่างจาก Thread+Mutex ที่เรียนในบทที่ 36-37 แต่ทั้งสองแนวทางล้วนแก้ปัญหา Concurrency แบบเดียวกัน เพียงมองปัญหาจากมุมต่างกัน
- นี่คือบทปิดท้าย **Part 8: Concurrency** — บทถัดไปจะเข้าสู่ **Part 9: Databases** ซึ่งเชื่อมโยงกับ Concurrency โดยตรงในหัวข้อ Transactions และ Isolation Levels (ปัญหาเดียวกันกับ Race Condition แต่เกิดในบริบทของฐานข้อมูล) โดยเริ่มจาก SQL vs NoSQL, Normalization
