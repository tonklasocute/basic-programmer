# บทที่ 46: Process Communication

## แนวคิดหลัก (Concept)

บทที่แล้วปิดท้ายด้วยคำถามสำคัญ: ถ้า Virtual Memory แยก address space ของแต่ละ process ออกจากกันอย่างสมบูรณ์ (process หนึ่งเข้าถึงหน่วยความจำของอีก process ไม่ได้เลย) แล้ว process ต่างๆ จะสื่อสารแลกเปลี่ยนข้อมูลกันได้อย่างไร? บทนี้เป็นบทปิดท้าย **Part 11: Operating Systems** โดยแนะนำกลไก **Inter-Process Communication (IPC)** ที่ OS จัดเตรียมไว้ให้ process ที่แยกหน่วยความจำกันโดยสิ้นเชิงสามารถสื่อสารกันได้อย่างปลอดภัย

- **IPC (Inter-Process Communication)** — กลุ่มกลไกที่ OS จัดเตรียมไว้ให้ process ต่างๆ แลกเปลี่ยนข้อมูลกันได้ แม้จะมี address space แยกจากกันอย่างสมบูรณ์ (ตามที่เรียนในบทที่แล้ว)
- **Pipe** — ช่องทางสื่อสารทางเดียว (หรือสองทางถ้าใช้ named pipe) ระหว่าง process ที่มีความสัมพันธ์กัน (เช่น process แม่-ลูก) ทำงานคล้าย Queue (FIFO จากบทที่ 14): ข้อมูลที่เขียนเข้าไปก่อนจะถูกอ่านออกมาก่อน
- **Shared Memory** — เทคนิคที่ OS อนุญาตให้หลาย process **แมปพื้นที่หน่วยความจำจริงชิ้นเดียวกัน**เข้ามาใน address space ของตัวเอง ทำให้เข้าถึงข้อมูลเดียวกันได้เร็วที่สุด (แต่ต้องใช้ Mutex/Semaphore จากบทที่ 36 ป้องกัน Race Condition เพราะเป็นการแชร์หน่วยความจำจริง)
- **Message Queue** — คิวข้อความที่ OS จัดการให้ process หลายตัวส่ง/รับข้อความแบบมีโครงสร้างกันได้ โดยไม่ต้องเชื่อมต่อกันโดยตรงตลอดเวลา
- **Socket** — กลไกสื่อสารที่ใช้ได้ทั้งระหว่าง process บนเครื่องเดียวกันและข้ามเครื่องผ่านเครือข่าย (ทบทวนจากบทที่ 42) ทำให้เป็นกลไก IPC ที่ยืดหยุ่นที่สุด

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **IPC มีไว้เพราะโปรแกรมสมัยใหม่แทบไม่มีตัวไหนทำงานอย่างโดดเดี่ยว**: เว็บเซิร์ฟเวอร์ต้องคุยกับฐานข้อมูล (คนละ process), เชลล์คำสั่ง (`ls | grep`) ต้องส่งผลลัพธ์จากโปรแกรมหนึ่งไปอีกโปรแกรมหนึ่ง, ระบบ Microservices (จะเรียนในบทถัดๆ ไป) ต้องให้ service หลายตัวคุยกัน — ถ้าไม่มีกลไก IPC ที่ปลอดภัย process ที่แยกหน่วยความจำกันจะทำงานร่วมกันไม่ได้เลย
- **Pipe มีไว้สำหรับรูปแบบการสื่อสารที่ง่ายที่สุด: ส่งข้อมูลทางเดียวระหว่าง process ที่เกี่ยวข้องกัน**: เหมาะกับสถานการณ์อย่างคำสั่งเชลล์ที่ต่อกันเป็นสายพาน (`cmd1 | cmd2 | cmd3`) ที่แต่ละคำสั่งส่งผลลัพธ์ให้คำสั่งถัดไปโดยตรง
- **Shared Memory มีไว้เมื่อความเร็วสำคัญที่สุด**: การส่งข้อมูลผ่าน Pipe หรือ Socket ต้อง**คัดลอกข้อมูล**ผ่าน OS kernel ไปมาหลายครั้ง (ช้ากว่า) ในขณะที่ Shared Memory ให้ process เข้าถึงข้อมูลชุดเดียวกันโดยตรงโดยไม่ต้องคัดลอกเลย — เร็วที่สุดในบรรดา IPC ทั้งหมด แต่แลกมาด้วยความซับซ้อนในการจัดการ Race Condition เอง
- **Message Queue มีไว้เมื่อ process ที่สื่อสารกันไม่จำเป็นต้องทำงานพร้อมกันตลอดเวลา**: ต่างจาก Pipe ที่มักต้องการให้ทั้งสองฝั่งพร้อมทำงานพร้อมกัน Message Queue ให้ process หนึ่งส่งข้อความทิ้งไว้ได้แม้อีก process จะยังไม่พร้อมรับในขณะนั้น (คล้ายหลักการของ Message Queue ระบบใหญ่ที่จะเรียนในบท System Design)

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Pipe** เหมือน **ท่อส่งเอกสารระหว่างสองแผนกที่อยู่ติดกัน** — แผนกหนึ่งใส่เอกสารเข้าท่อ อีกแผนกดึงออกมาอ่านตามลำดับที่ใส่เข้าไป (FIFO) ใช้ได้เฉพาะสองแผนกที่เชื่อมท่อกันโดยตรงเท่านั้น
- **Shared Memory** เหมือน **กระดานไวท์บอร์ดกลางที่ทุกคนในห้องประชุมเห็นและเขียนได้พร้อมกัน** — เร็วที่สุดเพราะทุกคนเห็นข้อมูลเดียวกันทันที แต่ต้องมีกติกาชัดเจน (เหมือน Mutex) ว่าใครเขียนได้เมื่อไหร่ ไม่งั้นจะเขียนทับกันสับสน
- **Message Queue** เหมือน **กล่องจดหมายส่วนกลางที่ทิ้งจดหมายไว้ได้แม้ผู้รับไม่อยู่** — ผู้ส่งไม่ต้องรอผู้รับมาเปิดอ่านทันที ผู้รับมาเปิดดูเมื่อพร้อมภายหลังได้
- **Socket** เหมือน **หมายเลขโทรศัพท์ที่ใช้โทรได้ทั้งในบ้านเดียวกันและข้ามประเทศ** — กลไกเดียวกันใช้ได้ทั้งสื่อสารในเครื่องเดียวกันและข้ามเครือข่ายทั่วโลก (เชื่อมโยงกับ TCP/IP บทที่ 42)

## แผนภาพอธิบาย (Visual explanation)

### Pipe — ท่อสื่อสารทางเดียวระหว่าง Process แม่-ลูก

```
Process แม่ (Parent)                    Process ลูก (Child)

write_end -----> [Pipe Buffer] -----> read_end

parent เขียนข้อมูลเข้า write_end             child อ่านข้อมูลจาก read_end
ข้อมูลไหลทางเดียว เรียงลำดับตามที่เขียนเข้าไป (FIFO เหมือน Queue บทที่ 14)

คำสั่งเชลล์: ls -la | grep ".txt"
             └─ process 1 ──┘ └─ pipe ─┘ └─ process 2 ──┘
```

### Shared Memory — สองอย่าง Process เข้าถึงหน่วยความจำจริงชิ้นเดียวกัน

```
Process A                              Process B

Virtual Address 0x2000  --\                /-- Virtual Address 0x3000
                            \              /
                             v            v
                    Physical Memory: [Shared Block]
                    (แมปเข้ามาในทั้งสอง address space พร้อมกัน)

A เขียนข้อมูล -> B เห็นการเปลี่ยนแปลงทันที (ไม่ต้องคัดลอกผ่าน kernel เหมือน Pipe/Socket)
ต้องใช้ Mutex (บทที่ 36) ป้องกัน Race Condition เพราะเป็นการแชร์หน่วยความจำจริง
```

### เปรียบเทียบความเร็วและความซับซ้อนของแต่ละกลไก IPC

```
                    เร็ว <---------------------------------------------> ช้า
Shared Memory   ────●──────────────────────────────────────────────────
Pipe            ─────────────●────────────────────────────────────────
Message Queue   ────────────────────●─────────────────────────────────
Socket (local)  ──────────────────────────●───────────────────────────
Socket (network)────────────────────────────────────────●─────────────

                    ง่าย <--------------------------------------------> ซับซ้อน (ต้องจัดการ sync เอง)
Message Queue   ────●──────────────────────────────────────────────────
Pipe            ─────────●─────────────────────────────────────────────
Socket          ──────────────●────────────────────────────────────────
Shared Memory   ────────────────────────●──────────────────────────────
```

## ตัวอย่างโค้ด (Code example)

```python
import multiprocessing
import time

# ===== Pipe: สื่อสารทางเดียวระหว่าง Process แม่-ลูก =====
def child_process_pipe(conn):
    conn.send("Hello from child!")                    # ส่งข้อมูลเข้า pipe
    conn.close()

if __name__ == "__main__":
    parent_conn, child_conn = multiprocessing.Pipe()     # สร้าง pipe คู่ (สองทาง)
    p = multiprocessing.Process(target=child_process_pipe, args=(child_conn,))
    p.start()
    print(parent_conn.recv())                             # "Hello from child!" -- รับจาก pipe
    p.join()

    # ===== Shared Memory: สอง Process เข้าถึงหน่วยความจำจริงชิ้นเดียวกัน =====
    shared_value = multiprocessing.Value('i', 0)            # 'i' = integer, เริ่มต้นที่ 0
    lock = multiprocessing.Lock()                             # ต้องใช้ Lock ป้องกัน Race Condition (บทที่ 36)

    def increment_shared(shared_value, lock):
        for _ in range(100000):
            with lock:                                          # Critical Section ครอบคลุม read-modify-write
                shared_value.value += 1

    processes = [multiprocessing.Process(target=increment_shared, args=(shared_value, lock)) for _ in range(4)]
    for p in processes:
        p.start()
    for p in processes:
        p.join()
    print(f"Expected: 400000, Got: {shared_value.value}")     # 400000 -- ถูกต้องเพราะมี Lock ป้องกัน

    # ===== Message Queue: ส่งข้อความที่ไม่ต้องรอผู้รับพร้อมทันที =====
    queue = multiprocessing.Queue()

    def producer(queue):
        for i in range(5):
            queue.put(f"Message {i}")                           # ใส่ข้อความเข้าคิว ไม่ต้องรอผู้รับ
            time.sleep(0.1)

    def consumer(queue):
        for _ in range(5):
            message = queue.get()                                 # ดึงข้อความออกจากคิว (รอถ้ายังไม่มี)
            print(f"Consumed: {message}")

    prod = multiprocessing.Process(target=producer, args=(queue,))
    cons = multiprocessing.Process(target=consumer, args=(queue,))
    prod.start(); cons.start()
    prod.join(); cons.join()
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. `multiprocessing.Pipe()` — สร้าง**ท่อสื่อสารคู่หนึ่ง** คืนค่าเป็นสอง connection object (`parent_conn`, `child_conn`) ที่เชื่อมต่อกันโดยตรง — เมื่อ process ลูกเรียก `conn.send("Hello from child!")` ข้อมูลถูกส่งผ่าน pipe buffer ที่ OS จัดการให้ และ process แม่เรียก `parent_conn.recv()` เพื่อดึงข้อมูลนั้นออกมา (การเรียก `recv()` จะ**บล็อกรอ**จนกว่าจะมีข้อมูลส่งมาจริง คล้ายการรับจาก Channel ในภาษา Go บทที่ 38)
2. `multiprocessing.Value('i', 0)` — สร้าง**หน่วยความจำที่แชร์จริง**ระหว่าง process (ไม่ใช่แค่ตัวแปร Python ธรรมดาที่แต่ละ process มีสำเนาของตัวเอง) — ทุก process ที่ได้รับ `shared_value` มาเป็นพารามิเตอร์เข้าถึง**หน่วยความจำจริงชิ้นเดียวกัน** ทำให้การแก้ไขจาก process หนึ่งเห็นผลในอีก process ทันที — เพราะเหตุนี้จึงต้องใช้ `lock` ครอบ `shared_value.value += 1` เหมือนที่เรียนในบทที่ 36 ทุกประการ (Race Condition เกิดขึ้นได้เหมือนกับ threading ล้วนๆ เพราะเป็นการแชร์หน่วยความจำจริงแบบเดียวกัน)
3. `multiprocessing.Queue()` — สร้าง**คิวข้อความ**ที่ OS จัดการให้ปลอดภัยจาก Race Condition โดยอัตโนมัติ (ไม่ต้องใช้ Lock เองเหมือน Shared Memory) `producer` เรียก `queue.put(...)` ใส่ข้อความเข้าคิวได้เรื่อยๆ โดยไม่ต้องรอว่า `consumer` พร้อมรับหรือยัง ส่วน `consumer` เรียก `queue.get()` ซึ่งจะบล็อกรอถ้ายังไม่มีข้อความในคิว — ความแตกต่างสำคัญจาก Pipe คือ Message Queue **ไม่ต้องการให้ทั้งสองฝั่งทำงานประสานจังหวะกันตลอดเวลา**
4. เปรียบเทียบทั้งสามตัวอย่าง — Pipe เหมาะกับการส่งข้อมูลทางเดียวแบบง่ายๆ ระหว่าง process ที่เกี่ยวข้องกันโดยตรง, Shared Memory เร็วที่สุดแต่ต้องจัดการ synchronization เอง (เหมือนใน Part 8), Message Queue สะดวกที่สุดเมื่อไม่ต้องการ synchronize จังหวะเวลาระหว่าง producer และ consumer

## Time Complexity

IPC เป็นเรื่องของกลไกการสื่อสารระหว่างระบบ ไม่ใช่อัลกอริทึม จึงเปรียบเทียบกันด้วย**ต้นทุนต่อการดำเนินการหนึ่งครั้ง**แทน Big O:

| กลไก | ต้นทุนโดยประมาณ |
|---|---|
| Shared Memory | เร็วที่สุด — ไม่มีการคัดลอกข้อมูลผ่าน kernel เลย |
| Pipe | ปานกลาง — ต้องคัดลอกข้อมูลผ่าน kernel buffer หนึ่งครั้ง |
| Message Queue | ปานกลางถึงช้ากว่า Pipe เล็กน้อย — มี overhead จากการจัดการคิวและ synchronization ให้อัตโนมัติ |
| Socket (บนเครื่องเดียวกัน) | ช้ากว่า Pipe — มี overhead ของ network stack แม้จะไม่ผ่านเครือข่ายจริง |
| Socket (ข้ามเครือข่าย) | ช้าที่สุด — ต้องผ่านทุกขั้นตอนตามบทที่ 42 (TCP Handshake ฯลฯ) |

## Space Complexity

- Pipe/Message Queue ใช้พื้นที่ buffer จำกัด (มักตั้งค่าได้) — ถ้า buffer เต็มและอีกฝั่งยังไม่มารับ ฝั่งที่เขียน (`send()`/`put()`) จะถูกบล็อกจนกว่าจะมีพื้นที่ว่าง
- Shared Memory ใช้พื้นที่เท่ากับขนาดข้อมูลที่ต้องแชร์พอดี ไม่มี overhead จากการคัดลอกซ้ำซ้อน

## แนวทางปฏิบัติที่ดี (Best Practices)

- เลือก Pipe/Message Queue เป็นค่าเริ่มต้นสำหรับ IPC ทั่วไป เพราะ OS จัดการความปลอดภัยจาก Race Condition ให้อัตโนมัติ ใช้ Shared Memory เฉพาะเมื่อวัดแล้วว่าความเร็วเป็นคอขวดจริงๆ (premature optimization ควรหลีกเลี่ยงเหมือนหลักการทั่วไปในการเขียนโปรแกรม)
- ถ้าใช้ Shared Memory ต้องออกแบบการล็อกให้รอบคอบตามหลักการในบทที่ 36-37 เสมอ (Critical Section เล็กที่สุดเท่าที่จำเป็น, ระวัง Deadlock ถ้าล็อกหลาย Shared Memory พร้อมกัน)
- ใช้ Socket เมื่อ process ที่สื่อสารกันอาจอยู่คนละเครื่องได้ในอนาคต (ออกแบบให้ขยายเป็นระบบกระจายได้ง่ายกว่า) แม้ปัจจุบันจะรันบนเครื่องเดียวกันก็ตาม

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- ใช้ Shared Memory โดยไม่มี Lock ป้องกัน คิดว่าเพราะเป็น "หน่วยความจำพิเศษของ IPC" จึงปลอดภัยจาก Race Condition โดยอัตโนมัติ — ที่จริง Race Condition เกิดขึ้นได้เหมือนกับตัวแปรที่แชร์ระหว่าง thread ทุกประการ (บทที่ 36-37)
- ใช้ Pipe ระหว่าง process ที่ไม่มีความสัมพันธ์กัน (ไม่ใช่ parent-child) โดยไม่รู้ว่า Pipe แบบไม่มีชื่อ (unnamed pipe) ใช้ได้เฉพาะ process ที่เกี่ยวข้องกันเท่านั้น — ต้องใช้ **Named Pipe** หรือกลไกอื่นแทนถ้า process ไม่มีความสัมพันธ์กัน
- เลือก Shared Memory ตั้งแต่ต้นเพราะ "เร็วที่สุด" โดยไม่พิจารณาความซับซ้อนที่เพิ่มขึ้นจากการต้องจัดการ synchronization เอง ทำให้เสียเวลาพัฒนามากกว่าประโยชน์ด้านความเร็วที่ได้จริง (over-engineering)
- ลืมปิด connection/queue หลังใช้งานเสร็จ ทำให้ resource รั่วไหล (คล้าย memory leak ที่กล่าวถึงใน Observer Pattern บทที่ 33)

## คำถามสัมภาษณ์งาน (Interview Questions)

1. เปรียบเทียบ Pipe, Shared Memory, Message Queue, และ Socket ในแง่ความเร็วและความซับซ้อนในการใช้งาน
2. ทำไม Shared Memory ถึงต้องใช้ Mutex/Lock เหมือนกับตัวแปรที่แชร์ระหว่าง thread (บทที่ 36) ทั้งที่เป็นกลไกของ Process ไม่ใช่ Thread
3. Pipe ต่างจาก Message Queue อย่างไร แต่ละแบบเหมาะกับสถานการณ์ไหน
4. ทำไม Socket ถึงเป็นกลไก IPC ที่ยืดหยุ่นที่สุด เชื่อมโยงกับความรู้เรื่อง TCP/IP จากบทที่ 42
5. ยกตัวอย่างสถานการณ์จริงในระบบที่คุณคุ้นเคย (หรือใช้งานอยู่) ที่ต้องใช้ IPC และอธิบายว่าเลือกใช้กลไกไหนเพราะเหตุใด

## แบบฝึกหัด (Practice Exercises)

1. เขียนโปรแกรมจำลองคำสั่งเชลล์ `ls | grep ".txt"` ด้วย `multiprocessing.Pipe` โดยให้ process แรกสร้างรายชื่อไฟล์จำลอง ส่งผ่าน pipe ไปยัง process ที่สองที่กรองเฉพาะไฟล์ `.txt`
2. เขียนโปรแกรมที่ใช้ Shared Memory (`multiprocessing.Array`) จำลองการนับคะแนนโหวตแบบเรียลไทม์จากหลาย process พร้อมกัน โดยต้องใช้ Lock ป้องกัน Race Condition ให้ถูกต้อง
3. เขียนระบบ Producer-Consumer ด้วย Message Queue ที่มี producer หลายตัวและ consumer หลายตัวทำงานพร้อมกัน (many-to-many) แล้วพิสูจน์ว่าทุกข้อความถูกประมวลผลครบไม่มีตกหล่นหรือซ้ำ

## Mini Project

**"ระบบประมวลผลภาพแบบกระจาย (Distributed Image Processing Pipeline)"**: เขียนโปรแกรมที่:
1. ใช้ Message Queue แบ่งงานประมวลผลภาพ (จำลองด้วย `time.sleep` แทนการประมวลผลจริง) ให้ Worker Process หลายตัวทำงานพร้อมกัน (คล้าย Fan-out/Fan-in จากบทที่ 38 แต่ใช้กลไกของ Process แทน Goroutine)
2. ใช้ Shared Memory เก็บสถิติความคืบหน้ารวม (จำนวนภาพที่ประมวลผลเสร็จแล้ว) ที่ทุก Worker อัปเดตร่วมกันแบบปลอดภัยด้วย Lock
3. ใช้ Pipe ส่งสัญญาณจาก Worker กลับไปยัง Process หลักเมื่องานเสร็จสมบูรณ์ทั้งหมด เพื่อให้ Process หลักแสดงรายงานสรุป
4. เปรียบเทียบเวลาที่ใช้ระหว่างการประมวลผลแบบ sequential (process เดียว) กับแบบกระจายงานผ่าน Message Queue (หลาย Worker Process) เมื่อมีภาพจำนวนมาก

## ข้อคิดสำคัญ (Key Takeaways)

- IPC คือกลุ่มกลไกที่ OS จัดเตรียมให้ process ที่แยก address space กันอย่างสมบูรณ์ (ตามบทที่แล้ว) สามารถสื่อสารแลกเปลี่ยนข้อมูลกันได้
- Pipe เหมาะกับการส่งข้อมูลทางเดียวแบบง่ายระหว่าง process ที่เกี่ยวข้องกัน ทำงานแบบ FIFO เหมือน Queue
- Shared Memory เร็วที่สุดเพราะไม่ต้องคัดลอกข้อมูลผ่าน kernel แต่ต้องจัดการ Race Condition เองด้วย Mutex/Lock เหมือนกับการแชร์หน่วยความจำระหว่าง thread ทุกประการ
- Message Queue สะดวกเมื่อ producer และ consumer ไม่จำเป็นต้องทำงานประสานจังหวะเวลากันตลอด และ OS จัดการความปลอดภัยให้อัตโนมัติ
- Socket เป็นกลไกที่ยืดหยุ่นที่สุดเพราะใช้ได้ทั้งบนเครื่องเดียวกันและข้ามเครือข่าย เชื่อมโยงกับความรู้เรื่อง TCP/IP โดยตรง
