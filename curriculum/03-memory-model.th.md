# บทที่ 3: Memory Model — Stack vs Heap, Process vs Thread

## แนวคิดหลัก (Concept)

จากบทที่ 1 เรารู้แล้วว่า RAM คือพื้นที่เก็บข้อมูลชั่วคราวขณะโปรแกรมทำงาน แต่ RAM ไม่ได้ถูกใช้แบบไร้ระเบียบ — ระบบปฏิบัติการ (OS) และภาษาโปรแกรมมีการ**แบ่งโซนหน่วยความจำ** ออกเป็นส่วนๆ ที่สำคัญที่สุดคือ **Stack** และ **Heap** ส่วนคำว่า **Process** และ **Thread** คือหน่วยของ "โปรแกรมที่กำลังทำงาน" ที่แต่ละอันจะได้รับหน่วยความจำเหล่านี้จัดสรรให้

- **Stack** — พื้นที่หน่วยความจำที่จัดการแบบ LIFO (Last In, First Out) ใช้เก็บตัวแปร local, พารามิเตอร์ฟังก์ชัน, และที่อยู่สำหรับกลับไปทำงานต่อ (return address) เวลาเรียกฟังก์ชัน
- **Heap** — พื้นที่หน่วยความจำที่จัดสรรแบบอิสระ (dynamic) ใช้เก็บข้อมูลที่ต้อง "อยู่ได้นานกว่า" ฟังก์ชันที่สร้างมัน เช่น object ที่สร้างด้วย `new` หรือ list ขนาดใหญ่
- **Process** — โปรแกรมหนึ่งชุดที่กำลังทำงาน มีพื้นที่หน่วยความจำ (address space) เป็นของตัวเอง แยกขาดจาก process อื่น
- **Thread** — "เส้นทางการทำงาน" ย่อยภายใน 1 process หลาย thread ใน process เดียวกัน **ใช้ Heap ร่วมกัน** แต่แต่ละ thread มี **Stack เป็นของตัวเอง**

## ทำไมต้องมีสิ่งนี้ (Why it exists)

- **Stack เร็วเพราะเรียบง่าย**: การจัดสรร/คืนพื้นที่ทำได้แค่เลื่อน pointer ขึ้น-ลง (คล้ายกองจาน) ไม่ต้องค้นหาที่ว่าง จึงเร็วมากและ CPU cache-friendly แต่ข้อจำกัดคือ ขนาดต้องรู้แน่นอนตอน compile และมีอายุผูกกับฟังก์ชันที่สร้างมันเท่านั้น
- **Heap มีไว้เพื่อความยืดหยุ่น**: บางครั้งเราต้องการข้อมูลที่ขนาดไม่แน่นอน (เช่น list ที่โตขึ้นเรื่อยๆ) หรือข้อมูลที่ต้องอยู่ต่อแม้ฟังก์ชันที่สร้างมันจบไปแล้ว (เช่น คืนค่า object กลับไปให้ผู้เรียก) Heap แก้ปัญหานี้ได้ แต่แลกมาด้วยความช้ากว่า (ต้องค้นหาที่ว่าง) และต้องมีการจัดการคืนพื้นที่ (garbage collection หรือ manual free)
- **Process แยกกันเพื่อความปลอดภัยและเสถียรภาพ**: ถ้า process หนึ่งพัง หรือมี bug เขียนทับหน่วยความจำมั่วซั่ว จะไม่กระทบ process อื่น (เช่น เบราว์เซอร์ crash ไม่ทำให้ทั้งเครื่อง crash)
- **Thread มีไว้เพื่อประสิทธิภาพ**: การสร้าง process ใหม่แต่ละครั้งมีค่าใช้จ่ายสูง (ต้องจัดสรรหน่วยความจำใหม่ทั้งหมด) แต่ thread ใช้ทรัพยากรของ process เดิมร่วมกัน ทำให้เบากว่าและสื่อสารกันง่ายกว่า เหมาะกับงานที่ต้องทำหลายอย่างพร้อมกันภายในโปรแกรมเดียว

## เปรียบเทียบกับชีวิตจริง (Real-world analogy)

- **Stack** เหมือน **กองจานในร้านบุฟเฟต์** — วางจานใหม่ทับบนสุดเสมอ (push) และหยิบจานบนสุดออกก่อนเสมอ (pop) ไม่มีทางหยิบจานที่อยู่ตรงกลางกองได้โดยตรง เป็นระเบียบ เร็ว แต่ตายตัว
- **Heap** เหมือน **โกดังเก็บของขนาดใหญ่** — คุณขอพื้นที่เก็บของ (จองล็อกในโกดัง) ได้ตามต้องการ ไม่ว่าจะขนาดเท่าไหร่ และของนั้นจะอยู่ที่นั่นจนกว่าจะมีคนมาเอาออก (free/garbage collect) แต่การหาล็อกว่างและจัดการพื้นที่ใช้เวลานานกว่ากองจาน
- **Process** เหมือน **บ้านแต่ละหลัง** — แต่ละหลังมีรั้วรอบขอบชิด มีของใช้เป็นของตัวเอง บ้านหนึ่งไฟไหม้ไม่ลามไปบ้านข้างๆ
- **Thread** เหมือน **สมาชิกในบ้านหลังเดียวกัน** — พ่อแม่ลูกอยู่บ้านเดียวกัน ใช้ครัว ห้องน้ำ (Heap) ร่วมกันได้ แต่ละคนมีห้องนอนส่วนตัว (Stack) ของตัวเอง

## แผนภาพอธิบาย (Visual explanation)

### โครงสร้างหน่วยความจำของ 1 Process

```
ที่อยู่สูง (High Address)
┌─────────────────────────────┐
│         STACK                │  ← โตลง (grows down)
│   (ตัวแปร local, การเรียก   │
│    ฟังก์ชัน, return address) │
│              ▼                │
│                                │
│              ▲                │
│         HEAP                  │  ← โตขึ้น (grows up)
│   (object, dynamic allocation)│
├─────────────────────────────┤
│      Data Segment             │  ← ตัวแปร global/static
├─────────────────────────────┤
│      Code Segment (Text)      │  ← ตัวคำสั่งโปรแกรม (read-only)
└─────────────────────────────┘
ที่อยู่ต่ำ (Low Address)
```

### Stack ตอนเรียกฟังก์ชันซ้อนกัน (LIFO)

```python
def a():
    x = 1
    b()

def b():
    y = 2
    c()

def c():
    z = 3
```

```
เรียก a() → เรียก b() → เรียก c()

┌─────────┐
│ c(): z=3 │  ← บนสุด (ทำงานอยู่ตอนนี้)
├─────────┤
│ b(): y=2 │
├─────────┤
│ a(): x=1 │  ← ล่างสุด (เรียกก่อน)
└─────────┘
   STACK

เมื่อ c() ทำงานเสร็จ → เฟรมของ c() ถูก "pop" ออกทันที
ค่า z หายไปโดยอัตโนมัติ ไม่ต้องเขียนโค้ดลบเอง
```

### Process vs Thread

```
┌──────────────────── PROCESS A ────────────────────┐
│                                                       │
│   ┌─────────┐   ┌─────────┐   ┌─────────┐          │
│   │Thread 1 │   │Thread 2 │   │Thread 3 │          │
│   │ Stack 1 │   │ Stack 2 │   │ Stack 3 │          │
│   └─────────┘   └─────────┘   └─────────┘          │
│              (แต่ละ thread มี Stack ของตัวเอง)      │
│                                                       │
│   ┌───────────────────────────────────────┐        │
│   │              HEAP (ใช้ร่วมกัน)          │        │
│   └───────────────────────────────────────┘        │
└───────────────────────────────────────────────────┘

┌──────────────────── PROCESS B ────────────────────┐
│         (หน่วยความจำแยกขาดจาก Process A โดยสิ้นเชิง) │
└───────────────────────────────────────────────────┘
```

## ตัวอย่างโค้ด (Code example)

```python
def create_list():
    local_number = 42          # เก็บใน Stack (ตัวแปร local, ขนาดคงที่)
    my_list = []                # ตัวแปร reference "my_list" อยู่ Stack
                                 # แต่ตัว list object จริงๆ อยู่ใน Heap
    for i in range(1_000_000):
        my_list.append(i)       # list โตขึ้นเรื่อยๆ ใน Heap ได้อย่างอิสระ
    return my_list               # คืนค่า Heap object กลับไปได้ แม้ฟังก์ชันจบแล้ว

result = create_list()
# local_number หายไปทันทีที่ create_list() จบ (Stack frame ถูก pop)
# แต่ result (list ใน Heap) ยังอยู่ เพราะมี reference ชี้ไปหามันจากภายนอก

import threading

def worker(name):
    total = 0                   # ตัวแปร local นี้อยู่ Stack ของ "thread นี้เท่านั้น"
    for i in range(1000):
        total += i
    print(f"{name}: {total}")

# สร้าง 3 thread ทำงานพร้อมกัน ใน process เดียวกัน (ใช้ Heap ร่วมกัน)
threads = [threading.Thread(target=worker, args=(f"T{i}",)) for i in range(3)]
for t in threads:
    t.start()
for t in threads:
    t.join()
```

## ทำงานทีละขั้นตอน (Step-by-step execution)

1. เรียก `create_list()` → OS/runtime จอง **Stack frame** ใหม่ให้ฟังก์ชันนี้ เก็บ `local_number` และตัวแปร reference `my_list` ไว้บน Stack
2. `my_list = []` → runtime ขอพื้นที่จาก **Heap** เพื่อสร้าง list object จริง แล้วให้ตัวแปร `my_list` บน Stack ชี้ (point) ไปยังตำแหน่งนั้นใน Heap
3. Loop เพิ่มข้อมูลเข้า list → list ใน Heap โตขึ้นเรื่อยๆ (บางครั้ง runtime ต้องย้ายไปยังพื้นที่ Heap ที่ใหญ่กว่าเบื้องหลัง)
4. `return my_list` → ค่า reference (ที่อยู่ใน Heap) ถูกส่งกลับไปให้ตัวแปร `result` แม้ Stack frame ของ `create_list()` จะถูกทำลายไปแล้ว list ใน Heap ก็ยังอยู่ เพราะยังมีคนอ้างอิงถึงมัน (`result`)
5. ในตัวอย่าง thread แต่ละ `worker()` ที่รันบน thread คนละตัว จะมี **Stack แยกกัน** ทำให้ตัวแปร `total` ของแต่ละ thread ไม่ปะปนกัน แต่ถ้าโค้ดใน thread เข้าถึง object เดียวกันใน Heap พร้อมกัน อาจเกิดปัญหา **race condition** (จะเรียนละเอียดในบท Concurrency)

## Time Complexity

- การจัดสรร/คืนพื้นที่บน **Stack**: O(1) เสมอ — แค่เลื่อน pointer
- การจัดสรรพื้นที่บน **Heap**: โดยทั่วไป O(1) เฉลี่ย (amortized) แต่บางครั้งช้ากว่าเพราะต้องค้นหาพื้นที่ว่างที่พอดี หรือขยายขนาด (เช่น list ที่โตเกิน capacity เดิม ต้อง copy ข้อมูลทั้งหมดไปที่ใหม่ → O(n) ในเคสนั้น)
- การสร้าง **Thread** ใหม่: เร็วกว่าการสร้าง **Process** ใหม่มาก เพราะไม่ต้องจัดสรรพื้นที่หน่วยความจำทั้งชุดใหม่

## Space Complexity

- Stack มีขนาดจำกัด (มักตั้งไว้ 1-8 MB ต่อ thread) — ถ้าเรียกฟังก์ชันซ้อนลึกเกินไป (เช่น recursion ที่ไม่มีจุดจบ) จะเกิด **Stack Overflow**
- Heap มีขนาดจำกัดตาม RAM ทั้งหมดของเครื่อง (หรือ limit ที่ OS ตั้งไว้) — ถ้าใช้จนหมดจะเกิด **Out of Memory (OOM)**

## แนวทางปฏิบัติที่ดี (Best Practices)

- หลีกเลี่ยงการสร้าง object ขนาดใหญ่บน Stack โดยไม่จำเป็น (ในภาษาที่ควบคุมได้ เช่น C/C++/Rust) เพราะ Stack มีขนาดจำกัดมาก
- ระวัง **recursion ที่ลึกเกินไป** โดยเฉพาะถ้าไม่มี base case ที่ถูกต้อง — จะทำให้ Stack Overflow
- เมื่อทำงานแบบ multi-thread ต้องระวังการเข้าถึง Heap ร่วมกัน (shared state) ให้ปลอดภัย ด้วยกลไกเช่น lock/mutex (รายละเอียดในบท Concurrency)
- ในภาษาที่มี garbage collector (Python, Java, Go, JavaScript) ไม่ต้อง free หน่วยความจำ Heap เอง แต่ควรเข้าใจว่า object ที่ไม่มีใคร reference ถึงแล้วเท่านั้นที่จะถูกเก็บกวาด

## ข้อผิดพลาดที่พบบ่อย (Common Mistakes)

- เข้าใจผิดว่าตัวแปรทุกตัวอยู่ที่เดียวกัน — จริงๆ ตัวแปร local ธรรมดาอยู่ Stack แต่ object/array/list มักอยู่ Heap (ตัวแปรบน Stack เป็นแค่ "reference" ชี้ไปหา Heap)
- เขียน recursive function โดยไม่มี base case → Stack Overflow ทันที
- คิดว่า Thread กับ Process เป็นสิ่งเดียวกัน — ที่จริง Thread เบากว่ามาก และแชร์ Heap กันได้ ขณะที่ Process แยกหน่วยความจำกันโดยสิ้นเชิง
- ในภาษาที่ไม่มี garbage collector (เช่น C) ลืม free หน่วยความจำ Heap ที่จองไว้ → เกิด **memory leak**

2. ทำไม recursion ที่ลึกมากๆ ถึงทำให้เกิด "Stack Overflow"?
3. Thread กับ Process ต่างกันอย่างไร? แต่ละอย่างเหมาะกับงานแบบไหน?
4. ทำไมการสร้าง Thread ถึงเร็วกว่าการสร้าง Process ใหม่?
5. Memory leak คืออะไร และเกิดขึ้นได้อย่างไรในภาษาที่มี garbage collector?

## แบบฝึกหัด (Practice Exercises)

1. เขียนฟังก์ชัน recursive แบบไม่มี base case (ตั้งใจ) แล้วรันดูว่าเกิด error อะไร (เช่น `RecursionError` ใน Python) — สังเกตข้อความ error ว่าพูดถึงอะไร
2. เขียนโค้ดสร้าง list ขนาดใหญ่มากๆ ใน loop (เช่น 50 ล้านตัว) แล้วสังเกตการใช้หน่วยความจำของโปรแกรมด้วยเครื่องมือ monitor ของระบบ (Task Manager)
3. อธิบายด้วยคำพูดของตัวเองว่าทำไมตัวแปรที่ return จากฟังก์ชันถึง "รอด" แม้ Stack frame ของฟังก์ชันนั้นจะถูกทำลายไปแล้ว

## ข้อคิดสำคัญ (Key Takeaways)

- Stack จัดการตัวแปร local แบบ LIFO เร็วมาก แต่ขนาดจำกัดและอายุสั้น (ผูกกับฟังก์ชัน)
- Heap จัดการข้อมูลที่ต้องอยู่ได้นานกว่าฟังก์ชันที่สร้างมัน หรือขนาดไม่แน่นอน แต่ช้ากว่าและต้องมีการจัดการคืนพื้นที่
- Process คือหน่วยของโปรแกรมที่แยกหน่วยความจำกันโดยสิ้นเชิง ปลอดภัยแต่หนัก
- Thread คือหน่วยย่อยภายใน Process เดียวกัน แชร์ Heap ร่วมกันแต่มี Stack แยก เบากว่าและเหมาะกับงานคู่ขนาน
- ความเข้าใจเรื่อง Stack/Heap เป็นพื้นฐานสำคัญก่อนเรียนเรื่อง references, pointers, และ recursion ในบทถัดไป
